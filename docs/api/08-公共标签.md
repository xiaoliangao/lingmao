# 公共标签 API

本章实现 `functional-completion-contract.md §4`。标签库在当前部署的公司之间共享；目标对象的标签读取和修改仍逐次校验真实领域权限、DataScope 和实际主体。可信命名空间只由 `DeploymentNamespace.tenant()` 提供，任何请求字段都不能选择另一个 tenant。这不代表全域多租户和公司成员 ACL 已完成。

## 1. 类型、权限与状态

对象类型接受下表的 12 个基础大写枚举，以及样衣域接入的 `SAMPLE`（权限和状态见 `09-研发打样.md`）。未知类型返回 400。目标不存在或不在 DataScope 返回 404；缺少领域权限返回 403。订单、采购、生产的当前审批人只沿用本域已存在的只读例外，不能据此修改标签。

| type | 读取权限 | 修改权限 | 普通 SELF 范围 | 可修改状态 | 实际主体 |
|---|---|---|---|---|---|
| STYLE | style:style:list | style:style:edit | 共享资料 | 与款式主档保存一致，所有现有状态 | NULL |
| MATERIAL | basic:material:list | basic:material:edit | 共享资料 | 与物料主档保存一致，所有现有状态 | NULL |
| SUPPLIER | supplier:supplier:list | supplier:supplier:edit | 共享资料 | 除 ADMITTING | NULL |
| TECH_PACK | techpack:pack:list | techpack:pack:edit | 共享资料 | DRAFT，所属款式未停用 | NULL |
| ORDER | order:order:list | order:order:edit | 制单人 / 业务员 / 跟单员 | DRAFT | ord_order.company_id |
| MRP_CALC | purchase:mrp:list | purchase:mrp:edit | 制单人，且全部来源订单仍可见 | DRAFT / CONFIRMED，沿用改备注规则 | mrp_calc.company_id 的真实值 |
| PURCHASE_ORDER | purchase:order:list | purchase:order:edit | 制单人 / 采购员 | DRAFT | pur_order.company_id |
| INV_DOC | inventory:doc:list | inventory:doc:edit | 制单人 | DRAFT | inv_doc.company_id |
| INV_COUNT | inventory:count:list | inventory:count:edit | 制单人 / 盘点人 | DRAFT | inv_count.company_id |
| PRODUCTION_ORDER | production:order:list | production:order:edit | 制单人 / 生产跟单 | DRAFT | prd_order.company_id |
| PRODUCTION_RECEIPT | production:order:list | production:receipt:add | 所属生产单制单人 / 生产跟单 | 回货 APPROVED，父生产 APPROVED / RUNNING / DONE | prd_receipt.company_id，须与父生产一致 |
| FG_DOC | fg:doc:list | fg:doc:edit | 制单人 | DRAFT | fg_doc.company_id |

回货单只新增标签元数据编辑能力，不修改回货数量、状态、业务版本或审核字段。作废回货和已关闭父生产单不可修改标签。写入锁序为父生产单 → 回货单 → 标签 registry，之后不再反向获取需求订单锁。

其他对象先锁真实领域主头 `FOR UPDATE`，再由 Repository 锁 registry、规范化名称、标签稳定 ID。对象业务版本和标签内容版本独立。修改后只有标签 version 递增，不改业务单头 version。

对真实 `company_id` 非 NULL 的对象，读、写和幂等重放都必须携带匹配的 `X-Company-Id`；缺失 400，不一致 403。共享资料不因请求头而变成某公司的私有资料。当前算料域的真实主头可为 NULL，标签层保持该值，并沿用全部来源订单的现有可见性与主体守卫；不会根据请求头虚构或回填算料归属。

## 2. DTO 与文本规范

所有 ID 以十进制字符串输出，version、条数为 JSON number。公开标签只含：

```json
{"id":"9007199254740993","name":"夏季","archived":false,"version":0}
```

不输出 tenantKey、canonical、deletedToken、目标关联或财务字段。写 DTO 不接收业务状态、审批人、主体、tenant 或实体审计列；沿全局严格反序列化规则，出现这些未知字段时整请求返回 400，不写入任何标签关系。

名称规范化只执行一次：NFKC → strip → 去掉一个前导 `#` → strip。显示名保留大小写，canonical 用 Locale.ROOT 小写。显示名为 1–64 个 Unicode 码点，拒控制字符、逗号、双向覆盖/隔离控制符；保留 ZWJ emoji。原始输入还限制 1024 个 UTF-16 单元，避免超大输入参与规范化。

已有名称回填必须提交 `"#" + displayName`，例如显示 `#蓝` 的标签提交 `##蓝`，普通 `蓝` 提交 `#蓝`。用户新增原始文本只规范化一次。重命名输入框显示原名称，提交时补相同传输前缀。

## 3. 选项查询

`GET /api/tags?keyword=&size=50&includeIds=1,2`

需要登录和 `biz:tag:list`。keyword 是字面前缀，`%`、`_`、反斜线不作为通配符。size 为 1–100，默认 50；原始 includeIds 最多 100 个，去重后按输入顺序先返回。includeIds 可含已经归档的历史标签，任一个不存在或不属于当前可信命名空间，整批 404。

总预算是 `max(size, 去重 includeIds 数量)`，最多 100。余量用当前活跃库按 `(canonical,id)` 排序、SQL 先排除 includeIds 再 LIMIT；余量为 0 时不执行搜索。响应是 `R<TagVO[]>`，不能把 includeIds 的 100 条再叠加 50 条搜索结果。

`GET /api/tags/filter-options?keyword=&size=50&includeIds=1,2`

专供业务列表筛选，权限、字面前缀、指定 ID 回显和总预算规则与上面相同；搜索结果同时包含活跃及归档标签，仍按 `(canonical,id)` 排序。归档项只用于查询历史关联，不因此允许建立新的历史关联。界面显示归档状态和稳定 ID，区分归档旧标签与同名重建的新标签。该接口不返回任何对象关联、命中数量或领域数据。

## 4. 对象读取与替换

`GET /api/tags/objects/{type}/{id}`

返回 `R<{version,tags:TagVO[]}>`。无 registry 时为 `version=0,tags=[]`，GET 不创建任何标签行。读权限来自第 1 节的领域权限，不借成品来源的专用白名单权限。

`POST /api/tags/objects/{type}/{id}/replace`

必须携带规范 UUID `Idempotency-Key`，以及公司的请求头（有真实主体时）。首次替换：

```json
{"version":0,"names":["#夏季","基础款"],"tagVersions":{},"retainIds":[]}
```

已有对象必须提交全部当前关联标签的版本，包含本次要移除的标签：

```json
{"version":1,"names":["#夏季"],"tagVersions":{"101":0,"102":1},"retainIds":["101"]}
```

names 原始最多 30 项，规范化去重保留首次顺序；最终关联数也最多 30。tagVersions 必须精确覆盖当前全部关联 ID/version。retainIds 必填、无重复、仅能来自当前对象，其当前 canonical 必须出现在 names 中。某 canonical 有 retainIds 时保留指定的准确历史关联；没有时才选取或自动创建活跃标签。

归档旧标签可以保留原关联或调整顺序；去掉后再输入同名，选择或建立新的活跃标签。同名的归档旧 ID 与另一活跃 ID 都已经挂在当前对象时，retainIds 可显式保留两者，不会静默合并丢失历史。相同 canonical 的历史项按 retainIds 顺序，其余按 names 顺序。

返回替换后的完整对象 DTO。并发对象版本、标签全局改名/归档版本不一致统一 1002；输入非法 400。常规多个对象并发输入同名会等待名称事务锁，合并成同一个活跃标签。

## 5. 全局管理和操作记录

`POST /api/tags/{id}/rename`，请求 `{"version":0,"name":"#新名称"}`。

`POST /api/tags/{id}/archive`，请求 `{"version":0}`。

两者需要 `biz:tag:manage` 和规范 UUID `Idempotency-Key`，返回新 TagVO。该权限只授予 manager 模板和既有超级管理员；普通标签读取权限不隐含全局管理权限。已归档标签不可再次改名或恢复，历史关联保留，活跃同名冲突返回 1000。

`GET /api/tags/{id}/logs?page=1&size=20`

需要 `biz:tag:list`，先校验可信命名空间中真实标签存在，含归档。返回标准 `PageResult<DocLogVO>`，size 最大 100。仅开放 PUBLIC_TAG 的专用时间轴，不开放附件、任意引用或任意类型写操作。

## 6. 幂等、缓存与审计

replace、rename、archive 分别使用稳定操作名 TAG_REPLACE、TAG_RENAME、TAG_ARCHIVE。同键在途 HTTP 409；已完成同键同体重放成功，同键异体为业务 1002。重放必须重新验证当前领域编辑权限、普通 DataScope、实际公司或库 manage 权限；不因为曾经成功就绕过后续停用、降权或归属变化。重放不执行第二次业务状态检查或第二次标签写入。

业务写入、幂等收据、真实 ObjLogs、字段级 DataLog 和缓存失效发件箱在同一数据库事务中提交。对象操作记到实际业务类型的时间轴；全局改名/归档记 PUBLIC_TAG 时间轴。DataLog 保留真实 INSERT/UPDATE/DELETE 和 old/new，不把所有变更伪装为整体替换。

Cache-Aside 复用现有 SharedCache：可信 tenant 前缀、真实范围标识、SingleFlight、Redis 租约、随机 TTL 和空值短 TTL。每个 payload 最多 100 个选项或 30 个关联。权限判断从不缓存。库 epoch 与对象 epoch 的失效只在事务提交后执行，同时使用已有 CACHE_INVALIDATE Outbox 做故障恢复。改名/归档换代所有库选项与对象回显，不执行全量关联查询或 Redis KEYS 扫描；事务回滚既不发布未提交标签，也不使旧缓存失效。

对象 payload TTL 为 30 秒、选项为 2 分钟，空结果为 5 秒，底层均有抖动；提交后的即时失效是主路径，TTL 是故障兜底。归档、同名重建与 NULL 公司兼容只适用于此部署模型，不据此宣称两个合法租户共库已通过。

## 7. 业务列表筛选

下列现有独立列表支持可选的 `tagIds=101,102`（也接受重复的 `tagIds` 查询参数）。语义是 **AND：对象必须同时包含全部所选标签**，与原业务条件、DataScope 和该列表原有的公司约束取交集。省略或空列表表示不按标签筛选；原始最多 30 项，必须是正整数，服务端再去重。超过上限、非正整数等非法输入返回 400；任一 ID 不在当前部署标签库时整批 404，不静默忽略。不按名称匹配，不新增 OR、跨对象标签继承或对子单关联标签的隐含查询。

| 对象 | 列表 | 同步使用该条件的入口 |
|---|---|---|
| STYLE | `GET /api/styles` | `/export` |
| MATERIAL | `GET /api/materials` | `/export` |
| SUPPLIER | `GET /api/suppliers` | `/export` |
| ORDER | `GET /api/orders` | `/counts`、`/export`；服务内部总计查询同口径 |
| MRP_CALC | `GET /api/mrp-calcs` | 列表总数 |
| PURCHASE_ORDER | `GET /api/purchase-orders` | `/export` |
| INV_DOC | `GET /api/inventory-docs` | `/export`；原 `kind` 必填 |
| INV_COUNT | `GET /api/inventory-counts` | `/export` |
| PRODUCTION_ORDER | `GET /api/production-orders` | `/counts`、`/export`；原 `kind` 必填 |
| FG_DOC | `GET /api/fg-docs` | `/export`；原 `companyId`、`kind` 必填 |
| SAMPLE | `GET /api/samples` | `/counts`；原 `companyId` 必填 |

非空 `tagIds` 除原领域权限外还需要 `biz:tag:list`，否则 403；未使用标签条件的调用沿用原权限。不能通过筛选获取原本不可见的对象或成本字段。标签库在部署内共享不等于拥有跨公司对象权限；对原本跨公司展示的订单等列表，也不把请求头重新解释成公司 ACL。

筛选在数据库的关联 `EXISTS` 条件中执行，固定对象类型，可信命名空间由服务端绑定；先取交集，再计算总数、分页或有界导出。只验证最多 30 个选中标签，不预拉全量匹配对象 ID，不逐行查标签。状态统计沿用原有口径（例如忽略当前状态分段），标签条件与其他非状态条件保持一致。指定导出行 ID 也必须满足当前筛选和可见范围，不能借 `ids` 绕过；范围不一致沿用原导出 404。

归档只停用名称复用，旧 ID 的历史关联继续可以筛选；同名重建后新旧 ID 是两个独立条件。清空界面标签条件会恢复原业务查询并回到第一页，翻页和导出使用当前已应用的标签 ID。

`TECH_PACK` 的款式/样衣版本概况与 `PRODUCTION_RECEIPT` 的生产详情回货记录属于嵌套展示，本节不改变它们的领域接口，也没有新增独立列表筛选入口。库存余额、库存流水、单据日志、选项选择器等不是上述目标对象列表，不支持这一筛选参数。公共 DataLog 新表查询入口仍由独立增量接线。
