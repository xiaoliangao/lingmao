# RFC 018 组织架构、账号导入、编码规则

状态：**已实现**（11-24）。用户说"先做能做的"，§7 五条按默认做；审的时候要改哪条再改。和草案不一样的地方在正文里标了"（实现时）"。

§8（甲方 11-25 给的编码规则）：**已实现**（11-25，V58）。用户 11-25 定：年份按编号那年（§8.4），其余照草案。
同一天甲方又给了领猫导出的产品类目、物料类目两张表：款号开头的 F 是一级品类的编码（通勤裤类是 T），加了"一级品类编码"一段；两张表能直接导进品类、物料分类（§8.7）。

对应：PRD §5.2、§6.9.2 第 1 条、Q05、Q14、Q28；数据库设计 §3.3、§3.8、§5.4；架构 §4.5。领猫的用户列表、组织架构、编码规则三张截图在 `docs/private/领猫参考/`（真实名单，不进仓库）。

## 0. 为什么现在做

- **账号名单**（Q14）：甲方说从领猫导出，11-25 前给。11-24 用户给了领猫的用户列表和组织架构截图：四十多个人，大多数人挂在几个部门下面，部门是一棵三级的树。现在系统里部门只是用户上的一个文本框，账号要一个个手建。
- **物料编码新规则**（Q05）：一直在等甲方给，进度表上挂着"新编码规则（等甲方给）"。改成管理后台能配，规则到了管理员自己改，不用等我们发版。领猫就是这么做的：每种编码一个页签，一条通用规则，再按品牌加规则，每条规则是几段拼起来（大类目编码 + 年份编码 + 设计师代号 + 固定项 + 000）。

三块都不用等甲方答复。做的顺序：部门 → 首次登录改密码 → 账号导入 → 编码规则，做完一块提交一块。迁移只有一个 V57。

## 1. 部门

### 1.1 现在和要改成的

`sys_user.dept` 是自由填的一个文本。领猫里一个人可以挂几个部门（采购兼理单的人挂了五个），部门是树：供应链部下面七个组，产品部 › 设计组 › 实习生是三级。

改成部门表 + 人和部门多对多。岗位（`post`）还是自由填的文本，一个人一个。

### 1.2 表

`sys_dept` 部门（新表，不用逻辑删除）：

| 列名 | 类型 | 非空 | 说明 |
|---|---|---|---|
| id | BIGINT IDENTITY | 是 | 主键 |
| parent_id | BIGINT | | 上级，顶层为空 → `sys_dept` |
| name | VARCHAR(32) | 是 | 名称 |
| sort | INT | 是 | 同级顺序，默认 0 |
| create_by … update_time | | | 公共列 |

- 同级不重名：`uk_sys_dept_name (COALESCE(parent_id, 0), name)`。
- 最多 5 级（Service 校验）。
- 不加"停用"：部门不用了就删。下面还有部门、还有人的删不掉（1005，说清楚有几个人、哪几个下级）。

`sys_user_dept` 人和部门：`user_id` → `sys_user`、`dept_id` → `sys_dept`，主键 `(user_id, dept_id)`，`idx_sys_user_dept_dept (dept_id)`。

- 删用户（逻辑删除）时一起删掉他的部门关联，不然部门永远删不掉（11-22 角色关联碰到过同样的事）。
- `sys_user.dept` 不再用：V57 把已有的值按名字建成顶层部门、挂上去；列留着（只增不删），注释写"V57 起不用，看 sys_user_dept"。

### 1.3 页面

管理后台 › 用户，照领猫的样子在左边放一棵部门树（约 220px 宽）：

- 最上面"全部"。点一个部门，右边只列这个部门和它下级部门的人。
- 鼠标移到部门上出三个小按钮：改名（可以换上级）、加下级、删除。树顶上"+ 部门"加顶层的。
- 同级排序在改名对话框里填，不做拖动。

用户对话框：部门改成多选的树形下拉（能搜，选上级不带下级）；岗位照旧。列表的"部门 · 岗位"一列拆成"部门"（多个用"、"隔开）和"岗位"两列。

### 1.4 部门用在哪

一期只是"这个人在哪个部门"和按部门找人：

- 数据范围还是本人 / 全部（PRD §3.2）；审批按部门分支是二期（PRD §6.9.3），到时候直接用这张表。
- 选人下拉（`/api/users/options`）每人带上部门名，显示成"小林 · 设计组"，同名、花名相近的人好分。

### 1.5 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/depts` | `system:user:list` | 整棵树，每个部门带直属人数 |
| POST | `/api/depts` | `system:user:edit` | 新建：名称、上级、排序 |
| PUT | `/api/depts/{id}` | `system:user:edit` | 改名、换上级、排序；不能挪到自己或自己的下级下面（400） |
| DELETE | `/api/depts/{id}` | `system:user:edit` | 有下级、有人 → 1005 |
| GET | `/api/users?deptId=` | 现有 | 加这个参数：这个部门和全部下级的人 |
| POST / PUT | `/api/users`、`/api/users/{id}` | 现有 | 加 `deptIds`；`dept` 不再收 |

管理后台只给超级管理员（V7 `admin_only`），不另加权限码。

## 2. 首次登录改密码

账号导入给所有人设同一个初始密码（§3.2），所以要加"第一次登录先改密码"。

- `sys_user.pwd_must_change BOOLEAN NOT NULL DEFAULT false`。导入建的、管理员新建的、管理员重置密码的置 true；本人改了密码置 false。已有的账号不动。
- 后端兜底：标了的账号登录照常拿令牌，但加载权限时一个都不给，只能调 `/api/auth/me`、改密码、退出；业务接口全是 403。改完密码重新发令牌。
- 前端：`/api/auth/me` 带 `mustChangePassword`。为 true 时整页只显示改密码的表单（用现有的自己改密码组件），不能关，右上角能退出。
- 这挡不住"知道初始密码的人抢先登别人的号"。内部四十多人，可以接受；手册和导入对话框里提醒：初始密码别用好猜的，导完尽快通知每个人登录。

## 3. 账号导入

### 3.1 流程

管理后台 › 用户 › 导入（`ImportDialog`）。导之前要先有：部门树（§1.3，照领猫的建一遍，十几个部门）、角色（预置的十个）。

对话框第一步（`#head`）填**初始密码**：8–32 位，所有导进来的人都用它，第一次登录必须改（§2）。

### 3.2 列

（实现时）模板的列名直接用领猫导出里的叫法，一列一个名字，领猫导出的文件不用改表头就能导；模板比领猫多角色、品类线、设计师编号、默认主体四列。

| 列 | 必填 | 怎么认 |
|---|---|---|
| 登录名 | | 3–32 位小写字母、数字、下划线（大写转小写）。空的或者不合这个格式的（领猫的登录名是"花名-岗位"这种中文），用手机号当登录名 |
| 昵称 | 是 | 系统里显示的名字（花名） |
| 电话 | 登录名用不了时必填 | 11 位手机号，空格、横杠去掉 |
| 所属部门 | | 几个部门用"；""、"或逗号隔开；按名字在部门树里找，有重名的写全路径"产品部/设计组"；找不到的这一行报错 |
| 职位 | | 原样存成岗位 |
| 角色 | | 按角色名称（也认编码），可以写几个；找不到的报错。空的照样建，导完的提示里列出"第几行没填角色，登录后什么都看不到" |
| 品类线 | | 服装、鞋类、百货（也认 APPAREL 这种值），可以写几个；空 = 三条都给（和 V44 给老账号的一样） |
| 设计师编号 | | 1–99，补成两位；和已有的（删了的账号也算）、表里别的行重复就报错 |
| 默认主体 | | 主体公司的编码、简称或全称，要是启用的 |
| 启用 | | 启用 / 停用；空 = 启用 |

性别、邮箱、内部编码不导：系统里没有这几项，用不上。

规则：

- 登录名已经有了（比如 admin）：这一行跳过、进提示，不改那个账号。改好文件再导一次不会重复建。
- 表里两行登录名一样：报错。
- 一行不对整批不导（RFC 001 §9.3），一次最多 500 行。
- 名单里"外部供应商"部门的人：一期不给工厂开账号（Q02），导之前删掉这几行；没删就照常建成普通账号。

### 3.3 导完批量改

用户列表加勾选列和底部批量条：**加角色、去角色、设品类线、启用、停用**。照现有的规矩逐条检查（不能停用自己、不能去掉自己的超级管理员），没成功的逐条报原因、留着勾。

## 4. 编码规则

### 4.1 现在

款号、物料编码、供应商编码的格式写死在代码里（`StyleCodes`、`MaterialServiceImpl.nextCode`、`SupplierServiceImpl.nextCode`），改格式要我们改代码发版。

### 4.2 管哪几种

| 编码 | 进不进 | 为什么 |
|---|---|---|
| 款号 | 进 | 甲方 11-11 定过一次，以后还可能按品类线分 |
| 物料编码 | 进 | 新规则等甲方给（Q05），面料、辅料、耗材、包材各一种 |
| 供应商编码 | 进 | 领猫有这一页，成本很低 |
| 单号 | 不进 | PRD §5.2 定死了；搜索、⌘K、导出都认前缀。要改以后加进同一张表 |
| 物料 SKU 码、款式 SKU 码 | 不进 | 是"编码-颜色码-尺码"拼的，跟着编码变 |
| 样衣编号 | 以后 | 二期做研发打样时加进来 |
| 客户编码 | 不进 | TRADE 关着 |

### 4.3 一条规则

- 每种编码有一条**通用规则**，不能删；可以再加几条"按什么分"的规则。
- 款号按**大类**分，物料编码按**物料类型**分，供应商编码只有通用规则。
  - 款号不照领猫按品牌分：我们的大类必填、建好不能改、已经决定品类线（BH 百货、XZ 鞋子），领猫的"百货""鞋子"两个品牌正好对上两个大类。品牌照样能作为一段放进编码（§4.4）。
  - 物料按物料类型分：甲方说的"物料、辅料、耗材、包材规则不一样"就是物料类型（字典 `material_type`，每个物料必填）。
- 一个大类（物料类型）只能在一条规则里。编的时候先找写了它的那条，没有用通用的。

### 4.4 段

| 段 | 能用在 | 取什么 | 例 |
|---|---|---|---|
| 固定文字 | 都能 | 填的 1–8 位大写字母、数字、横杠 | `GYS` |
| 大类编码 | 款号 | 字典 `style_class` 的值 | `FS` |
| 品牌编码 | 款号 | 字典 `brand` 的值；不是字母数字的，编的时候报错让管理员改字典 | `AB` |
| 品类编码 | 款号 | 品类树上这个品类的编码（V57 给品类加一列编码，选填）；规则里用了这一段、品类没填编码的，报错让去 基础资料 › 品类 填，或者手填款号 | `03` |
| 款式年份 | 款号 | 款式上"年份"的后两位（领猫的"年份编码"） | `27` |
| 日期 | 都能 | 建档那天，格式选 yy / yyMM / yyMMdd | `261124` |
| 设计师编号 | 款号 | 设计师的两位编号；没有编号照现在提示 | `07` |
| 物料分类编码 | 物料编码 | 二级分类的 2 位码 | `ML` |
| 流水 | 都能，**必须有且只有一个** | 2–6 位，从 1 起 | `0001` |

V57 预置三条通用规则，和现在的格式一模一样，装上新版编出来的号不变：

- 款号：大类编码 + 日期（yyMMdd）+ 设计师编号 + 流水 2 位
- 物料编码：物料分类编码 + 流水 4 位
- 供应商编码：固定文字 GYS + 流水 4 位

### 4.5 流水怎么分

- 流水按"流水以外的段拼出来的那一串"分开记（`sys_serial.seq_key`）：换了日期、大类、设计师，就从 1 重新起。流水不在最后时，在它的位置放一个 `#`。
- 现在的 key 正好就是这样拼的（`FS26112407`、`ML`、`GYS`），换成规则后接着往下编，**不用迁移流水**。
- 两种编码碰巧拼出同一个 key 时共用一个流水：号会跳着走，但不会重：每张表的编码有唯一索引，取到被占的号再取下一个（现在就这样）。
- 流水用完（超过位数）：款号照现在提示手填；物料、供应商报错，让管理员给规则的流水加一位。
- 设计师编号的锁（第一次用来编号后不能改）只在规则里有"设计师编号"这一段时才上。

### 4.6 改规则

- 只管以后新编的，已有的编码一个都不变。
- 保存时检查：流水有且只有一个；每段都能用在这种编码上；最长时总长不超过编码列（32 位），拼出来的 key 不超过 32 位；按什么分的值没在别的规则里。
- 操作日志记改前、改后。
- 新建款式页的"自动编号"预览照旧，按适用的那条规则；物料、供应商保存时才编。

### 4.7 页面

管理后台 › 系统管理 › 编码规则（`admin_only`）。照领猫：

- 三个页签：款号、物料编码、供应商编码。
- 每个页签：通用规则一张卡，下面是别的规则，各一张卡。卡上一行段（"大类编码 + 日期 yyMMdd + 设计师编号 + 流水 2 位"），旁边一个例子（`FS2611240701`）；按什么分的显示成标签（"TS 通勤裤""FS 非通勤裤"）；右边编辑、删除（通用的没有删除）。
- 底下"+ 新增规则"。
- 编辑对话框：上面选按什么分（多选；已在别的规则里的灰掉）；中间是段的列表，每行一个类型下拉 + 它的参数（固定文字填字、日期选格式、流水选位数）+ 上移、下移、删除；底下"加一段"；最下面实时显示例子。

### 4.8 表

`sys_code_rule` 编码规则（新表，不用逻辑删除）：

| 列名 | 类型 | 非空 | 说明 |
|---|---|---|---|
| id | BIGINT IDENTITY | 是 | 主键 |
| target | VARCHAR(16) | 是 | 哪种编码：`STYLE` / `MATERIAL` / `SUPPLIER` |
| name | VARCHAR(32) | 是 | 规则名，如"通用规则""鞋子" |
| scope_values | VARCHAR(64)[] | 是 | 按什么分：款号存大类的字典值，物料存物料类型的字典值；空数组 = 通用规则 |
| segments | JSONB | 是 | 段，按顺序，如 `[{"type":"STYLE_CLASS"},{"type":"DATE","format":"yyMMdd"},{"type":"DESIGNER"},{"type":"SEQ","width":2}]` |
| sort | INT | 是 | 页面上的顺序 |
| create_by … update_time | | | 公共列 |

- `uk_sys_code_rule_general (target) WHERE scope_values = '{}'`：每种编码一条通用规则。
- 按什么分的值不重复由 Service 查：存之前先锁这种编码的通用规则那一行，同一种编码的保存排队。
- `scope_values` 存的是字典值，和别的字典列一样不建外键。
- 每次编号读一次库（一种编码几行），不缓存。

`bas_category` 加 `code VARCHAR(8)`：品类编码，选填，字母数字；不要求唯一（领猫的叶子类目编码在不同上级下可能重复）。品类页的对话框加这一项。

### 4.9 代码放哪

- `module.system` 加 `CodeRuleService`：按编码种类和这一次的值（大类、品牌、品类编码、款式年份、设计师编号、物料类型、物料分类码）找到适用的规则，拼出 key 和流水位数，给一个"填上流水得到编码"的方法。它不查款式、物料、供应商表。
- 取号和"被占了再取下一个"还在各自的域里：`StyleCodes`、`MaterialCodes`（实现时从 `MaterialServiceImpl.nextCode` 拆出来，新建、导入共用）、`SupplierServiceImpl.nextCode` 改成先问 `CodeRuleService`，循环照旧。流水用 `SerialNoGenerator.nextSeq(key)` 只拿数字，位数由调用方判断。
- 新建物料的编码预览：`GET /api/materials/code-preview?categoryId=&materialType=`（实现时加的，表单上选了分类和物料类型就显示）。
- 款式要的品类编码由 style 域调 basic 的品类服务取，传给 `CodeRuleService`。

## 7. 按默认做的，你看要不要改

1. **领猫的"内部编码"不当设计师编号**。截图里几个开发有内部编码（一两位数），但一个采购也有；甲方答 Q28 说设计师编号由管理员从 01 起按顺序给。所以只认模板的"设计师编号"列，内部编码不导；设计师没几个，导完在用户页填。要照搬领猫的内部编码就说一声，导入认它、补成两位。
2. **领猫的登录名用不了，用手机号登录**。领猫的登录名是"花名-岗位"的中文；系统只收小写字母数字，要么甲方在模板里另填一列英文登录名，要么用手机号。另一个做法是放开登录名让它能填中文，不建议：登录时要打中文还带横杠。
3. **款号按大类分规则，不按品牌**（理由见 §4.3）。
4. **单号不进编码规则**（理由见 §4.2）。
5. **所有导入的人一个初始密码，第一次登录必须改**（§2）。另一个做法是每人一个随机密码、导完下载一张表发给每个人，更安全但要一个个发。

## 8. 甲方 11-25 给的编码规则

### 8.1 规则

| 编码 | 例子 | 每一段 |
|---|---|---|
| 款号 | `FS2622Z33-001` | F 一级品类（服装；通勤裤类是 T）· S 品牌 · 26 年份 · 22 设计师号 · Z 自营 · 33 三级分类 · `-` · 001 流水 |
| 物料编码 | `27LL03-003` | 27 年份 · LL 一级分类 · 03 二级分类 · `-` · 003 流水 |

### 8.2 在编码规则页怎么配

- **款号**：加一条"服装"规则，按大类选 TS 通勤裤、FS 非通勤裤（服装线的两个大类）：
  一级品类编码 + 品牌编码 + 款式年份 + 设计师编号 + 固定文字 `Z` + 品类编码 + 固定文字 `-` + 流水 3 位。
  - F、T 是甲方产品类目里两个一级的编码（服装（非通勤裤类）F、通勤裤类 T），跟着款式选的品类往上找，不看大类。
    （草案写的是固定文字 F，看了类目表才知道通勤裤是 T。老款号 FS、TS 开头就是一级 + 品牌 S，大类的值 FS、TS 也是这么来的。）
  - 鞋子、百货甲方还没给，先照通用规则（现在的格式）。
  - Z 自营：TRADE 关着，款式都是自营，用固定文字。以后有代工之类的再加一段。
  - 流水按 `一级品类 + 品牌 + 年份 + 设计师 + Z + 品类 + -` 分开记，每一组最多 999 个。
- **物料编码**：改通用规则：
  年份 + 一级分类编码 + 二级分类编码 + 固定文字 `-` + 流水 3 位。每个年份、二级分类最多 999 个。
- 只管以后新编的，已有的编码不变（§4.6）。

### 8.3 要改的代码

现有的段配不出来的有四处（第 4 处是看了类目表加的）：

1. **品牌编码**。字典里品牌的值是导入款式时的中文名（`StyleExcel.createBrand`），字典的值建好又不能改，所以"品牌编码"这一段取不出 `S`。
   - 给字典 `brand` 加一列"编码"：用 `text_value`，和大类的"品类线"是同一列，V58 只改 `sys_dict_type.text_label`。
   - 品牌编码这一段先取编码；没填的，值本身是字母数字就用值（和现在一样）；都不行就报错，让去 管理后台 › 系统管理 › 字典管理 › 品牌 填。
2. **物料分类编码**。现在二级的编码只能是 2 位字母、全部分类里不重复，而且建好不能改。甲方的二级是 `03` 这种数字，不同的一级下面会重复。
   - 改成 2 位字母或数字，同一个上级下面不重复（V58 换唯一索引）。
   - 一级的编码照旧选填（实现时：原来一级根本不收编码，现在收）；规则里用了"一级分类编码"、一级又没填的，编号时报错，让去 资料 › 基础 › 物料分类 填。
   - 编码建好能改。原来不让改，是因为它就是物料编码的前缀；现在格式由规则定，改了只影响以后新编的。
3. **新加一段"一级分类编码"**（物料编码用）：取物料所在二级分类的上级的编码。原来的"物料分类编码"改叫"二级分类编码"（存的类型名 `MAT_CATEGORY` 不变，已配的规则不用动）。
4. **新加一段"一级品类编码"**（款号用，`TOP_CATEGORY`）：从款式选的品类往上找到一级，取它的编码；一级没填的，编号时报错，让去 资料 › 基础 › 品类 填。原来的"品类编码"取款式选的那一级（一般是三级）。

年份：见 §8.4。

前端跟着改：编码规则页的段多一种；物料分类对话框的编码能改、能填数字；字典页的品牌多一列"编码"（字典页已经能显示 `text_value`，大类的"品类线"就是这么显示的）。接口文档、`web/src/types` 一起改。

### 8.4 要定的

**物料编码的"年份"是哪一年？** 例子里是 27，今年是 26。

- **用户 11-25 定：例子只是例子，按编号那年**，用现有的"日期 yy"段，不用改代码。现在建的物料编出来是 26。
- 没采用的另一种：这料是给哪一年的货开发的，要给物料加"年份"字段、再加一段"物料年份"。

### 8.7 导入品类、物料分类

甲方 11-25 给了领猫"基础档案"导出的两张表：产品类目 107 个（一级 2、二级 25、三级 80），物料类目 114 个（一级 16、二级 98）。手工建两百多个分类、再逐个填编码，太慢也容易错，所以品类、物料分类页加了「导入」，这两张表原样能导。

- 列：分类名称、分类编码、状态、排序。分类名称是从一级写到这一级的路径，用 `>` 隔开（`服装（非通勤裤类）>裙子>半身裙`）。扩展一到扩展七、描述认得、不导。
- 按路径对：
  - 系统里已有的（同一个上级下同名）：改编码、状态；表里空着的不动，不清掉管理员填过的。
  - 没有的：建上，排序用表里的。
  - 上级要么系统里已有，要么也在表里，先建上级再建下级。
- 有一行不对，整批不导，逐行报原因（RFC 001 §9.3）：
  - 路径超过层级（品类 3 级、物料分类 2 级），上级哪儿都找不到。
  - 编码格式不对：品类 1-8 位字母数字；物料分类 2 位字母数字，新的二级必填。`3` 这种会提示可能是 Excel 吃掉了前面的 0。
  - 物料分类在同一个上级下编码重复：表里的、系统里不在表里的都算。
  - 状态不是启用或停用；同一个分类写了两行。
- 改了哪些已有的、哪些和系统里一样没改，按行号列在"导入完成"下面。同一个文件再导一次，什么都不变。
- 权限：新增 + 修改（会建也会改）。走 `FileImportService`，和别的导入一样：解析在事务外，写库一个事务，同一个文件重复提交返回上次的结果。
- 不删：表里没有的分类留着。要去掉的，在页面上停用或删除。
- 代码：`CategoryTreeImport`（两棵树共用），接口 `POST /api/categories/import`、`/api/material-categories/import`，模板 `GET …/import-template`。
- 验证：
  - `CategoryTreeImportTest`：建树先上级后下级；已有的只改有变化的；坏行整批不导。
  - 甲方两张原表在开发库导过一遍，全部导进，编码都在。配上 §8.2 的规则预览：F 下的品类出 `FS26Z95-001`，T 下的出 `TS26Z66-001`，物料出 `26LL03-001`。测完删掉。
