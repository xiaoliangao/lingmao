## 1. 解决什么

两件事让系统用起来费劲：

- **问一个问题要翻好几页**。"220g 斜纹棉还剩多少、在途多少、哪几张单占着"要看库存、待到料、算料三页；"张三手上还有哪些单没回货"要在生产单列表里筛。跟单、采购、管理层每天都在问这类问题。
- **数据从微信、照片、Excel 进来，全靠人手抄**。工厂的送货单照片、供应商的报价截图、品牌方格式不一的订单表，现在都是对着抄进系统。

做一个助手：在系统里用一句话问，回答带上能点开核对的链接；拍照、贴表格，它整理成单据草稿，由人确认后提交。

企查查风险排查（架构 §14.5）、OCR 对账（§14.7）也是 agent 干活，和助手共用同一个底座（§3），不各搭一套。

不做：

- 不让模型直接写 SQL 查库（§9 第 1 条）。
- 不替人提交、审核、过账、作废、删除。助手写的东西只到草稿（§5 第 3 条）。
- 不让模型做业务判断：风险等级、能不能审、库存够不够、价格合不合理，都由系统里已有的规则定。
- 一期、二期不做：手机上的助手、语音、跨对话的长期记忆。

## 2. 两种 agent

| | 后台 agent | 助手 |
|---|---|---|
| 谁触发 | 定时任务、事件（每周复查、申请准入） | 用户在页面上点开问 |
| 用谁的身份 | 专门的 agent 账号 + 长期令牌（`sys_api_token`，架构 §14.8） | 用户自己：用登录令牌换一个短期的受限令牌（§3.3） |
| 能做什么 | 账号的角色给什么权限就是什么，一般只有一两个接口 | 和这个用户一样，再减掉"改状态"的接口 |
| 例子 | 企查查取数、OCR 识别、每天早上的待盯清单 | 问数、打开筛好的列表、解释、录单 |

## 3. 底座：助手服务

### 3.1 形态

一个单独的容器 `assistant`，放进部署包的 compose，用 profile 默认不起：

```
             ┌──────────── assistant（可选容器，默认不起）────────────┐
 浏览器 ───▶ │ 对话 · 定时任务 · 调模型 · 工具白名单                  │ ──▶ 大模型（OpenAI 兼容接口）
  /assistant │ 自己的表在 PostgreSQL 的 assistant schema               │ ──▶ 企查查 MCP（后台 agent 用）
             └───────────────────────┬────────────────────────────────┘
                                     │ 短期受限令牌 / agent 账号令牌
                                     ▼
                     app（权限、数据范围、打码、业务规则都在这）
```

- Nginx 把 `/assistant/` 转给它，和 `/api/` 并列。
- **app 不依赖它**：app 的代码里没有任何调用助手服务的地方。不起这个容器，页面上的入口不出（§6.1），别的功能一点不受影响。
- 为什么不写进 app 里：模型调用慢（几秒到几十秒）、会失败、依赖外网，放进 app 会占着请求线程，外部模型一出问题就可能拖累业务接口；单独一个容器能单独发版、单独关掉，部署包也能不带它。

### 3.2 工具

工具就是 app 已有的接口。打包脚本本来就导出 `openapi.json`，助手服务按一份白名单生成工具：

```yaml
# assistant/tools.yaml：一个接口一条，没列的接口模型看不见
- op: GET /api/stocks                 # 对上 openapi.json 里的接口
  tool: stock_list
  kind: read                          # read 只读；draft 建草稿
  perm: inventory:stock:list          # 用户没有这个权限，就不把这个工具交给模型
  hint: 按物料、仓库查现库存。问"还剩多少"时用
- op: POST /api/inventory-docs/from-purchase/{purchaseOrderId}
  tool: stock_in_draft_from_purchase
  kind: draft
  perm: inventory:doc:add
```

- 工具的参数和说明从 `openapi.json` 取（接口上 springdoc 的 `@Operation`、`@Parameter` 中文说明），`hint` 只补"什么时候用它"。所以一期写接口时把说明写清楚（§10）。
- 每次对话开始，先调 `/api/auth/me` 拿用户的权限码，只把有权限的工具交给模型。
- 改状态的接口（`submit`、`audit`、`unaudit`、`void`、`close`、删除、导入的提交）一律不进白名单。

### 3.3 身份：短期受限令牌

助手代用户调接口，不能直接拿用户的登录令牌：那样模型理论上能调任何这个用户能调的接口，"只到草稿"只靠白名单拦，没有第二道防线。

做法：

1. 前端打开助手时调 `POST /api/auth/assistant-token`，app 用当前登录身份发一个短期令牌：有效 30 分钟，标着"经助手"（`scope = ASSISTANT`）。
2. 前端把它交给助手服务，助手服务调工具时带它；用完即弃，不落库。
3. app 的安全过滤器看到 `scope = ASSISTANT`：GET 照常；非GET仅放行经核对无即时业务效果的草稿接口；不能只按URL白名单判断。含post参数的工具强制post=false，服务端对ASSISTANT身份拒绝post=true、自动过账、报工实绩和现价写入等效果，返回403。
4. 用这个令牌建的草稿，操作日志的操作人照样是用户本人，另记"经助手"。

这样"只到草稿"由 app 自己保证，助手服务写错了白名单也越不过去。数据范围、银行账号打码、看成本的权限本来就在接口里，不用另做。

后台 agent 用 agent 账号的长期令牌（架构 §14.8）：令牌在管理后台生成、吊销，系统里只存摘要；账号的角色只给它要用的几个权限。

### 3.4 模型

```java
/** 调大模型：多轮对话 + 工具调用；看图的录单另配一个模型（可以是同一个） */
interface LlmProvider {
    LlmReply chat(List<LlmMessage> messages, List<ToolSpec> tools);
}
```

- 走 OpenAI 兼容的 chat completions 接口（国内多数大模型都支持这个格式），地址、Key、模型名放 `.env`：`ASSISTANT_LLM_BASE_URL`、`ASSISTANT_LLM_API_KEY`、`ASSISTANT_LLM_MODEL`；看图的 `ASSISTANT_VISION_MODEL`（空 = 不开录单）。
- 甲方不让数据出公司（Q45）：接自部署的模型，OCR 计划里那台 GPU 服务器（架构 §14.7）也能用。换模型只改 `.env`。
- 具体用哪家、多少钱，做的时候和甲方一起定，这里不写死。

### 3.5 存什么

助手服务自己的表放在同一个 PostgreSQL 的 `assistant` schema 里，用单独的库账号，app 不读也不写它们。好处是每天的备份（`pg_dump`）自动带上，不用另配。

| 表 | 存什么 |
|---|---|
| `ast_conversation` | 谁、什么时候开的对话、标题 |
| `ast_message` | 每条提问和回答（回答里的数字和链接按结构存，§5 第 4 条） |
| `ast_tool_call` | 每次调了哪个工具、参数、返回多少条、用时、成功没有 |
| `ast_usage` | 按人按天的 token 数和次数 |
| `ast_brief` | 每天早上的待盯清单（§4.1 第 4 条） |

上传的图片走 app 现有的文件上传（`POST /api/files`），生成草稿时挂到单据的附件上，表里只存文件引用。

### 3.6 用什么写

| | Java（单独一个小 Spring Boot） | TypeScript / Python |
|---|---|---|
| 好处 | 和 app 一种语言、一套构建，用户审得了 | 大模型、MCP 的 SDK 最成熟，例子最多 |
| 代价 | 要确认那时 Spring AI 或 MCP 的 Java SDK 对 Spring Boot 4 的支持 | 多一种语言、一套构建和镜像，用户要多学一样 |

推荐先用一天试 Java：OpenAI 兼容接口的工具调用、连企查查 MCP、流式输出，三样都顺就用 Java；有一样卡住再换 TypeScript。

### 3.7 app 这边要补的

| 补什么 | 说明 |
|---|---|
| `sys_api_token` + 用户类型 `AGENT` | 数据库设计 §3.10 已经设计好；令牌在管理后台生成、吊销 |
| `POST /api/auth/assistant-token` 和过滤器 | §3.3 |
| 汇总接口（放 board） | 口径固定的几个数：按月按品牌的订单件数、按供应商的采购额、到货及时率、延期的生产单数、回货次品率。助手问数只用它们，以后的报表（PRD 13.06）也用它们，口径只有一份 |
| 系统信息里带 `assistantEnabled` | 部署时启用了助手服务就是 true，前端按它出入口（§6.1） |
| 菜单和权限 `assistant:chat:use`、`assistant:draft:use` | 谁能问、谁能录单，在角色里给 |

## 4. 能做什么

### 4.1 第一档：只读（先做）

1. **问数**。比如"220g 斜纹棉还剩多少、在途多少、哪几张单占着""张三手上还有哪些单没回货""这个月各工厂的回货次品率"。回答里每个数字都带一个链接，点开是筛好条件的列表页；工具查不到就直说查不到，再给最接近的页面。
2. **一句话打开列表**。"上周驳回的采购单"→ 打开采购单列表，状态、日期都筛好。入口在 ⌘K 里：页面和单号都搜不到时，回车交给助手（§6.1）。
3. **解释"为什么"**。不能反审核（读下游单据）、超收被拦（读采购单的已入库和上限）、这个料显示缺料（读算料和在途）、这张单在等谁审（读审批块）。现在这类问题只能去问人。
4. **每天早上待盯清单**。后台每天 7 点按人生成：读首页待办、待到料、生产看板，排出"今天要盯的 5 件事"和原因，放在首页一块卡片里（用户能关）。二期有消息推送后，可以推到企微或钉钉。

### 4.2 第二档：录单，只出草稿

| 从什么 | 到什么 | 怎么对上系统里的数据 |
|---|---|---|
| 工厂送货单的照片 | 物料入库单草稿 | 认出供应商、送货单号、品名和数量，对上这家供应商没入齐的采购行，再调"由采购单生成入库单" |
| 供应商的报价截图、微信消息 | 独立报价提案（不是现价记录） | 对上物料、供应商和单位，保存独立提案；人确认前不调现价写接口、不新增prc_price生效记录，对不上的列出人工确认 |
| 手写或拍照的尺寸表 | 资料包尺寸指示（草稿版本） | 部位对上字典 `size_point`，尺码对上款式的尺码组 |
| 品牌方格式不一的订单 Excel、领猫的导出 | 套成系统的导入模板 | 列对照让人确认一次、记下来，下次同样格式自动套；导入还是走现有的导入接口和校验 |
| 跟单员在手机上说一句"FS2611080701 裁剪完了 300 件，面料有色差" | 独立报工/异常提案 | 认出单号、节点、数量、异常类型，未确认不写节点实绩；跟单员确认后以正常业务身份执行 |

规则：

- 都是草稿，单据的备注里写"由助手生成"，原图挂进附件，事后查得到从哪来的。
- 认不准的不猜：对不上的行、不确定的数标出来让人选，不填一个看着像的。
- 第 5 条要手机页面加入口，放在二期手机审批（PRD 13.05）之后。

### 4.3 第三档：随待定模块

- **OCR 对账**（M11，架构 §14.7）：识别工厂的对账单后，用人话解释每处差异（"差 3 件：回货单 HH… 记 117，对方记 120"）。识别和比对还是系统做。
- **主数据体检**：名字相近的疑似重复供应商、资质快到期的、在产款没有已生效资料包的、缺单位或缺价格的物料。只列建议，由人处理。
- **企查查**（架构 §14.5）：后台 agent 取数、回写快照；新增的风险条目由模型写一段人话摘要，放在风险页签上。风险等级照旧由 `RiskService.record` 按字典定。

## 5. 规矩

1. **看到的和能做的 = 这个身份用接口能做的**，一样不多：工具只包已有接口，令牌是用户本人的（§3.3）。
2. **规则在系统里**：模型只负责取数、整理、解释、认图。判断交给已有的接口和规则。
3. **写只到草稿**：白名单不收改状态的接口，app 的过滤器再拦一次（§3.3）。最后一下由人点。
4. **数字能核对，模型不自己算**：回答按结构返回（文字 + 数字列表，每个数字带来源链接），前端渲染；要汇总的用汇总接口（§3.7），汇总接口没有的就说"这个数系统里没有现成的"，不让模型拿几条记录自己加。
5. **全部留痕，有限额**：提问、调了哪些工具和参数、回答、token 都记下来（§3.5）；按人每天限次数、全系统每天限 token（计数放 Redis，架构 §9），超了提示明天再用。管理后台能按人、按天看用量和记录。
6. **能整个关掉**：容器停了，入口消失，系统照常。

## 6. 页面

### 6.1 入口

- 系统信息里 `assistantEnabled` 是 true、用户有 `assistant:chat:use` 才出入口；助手服务调不通时入口显示"暂时用不了"，不报错弹窗。
- ⌘K：页面和单号都搜不到时，最后一项是"问助手：<输入的话>"，回车打开助手抽屉并发出这句话。
- 侧边栏底部"助手"一项，快捷键 ⌘J，打开右侧抽屉。

### 6.2 助手抽屉

- 右侧抽屉，宽 420px，不挡主页面；切页签不关，对话留着。
- 回答：一段文字 + 数字卡片（数字、说明、"去看"链接）+ 有表格时最多 10 行的小表；点链接在主区域打开那一页（`docRoute` 或带查询参数的列表地址），抽屉留着。
- 有 `assistant:draft:use` 时多一个"传图片 / 表格"按钮；生成草稿后显示"已生成入库单草稿 RK…，去核对"，点了打开那张单。
- "新对话"清空上下文；不跨对话记东西。

### 6.3 首页卡片

"今天要盯的"一张卡片，5 条，每条一句话 + 链接，能关（记在用户设置里）。

### 6.4 管理后台

"助手记录"一页（只给超级管理员）：按人、按天看提问、调了哪些工具、用了多少；能按人停用。数据由助手服务的接口给，app 只放页面。

## 7. 列表页要能从地址带筛选

"一句话打开列表"要求各列表页的筛选条件能写进地址（`/purchases?status=PENDING&dateFrom=…`），打开就是筛好的。首页待办点过去已经在用一部分，开发助手前把所有列表页核对一遍、补齐；这件事对首页、⌘K 本身也有用。

## 8. 质量

- **评测集**：攒 30 个左右甲方真实会问的问题，在一份固定的测试数据（集成测试的种子数据扩一点）上写好标准答案，包括"应该答查不到"的。
- 换模型、改提示词、改 `tools.yaml` 之前跑一遍：数字对、链接对、该拒绝的拒绝了；比上一版差就不发。
- 录单另有一组样张（送货单、报价截图各 10 张），看对上的行数和标错的行数。
- 上线后每周看一次"答错了"的反馈（回答下面一个"不对"按钮），补进评测集。

## 9. 取舍

1. **不做模型直接写 SQL（text-to-SQL）**。直接查库会绕过数据范围、银行账号打码、看成本的权限，一句话就可能问出不该看的价格；SQL 写错了也看不出来。用工具调用，每个数都出自已有的接口，口径和页面上一样。
2. **助手单独一个容器，不写进 app**（§3.1）：慢、会失败、依赖外网的东西和业务接口隔开；能单独关掉、单独发版。
3. **助手用用户本人的短期受限令牌，不用 agent 账号**：用 agent 账号就得给它所有人的权限再自己做过滤，等于把权限系统重写一遍。
4. **不微调模型**：工具调用 + 提示词 + 评测集就够，换模型的成本低。
5. **汇总口径放 board、只写一份**：助手和以后的报表共用，不会出现"助手说的和报表对不上"。

## 10. 一期、二期顺手做的

不写空代码（架构 §14.1 第 4 条），只把以后要用的写对：

- 每个接口的 springdoc `@Operation(summary=…)`、`@Parameter` 写清楚中文说明（第 3 批起各步的要求里已经加了）。11-21 补齐：410 个接口都有 summary；接口文档读 Javadoc（therapi），查询条件对象拆成一个个查询参数（`default-flat-param-object`），`xxxId`、`xxxDateFrom` 这种各处意思一样的名字没写说明的按名字补一句（`config/OpenApiConfig`），认不出的不编、在字段上写（`ownerId` 在首页是负责人、别处可能是物权方，这种不进兜底表）；上传的文件（`MultipartFile`）和当前登录的人不拆，上传、导入接口声明 `consumes` multipart，`OpenApiDocsIT` 起应用导一次文档守着。参数 941 个都有说明；返回体字段有说明的约 1/7，以后写 DTO 照样在字段上写 Javadoc。
- 列表页的筛选能从地址带（§7），新写的列表页照这个写。
- board 写首页待办时，数的口径集中在一处，以后的汇总接口接着放这里。

## 11. 测试点

| 测什么 | 怎么测 |
|---|---|
| 受限令牌 | 拿 `scope = ASSISTANT` 的令牌调 `submit`、`audit`、删除 → 403；调建草稿的接口成功，操作日志记"经助手"；令牌过期 → 401 |

## 12. 要甲方定的、要用户定的

要甲方定（PRD Q45）：

1. 要不要做，先做哪一档。
2. 价格、供应商这些数据能不能发给外部的大模型；不能的话用自部署的模型，GPU 服务器谁来准备。
3. 用谁的模型、费用谁出、每天的限额定多少。

要用户定的（推荐的写在前面）：

1. **单独一个容器**（§3.1），不写进 app。
2. **短期受限令牌**（§3.3），"只到草稿"由 app 再拦一道。
3. **助手服务先试 Java**，不顺再换 TypeScript（§3.6）。
4. **第一档先做问数、打开列表、解释**，待盯清单和录单随后。

审查补充：提案域、受限身份及工具效果校验均在本RFC后续实施，不给一期价格档案新增假DRAFT状态。验证包括post=true、大小写/嵌套参数、批量接口绕行、未确认不影响现价/库存/生产状态（RFC010 §7）。
