# RFC 004 供应商

状态：**已定**（2026-11-15 用户审过；"等用户定的问题"一节标了结论）。

对应：PRD §6.8.1、§6.8.2、§6.1.6、§6.9.2、§10、Q29、Q30、Q34–Q36；架构 §3.1、§4.2、§4.6、§4.8、§8；数据库设计 §1.6、§6.1–§6.5、附录 A.1。第 2 批共用的规则见 RFC 003 §2。

## 1. 解决什么

供应商档案（分类、擅长品类、资质证照）、准入审批、关键字段改动审批、停用和黑名单、银行信息脱敏、工厂仓同步、Excel 导入导出，以及给价格档案和第 3、4 批单据用的"这家能不能选"。

不做：

- 风险排查、合同（Q22 待排期）：详情页不放这两个页签。
- 一家多个收款账户（`sup_supplier_bank`，随 M11 财务结算）。
- 往来单据页签、拉黑时列出未完成单据：要第 3 批的引用查询（RFC 001 §17），那时补。
- 首页待办"供应商待审批""证照快到期"：首页待办在第 4 批。这一批在列表上能筛出来（§8）。

## 2. 状态和动作

状态和转换照架构 §4.6，写成 `StatusFlow` 的转换表，改状态一律比较并交换（0 行 → 1002）。每个动作写 `biz_doc_log`（`SUPPLIER`），原因写进备注。

| 动作 | 从 → 到 | 权限码 | 另外的要求 |
|---|---|---|---|
| 新建 | → 待准入 | `add` | 状态不收参数 |
| 导入 | → 待准入；或合作中、停用 | `import`；后两种还要 `admit` | §9 |
| 申请准入 `submit` | 待准入 → 审批中 | `edit` | 缺项一次列全，1000 + 缺项清单（§2.1）；记申请人、申请时间 |
| 撤回 `withdraw` | 审批中 → 待准入 | `edit` | 只有申请人能撤 |
| 驳回 `reject` | 审批中 → 待准入 | `admit` | 原因必填；不能是申请人 |
| 通过 `audit` | 审批中 → 合作中 | `admit` | 不能是申请人；记准入人、准入时间 |
| 停用 `disable` / 启用 `enable` | 合作中 ⇄ 停用 | `edit` | |
| 拉黑 `blacklist` | 除黑名单外任意 → 黑名单 | `admit` | 原因必填；记拉黑人、时间 |
| 解除 `unblacklist` | 黑名单 → 停用；**从没准入过的回待准入** | `admit` | 原因必填 |

"不能自己批"写在 Service 里，比较 `admit_apply_by` 和当前用户（架构 §4.6）。超级管理员也一样。

解除黑名单和 PRD 不一样的那一处：PRD 写"黑名单 → 停用"，可是一家待准入的被拉黑再解除，变成停用，再点启用就成了合作中，绕过了准入。所以按 `admit_time` 分：准入过的回停用，没准入过的回待准入。

### 2.1 申请准入的检查

缺哪项列哪项（PRD §6.8.2）：统一社会信用代码；营业执照（资质里有 `LICENSE`，有效期为空或不早于今天）；联系人；开户行；账号。

### 2.2 各状态下能改什么

| 状态 | 普通字段 | 关键字段（★） | 资质 |
|---|---|---|---|
| 待准入 | 直接改 | 直接改 | 能增删 |
| 审批中 | 不能改 | 不能改 | 不能增删 |
| 合作中、停用、黑名单 | 直接改 | 挂起等审批（§4） | 能增删 |

黑名单也要审批：架构 §4.6 只写了合作中、停用，原型三种都拦。黑名单解除以后回停用，再启用就能下单，拉黑期间改的账号不审就成了漏洞。

审批中的拦法：保存的条件里带 `status <> 'ADMITTING'`，0 行 → 1000"准入审批中不能改，先撤回"。资质增删先 `SELECT … FOR SHARE` 锁住供应商行再查状态，和 submit 的比较并交换互斥。

## 3. 表结构

照数据库设计 §6.1–§6.5，不另加列。几点说明：

- `sup_supplier` 上的 ★ 列和 `status`、准入、拉黑的列，实体上都标 `NEVER`（RFC 001 §4.4）。普通保存改不到它们；待准入时改关键字段走单独的条件更新（§4）。
- `sup_supplier_category`、`sup_supplier_good_at`：保存时整批删了重插。
- `sup_supplier_cert`：文件存 `/files/...`，返回时签名。证照不删文件（RFC 001 §10）。
- `sup_supplier_change`：`changes` 里存全号（批准时要写回），返回时按 §5 脱敏。
- 迁移一个文件，排在 RFC 003 §11 的第 3 个：`sup_supplier` → 三张子表 → `sup_supplier_change`。`sup_supplier_good_at` 指向 `bas_category`，所以排在 basic 第一个文件之后。

## 4. 关键字段改动

关键字段：全称、信用代码、结算方式、账期、发票类型、税率、开户行、账号、收款户名（PRD §6.8.2 的九个；原型的 `SUP_KEY` 漏了收款户名，照 PRD）。

保存（`PUT /api/suppliers/{id}`）在一个事务里：

1. 普通字段：整体覆盖，条件带 `status <> 'ADMITTING'`。
2. 关键字段和当前值比，没变化的去掉。信用代码原来是空的，从这里拿出来当普通字段直接更新（用户 11-15 定，§16）。
3. 待准入：剩下的直接更新，条件带 `status = 'PENDING_ADMIT'`；0 行 → 1002。
4. 其他状态：剩下的插一条 `PENDING` 改动，`changes = [{field, label, before, after}]`。已经有一份待批的 → 1000"已有一份待批的改动，先撤回或等批完"（先查一次，部分唯一索引兜底）。
5. 返回 `{ applied: [...], pending: [...] }`，前端分别提示"已保存""账期 30 → 60 等审批"。

审批（`POST /api/suppliers/{id}/changes/{changeId}/approve`）：

1. 比较并交换 `PENDING → APPROVED`，不能是申请人。
2. 逐项核对 `before` 还等于当前值，不等 → 1002"资料已经变了，请重新提交"（整个事务回滚，改动还是待批）。
3. 写回 `sup_supplier`；信用代码撞了唯一索引 → 1000"和 GYS0003 重复"。
4. 写 `biz_doc_log`，备注是"账期 30 → 60"这样的一串，账号脱敏。

驳回（原因必填，不能是申请人）、撤回（只有申请人）都是比较并交换。改动的列表 `GET /api/suppliers/{id}/changes` 在详情页的操作记录里一起显示。

挂起期间新单据用旧值（PRD §6.8.2），不用另做什么：单据读的就是 `sup_supplier`。

### 4.1 信用代码

- 存之前去空格、转大写。
- 按 GB 32100-2015 校验：18 位，字符集不含 I、O、Z、S、V，最后一位是前 17 位的加权校验码。
- 全表唯一（`uk_sup_supplier_credit`）。保存前先查一次，重复时提示"和 GYS0003 某某 重复"；唯一索引兜底。
- 待批改动里的信用代码不占号：两份改动可能改成同一个号，后批的那份在写回时被唯一索引拦住。

## 5. 银行信息

按 Q30 的默认做法（PRD §6.8.1、数据库设计 §1.6）：

- 只遮账号，前 4 后 4，中间 `****`。开户行、收款户名不遮。
- 没有 `supplier:supplier:bank` 的人：详情返回遮过的账号，改动记录里的账号也遮；保存时请求里的账号**不收**（前端那一格只读，后端忽略），免得把遮过的值存回去。
- 有 `bank` 的人：详情照样返回遮过的；点"显示"调 `GET /api/suppliers/{id}/bank` 取全号，这个接口贴 `@OperLog(module = "供应商", action = "查看银行账号")`，每点一次记一条。打开编辑时前端也调它，把全号填进表单。保存时收到的账号和当前值遮过的样子一样，当作没改（兜底，防止把遮过的值存回去）。
- 列表、导出不出账号列。
- 操作日志（`OperLogAspect`）现在只遮名字里带 `password` 的字段，加上带 `bankaccount` 的（不分大小写）：保存请求里的全号不进日志。

## 6. 工厂仓

调 basic 的 `WarehouseService`（RFC 003 §6），和供应商的改动在同一个事务里：

| 时机 | 调 |
|---|---|
| 新建、导入、保存后，分类含成衣厂或加工厂 | `syncFactoryWarehouse(id, code, shortName, true)`：没有就建，有就改名 |
| 保存后分类里没有这两类，但改了简称 | `syncFactoryWarehouse(id, code, shortName, false)`：有就改名，没有不建 |
| 删除供应商 | `deleteFactoryWarehouse(id)` |

停用、拉黑、启用、解除都不调（架构 §3.1）。

## 9. 导入导出

列对照照数据库设计附录 A.1，模板就是领猫导出的样子（理由同 RFC 003 §9）：

- 工作表"供应商管理"一行一家，表头用领猫列名；"银行收付款信息"可选，按附录 A.1 的规则取一个账户，多出来的进导入提示。
- 我们多出来的列接在后面，选填：账期、税率、微信。
- 导入时选状态：合作中（默认）或待准入。选合作中要 `admit`，"是否冻结"为是的导成停用；导成合作中、停用的，准入人、准入时间记导入人、导入时间，写一条"导入"日志。选待准入时全部待准入。
- 分类按 Q34 的默认对照：面料 → 面料商，辅料 → 辅料商，成品加工 → 成衣厂，物料采购、质检机构 → 其他；对不上的整批报错，列出值。
- 信用代码选填（Q29）：格式不对的这一格不导，进提示；和已有的、和同一个文件里的重复，整批报错。
- 采购员按显示名匹配，对不上的留空、进提示。擅长类目按名称匹配品类，对不上的进 `legacy_attrs`。
- 账号、电话按单元格里存的原文读（Q35），不经过 Excel 的数字格式。
- 外部供应商编码、是否指定、Att01–Att10、地址电话、传真进 `legacy_attrs`（Q36），有值才存。
- 只新增，编码已存在算错误；分类含成衣厂、加工厂的同一个事务里建工厂仓。
- 导完把 GYS 流水推到已用的最大号（`raiseTo`，RFC 003 §10）。

导出：一行一家，列和模板一致，不出账号、户名、开户行。

## 10. 删除

- 审批中、黑名单的不能删（1000）。审批中的先撤回；黑名单留着，信用代码一直占着，换个名字重建也会撞上。
- 其他状态没被引用就能删。事务里依次删：分类、擅长品类、证照、改动记录、工厂仓（`deleteFactoryWarehouse`）、附件、操作记录、供应商。工厂仓或供应商被物料、价格档案、单据引用，外键拦住 → 1005，整个回滚。

## 11. 审批要不要多级

**第 2 批一级就够，多级审批不用挪到第 1 批。**

- PRD §6.8.2 要的是"另一个有准入权限的人批准"，一级。架构 §4.6、§4.8 也写了供应商准入是单级，照状态 + 审核权限做，不走多级审批那一套。
- 以后甲方要分级（比如采购经理批完总经理再批），第 3 批的多级审批（架构 §4.8）接上：submit 时 `ApprovalService.start`，audit、reject 改成调 `pass`、`reject`，最后一级通过时再走现在的比较并交换。状态机和表都不用动，审批中的人看到的还是"准入审批中"。改动审批同理。

## 13. 关键流程和并发

| 场景 | 怎么保证 |
|---|---|
| 一边申请准入、一边改资料 | 保存带 `status <> 'ADMITTING'`；submit 是比较并交换；两边谁后到谁失败 |
| 申请准入时另一个人在删营业执照 | 资质增删锁供应商行再查状态（§2.2） |
| 两个人同时给同一家提改动 | `uk_sup_change_pending` |
| 批准时关键字段已被别的途径改了 | 核对 `before`，不等 → 1002 |
| 两家同时改成同一个信用代码 | 唯一索引 |

## 14. 取舍

- **解除黑名单按准入过没有分两种去向**（§2）：堵住"待准入 → 拉黑 → 解除 → 启用"绕过准入。
- **黑名单也走改动审批**（§2.2）：跟原型，不跟架构 §4.6 的字面。
- **账号保存时没权限就不收**（§5）：不然没权限的人一保存，就把"6222****1234"存进去了。
- **工厂仓不随停用、拉黑变**：架构 §3.1 已定，工厂仓里可能还有料。
- **导入的状态是一个选项，不是每行一列**：附录 A.1 第 12 列就是这样写的；领猫里冻结的一列已经够区分停用。

### 和上文不一样，或者上文没写到的

- **锁的顺序**：保存先 `SELECT … FOR UPDATE` 锁住供应商再比较，批准改动也是先锁供应商、再比较并交换改动。两边都是"供应商 → 改动"，不会互相等成死锁。§4 第 1 步说的"条件带 `status <> 'ADMITTING'`"也带着，锁住以后它其实拦不到什么，留着兜底。
- **新建也不收账号**：§5 只说了保存。没有 `bank` 权限的人新建时，请求里的账号同样忽略，前端那一格只读。
- **申请人清空**：撤回、驳回、拉黑时把 `admit_apply_by`、`admit_apply_time` 清掉。不清的话，"待我审批"和"不能自己批自己"会拿上一次的申请人来比。
- **详情的 `actions`**：后端按状态、权限、是不是申请人算好，前端照着显示按钮。除了状态动作，还有 `edit`（不在审批中、有 `edit`）和 `remove`（不在审批中、不在黑名单、有 `remove`）。改动也带自己的 `actions`（`approve`、`reject`、`withdraw`）。
- **保存的返回**：`{ id, applied, pending }`，比 §4 第 5 步多一个 `id`，新建完前端拿它跳详情页。`applied`、`pending` 是给人看的文字（字典翻成中文，税率带 %，账期带"天"）。
- **下拉 `/options`**：多收 `keyword`、`includeId` 两个参数；`usage` 不传当 `SAMPLE`；最多 50 条。`includeId` 是编辑旧记录时把已选的那家带上：它停用了、不在前 50 条里，也照样显示名字。
- **`checkUsable` 的提示**：`"<简称> 现在是「停用」，只有合作中的供应商能下大货单"`，`SAMPLE` 的是"不能用来打样、录价格"。
- **证照地址**：去掉签名后必须以 `/files/` 开头、不超过 255 个字，否则 400"文件要先通过上传接口上传"。证照的增删改先 `SELECT … FOR SHARE` 锁住供应商行再看状态（§2.2），审批中的报 1000"准入审批中不能改资质，先撤回"。
- **操作记录的动作名**：`create`、`update`、`import`、`submit`、`withdraw`、`audit`、`reject`、`disable`、`enable`、`blacklist`、`unblacklist`，改动是 `change`、`change-approve`、`change-reject`、`change-withdraw`，证照是 `cert-add`、`cert-edit`、`cert-remove`。中文名在详情页传给 `DocLogList`。"查看银行账号"记在操作日志（`sys_oper_log`），不记在单据的操作记录里。
- **改动记录单独一个页签**：§4 说改动列表"在操作记录里一起显示"，做出来是两个页签：操作记录里有"提改动""批准改动"这几行（备注里是改了什么），改动记录页签一行一份改动，看得到结果、谁批的、驳回原因。
- **导入**：
  - "是否冻结"认"是""冻结"两种写法；银行表的状态认"停用""禁用""否"为不用。
  - 不拦导入的提示（信用代码格式不对、采购员对不上、多出来的银行账户……）同一类合并成一条，列出行号。
