# RFC 001 框架补齐

状态：**草案**（2026-11-05），等用户审。

对应：架构 §4 ~ §11、§15；PRD §5、§6.9.2、§8。

## 1. 解决什么

业务模块开工之前，先把每个模块都要用的东西补齐，顺手修掉积压的 bug。分两批：

- **A 批，11-14 发版前**：第 1 次发版的主数据页面、Excel 导入、甲方试用要用到的。
- **B 批，11-21 发版前、订单开工前**：只有单据才用到的。第 1 次发版只有主数据、没有单据，按"不提前写空代码"（架构 §14.1），这批等第一张单据（订单）开工时再写，细节到时候在订单 RFC 里补。

不在本 RFC 里：

- 用户的默认主体、部门、岗位（PRD §6.9.2 第 1 条）：要先有主体公司表，放在基础资料 RFC。
- 预置角色模板（PRD §3.1）：随各模块的菜单迁移一起插。
- 库存过账引擎（架构 §5）：放在出入库 RFC。
- 打印布局、手机布局：随第一个用到它的功能做（资料包打印、手机报工）。
- 部署：RFC 002。

## 3. 积压 bug

原因都是读代码确认过的。008、009 原来标"待验证"，读代码确认后端确实没拦。

| 编号 | 现象 | 原因 | 怎么修 |
|---|---|---|---|
| 001 | 字典类型删了，同名的建不回来 | V1 的 `uk_sys_dict_type_code` 是普通唯一索引，逻辑删除的行还占着编码。Service 查重时自动带 `deleted = false`，查不到，插入时被索引拦住，返回 500 | 新迁移把它换成部分索引 `WHERE deleted = false`。另外唯一冲突统一转成 1000（§5），以后哪里漏了也不会是 500 |
| 002 | 修改后 `update_time` 不变 | `strictUpdateFill` 只在字段是 null 时才填。修改是先查出实体（`update_time` 有旧值）再 `updateById`，旧值不是 null，就没填 | 更新时改用 `setFieldValByName`，无条件覆盖 |
| 003 | 请求体 JSON 格式错返回 500 | 解析失败抛 `HttpMessageNotReadableException`，没有对应的处理方法，落到兜底 | 返回 400（§5.2） |
| 004 | 提示"size size 最多 500" | 校验消息里已经写了字段名，处理器又在前面拼了一次 | 只用消息本身。约定每个校验注解都写完整的中文 `message`；加一个测试扫描所有 DTO，有注解没写 `message` 就失败 |
| 005 | 修改时备注传 null，旧备注清不掉 | MyBatis-Plus 更新默认跳过 null 字段，传 null 等于"不改" | §4.2 |
| 006 | 方法不对返回 500 | `HttpRequestMethodNotSupportedException` 没处理 | 返回 405 |
| 007 | 上传不带 file 返回 500 | 抛 `MissingServletRequestPartException`，没处理 | 返回 400"缺少参数 file" |
| 008 | 管理员能去掉自己的 admin 角色 | `assignRoles` 不看改的是不是自己。唯一的超级管理员把自己的 admin 去掉，就再没人能进管理后台 | 不能去掉自己的超级管理员角色，不能停用自己（删除自己已经拦了） |
| 009 | 停用菜单后，它下面的按钮权限还有效 | `selectPermsByUserId` 只看按钮自己的 `status`，不看上级 | 用递归查询找出"自己和所有上级都启用"的菜单，权限和侧边栏都只从这里取 |

## 4. 审计填充和保存

### 4.1 谁改的

`AuditMetaObjectHandler` 补上 `create_by`、`update_by`：从登录信息里取当前用户 id。没有登录用户的场合（启动时建 admin，以后的定时任务）留空。时间从注入的 `Clock` 取（§6.2）。

### 4.2 保存是整体覆盖

**规定**：修改接口（`PUT`）收到的是这条记录所有可编辑字段的值，某个字段没传或传 null，就是把它清空。前端编辑表单本来就是整张提交的。

MyBatis-Plus 的 `updateById` 默认跳过 null 字段，所以清不掉（bug 005）。考虑过三种改法：

| 做法 | 问题 |
|---|---|
| 可清空的字段逐个标 `updateStrategy = ALWAYS` | 漏标一个，那个字段就清不掉；更糟的是改状态用的 `update(new Xxx(), 条件)` 会把这些字段一起写成 NULL（实体是新建的、全是 null），改个状态把备注清了 |
| 全局改成 `ALWAYS` | 同上，而且所有字段都会被清 |
| ✅ 一个公共方法：把实体里为 null 的字段显式写成 NULL | 全局策略不动，改状态的写法照旧 |

```java
DictType entity = getById(id);              // 不存在抛 404
BeanUtils.copyProperties(req, entity);      // 请求里的 null 也拷过去
dictTypeMapper.update(entity, Updates.replaceById(entity));
```

`common.mybatis.Updates.replaceById` 按 MyBatis-Plus 的表结构信息（`TableInfoHelper`），给每个为 null 的字段加一条 `SET 列 = NULL`，条件是 `id = ?`。主键、自动填充的审计列、逻辑删除列、下面标了 `NEVER` 的列不写。

### 4.3 "由动作改"的列

状态、审核人、审核时间、版本号、回写的累计数（已入库、已排产……），只能由各自的动作（审核、过账回写）用条件更新改。实体上标：

```java
@TableField(updateStrategy = FieldStrategy.NEVER)
private String status;
```

标了 `NEVER`，`updateById` 和 `replaceById` 永远不写这一列；动作用 Wrapper 的 `.set(...)` 改，不受影响。

为什么：保存是"先查出来、改、再整条写回去"。如果状态也跟着写回去，A 打开供应商编辑页的同时 B 把这个供应商拉黑了，A 一点保存，状态又变回"合作中"。标了 `NEVER`，A 的保存根本不碰状态。这也是架构原则"累计数只能由一个地方改"（§1 第 4 条）的落地方式。

## 5. 错误码和错误编号

### 5.1 业务错误带数据

`BizException` 加一个可选的 `data`，`R.fail(code, msg, data)` 带回前端。错误码常量集中在 `common.exception.ErrorCodes`：

| code | 意思 | data |
|---|---|---|
| 1000 | 一般业务错误 | — |
| 1001 | 库存不足 | 缺料清单 |
| 1002 | 状态已变化，或单据被别人改过 | — |
| 1003 | 导入校验没通过 | `[{row, column, message}]` |
| 1004 | 超出上限 | 哪几行、上限多少 |
| 1005 | 有下游单据 | `DocRef` 列表 |

### 5.2 异常怎么变成返回

HTTP 状态码仍然一律 200，`code` 在返回体里（沿用现在的约定，前端只看 `code`）。

| 异常 | 什么时候 | code | msg |
|---|---|---|---|
| `BizException` | 业务规则不允许 | 自带 | 自带 |
| `BindException`、`HandlerMethodValidationException` | 参数校验没过 | 400 | 各条消息用"；"连起来（bug 004） |
| `HttpMessageNotReadableException` | 请求体不是合法 JSON，或字段类型、时间格式不对（bug 003） | 400 | 请求体格式不对；认得出字段时带上字段名 |
| `MethodArgumentTypeMismatchException` | `/api/users/abc` | 400 | 参数 id 格式不对 |
| `MissingServletRequestParameterException`、`MissingServletRequestPartException` | 缺参数；上传不带 file（bug 007） | 400 | 缺少参数 file |
| `HttpMediaTypeNotSupportedException` | Content-Type 不对 | 400 | — |
| `MaxUploadSizeExceededException` | 已有 | 400 | 文件太大 |
| `AccessDeniedException` | 已有 | 403 | 没有权限 |
| `NoResourceFoundException` | 已有 | 404 | 接口不存在 |
| `HttpRequestMethodNotSupportedException` | bug 006 | 405 | 不支持 POST 请求 |
| `DuplicateKeyException` | 唯一索引拦住了：查重之后、插入之前，别人刚好建了同样的编码 | 1000 | 数据重复，可能别人刚建了同样的编码，请刷新后再试（日志里记约束名） |
| 其他 | 程序错误（包括外键冲突：说明少了一处检查） | 500 | 服务器出错了，错误编号 xxxxxxxx |

### 5.3 错误编号

- 一个过滤器排在最前面（比 Spring Security 还早，所以 401 也有编号）：每个请求生成 8 位随机编号，放进日志上下文（MDC），写进响应头 `X-Trace-Id`。
- 日志格式加上编号：同一个请求的每一行日志都带它。
- `sys_oper_log` 加一列 `trace_id`，操作日志和应用日志能对上。
- 超过 1 秒的请求记一条 warn：方法、路径、耗时。
- 500 的提示里带编号。用户截图发过来，在服务器上 `grep` 编号就能找到那次请求的全部日志。

为什么 8 位：一天几千个请求，8 位十六进制（约 43 亿种）在日志保留期内撞上的概率可以忽略，又短到能在电话里念出来。

## 6. 单号和"今天"

### 6.1 单号

照架构 §4.5 改成 PostgreSQL 生成，表结构比架构里的稍微通用一点：主数据的编码（供应商 `GYS0008`、客户 `KH0003`、物料 `ML0012`）也要流水号，但它们不分天。

```sql
CREATE TABLE sys_serial (
    seq_key     VARCHAR(32) PRIMARY KEY,   -- 按天的：前缀 + 日期，如 CG20261105；不分天的：前缀，如 GYS
    seq         INT         NOT NULL,
    update_time TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 取号：第一次插入 1，之后每次 +1，一条语句，在调用方的事务里执行
INSERT INTO sys_serial (seq_key, seq) VALUES (?, 1)
ON CONFLICT (seq_key) DO UPDATE SET seq = sys_serial.seq + 1, update_time = now()
RETURNING seq;
```

`SerialNoGenerator`：

| 方法 | 结果 | 用在 |
|---|---|---|
| `daily("CG")` | `CG202611050001` | 单据（PRD §5.2 的前缀） |
| `next("GYS", 4)` | `GYS0008` | 主数据编码 |

用 `JdbcTemplate` 执行，和 MyBatis 用同一个数据源，自动加入当前事务：建单失败，号也一起回滚，单号连续。代价是同一个 key 的取号要排队（行锁持有到事务提交），20 个人用感觉不到。

自动编码会撞上手填的或从领猫导入的编码（PRD Q05 允许手填）。处理办法在模块里：取到的号已经存在就再取下一个。基础资料 RFC 细说。

Redis 版的生成器和它的测试删掉。

### 6.2 今天

注册一个 `Clock`（东八区），代码里写 `LocalDate.now(clock)`，不写 `LocalDate.now()`。单号日期、审计时间、上传目录的日期都从它取；以后的逾期、临期也一样。测试里换成固定时钟，"今天"就是可控的。

## 7. 登录加固、自己改密码

- **连续输错 5 次锁 15 分钟**，按用户名计数（Redis `login:fail:{用户名}`，第一次失败时设 15 分钟过期，登录成功清零）。锁定期间密码对了也不让进，提示还要等几分钟。输错时提示还能试几次。
  为什么按用户名、不按 IP：甲方办公室出口是同一个 IP，按 IP 锁会把整个公司锁在外面。代价：别人故意输错能把某个账号锁 15 分钟；管理员给他重置密码时一并清零。
- **新设的密码至少 8 位**：建用户、重置密码、自己改密码。已有的密码不受影响。
- **新接口：自己改密码** `PUT /api/auth/password`，参数 `{oldPassword, newPassword}`。初始管理员密码是安装时随机生成的（RFC 002），必须能自己改掉；现在只有管理员给别人重置，没有自己改的入口。页面在右上角用户菜单里。
- **不做**：改密码后踢掉其他设备上的登录。token 最长 2 小时过期；要立即让某人下线，停用账号是马上生效的。

## 8. 数据范围

**A 批**：角色加数据范围，甲方试用时就能把角色配好。

```sql
ALTER TABLE sys_role ADD COLUMN data_scope VARCHAR(8) NOT NULL DEFAULT 'SELF';   -- ALL 全部 / SELF 本人
UPDATE sys_role SET data_scope = 'ALL' WHERE code = 'admin';
```

- 角色的新建、修改接口加 `dataScope`，角色页面加"数据范围：全部 / 本人"单选，列表加一列。
- 加载权限时，用户只要有一个启用的角色是"全部"，就多给一个 `data:all` 权限（架构 §8）。`/api/auth/me` 返回的权限里有它，前端据此显示"我的 / 全部"切换。
- 默认"本人"：新建角色忘了设，最多是看不到别人的单（会来问），不会看到不该看的。

**B 批**：查询时用的工具 `DataScope`，写法见架构 §8。另给 XML 里手写的查询准备一段 SQL 片段。列表、详情、导出都要过它；详情不在范围里返回 404。

## 9. Excel 导入导出

用 Apache POI（`poi-ooxml`，取实现时的最新稳定版）。理由见架构 §11。

### 9.1 一份列定义

每个能导入导出的资源写一份列定义：表头、是否必填、示例、怎么解析、怎么校验、导出时取哪个值。模板、导入、导出都用它，表头和规则只写一处。

### 9.2 模板

- 第一个工作表"数据"只有表头，必填列的表头带 `*`。编码类的列设成文本格式（不然 `0012` 会变成 `12`），字典类的列带下拉。
- 第二个工作表"填写说明"：每一列的意思、是否必填、格式、例子。
- 不在数据表里放示例行：用户忘了删，就被当成数据导进去了。

### 9.3 导入

1. 只收 `.xlsx`，10MB、5000 行以内，空行跳过。
2. 表头按名字对，不按位置：甲方调了列的顺序也能导。缺必填列，直接报错。
3. 逐行解析、校验，再查文件内部的重复（同一个编码出现两次）和库里的情况（编码已存在、引用的分类不存在）。
4. **有任何一个错，整批不导**，返回 1003 和全部错误（第几行、哪一列、什么问题）。甲方改好再传一次就行，不会出现"导进去一半"要人工收拾。
5. 全对，在一个事务里写入，返回导入了多少条。

默认只新增，编码已存在算错误。要不要支持"已存在就更新"，各模块的 RFC 再定。

解析时注意的几处：数字按单元格显示的文本转成 `BigDecimal`，不经过 `double`（不然 0.1 会变成 0.1000000000000000055）；日期认 Excel 日期和 `2026-11-05` 文本两种；首尾空格去掉。

### 9.4 导出

和列表用同一个查询条件；用 POI 的流式写法（内存里只留 100 行）；上限 5 万行，超了提示缩小筛选范围。文件名如 `供应商-20261105.xlsx`。

### 9.5 接口形状

| 接口 | 返回 |
|---|---|
| `GET /api/<资源>/import-template` | 文件 |
| `POST /api/<资源>/import`（`multipart`，字段 `file`） | `{ total }`；校验没过返回 1003 |
| `GET /api/<资源>/export?<和列表一样的筛选参数>` | 文件；出错时返回普通的 `R` |

权限码 `<域>:<资源>:import`、`<域>:<资源>:export`。

## 10. 图片

- **前端**：上传图片前用 canvas 压到长边 1600px、JPEG 质量 0.8。手机照片一张 3-8MB，压完约 300KB。浏览器画图时已经按照片的方向信息摆正，压出来的图不会是歪的。
- **后端**：收到 jpg、png 时生成一张长边 320px 的缩略图，放在原图旁边，文件名加 `_s`。`FileVO` 加 `thumbUrl`，其他类型为空。用 JDK 自带的 `ImageIO`，不加依赖。缩略图生成失败只记 warn，上传照样成功。
- **上传的文件只增不删**：删附件、换图只删引用，不删文件。误删能找回，备份也简单（RFC 002 §8）。

## 11. 架构测试和集成测试

### 11.1 ArchUnit

加 `archunit-junit5`，一个测试类写这几条，违反了 `mvn test` 就失败：

1. 业务域之间没有环。
2. 只能按架构 §3.2 的方向依赖。测试里写一张"谁可以依赖谁"的表，和图一致；可以跨层依赖（production 直接用 techpack），不能反向。图改了，表跟着改。
3. controller 不直接用 mapper。
4. 跨域只能用对方的 service 接口、dto、entity，不能用 mapper、service.impl、controller。
5. `common` 不依赖 `module`、`config`、`security`。

### 11.2 数据库集成测试

- 测试类以 `IT` 结尾，由 Maven 的 failsafe 插件在 `mvn verify` 时跑；`mvn test` 只跑单元测试，不碰数据库。
- 连本机 Docker 里的 `scm_test` 库，配置在 `application-it.yaml`（本机库没有密码，可以进仓库）。
- 启动时先检查库名必须以 `_test` 结尾，否则直接失败；然后清空、重新执行全部迁移。同一次运行里的测试共用一个库，每个测试自己造数据、用随机编码，不依赖表是空的。
- 现在的 `ScmApplicationTests` 改名 `ScmApplicationIT`。它以后连 `scm_test`，不会再把开发库 `scm` 的迁移执行掉，`CLAUDE.md` 里"跑测试要排除它"那条就可以删了。

## 13. 单据框架（B 批）

这里只定骨架，细节随订单 RFC 补。

- `BizType`：全系统单据和主数据类型的枚举，带单号前缀和中文名。
- `DocStatus` 和每种单据的转换表 `StatusFlow`（架构 §4.2）。当前状态不允许这个动作，返回 1002：页面上的按钮是按打开时的状态显示的，点了不行说明状态在这期间变了。
- 单头公共列（架构 §4.1）放进一个基类。`status`、`audit_by`、`audit_time`、`version` 都标 `NEVER`（§4.3）。
- **版本号用显式条件，不用 MyBatis-Plus 的乐观锁插件**（改了架构 §4.3）：保存草稿带上打开时的 `version`，条件是 `id = ? AND status = 'DRAFT' AND version = ?`，同时 `version = version + 1`；状态动作也让 `version + 1`。为什么：插件对不同的更新方法行为不一样，要记住哪些方法管、哪些不管；写在条件里，读代码就看得到（架构原则"显式"）。另外，状态动作也要让版本号加一，否则 A 开着草稿、B 提交了，A 再保存时版本号还对得上，会把单子改回草稿——现在保存还要求 `status = 'DRAFT'`，两道保险。
- 草稿保存 = 整单覆盖（架构 §4.1）。
- `Num`：取整规则（架构 §6），第一个算金额的模块（订单）开工时写。

## 14. `biz` 域（B 批）

表结构草稿：

```sql
-- 操作记录：只追加
CREATE TABLE biz_doc_log (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    doc_type    VARCHAR(32)  NOT NULL,     -- BizType 枚举名，如 PURCHASE_ORDER
    doc_id      BIGINT       NOT NULL,
    action      VARCHAR(16)  NOT NULL,     -- create、submit、audit、reject……
    from_status VARCHAR(16),
    to_status   VARCHAR(16),
    remark      VARCHAR(500),              -- 驳回原因、变更原因
    extra       JSONB,                     -- 附加信息；二期的"改前 → 改后"也放这里
    operator_id BIGINT,                    -- 系统触发的为空
    create_time TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_biz_doc_log_doc ON biz_doc_log (doc_type, doc_id, id);

-- 附件：文件本身已经通过 /api/files 传好了，这里只记挂在哪张单上
CREATE TABLE biz_attachment (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    doc_type    VARCHAR(32)  NOT NULL,
    doc_id      BIGINT       NOT NULL,
    file_url    VARCHAR(255) NOT NULL,
    thumb_url   VARCHAR(255),
    file_name   VARCHAR(255) NOT NULL,     -- 原始文件名
    file_size   BIGINT       NOT NULL,
    create_by   BIGINT,
    create_time TIMESTAMPTZ  NOT NULL DEFAULT now(),
    update_by   BIGINT,
    update_time TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted     BOOLEAN      NOT NULL DEFAULT FALSE
);
CREATE INDEX idx_biz_attachment_doc ON biz_attachment (doc_type, doc_id) WHERE deleted = false;

-- 变更提醒：上游变了，给每张受影响的下游单据一条
CREATE TABLE biz_doc_notice (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    doc_type     VARCHAR(32)  NOT NULL,    -- 收到提醒的单据
    doc_id       BIGINT       NOT NULL,
    source_type  VARCHAR(32)  NOT NULL,    -- 谁引起的，如 ORDER_CHANGE
    source_id    BIGINT       NOT NULL,
    content      VARCHAR(500) NOT NULL,    -- 如"订单 DD202611050001 已变更：黑色 M 码 100 → 120"
    owner_id     BIGINT,                   -- 提醒谁：下游单据的负责人
    handled_by   BIGINT,
    handled_time TIMESTAMPTZ,
    create_time  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_biz_doc_notice_doc ON biz_doc_notice (doc_type, doc_id);
CREATE INDEX idx_biz_doc_notice_todo ON biz_doc_notice (owner_id) WHERE handled_time IS NULL;
```

这三张表用 `doc_type + doc_id` 指向各种单据，没法加外键；靠"只有单据的 Service 会写它们"保证。

**接口挂在各单据下面**，不做成一组公共接口（改了架构 §7.1）：

```
GET    /api/orders/{id}/logs
GET    /api/orders/{id}/attachments
POST   /api/orders/{id}/attachments
DELETE /api/orders/{id}/attachments/{attachmentId}
GET    /api/orders/{id}/references        下游单据
GET    /api/orders/{id}/notices
POST   /api/orders/{id}/notices/{noticeId}/handle
```

为什么：看操作记录、传附件的权限和看这张单的权限是一回事。挂在单据下面，权限和数据范围由单据自己的接口把关；做成 `/api/doc-logs?type=&id=` 这种公共接口，就得另写一套"按类型查权限"的机制，漏一种单据就是越权。重复的那几行由一个公共基类或辅助方法收掉，订单 RFC 里定具体写法。

引用查询 `ReferrerProvider` 和 `ReferenceService` 照架构 §4.4。

## 18. 实现记录

**11-05，1a**（0e3dfbe、99ce9b9、c12e0a2）：错误码、错误编号、bug 003 / 004 / 006 / 007 / 008、登录加固、自己改密码、ArchUnit。和上文不一样、或者上文没写到的：

- ArchUnit 用 `archunit-junit6`：项目跟着 Boot 4.1 用的是 JUnit 6。
- 跨域只认对方的 `service`（接口，不含 `impl`）、`dto`、`entity` 三个包，带来几个后果：
  - 给别的域实现的接口要放在 `service` 包里，比如 inventory 的 `StockSourceHandler` 放 `inventory.service`。
  - 要给别的域用的枚举，放 `entity` 或 `dto`。
  - `system` 的 `cache`、`aspect` 包，别的域不能直接用。
- `biz` 可以用 `system`，反过来不行。
- 用户名不存在也计入登录失败、提示一样，试不出哪些用户名是真的。登录用户名限长 32 位。
- 错误编号的日志格式只设 `logging.pattern.correlation`，用的是 Boot 默认格式里留给它的位置。以后谁要改日志格式，都要保留 `%correlationId`。
- 操作日志打码改成字段名里含 password 的都遮，`oldPassword`、`newPassword` 不会明文进日志。

留到 1b 修：

- 上传请求体本身坏了（`MultipartException`），现在返回 500，要改成 400。
- 密码超过 72 字节（BCrypt 的上限，25 个以上汉字），现在返回 500，要在校验时拦住。
- 登录失败计数的 INCR 和 EXPIRE 是两步：两步之间 Redis 断开，键就没有过期时间。下次输错时发现没有过期时间，就补上。

留到第二阶段：过滤器链里抛的异常（比如 Redis 连不上）走的是 Boot 的 `/error`，返回的不是 `R`。
