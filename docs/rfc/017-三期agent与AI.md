## 1. 解决什么

PRD §2.1 里的"三期"，指 2027 年起做的聚水潭、外部账号、开放 API、PDA。企查查是"待排期"（Q22），智能助手排在"一期二期之后"（Q45）。本文按用户 11-21 的说法，把这两样和识别类 AI 功能归到三期一起设计。它们都是"系统以外的东西来调系统"，底座只该有一套。

要解决三件事：

- **一套底座**：企查查、助手、OCR 要是各写各的身份、权限、留痕，就有三套，口径对不上。
- **不碰坏已有功能**：业务规则、状态流转、库存过账、字段权限都已经在 Service 和接口里，AI 一样都不重写。
- **先后顺序**：每一样卡在不同的甲方答复上，所以按"卡在谁身上"排，不按想做什么排。

不做：

- 聚水潭推入库、开放 API、工厂外部账号、PDA：三期另写 RFC。它们只复用本文 §3.1 的身份底座（`user_type`、`sys_api_token`），不在这里设计。
- 模型写 SQL 查库。
- 模型替人提交、审核、过账、作废、删除。
- 模型做业务判断：风险等级、能不能审、料够不够、价格合不合理。
- 手机上的助手、语音、跨对话的长期记忆。
- 训练或微调模型。

## 2. 总原则

一句话：**agent 和 AI 是系统的另一个用户，只送"看到了什么"，规则只在系统里。**

样板是架构 §14.5 企查查的 agent 模式：agent 只送标准化的风险条目，等级、新增、待办都由 `RiskService.record` 定。

1. **app 里不调大模型**：
   - 调模型的代码都在可选的助手服务里。app 不依赖它：不起它，系统照常。
   - 直连企查查、第三方 OCR 这种不带模型的外部接口，照架构 §12.7 可以在 app 里调，但不在业务事务里调，要设超时。
2. **看到的 = 这个身份用接口能看到的**：权限、数据范围、品类线、字段权限都在接口层，AI 不另做一套。没权限的字段整个从 JSON 里去掉，不是打码（生产加固契约 §2）。
3. **两种写分开讲**（§3.2）：
   - agent 账号只能往专门给它开的"收数接口"送事实。
   - 经助手的用户令牌只能读；助手产出的是预填，人在页面上点保存才算数。
4. **数字能核对**：回答里的每个数都带来源链接。要汇总的数只用口径固定的接口（§6），没有就说没有。
5. **全部留痕、有限额、能整个关掉。**

## 3. 底座

### 3.1 三种调用身份

| 身份 | 谁 | 令牌 | 能做什么 | 第一个用它的 |
|---|---|---|---|---|
| 用户本人 | 浏览器 | 现在的登录令牌，加浏览器绑定的刷新 Cookie（生产加固契约 §2） | 照角色 | 已有 |
| 用户经助手 | 用户打开助手时，助手服务替他调接口 | 短期令牌 `scope = ASSISTANT`：30 分钟、不能刷新、只读 | 这个用户能读的，再减掉白名单外的 | 问数 |
| agent 账号 | 后台 agent（企查查，以后的批量识别） | 长期令牌 `sys_api_token`（数据库设计 §3.10），账号的 `user_type = AGENT` | 角色只给它要用的一两个接口 | 企查查 |

- **用户的登录令牌不交给助手服务**：短期令牌由 `POST /api/auth/assistant-token` 用当前登录身份换来。它和登录令牌一样登记用户版本，改密、停用、删除时一起失效。
- **授权只看服务器上的当前身份**，不认请求头（生产加固契约 §2）。
- **以后的对外接入照这一套**：工厂账号（`user_type = FACTORY`，Q02）、开放 API、聚水潭对接，都是"长期令牌 + 最小角色"，不另做。

### 3.2 两种写

| | agent 账号 | 经助手的用户令牌 |
|---|---|---|
| 写什么 | 只往专门的收数接口送事实，如 `POST /api/suppliers/{id}/risk-snapshots`（架构 §14.5） | 不写。非 GET 一律 403 |
| 规则在哪 | 收数接口的 Service 定等级、做比对、出待办 | 用户点保存时走普通接口、普通校验 |
| 为什么 | 送来的是外部事实，没有人在场确认；收数接口只收这一种东西，口径固定 | 业务单据要人确认，见下 |

为什么不让助手直接建草稿（11-21 和 agy 讨论后定的）：

- 草稿保存是整单覆盖（`docs/api/README.md` §3.3），AI 可能冲掉人改过的内容。
- 生产异常不是单据、没有草稿，一建就生效（`docs/api/05-生产.md` §2.4）。
- 一个仓库同时只能有一张没审的盘点单（数据库设计 `uk_inv_count_open`），AI 建一张就占住了这个仓。

只读也不是没风险：导出、文件下载、一页 500 条都是 GET。所以工具白名单（§3.3）和单独的限流额度照样要有，导出类接口不进白名单。

### 3.3 工具

工具是已有接口的薄包装（架构 §14.8）：

- 助手服务按白名单 `tools.yaml`，从打包时导出的 `openapi.json` 生成工具，写法见 RFC 009 §3.2。没列进白名单的接口，模型看不见。
- 每次对话先调 `/api/auth/me`，用户没权限的工具不交给模型。

两处补充：

- **字段被去掉要告诉模型**：按 `/api/auth/me` 的权限码，在系统提示里写明"这个用户看不到成本 / 销售报价 / 加工价 / 联系方式 / 银行账号"，免得模型把"看不到"说成"0 元"或"没填"（写在系统提示里一次说清，不在各个工具说明里各写一遍）。银行全号的接口不给助手（`@NoAssistant`），有权限的人助手也只看到遮住的样子，提示里一并说明。
- **白名单只收 GET**，而且导出、下载、批量导出不收。

**识别要读的文件**（送货单照片、工艺单 Excel）：

- 由浏览器用用户自己的登录令牌上传，走现有的 `POST /api/files`。
- 浏览器把这次对话里附的文件的签名地址（架构 §8）交给助手服务；助手只能取这些文件，不能自己去下载别的。

**回答只链到系统里的页面**：渲染时只认站内路由，不渲染外部链接和外部图片。不然模型被注入后，可以把数据拼进一个外部图片地址，浏览器一加载，数据就发出去了。

### 3.4 助手服务

一个单独的容器 `assistant`，在部署包的 compose 里用 profile 默认不起（RFC 009 §3.1 的图照用）。补三条：

- **资源**：
  - 甲方服务器是 2 核 4G 起（Q21），上面已经有 app、PostgreSQL、Redis、Nginx、备份五个容器。
  - 助手容器在 compose 里硬限内存和 CPU，库连接池单独开、上限设小。
  - 模型本身不在这台机器上，用外部接口或另一台 GPU 机器。
  - 运行时用什么、限多少内存，见 §10 第 1、2 条；那里的数字是估计，要等一天的技术验证实测。
- **自己的表**：
  - 放在同一个 PostgreSQL 的 `assistant` schema，用单独的库账号和单独的迁移，app 的 Flyway 不管它。
  - 每天的备份照样带上。
  - 表沿用 RFC 009 §3.5 的，再加 §5 的 `ast_proposal`。
- **两个身份分开跑**：
  - 企查查 agent 用 agent 账号，只有取待查、送快照、送工商候选三个接口（B 档）。它能连外网（企查查 MCP），但拿不到内部数据。
  - 用户助手拿得到内部数据，但它的工具里没有任何往外发东西的。
  - 两者在同一个进程里也不共用令牌和对话。
  - 这是防提示词注入的主要办法。另外，工具返回的内容、用户传的图片和 Excel，一律当不可信文本。

### 3.5 模型和数据出不出公司

三种部署方式，甲方按 Q45 选一种，换的时候只改 `.env`：

| 方式 | 用什么 | 能开哪些功能 |
|---|---|---|
| 不起助手服务 | — | §4 的 A 档；企查查只能走直连（`scm.risk.mode = api`） |
| 起助手服务、不配模型 | — | A 档；B 档企查查 agent（本身不用模型） |
| 外部模型 | 云端模型（OpenAI 兼容接口） | 全部；价格、供应商数据要出公司 |
| 自部署模型 | 内网一台 GPU 机器，和架构 §12.7 的 MinerU 用同一台也行 | 全部；要甲方准备机器 |

企查查 agent 不受 Q45 卡：发出去的只有信用代码和企业名称，取数也不用模型。

部署方式只决定功能能不能用；开不开、开哪几档，由 §3.7 的统一开关决定。

### 3.6 留痕和限额

- **助手服务记**：谁、什么时候、问了什么、调了哪些工具和参数、怎么回答的、用了多少 token（RFC 009 §3.5）。
- **agent 账号**：调接口和人一样写操作日志，操作人是这个 agent 账号（架构 §14.8）。
- **限额**：按人每天限次数，全系统每天限 token。~~计数放 Redis~~ 计数放助手自己的表 `assistant.ast_usage`（11-22 做②时改）：一条带条件的 upsert 就不会多算，助手也就不用连 Redis、碰不到 app 的限流状态；和业务接口的限流本来就是分开的（架构 §9）。
- 经助手保存的单据要不要标出来，见 §5 和 §10 第 4 条。

### 3.7 统一开关

用户 11-21 要求：项目里的 AI 功能只有一个开关。超级管理员在管理后台开关，立刻生效。

**管哪些**：

- **管**：B 档企查查 agent（agent 账号发来的请求）、C 档助手、D 档识别预填、E 档后台归因。凡是模型或者不是人的调用方碰系统的路径，都归它管。
- **不管**：
  - A 档：普通功能，照菜单权限。
  - 企查查直连（`scm.risk.mode = api`）：既没有模型也没有 agent，是普通的外部接口。
  - 谁能用：照旧在 `sys_menu` 里按角色给。
  - 第三方 OCR（PRD §9.5）算不算在内，跟 M11 一起定。
- **替换草案里分散的几个开关**：
  - RFC 009 的 `assistantEnabled`（§3.7、§6.1）
  - 本文 §3.5 部署方式表里"开哪些功能"那一列
  - compose 的 profile：以后只决定容器装没装，不再当开关用

**存在哪**：

- `sys_config` 里一个键 `ai.switch`，值形如 `{"enabled": false, "features": {...}}`：一个总开关，每档再一个分开关。
- 分开关在那一档功能做的时候再加，不提前写。
- 只在一个地方读：`AiSwitchService`。和 `TradeFeature` 一样，别处都问它。
- 没有这一行、没有这个键、读出错，一律当作关。
- **和贸易代工开关不同，它不放在部署配置里**：AI 出了问题（答错、数据往外发、费用超了）要能马上关掉，改 `.env` 得重启。
- **生效时间**：
  - 每次都读库、不缓存，改了下一个请求就按新状态走；没有这一行也马上按关（缓存只在切换接口里清的话，有人直接删掉这一行时会照旧当开着）。
  - 只有登录信息（`/api/auth/me`）和受限令牌、agent 账号的请求才查这个开关，普通用户的请求不多一次查询。

**在 app 里拦**：前端藏入口只管显示，助手服务自己的检查也不算数，真正的拦截在 app 里。

1. **换短期令牌**（`POST /api/auth/assistant-token`）：关着时返回 403"AI 功能没有打开"。
2. **安全过滤器**：`scope = ASSISTANT` 的令牌和 `user_type = AGENT` 账号的请求，关着时一律返回 403，包括关之前已经发出去、还没过期的令牌。
3. **定时任务**：每周风险复查、每天早上的待盯清单，关着时不往待查表放任务，也不生成。
4. **分开关**：总开关开着、某一档关着，只拦那一档。每个收数接口、每种令牌用途都标明属于哪一档。

**关掉以后**：

- **企查查是 agent 模式时**：
  - 不再放新任务。
  - 待查表里已有的任务留着：关掉等于暂停，开回来 agent 接着取，不漏查；一家同时只排一条（数据库设计 §6.7），不会堆出重复的。
  - 供应商详情的"现在查一次"提示"AI 功能关着，查不了"。
- **打开带 `?proposal=` 的链接**：提示"AI 功能关了，这份预填用不了"，按普通新建打开。
- **什么都不删**：提案、对话记录、操作日志都留着，开回来还在（提案照旧 24 小时过期）。已经保存的单据、风险快照、已经写好的摘要也都不动。
- **首页待盯卡片**：退回规则版（§4 C 档）。
- **入口**：⌘K 里的"问助手"、助手抽屉、预填入口都不显示。前端从 `/api/auth/me` 新加的 `features.ai` 读开关，只用来决定显示不显示。

**谁能开、怎么留痕**：

- 管理后台加一页"AI 功能"，只给超级管理员（`admin_only`）：一个总开关，下面是各档的分开关，每个旁边一句话说清这一档做什么。
- **打开时弹窗说明数据会发到哪**：
  - 写明模型用的是哪种方式（外部 / 自部署 / 没配）。不写主机名：`/assistant/info` 不用登录，自部署模型的内网地址不往外说（11-22 审查后去掉）；要知道连的是哪，管理员看 `.env`。
  - 这些由浏览器直接向 `/assistant/` 取（助手服务读自己的 `.env`），app 照旧不调助手服务。
  - 助手服务没启动时，弹窗写"助手服务没有启动"，开关照样能打开。
- 每次切换都写操作日志：谁、什么时候、从什么改成了什么。

**11-21 先做了的**（用户说先把开关做好）：

- V52 加 `ai.switch`（默认关）和管理后台 › 系统管理 › AI 功能一页；`AiSwitchService` 是唯一读它的地方。
- 接口 `GET`、`PUT /api/admin/ai-switch`，只给超级管理员；操作日志的参数里记改前、改后（`OperLogDetail`）。
- `/api/auth/me` 加 `features.ai`。
- 当时开关还没接上任何一档。11-22 第①步接上了"在 app 里拦"的第 1、2 条（助手令牌，见 §13）；第 3 条随早上待盯清单做，agent 账号随 B 档做，各档分开关随那一档做。

**和部署的关系**：

- 容器装没装（compose profile）、模型配没配（`.env`），决定的是"能不能用"；这个开关决定"用不用"。
- 三者都满足，用户又有菜单权限，功能才会出现。

## 4. 功能和先后

按"卡在谁身上"分五档。每一样都写明它改的是哪个页面，回归风险就在那里。

### A 档：不用大模型（不等 Q45）

| 功能 | 改哪个页面 | 怎么做 | 现在的样子 |
|---|---|---|---|
| 物料匹配候选 | 资料包 › 物料清单 › 从 BOM 表导入的预览；以后的领猫数据导入 | 认不出的行，按名称、规格、老编码的相似度排出前 5 个候选，人来点选。不在导入里新建物料（Q49） | `BomImporter` 只按名称精确对（`lower(btrim(name))`），认不出就让人从头挑。V28、V45 已经给物料的编码、名称、成分、老编码建了 trigram 索引，现在只用在关键字搜索上 |
| 审单红旗卡 | 需求订单 › 审核对话框 | 在现有评审信息上加几条，每条带链接，只提示、不拦：<br>1. 承诺交期够不够：同款（没有就同品类）以往从审核到回齐用了多少天，和这张单剩下的天数比<br>2. 默认加工厂最近的表现：近 90 天逾期几张、回货次品率多少<br>3. 交期前工厂手上的在制件数（已有；Q60 答了再算还能做多少件） | `GET /api/board/orders/{id}/review` 已经返回资料包版本、缺料前 5 种、默认加工厂在制（`docs/api/02-需求订单.md` §3.8） |
| 主数据体检 | 管理后台加一页，或首页待办加一条 | 只列出来、不改：<br>1. 疑似重复的供应商（名称相近、信用代码相同）<br>2. 资质快到期的供应商<br>3. 在产却没有生效资料包的款<br>4. 缺单位或缺价格的物料 | 没有 |

agy 原来提的"涨价多少、晚于开裁"不放进需求订单的审核：

- 需求订单上的单价是销售价，而价格档案里存的是物料价和加工价，两者比不了。单价和档案价不一样的情况，采购单、生产单审核时已经会提示（Q25，11-21 做了）。
- 开裁日期在生产单上，需求订单审核时生产单还没生成。"晚于开裁"已经显示在待到料页签里（PRD §6.6.3）。

这三样其实是普通功能，不需要助手服务。它们排在第 5 批上线准备之后，各自先写 RFC。要不要往前提，见 §10 第 3 条。

### B 档：企查查 agent（等 Q22 排期、Q23 账号）

设计在架构 §14.5、PRD §6.8.3 和 §9.4、数据库设计 §6.7。这里只补四条。

1. **先补信用代码**：
   - 领猫导进来的供应商没有信用代码（Q29），刚上线时几乎一家都查不了。
   - 所以第一步是 PRD §9.4 的"补工商信息"：agent 按全称查，可能查到几家同名的，全部作为候选送回来。
   - agent 怎么知道查哪几家：在供应商详情点"查工商信息"，或者在列表里勾上"缺信用代码"的几家批量点，系统往待查表里放一条"查工商"任务。待查表 `sup_risk_task` 要加一列任务类型：查风险按信用代码查，查工商按全称查（审过后改数据库设计 §6.7）。agent 照样从 `GET /api/risk-checks/pending` 取。
   - agent 调 `POST /api/suppliers/{id}/registry-candidates` 送候选，候选显示在供应商详情的一块里。
   - 人点"用这家"才写进档案，按 §6.8.2 的改动规则生效。
   - 这也是"agent 送事实、系统定规则"。
2. **取数和标准化写成固定代码，模型最多写摘要**：
   - 每周比对靠 `RiskItem.key`（风险类型 + 案号 / 文书号 / 登记日期）保持不变。
   - 要是让模型整理条目，换个说法 key 就变了，会冒出假的"新增风险"。
   - 新增条目的人话摘要可以让模型写，放在风险页签上；等级照旧由字典定。
3. **它是底座的第一个用户**：
   - 要用到 `sys_api_token`、`user_type = AGENT`、`sup_risk_task`、快照表，以及管理后台生成和吊销令牌的页面。
   - 只开三个接口（取待查、送快照、送工商候选），暴露面最小。做完它，底座就实际验过一遍了。
4. **直连备用**：`scm.risk.mode = api` 时，app 里的 `QccRiskProvider` 直接调企查查，不经 agent（架构 §14.5）。甲方那边跑不了 agent 时用这个。

## 5. 预填怎么接到页面

照翻单的做法：翻单的地址是 `/orders/<原单 id>/repeat`，表单按地址里的 id 自己去取原单（`web/src/views/order/order/form.vue` 开头的注释）。预填也一样，地址里只放引用，不放内容。

1. **存提案**：助手识别完，在助手服务里存一条 `ast_proposal`，记下属于谁、目标页面、内容（JSON）、原图的文件引用，24 小时后过期。
2. **打开页面**：抽屉里显示"已整理成入库单，去核对"。点了以后，用目标页面现有的新建地址打开，后面带 `?proposal=<id>`。
3. **表单取内容**：
   - 表单按 id 向助手服务取内容，只有本人取得到。
   - 浏览器每次取之前，先用登录身份换一个新的短期令牌（§3.1）。助手服务拿这个令牌调 `/api/auth/me` 认出是谁，和提案的主人对上才给。提案能存 24 小时，令牌只有 30 分钟，两者不冲突。
   - 里面的物料、供应商、采购行**不信模型给的 id**：按编码、单号用普通接口重新查一遍，查不到的标出来让人选。
4. **人来保存**：人改完点保存，走普通接口、普通校验；原图挂进单据附件。
5. **页面要加的**：
   - 每个目标页面都要加一个"带预填打开"的入口。现在只有订单表单有（翻单）；入库单新建、手机报工、价格录入、工艺单识别预览都要加。
   - 这是改现有页面，算在各功能的工作量里，也是回归测试的重点。

**"经助手"标记**：

- 保存走的是普通令牌，而生产加固契约规定请求体里多出来的字段直接返回 400，所以不能在请求体里加字段。
- 要标的话用请求头 `X-Assist-Proposal: <id>`。它和 `X-Request-Id` 一样只是追踪信息，不是授权；app 把它写进操作日志的 `extra`。
- 不标也行：原图在附件里，能看出来源。见 §10 第 4 条。

## 9. 取舍

1. **助手只读 + 预填，不建草稿**（推翻 RFC 009 §3.3 的"只到草稿"）：
   - 建草稿就要逐个核对接口的实际效果，还会碰上整单覆盖、异常没草稿、盘点单占仓。
   - 预填把确认这一步留在页面上，app 不用为 AI 开任何写口子。
   - 代价是每个目标页面要加预填入口。
2. **agent 账号能写，但只写收数接口**：外部事实（企查查）没有人在场确认，又不能让 agent 碰业务单据。收数接口只收一种东西，规则在 Service 里。
3. **用户点的识别当场返回，不排队**：排队就得由后台账号去取文件，后台账号就得能看所有品类线和价格；当场用本人令牌，权限天然是对的。
4. **企查查的标准化不用模型**：比对靠稳定的 key。
5. **不用大模型的先做**：物料匹配候选、审单红旗卡、主数据体检不卡在 Q45 上，服务器跑得动，见效快。

**导出、下载谁来拦**（§3.2、§3.3 原来没说死）：app 拦。助手令牌只能调返回 JSON（`R`）的 GET 接口；返回文件的（导出、下载、打印、模板）和非 GET 一样回 403。助手服务的白名单再挡一层，但不算数。

**权限挂哪**：`assistant:chat:use` 是一个不挂在任何页面下的权限（`sys_menu` 顶层的按钮，侧边栏不显示，角色里能勾）。预置的业务角色都给；开关默认关，所以装好了也用不了，管理员在角色里调。

**模型**：本轮不定用谁的。地址、Key、模型名照 RFC 009 §3.4 放部署配置（OpenAI 兼容接口），自动化测试用本地假模型。要真试时，用户自己把模型地址和 Key 填进不进 git 的配置文件；不拿试用环境的真实数据去调外部模型。

**C 档的前提，本轮核实后再承诺**：问数要 §6 的汇总接口（口径等 Q66）；"一句话打开列表"要各列表页能从地址带筛选（RFC 009 §7，`useTable` 现在不读地址）。先做现成接口答得了的：库存和在途、单据状态和"在等谁审"、为什么不能反审核、进度总览、待到料。

**① 做完的样子（11-22，agy 审过两轮、按审查改过）**：

- 令牌：`sys_login_session` 加 `scope`、`parent_jti`（V54）。用途以库里登记的为准，令牌里的声明和登记的对不上就当没登录。从哪张登录令牌换的记在 `parent_jti`：那张退出时一起删，刷新时改挂到新令牌下（不打断正在用的助手）；那张不在了（比如和退出同时换的）就不再认；那张到点了不算不在：定时清理过期登录时，下面还挂着没过期助手令牌的先留着（最多再留 30 分钟），助手令牌用满自己的 30 分钟，过期的登录令牌自己照样认不出、换不了。换令牌时给那张登录加共享锁，退出、刷新先加排他锁，两边排队。改密、停用、删除照旧靠用户版本一起失效。
- 过滤器（`JwtAuthFilter`）：助手令牌在 AI 功能关着、不是 GET（含 HEAD）、角色里没有 `assistant:chat:use` 时回 HTTP 403；认出来的请求多带一个权限标识 `scope:ASSISTANT`。`scope:` 开头是保留的：库里的权限码这样开头的不认，菜单管理也不让填。
- 拦截器（`AssistantScopeInterceptor`）按接口方法认：不返回 `R` 的（导出、下载、模板、盘点表）、参数里拿响应对象自己写的（含 `WebRequest`）、标了 `@NoAssistant` 的（工艺单 Excel 预览、供应商银行账号）回 403。以后加的导出接口不用登记。
- 文件签名地址：`FileUrlSigner` 对助手令牌的请求不签（返回空）。签名地址 7 天有效、不认人，发出去以后关开关、退出都收不回来；助手要读的文件按 §3.3 由浏览器交给它。
- 限流：换令牌每人每分钟 30 次；助手令牌的请求每人每分钟 120 次，导出、预览的专门额度照样先算（`SensitiveRateFilter`）；助手令牌的额度和这个人在页面上的分开记，助手乱调导出打满了也不连累他自己导出。被过滤器拒掉的请求不进限流，代价和普通请求一样（查一次会话、开关、权限），没另做。
- 测试：`AssistantTokenIT` 从路由表取全部写接口（220 多个）和不让助手调的 GET（写死了导出、盘点表、预览、银行账号几条做锚），用助手令牌逐个调，全部 403；另测开关关掉（含删掉 `ai.switch` 这一行后已有的令牌和换令牌）、收回权限、改密、退出、过期、停用、走 `RefreshSessionService.rotate` 的刷新改挂、登录被删后不再认、登录到点后照样能用到自己过期、同一张资质证书助手拿到的文件地址是空的。单测：过滤器（含库里的保留权限码不认）、换令牌、文件签名、限流（两个额度、分开记、超限 429、限流状态读不到 503、换令牌额度）、拦截器的参数检查、菜单不让填保留前缀。
- 统一开关的第 3 条（定时任务）随早上待盯清单做；agent 账号随 B 档做。
