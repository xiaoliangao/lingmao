# RFC 007 研发打样

状态：**已定**（11-17 用户审过：完整版；第 2–5 条按推荐；完整版新增的 3 条也按推荐，§10）。

对应：PRD §6.3、§5.1–§5.6、§3、§2.2 的 M03、Q06、Q26；架构 §3、§4.2、§4.4、§4.5、§4.7、§8、§14.1、§14.2；数据库设计 §16、§9.1、§8.1。原型 `docs/原型/src/6-pages-later.js` 的 `/samples`、`/samples/:no`（规则 `smpNew`、`smpDispatch`、`smpReport`、`smpReview`、`smpConvert`）。

## 1. 解决什么

样衣档案；一个版次一张打样单（DY），派给内部版房或外部工厂，按节点跟进度；送样后评审，改版就自动开下一版；评审通过后转大货（生成款式和 SKU，研发 BOM 带过去并复制成生产 BOM V1 草稿）。研发 BOM 挂在样衣上，复用资料包。

不做：

- 打样费用、打样工厂对账：随 M11（待定）。
- 样衣导入导出：领猫里的样衣不迁（PRD §10 只迁主数据）；导出 PRD §5.4 没要求。
- 手机上报打样节点：先只在电脑上报；版师要在手机上报时照手机报工加一页。
- 转大货以后的产前样：那时已经是款式，归生产（节点模板里加"产前样确认"，架构 §14.2 质量一行）。

### 1.1 做完整版，不做开关

用户 11-17 定：打样单、派单、打样节点、评审挂在打样单上，照 PRD §6.3.2 和数据库设计 §16 的完整版做；不做"可选开关"（PRD 原来的默认做法）。Q26 甲方要是答"要精简"，用不上的环节在页面上收起来，表和接口不动。

甲方要是连样衣都不要，用 §6.5 的办法把菜单藏起来。

当前版次、当前打样单 = 版次最大的那张，现算（`uk_dev_sample_order_ver` 让它是一次索引查找）。样衣图片挂 `biz_attachment`（`SAMPLE`），打样单附件挂 `SAMPLE_ORDER`，评审照片挂 `SAMPLE_REVIEW`。`BizType` 加 `SAMPLE("样衣", "YY")`、`SAMPLE_ORDER("打样单", "DY")`、`SAMPLE_REVIEW("样衣评审", null)`。

和数据库设计 §16 草案的出入：

| 出入 | 理由 |
|---|---|
| `size_group_id` 必填、颜色至少一个、`wave` 选填 | 研发 BOM、打样单的颜色尺码、转大货都要尺码组和颜色（用户 11-17 同意）；波段款式上就是选填 |
| 打样单 `make_way` 可空，`color_codes`、`size_codes` 必填 | 派单前还不知道谁打；新建时默认第一个颜色、基码 |
| 节点 `done_time` → `done_date DATE`，加 `done_by`；`plan_date` 必填；加延期的部分索引 | 和生产节点一样按业务日期记，事后补报常见；首页"打样延期"要按计划日期查 |
| 评审去掉 `sample_id`，`sample_order_id` 必填、唯一；`review_time` → `review_date` | 评审挂打样单，样衣从打样单取；评审是会上定的，事后补录常见 |
| `sty_style` 不加 `sample_id` | 用 `sty_style.sample_no` 和 `dev_sample.converted_style_id`，见 §6.4 |

## 3. 规则

### 3.1 两层状态

| 样衣 `SAMPLE_STATUS` | 标签 | 打样单 `SAMPLE_ORDER_STATUS` | 标签 |
|---|---|---|---|
| `DEVELOPING` 开发中 | `progress` | `WAIT_ASSIGN` 待派单 | `pending` |
| `PASSED` 已通过 | `pending`（等转大货） | `MAKING` 打样中 | `progress` |
| `CONVERTED` 已转大货 | `done` | `WAIT_REVIEW` 待评审 | `pending` |
| `ELIMINATED` 已淘汰 | `closed` | `PASSED` 已通过 / `REVISE` 需改版 | `done` / `closed` |
| | | `ELIMINATED` 已淘汰 / `CANCELLED` 已取消 | `closed` / `void` |

**一条不变的规矩**：样衣开发中 ⇔ 当前打样单是待派单、打样中、待评审之一；样衣是别的状态时，当前打样单已经结束（已通过、已淘汰、已取消）。下面每个动作都在一个事务里同时改两层，维持它。列表上的"状态"一列：样衣开发中显示当前打样单的状态，否则显示样衣的状态（原型 `smpState`）。

| 动作 | 权限码 | 打样单 | 样衣 | 要求 |
|---|---|---|---|---|
| 新建样衣 | `add` | 生成第 1 版：初样、待派单 | → 开发中 | 要样日期必填，默认 10 天后 |
| 改打样单 | `edit` | 待派单改全部；打样中只改打样方、要样日期、要求（改派） | | 带 `version` |
| 派单 `dispatch` | `make` | 待派单 → 打样中，生成节点（§3.2） | | 外部选工厂、内部选版师 |
| 报节点完成、撤销 | `make` | 打样中；"送样"报完成 → 待评审，撤销送样 → 打样中 | | §3.2 |
| 评审：通过 | `review` | 待评审 → 已通过 | 开发中 → 已通过 | |
| 评审：改版 | `review` | 待评审 → 需改版，生成下一版 | 开发中 | 意见必填，就是下一版的改版原因 |
| 评审：淘汰 | `review` | 待评审 → 已淘汰 | 开发中 → 已淘汰 | 意见必填 |
| 终止开发 `stop` | `review` | 待派单、打样中、待评审 → 已取消 | 开发中 → 已淘汰 | 原因必填 |
| 恢复开发 `reopen` | `review` | 生成下一版，改版原因 = 恢复原因 | 已通过、已淘汰 → 开发中 | 原因必填 |
| 转大货 `convert` | `convert` | | 已通过 → 已转大货 | §3.5 |

"生成下一版"：版次 +1、类型改版样、待派单，打样方式、工厂、版师、数量、颜色、尺码、要求照上一版，要样日期 7 天后（原型 `smpReview`）。派单前都能改，类型可以改成齐色齐码样、产前样。

写成两张 `StatusFlow`。每个动作先 `SELECT … FOR UPDATE` 锁样衣行，再比较并交换打样单、样衣的状态（0 行 → 1002）。操作记录都写在样衣上（`biz_doc_log`，`SAMPLE`），文字带版次："第 2 版派给 某制衣厂，11-20 要样"。

- **改样衣**：开发中、已通过能改；已转大货、已淘汰只读（1000"样衣已转大货，去款式 FS… 改"）。颜色改了只影响待派单的打样单（去掉没有了的颜色），派过单的不动。尺码组只有第 1 版派单前、没有研发 BOM 时能换（1000"已经开始打样了，尺码组不能换"），换了把第 1 版的尺码改成新尺码组的基码。
- **删样衣**：只有第 1 版还是待派单、没有研发 BOM 的能删，连打样单、颜色、图片、操作记录一起删；挂了研发 BOM 的外键拦住 → 1005。别的只能终止开发。

### 3.2 打样单和节点

- **打样单字段**：类型、数量（≥ 1）、颜色（样衣颜色的子集，至少一个）、尺码（尺码组的子集，至少一个）、要样日期、改版原因（第 2 版起必填，400）、要求说明、附件。
- **派单**：外部工厂调 `SupplierService.checkUsable(id, SAMPLE)`（待准入、审批中的也能打样，PRD §6.8.2），分类要是成衣厂或加工厂；内部选启用的用户。默认带样衣的打样工厂。
- **生成节点**：按字典 `sample_node` 的启用项和排序，从要样日期往前倒排：最后一个节点（送样）的计划 = 要样日期，前一个 = 后一个的计划 − 后一个的天数（原型 `smpPlan`）。计划早于今天的照样生成，显示延期。负责人默认：内部是版师，外部是样衣的设计师（跟工厂的人）。字典以后改了，已经生成的节点不变。
- **当前节点** = 第一个没完成的。**卡在谁那里** = 当前节点的负责人，外部的前面加工厂简称（"某制衣厂 · 许然"）。节点状态照生产单的 `NODE_STATE` 现算：已完成、延期（过了计划没完成）、临期（还剩 ≤ 1 天）、进行中（当前节点）、未开始。
- **报完成**：日期默认今天，不能晚于今天（400）。前面还有没报的照样报上，`warning` 写"前面还有节点没报完成"（同生产单，跳着报提示、不拦）。"送样"报完成 → 打样单变待评审。已经报过的再报 = 改完成日期。
- **撤销完成**：打样中、待评审能撤；撤销送样 → 回到打样中。评审过的不能撤（1002）。
- **改节点计划**：打样中，一次发全部节点的计划日期、负责人、备注；不带 `version`（理由同生产单 05 §3.3.2）。改派、改要样日期不自动重排计划，页面提示"节点计划没跟着改"。改派时没完成的节点负责人换成新打样方的默认。

### 3.3 评审

只评当前打样单，打样单要是待评审（1002"送样以后才能评审"）。评审日期默认今天、不能晚于今天；评审人至少一个，默认自己；照片最多 9 张。结论见 §3.1 的表。改版、淘汰不写意见 400。

### 3.4 字段校验

照款式（RFC 005 §6）：品类调 `CategoryService.checkSelectable`；尺码组、颜色、字典项新选的要启用；年份 2000–2099；金额 ≥ 0。TRADE 关时来源不能是 `CUSTOMER_SAMPLE`、客户两列必须为空（400）。打样工厂、面料供应商新选的调 `checkUsable(id, SAMPLE)`。设计师默认自己；没有设计师编号不拦，转大货自动编号时才要。

### 3.5 研发 BOM

样衣的研发 BOM 就是资料包的研发阶段（架构 §14.2），代码和页面都复用：

- 样衣详情的"研发 BOM"页签就是款式详情里的资料包组件，传样衣 id。只能建研发 BOM；版本、草稿、生效、修订、核价、导出 PDF 都和款式上的一样。
- 资料包要的"有哪些颜色、什么尺码组、吊牌价多少、能不能改"，挂在样衣上时由 dev 告诉它（§6.2 的 `SamplePackOwner`）：颜色、尺码组取样衣的，吊牌价取预估吊牌价，没有默认加工厂；已转大货、已淘汰的不能改。
- 挂在样衣上的研发版不能"转生产 BOM"：1000"样衣还没转大货，转大货时自动转成生产 BOM"。"按款看成本"只列款式。

### 3.6 转大货

样衣已通过后点"转大货"，弹窗填：款号（自动编号 / 手填）、大类、名称（默认样衣名称）、花名、默认加工厂（成衣厂、加工厂，默认通过那一版的外部工厂，没有就用样衣的打样工厂）。

一个事务（dev 的 `@Transactional`，style、techpack 的方法加入它）：

1. 锁样衣，不是已通过 → 1002。
2. 拼 `StyleCreateReq`：大类、款号方式、名称、花名、默认加工厂取弹窗；品牌、品类、年份、季节、波段、设计师、版师、来源、客户两列、尺码组、颜色、图片取样衣；吊牌价 ← 预估吊牌价，参考成本价 ← 预估成本。调 `StyleService.createFromSample(req, sampleCode)`：和新建款式同一段代码（取款号、锁设计师编号、建颜色、生成 SKU、复制图片），另记 `sample_no` 和操作记录"由样衣 YY… 转大货"。款号日期是转大货当天（PRD §6.3.3）。编不出号照款式的 1000 报，弹窗里改手填。
3. `TechPackService.adoptSamplePacks(sampleId, styleId)`：样衣的资料包全部挂到款式上（`style_id` = 新款式，`sample_id` 留着），有已生效的研发版就照"转生产 BOM"复制成生产 V1 草稿（单价按价格档案重取，架构 §4.7），款式的资料包状态改成"研发中"。返回生产草稿 id，没有已生效研发版返回 null。
4. 样衣 已通过 → 已转大货，写 `converted_style_id`、`convert_by`、`convert_time`；`uk_dev_sample_style` 兜底。写操作记录"转大货 → FS2612150701"。

返回 `{ styleId, styleCode, skuCount, prodPackId }`。前端提示"FS2612150701 已生成，15 个 SKU，研发 BOM 已复制成生产 V1 草稿，核对后生效"（没有研发 BOM 的换成"样衣没有生效的研发 BOM，资料包要另建"），跳到款式详情。

研发版整个挂到款式上（用户 11-17 同意）：转完以后款式的版本条里是"研发 V1、V2 → 生产 V1"，核价的"研发估"、按款看成本都按款式算，和一期直接在款式上建研发 BOM 的款一个样子。转出来的款式删不掉：`converted_style_id` 的外键拦住（1005）。

## 6. 边界和解耦

### 6.1 依赖方向

dev 只往下依赖：`dev → techpack`（间接用到 style、price、supplier、basic），加上 system、biz。`ArchitectureTest.DIRECT` 加 `entry("dev", Set.of("techpack"))`；board 一行加 `"dev"`（首页，§6.3）。一期的任何域都不 import dev 的类：style 只收一个样衣编号字符串，techpack 只认自己定义的接口。

### 6.2 要一期提供的

| 谁 | 方法 | 什么时候留 |
|---|---|---|
| techpack | 取款式信息（颜色、尺码组、吊牌价、默认加工厂、款号款名花名、能不能改）集中在一处，返回 `PackOwner`；建版本、生效、修订、核价、PDF 都只用它 | **第 3 批「资料包」顺手留**。二期挂样衣只在这一处加分支 |

```java
/** techpack 定义，dev 实现：资料包挂在样衣上时，它的颜色、尺码组这些由 dev 给 */
public interface SamplePackOwner {
    /** 不存在 404。forWrite = true 时 FOR SHARE 锁住样衣行，和转大货互斥 */
    PackOwner sample(long sampleId, boolean forWrite);
}

/** 一期就有：款式上的资料包由 techpack 自己用 StyleService 拼出同一个记录 */
public record PackOwner(String code, String name, String aliasName, long sizeGroupId, List<Long> colorIds,

```

### 6.4 `tp_tech_pack.sample_id` 这个口子

- **外键加**：数据库设计 §1.4"外键都加"。它让"挂了研发 BOM 的样衣删不掉"自动成立，不用 dev 去问 techpack。外键是数据库层面的，Java 依赖照样只有 `dev → techpack`。
- **谁写**：只有 techpack 写（表主人，架构 §3.2 第 3 条）。建版本时照请求里的 `sampleId` 写；转大货时 dev 调 `adoptSamplePacks`，由 techpack 改 `style_id`。dev 不碰 `tp_` 表。
- **迁移放哪**：dev 的迁移里，排在 `dev_sample` 后面。只放宽、只加列，旧版本的应用照样能跑（架构 §12.3）。
- **款式上不反过来加 `sample_id`**：款式已经有 `sample_no`（导入时照填领猫的，转大货时自动带），从样衣找款式用 `converted_style_id`，从款式找样衣按它查一次。少一个"下层表指向上层表"的列。

### 6.5 怎么隐藏

|---|---|

| 首页 | "打样中"、两组待办、两个数都不出 |
| 款式详情 | 来源样衣只显示 `sample_no` 文字；转过来的款式、资料包一切照常（它们已经是款式的） |

## 7. 关键流程和并发

| 场景 | 怎么保证 |
|---|---|
| 同一个样衣上两个人同时动（评审和终止、派单和改派、两人同时报送样） | 每个动作先 `FOR UPDATE` 锁样衣行，同一个样衣的动作排队；拿到锁后比较并交换状态，后到的看到新状态 → 1002。锁的顺序固定是先样衣、后打样单，不死锁 |
| 改版和恢复开发都要"生成下一版" | 锁样衣后取最大版次 +1；`uk_dev_sample_order_ver` 兜底 |
| 同一版评两次 | 打样单 待评审 → 结论的比较并交换；`uk_dev_review_order` 兜底 |
| 开着旧页面改打样单 | 带 `version`，过期 1002 |
| 转大货中途失败（款号编不出、SKU 生成出错） | 一个事务：款式、SKU、款号流水、资料包改动、样衣状态一起回滚 |
| 转大货时有人在建研发 BOM、改草稿 | 建版本走 `sample(id, true)` 的 `FOR SHARE`，和转大货的 `FOR UPDATE` 互斥；`adoptSamplePacks` 让 `version_lock + 1`，开着旧页面的保存回 1002 |
| 删样衣时它刚挂上研发 BOM | 外键 → 1005 |

## 8. 取舍

- **当前版次现算**，不在样衣上存一列：版次只在打样单上，生成下一版和取当前版都在锁住样衣以后做，没有两处要对齐的数。
- **送样报完成就待评审**，不要求每个节点都报完（原型要全部报完）：样衣到了就该评，前面的节点漏报不该卡住评审（§10 第 1 条）。
- **两层状态在一个事务里一起改**，不让样衣状态现算：列表要按样衣状态筛、转大货要比较并交换它，存下来最直接；不变的规矩（§3.1）由每个动作维持，测试覆盖每条转换。
- **研发 BOM 整个挂到款式上**（§3.6）、**techpack 定义接口、dev 实现**（techpack 在下层，反过来调就成环，§6.2）、**转大货复用款式的建款代码**（款号、设计师编号、SKU 的规则只写一处）：用户 11-17 同意。
- **打样单不单独成页**：一个样衣几版打样单，在样衣详情里按版次看最清楚（原型就是这样）；要按工厂、版师看，在样衣列表上筛"打样方"。

## 10. 用户定的

用户 11-17 定：做完整版，不做开关（§1.1）；尺码组必填、颜色至少一个；加恢复开发；研发 BOM 转大货时整个挂到款式上；转大货单独给 `dev:sample:convert`。按默认做：Q06 一个样衣只转一个款。

完整版新增的 3 条，用户 11-17 定按推荐：

1. **"送样"报完成就进待评审**，前面漏报的节点留着、只提示（§8）。原型是全部节点报完才待评审。
2. **打样延期进首页待办**（`SAMPLE_LATE`，给当前节点负责人；外部工厂打的，负责人默认是设计师）。打样节点的价值就在"卡在谁那里"，不进待办就只能有人天天翻列表。
3. **加"终止开发"**：开发中的样衣不等评审直接淘汰，当前打样单变已取消（原因必填）。PRD 的打样单状态里有"已取消"，但没写怎么到这一步；没有它，不想做了的样衣只能一直挂在待派单、打样中。
