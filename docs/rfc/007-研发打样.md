# RFC 007 研发打样

状态：**草案**（2026-11-17），等用户审。

对应：PRD §6.3、§5.1–§5.6、§3、§2.2 的 M03、Q06、Q26；架构 §3、§4.2、§4.4、§4.5、§4.7、§8、§14.1、§14.2；数据库设计 §16、§9.1、§8.1。原型 `docs/原型/src/6-pages-later.js` 的 `/samples`、`/samples/:no`（规则 `smpNew`、`smpReview`、`smpConvert`）。

## 1. 解决什么

样衣档案、版次和评审、研发 BOM 挂在样衣上、评审通过后转大货（生成款式和 SKU，研发 BOM 带过去并复制成生产 BOM V1 草稿）。

不做：

- 打样单（DY）、派单、打样节点（PRD §6.3.2）：Q26 默认先做简版，见 §1.1。
- 首页"样衣待评审"待办：简版里没有"送样"这一步，分不出哪些在等评审。首页只在"开发款式"格子里加一个"在开发样衣"的数（§6.3）。
- 样衣导入导出：领猫里的样衣不迁（PRD §10 只迁主数据）；导出 PRD §5.4 没要求。

### 1.1 Q26：做简版，不做"可选开关"

PRD 的默认做法是"简版先做，打样单和节点做成可选、在设置里打开"。**推荐只做简版，不做开关**：

- 系统只有一个甲方。要不要打样单是甲方开发负责人一句话的事，答了以后全公司都这么用，不会有"有人开、有人关"。开关只在答复之前有用，而答复之前我们本来就只做简版。
- 开关的代价不小：列表的列、详情的版次块、评审挂在样衣还是挂在打样单、状态显示（样衣状态还是打样单状态），每一处都要写两套，测试也翻倍。
- 表按"以后加打样单只加表、加列"来设计（§2）：甲方要完整版时，加 `dev_sample_order`、`dev_sample_node` 两张表，评审加一列 `sample_order_id`，简版的数据原样留着、照样能看。那时作为一个增量做，不留开关。
- 甲方要是连样衣都不要，用 §6.5 的办法把菜单藏起来。

## 2. 表结构

迁移一个文件 `V?__dev_sample.sql`：四张 `dev_` 表、`tp_tech_pack` 加列、字典、菜单和授权。公共列照数据库设计 §1.2，下面只写业务列。

```sql
CREATE TABLE dev_sample (                       -- 公共列：主数据
    code               VARCHAR(32)  NOT NULL,   -- YY + yyMM + 4 位，如 YY26110001
    name               VARCHAR(100) NOT NULL,
    brand              VARCHAR(64)  NOT NULL,   -- 字典 brand
    category_id        BIGINT       NOT NULL REFERENCES bas_category (id),
    year               SMALLINT     NOT NULL,
    season             VARCHAR(64)  NOT NULL,   -- 字典 season
    wave               VARCHAR(64),             -- 字典 wave
    designer_id        BIGINT REFERENCES sys_user (id),
    pattern_maker_id   BIGINT REFERENCES sys_user (id),
    source             VARCHAR(64)  NOT NULL,   -- 字典 style_source
    customer_id        BIGINT REFERENCES bas_customer (id),   -- TRADE 留口子
    customer_style_no  VARCHAR(64),
    size_group_id      BIGINT       NOT NULL REFERENCES bas_size_group (id),
    sample_factory_id  BIGINT REFERENCES sup_supplier (id),
    fabric_supplier_id BIGINT REFERENCES sup_supplier (id),
    fabric_desc        VARCHAR(255),
    expect_finish_date DATE,
    est_tag_price      NUMERIC(14,2),
    est_cost           NUMERIC(14,4),
    status             VARCHAR(16)  NOT NULL DEFAULT 'DEVELOPING',  -- 动作改
    current_version    INT          NOT NULL DEFAULT 1,             -- 动作改
    converted_style_id BIGINT REFERENCES sty_style (id),            -- 动作改
    convert_by         BIGINT,
    convert_time       TIMESTAMPTZ,
    remark             VARCHAR(500)
);
CREATE UNIQUE INDEX uk_dev_sample_code  ON dev_sample (code);
CREATE UNIQUE INDEX uk_dev_sample_style ON dev_sample (converted_style_id) WHERE converted_style_id IS NOT NULL;  -- Q06
-- 其余外键列各一个索引；列表筛选 idx_dev_sample_status (status)、idx_dev_sample_season (year, season)

CREATE TABLE dev_sample_color (                 -- 关联表，整批删了重插
    sample_id BIGINT NOT NULL REFERENCES dev_sample (id),
    color_id  BIGINT NOT NULL REFERENCES bas_color (id),
    seq       INT    NOT NULL,
    PRIMARY KEY (sample_id, color_id)
);  -- 反向索引 idx_dev_sample_color_color (color_id)

CREATE TABLE dev_sample_review (                -- 公共列：只插
    sample_id      BIGINT        NOT NULL REFERENCES dev_sample (id),
    sample_version INT           NOT NULL,      -- 评的是第几版
    review_date    DATE          NOT NULL,
    result         VARCHAR(16)   NOT NULL,      -- PASS / REVISE / ELIMINATE
    opinion        VARCHAR(1000)
);
CREATE UNIQUE INDEX uk_dev_review_version ON dev_sample_review (sample_id, sample_version);  -- 一版评一次

CREATE TABLE dev_sample_reviewer (
    review_id BIGINT NOT NULL REFERENCES dev_sample_review (id),
    user_id   BIGINT NOT NULL REFERENCES sys_user (id),
    PRIMARY KEY (review_id, user_id)
);  -- 反向索引 idx_dev_reviewer_user (user_id)

-- 研发 BOM 挂样衣（架构 §4.7、§14.2）。只放宽、只加列
ALTER TABLE tp_tech_pack ALTER COLUMN style_id DROP NOT NULL;
ALTER TABLE tp_tech_pack ADD COLUMN sample_id BIGINT REFERENCES dev_sample (id);
CREATE INDEX idx_tp_pack_sample ON tp_tech_pack (sample_id);
CREATE UNIQUE INDEX uk_tp_pack_sample_version ON tp_tech_pack (sample_id, version)
    WHERE style_id IS NULL AND sample_id IS NOT NULL;
CREATE UNIQUE INDEX uk_tp_pack_sample_effective ON tp_tech_pack (sample_id)
    WHERE style_id IS NULL AND sample_id IS NOT NULL AND status = 'EFFECTIVE';
```

图片挂 `biz_attachment`（`SAMPLE`，`IMAGE`），评审照片挂 `SAMPLE_REVIEW`。`BizType` 加 `SAMPLE("样衣", "YY")`、`SAMPLE_REVIEW("样衣评审", null)`。

和数据库设计 §16 草案的出入：

| 出入 | 理由 |
|---|---|
| 不建 `dev_sample_order`、`dev_sample_node`；评审去掉 `sample_order_id` | 简版用不上，不建空表（架构 §14.1 第 4 条）。完整版时加表、加列 |
| `dev_sample` 加 `current_version` | 简版没有打样单，版次没处算；改版、恢复开发都让它 +1，评审的比较并交换也比它 |
| `size_group_id` 改必填，颜色至少一个 | 研发 BOM 的分码用量、随款色配料要它们；转大货建款时尺码组必填；原型新建样衣也要求选颜色 |
| `wave` 改选填 | 款式上是选填的，样衣比款式严没有意义 |
| 评审 `review_time TIMESTAMPTZ` → `review_date DATE`，加 `sample_version` | 评审是会上定的，事后补录常见，按业务日期记（架构 §6）；`(sample_id, sample_version)` 唯一，一版评一次 |
| `sty_style` 不加 `sample_id` | 用已有的 `sty_style.sample_no` 和 `dev_sample.converted_style_id`，见 §6.3 |

## 3. 规则

### 3.1 状态和动作

| 动作 | 从 → 到 | 权限码 | 要求 |
|---|---|---|---|
| 新建 | → 开发中，第 1 版 | `add` | 编号 `SerialNoGenerator.next("YY" + yyMM, 4)`，日期取 `Clock` |
| 评审 通过 | 开发中 → 已通过 | `review` | |
| 评审 改版 | 开发中 → 开发中，版次 +1 | `review` | 意见必填（400），它就是下一版的改版原因 |
| 评审 淘汰 | 开发中 → 已淘汰 | `review` | 意见必填（400） |
| 恢复开发 `reopen` | 已通过、已淘汰 → 开发中，版次 +1 | `review` | 原因必填，写进操作记录 |
| 转大货 `convert` | 已通过 → 已转大货 | `convert` | §3.4 |

写成 `StatusFlow`，改状态一律比较并交换，条件里同时带 `current_version`；0 行 → 1002。每个动作写 `biz_doc_log`（`SAMPLE`）。

状态标签：开发中 `progress`、已通过 `pending`（等转大货）、已转大货 `done`、已淘汰 `closed`。

"当前版的改版原因" = 上一条"改版"评审的意见，现算（PRD §6.3.2 规则"改版原因默认带上一版的评审意见"）。

- **改**：开发中、已通过能改；已转大货、已淘汰只读（1000"样衣已转大货，去款式 FS… 改"）。
- **删**：只有开发中、第 1 版、没评审过的能删；连颜色、图片、操作记录一起删。挂了研发 BOM 的由外键拦住 → 1005"先删研发 BOM 草稿；已生效的样衣只能淘汰"。

### 3.2 字段校验

照款式（RFC 005 §6）：品类调 `CategoryService.checkSelectable`；尺码组、颜色新选的要启用；字典列新选的要启用；年份 2000–2099；金额 ≥ 0。TRADE 关时来源不能是 `CUSTOMER_SAMPLE`、客户两列必须为空（400）。

- 打样工厂、面料供应商：新选的调 `SupplierService.checkUsable(id, SAMPLE)`，待准入、准入审批中的也能选（PRD §6.8.2）。
- 设计师默认是自己；没有设计师编号不拦，转大货时才要（自动编号用）。
- 颜色整组替换。尺码组：样衣已经有研发 BOM 的不能换（1000"已有研发 BOM，分码用量是按这个尺码组填的"），调 `TechPackService.existsForSample`。

### 3.3 研发 BOM

样衣的研发 BOM 就是资料包的研发阶段（架构 §14.2），资料包的代码和页面都复用，不另做一套：

- 样衣详情的"研发 BOM"页签就是款式详情里的资料包组件，传样衣 id。只能建研发 BOM；版本、草稿、生效、修订、核价、导出 PDF 都和款式上的一样。
- 资料包要的"这个款有哪些颜色、什么尺码组、吊牌价多少、能不能改"，挂在样衣上时由 dev 告诉它（§6.2 的 `SamplePackOwner`）：颜色、尺码组取样衣的，吊牌价取预估吊牌价，没有默认加工厂；已转大货、已淘汰的不能改。
- 挂在样衣上的研发版不能"转生产 BOM"：1000"样衣还没转大货，转大货时自动转成生产 BOM"。
- 核价（研发估）照常算；"按款看成本"只列款式，不含样衣。

### 3.4 转大货

样衣"已通过"后点"转大货"，弹窗填：款号（自动编号 / 手填）、大类、名称（默认样衣名称）、花名、默认加工厂（`SupplierSelect`，成衣厂、加工厂，默认打样工厂）。

一个事务（dev 的 `@Transactional`，style、techpack 的方法都加入这个事务）：

1. `SELECT … FOR UPDATE` 锁住样衣，不是已通过 → 1002。
2. 拼 `StyleCreateReq`：大类、款号方式、名称、花名、默认加工厂取弹窗；品牌、品类、年份、季节、波段、设计师、版师、来源、客户两列、尺码组、颜色、图片取样衣；吊牌价 ← 预估吊牌价，参考成本价 ← 预估成本。调 `StyleService.createFromSample(req, sampleCode)`：和新建款式同一段代码（款号取号、锁设计师编号、建颜色、生成 SKU、复制图片），另记 `sample_no`、操作记录"由样衣 YY… 转大货"。款号日期是转大货当天（PRD §6.3.3）。编不出号（设计师没编号、流水满了）照款式的 1000 报，弹窗里改成手填。
3. `TechPackService.adoptSamplePacks(sampleId, styleId)`：样衣的资料包全部挂到款式上（`style_id` = 新款式，`sample_id` 留着），有已生效的研发版就照"转生产 BOM"复制成生产 V1 草稿（单价按价格档案重取，架构 §4.7），款式的资料包状态改成"研发中"。返回生产草稿的 id，没有已生效研发版返回 null。
4. 比较并交换 已通过 → 已转大货，写 `converted_style_id`、`convert_by`、`convert_time`；`uk_dev_sample_style` 兜底。
5. 样衣写操作记录"转大货 → FS2612150701"。

返回 `{ styleId, styleCode, skuCount, prodPackId }`。前端提示"FS2612150701 已生成，15 个 SKU，研发 BOM 已复制成生产 V1 草稿，核对后生效"（没有研发 BOM 的换成"样衣没有生效的研发 BOM，资料包要另建"），跳到款式详情。

为什么把研发版整个挂到款式上，不只复制一份生产版：转完以后款式的版本条里就是"研发 V1、V2 → 生产 V1"，核价的"研发估"、按款看成本"没有生产版取研发版"都按款式算，和一期直接在款式上建研发 BOM 的款一个样子；样衣详情照样看得到这几版（只读）。

转出来的款式删不掉：`dev_sample.converted_style_id` 的外键拦住（1005）。

## 4. 接口

权限码前缀 `dev:sample:`。类型放 `web/src/types/dev.ts`，接口函数 `web/src/api/dev.ts`（`sampleApi`）。

| 方法 | 路径 | 权限 | 做什么 |
|---|---|---|---|
| GET | `/api/samples` | `list` | 列表 |
| GET | `/api/samples/counts` | `list` | 分段控件上各状态的数 |
| GET | `/api/samples/{id}` | `list` | 详情 |
| POST | `/api/samples` | `add` | 新建 |
| PUT | `/api/samples/{id}` | `edit` | 改（整体覆盖） |
| DELETE | `/api/samples/{id}` | `remove` | 删 |
| PUT | `/api/samples/{id}/images` | `edit` | 图片整组替换 |
| GET | `/api/samples/{id}/reviews` | `list` | 评审记录 |
| POST | `/api/samples/{id}/reviews` | `review` | 评审 |
| POST | `/api/samples/{id}/reopen` | `review` | 恢复开发 |
| GET | `/api/samples/{id}/convert-preview?styleClass=` | `convert` | 转大货弹窗：款号预览、SKU 数、研发 BOM |
| POST | `/api/samples/{id}/convert` | `convert` | 转大货 |
| GET | `/api/samples/{id}/logs` | `list` | 操作记录 |
| GET | `/api/samples/by-style/{styleId}` | `list` | 款式详情的"来源样衣" |
| GET | `/api/tech-packs?sampleId=` | `techpack:pack:list` | 样衣的资料包概况（01 加参数） |
| POST | `/api/tech-packs` `{ sampleId, stage: 'DEV' }` | `techpack:pack:add` | 给样衣建研发 BOM（01 加参数） |

- **列表** `PageParams & SampleQuery` → `PageResult<SampleRow>`，新建的在前。筛选：状态（多选）、品类（含下级）、年份、季节、设计师、品牌、打样工厂；关键字：编号（空格隔开查多个）、名称。`SampleRow`：编号、名称、主图缩略图、品牌、品类名、年份、季节、波段、当前版次、设计师、打样工厂、预计完成日期、最近一次评审（结论、日期）、状态、转大货款号。
- **详情** → `SampleDetail`：档案全部字段 + 颜色（`ColorOption[]`）+ 尺码组 + 图片 + 当前版的改版原因 + 转大货款号和款式 id + `actions`（`edit`、`remove`、`review`、`reopen`、`convert`，后端按状态 ∩ 权限算）。
- **新建、改** 请求 `SampleForm`，新建返回 `SampleCreated { id, code }`，改不收编号、状态。
- **评审** 请求 `ReviewForm { result, opinion, reviewDate, reviewerIds, photos: FileVO[] }`：评审日期默认今天、不能晚于今天；评审人至少一个，默认自己。返回新的 `SampleDetail`。
- **转大货预览** → `ConvertPreview { code, codeError, skuCount, devPack }`：`code` 是 `StyleService.codePreview` 的结果（只看不取），编不出来时 `code` 为 null、`codeError` 是原因；`devPack` 是会转成生产 V1 的那一版（`{ id, name }`），没有是 null。
- **转大货** 请求 `ConvertForm { codeMode, code, styleClass, name, aliasName, defaultFactoryId }` → `ConvertResult`（§3.4）。错误：不是已通过 1002；款号的错照 RFC 005 §3（1000）。
- **来源样衣** → `SampleRef { id, code, name } | null`，按 `converted_style_id` 查。

数据范围（PRD §3.2）：本人范围的只看设计师或建档人是自己的样衣；开发、开发主管的模板是全部。

## 5. 页面

菜单（迁移插入）：在"开发"目录（`/dev`）下，"样衣"`/samples`，组件 `dev/sample/index`，权限 `dev:sample:list`，图标 `EditPen`，排 20（V16 给企划、样衣留的空）。按钮挂在它下面：新建 `add`、编辑 `edit`、删除 `remove`、评审 `review`、转大货 `convert`。

角色模板（PRD §3.1 没有这一行，按 §3 的"开发：二期起建样衣"定）：开发、开发主管给全部五个；管理层给 `list`、`review`；其他角色不给。

详情页加进 `DETAIL_ROUTES`：`/samples/:id` → `views/dev/sample/detail.vue`，挂在 `/samples` 下，页签名"样衣 YY26110001"。

**列表 `/samples`**（照原型 `/samples`）：`PageHeader` 标题"样衣"，按钮"新建样衣"（`add`）。`FilterBar`：`#left` 放状态分段控件（全部 / 开发中 / 已通过 / 已转大货 / 已淘汰，数用 `counts`）；筛选里放品类、年份季节、设计师、品牌、打样工厂。列（`useColumns`）：样衣（缩略图 + 编号，`fixed="left"`）、名称、品类、季节（"2027 春 · 第 1 波"）、版次（"第 2 版"）、设计师、打样工厂、预计完成（开发中且过了日期标红）、最近评审（"改版 · 11-06"）、状态（`fixed="right"`）；默认不显示：品牌、来源、版师、面料、预估吊牌价、预估成本、转大货款号、建档时间。没有勾选列：现在没有要批量做的事。空表格："还没有样衣：点右上角「新建样衣」，转大货以后在款式里接着做"。

**新建、编辑**：对话框（照原型 `SmpNew`），`label-position="top"`、`.form-grid` 两列，`useUnsavedChanges(form, dialogVisible)`。字段：名称、品牌、品类（`el-tree-select`，只能选叶子）、年份季节、波段、来源、颜色（`ColorSelect`）、尺码组、设计师、版师（`UserSelect`）、打样工厂（`SupplierSelect`，成衣厂、加工厂，`usage="SAMPLE"`）、面料供应商、面料描述、预计完成日期、预估吊牌价、预估成本、图片（`ImageUpload`，新建时一起传）、备注。

**详情 `/samples/:id`**（照原型 `/samples/:no`）：`PageHeader` 标题是编号、`sub` 是名称，按钮照 `actions`：评审（主按钮）、转大货（已通过时是主按钮）、编辑；"更多"里放恢复开发、删除。已转大货的页头多一个"款式 FS…"链接。`<div class="page">` 左右两栏：

- 左：页签"版次和评审"（倒序，一版一块：第 n 版、改版原因、评审结论 / 意见 / 评审人 / 日期 / 照片；当前版没评审的写"等评审"）、"研发 BOM"（资料包组件，见 §6.2 前端一条）、"操作记录"（`DocLogList`）。
- 右：图片（能改时可编辑）、属性（品牌、品类、季节、来源、设计师、版师、尺码组、颜色、打样工厂、面料、预计完成、预估吊牌价、预估成本、转大货款号和时间）。

**评审**对话框（照原型 `SmpReview`）：结论分段控件（通过 / 改版 / 淘汰）、意见（改版、淘汰时必填）、评审日期、评审人（`UserSelect` 多选）、照片。按钮文字跟着结论变："通过""改版，开第 2 版""淘汰"。

**转大货**对话框（照原型 `SmpConvert`）：款号一栏"自动编号 / 手填"切换，自动时显示预览的号或琥珀色的原因；大类、名称、花名、默认加工厂；底下一行"3 色 × 5 码，生成 15 个 SKU；研发 V2 会复制成生产 V1 草稿"。

## 6. 边界和解耦

### 6.1 依赖方向

dev 只往下依赖：`dev → techpack`（间接用到 style、price、supplier、basic），加上 system、biz。`ArchitectureTest.DIRECT` 加一行 `entry("dev", Set.of("techpack"))`；board 那一行加 `"dev"`（首页的数，§6.3）。一期的任何域都不 import dev 的类：style 只收一个样衣编号字符串，techpack 只认自己定义的接口。

### 6.2 要一期提供的

| 谁 | 方法 | 什么时候留 |
|---|---|---|
| techpack | 取款式信息（颜色、尺码组、吊牌价、默认加工厂、款号款名花名、能不能改）集中在一处，返回 `PackOwner` 记录；建版本、生效、修订、核价、PDF 都只用它，不直接到处调 `StyleService` | **第 3 批「资料包」顺手留**。二期挂样衣只在这一处加分支 |
| style | `void updateTechPackStatus(long styleId, TechPackStatus status)` | 第 3 批「资料包」，RFC 005 §4 已经写了 |
| style | `StyleCreateResult createFromSample(StyleCreateReq req, String sampleNo)`：同 `create`，另记 `sample_no` 和操作记录；不开新事务 | 二期加（只加方法）。一期要保证 `create` 的内部能在别人的事务里调 |
| techpack | `boolean existsForSample(long sampleId)` | 二期加 |
| techpack | `Long adoptSamplePacks(long sampleId, long styleId)`：§3.4 第 3 步；改到的资料包 `version_lock + 1` | 二期加，内部复用"转生产 BOM" |

```java

public interface SamplePackOwner {
    /** 不存在 404。forWrite = true 时 FOR SHARE 锁住样衣行，和转大货互斥 */
    PackOwner sample(long sampleId, boolean forWrite);
}

/** 一期就有：款式上的资料包由 techpack 自己用 StyleService 拼出同一个记录 */

                        BigDecimal tagPrice, Long defaultFactoryId, String lockedReason /* null = 能改 */) {}
```

资料包的主人怎么认：`style_id` 不空就是款式（转过大货的样衣版本也算款式的），否则是样衣。techpack 用 `ObjectProvider<SamplePackOwner>` 取实现；dev 的实现单独一个类，只用 dev 自己的 Mapper，不注入 `TechPackService`，免得 Bean 循环依赖。

前端：资料包组件（`views/style/style/techpack/TechPackTab.vue`）的 props 从 `styleId` 改成"款式 id 或样衣 id"；`TechPackOverview`、`TechPackDetail` 加 `sampleId`，`styleId` 改成可空；样衣上的版本 `styleCode`、`styleName` 放样衣编号、名称。改 `docs/api/01` 和 `types/techpack.ts`。资料包的 `DocRef`：挂样衣的 `kind = 'SAMPLE'`、`parentId` = 样衣 id，`docRoute` 去 `/samples/:id?tab=techpack&techPackId=`。

### 6.4 `tp_tech_pack.sample_id` 这个口子

- **外键加**：数据库设计 §1.4"外键都加"。它让"挂了研发 BOM 的样衣删不掉"自动成立，不用 dev 去问 techpack。外键是数据库层面的，Java 依赖照样只有 `dev → techpack`。
- **谁写**：只有 techpack 写（表主人，架构 §3.2 第 3 条）。建版本时 techpack 照请求里的 `sampleId` 写；转大货时 dev 调 `adoptSamplePacks`，由 techpack 改 `style_id`。dev 不碰 `tp_` 表。
- **迁移放哪**：放在 dev 的迁移里，排在 `dev_sample` 后面（外键要它先存在）。只放宽 `style_id`、只加列，旧版本的应用照样能跑（架构 §12.3）。
- **为什么不在款式上反过来加 `sample_id`**：款式已经有 `sample_no`（导入时照填领猫的，二期转大货时自动带），样衣上的 `converted_style_id` 已经能从样衣找到款式；从款式找样衣按它查一次就行。少一个"下层表指向上层表"的列，也就少一处要 style 写、dev 用的约定。

### 6.5 怎么隐藏

甲方不要样衣时：超级管理员在**管理后台 › 菜单**把"开发 › 样衣"这一页停用。不改代码、不发版，随时能再启用。

现有机制就够（bug 009，RFC 001 §18）：权限和侧边栏都从"自己和所有上级都启用"的菜单里取，停用一页，它下面的按钮权限跟着失效，超级管理员也一样。藏了以后：

| 地方 | 表现 |
|---|---|
| 侧边栏、⌘K | 没有样衣 |
| 后端接口 | `dev:sample:*` 全部 403 |
| 首页 | "在开发样衣"不出（没有权限） |
| 款式详情 | 来源样衣只显示 `sample_no` 文字，不是链接；转过来的款式、资料包一切照常（它们已经是款式的） |
| 数据 | 都留着，再启用就回来 |

不选另加一个配置开关（照 `TradeFeature`）：要甲方 IT 改部署配置、重启，还得在每个接口里问开关；菜单停用已经把接口、页面、首页一起关掉了。

## 7. 关键流程和并发

| 场景 | 怎么保证 |
|---|---|
| 两个人同时评审同一版 | 先比较并交换样衣（条件带状态和 `current_version`），再插评审；`uk_dev_review_version` 兜底 → 1002 |
| 同时点两次转大货 | `FOR UPDATE` 锁样衣，第二个看到已转大货 → 1002；`uk_dev_sample_style` 兜底 |
| 转大货中途失败（款号编不出、SKU 生成出错） | 一个事务：款式、SKU、款号流水、资料包改动、样衣状态一起回滚 |
| 转大货时有人在建研发 BOM、改草稿 | 建版本走 `sample(id, true)` 的 `FOR SHARE`，和转大货的 `FOR UPDATE` 互斥；`adoptSamplePacks` 让 `version_lock + 1`，开着旧页面的保存回 1002，刷新后看到的是款式上的同一版 |
| 有研发 BOM 时换尺码组 | 保存先锁样衣再查 `existsForSample`，和建版本的 `FOR SHARE` 互斥 |
| 删样衣时它刚挂上研发 BOM | 外键 → 1005 |

## 8. 取舍

- **简版不留开关**（§1.1）。
- **研发 BOM 整个挂到款式上**，不只复制一份生产版（§3.4）：代价是 techpack 要认"挂在样衣上"这一种主人（§6.2），收益是转大货以后款式上的历史、核价对比和一期的款没有两样。
- **techpack 定义接口、dev 实现**，不让 techpack 调 dev：techpack 在下层，反过来就成环。
- **版次存一列**，不从评审现算：恢复开发也要让版次 +1，存下来最直接，也正好做比较并交换的条件。
- **转大货复用款式的建款代码**（`createFromSample`），不在 dev 里拼 `sty_` 表：款号、设计师编号、SKU 的规则只写一处。

## 10. 按默认做的、要用户定的

按默认做的：Q06 一个样衣只转一个款（`uk_dev_sample_style`）；Q26 先做简版。

要用户定的（推荐的写在前面）：

1. **Q26 只做简版、不做"可选开关"**（§1.1）。甲方要打样单、节点时作为增量做，表不用改。
2. **尺码组必填、颜色至少一个**（§2）：PRD 写的是选填。研发 BOM 和转大货都要它们。
3. **加"恢复开发"**（已通过、已淘汰 → 开发中，版次 +1）：PRD 没写；评审点错了、通过后又想改，没有它只能新建一个样衣。
4. **研发 BOM 转大货时整个挂到款式上**（§3.4），不只复制成生产 V1。
5. **转大货单独给 `dev:sample:convert`**，默认给开发、开发主管：转大货就是建款，和 `style:style:add` 给的是同一群人。
