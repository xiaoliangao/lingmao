# RFC 003 基础资料

状态：**已定**（2026-11-15 用户审过；"等用户定的问题"一节标了结论）。

对应：PRD §2.6、§3.1–§3.2、§5.2、§5.6–§5.8、§6.1、§6.9.2 第 1、4 条、§10；架构 §3.1、§3.2、§6、§8、§14.4；数据库设计 §1、§3.1–§3.3、§5、附录 A.2。建在 RFC 001（第 1 批）上。

## 1. 解决什么

第 2 批主数据的底层：主体公司、TRADE 开关的后端校验、品类、颜色、尺码组、物料分类、物料 + SKU、仓库（含工厂仓）、字典的新列和预置、用户的默认主体等四个字段、预置角色模板和菜单、物料的 Excel 导入导出。第 2 批四份 RFC（003–006）共用的规则在 §2，迁移顺序在 §11。

不做：

- 客户（PRD §6.1.8）：TRADE 关，只建 `bas_customer` 表，让款式的 `customer_id` 能加外键（架构 §14.4）；没有实体、接口、页面。
- 货位（二期）、品类的尺寸指示模板（二期）。
- 停用仓库前查有没有库存：basic 看不到库存，出入库 RFC（第 4 批）定怎么拦。
- 物料详情的"用到它的款式"（第 3 批随资料包）、"成交记录"（第 4 批随采购单）。
- 字典 `text_value` 的页面（第 3 批随设置 › 工艺标准，列这次先加）。
- 按主体隔离（二期，Q13）。

## 2. 第 2 批共用的规则

003–006 都照这几条，后面不再重复。

- **删除**：主数据没被引用就能删，被引用的由外键拦住，返回 1005"已被××引用，只能停用"（RFC 001 §4.3）。Java 里不先查引用。删的时候同一个事务里先删本域的子表（SKU、尺码、分类关联……），再删 `biz_attachment`、`biz_doc_log` 里挂在它上面的，最后删自己。
- **编码建好不改**：颜色、尺码、物料、物料 SKU、款号、供应商、仓库、主体的编码保存后不能改。编码进了 SKU 码、单号或打印件；录错了而且没用过的，删掉重建。
- **"用过以后不能改"一律换成"建好就不能改"**（§15）。basic 在依赖图最底下（架构 §3.2），查不到款式、资料包、库存有没有用它；没用过的删掉重建，用过的外键拦住。落到三处：尺码组只能追加尺码、基码不能换（§5.3）；物料的库存单位不能改（§7.2）；字典项的 value 不能改（§4.2）。
- **停用**：停用的不出现在新单据的下拉里，已有单据不受影响（PRD §5.6）。"能不能选进单据"由用它的域调 basic 的 Service 查，basic 只给状态。
- **数据范围**：主数据不分"本人 / 全部"，PRD §3.2 只管单据。
- **下拉接口**：`/options`、`/tree`、`/pick` 这类给别的页面用的，只要登录，只返回启用的、只带显示要的列。列表、详情要 `:list`。
- **保存**：`PUT` 整体覆盖（RFC 001 §4.2）；`status` 和"由动作改"的列标 `NEVER`（RFC 001 §4.4），启用、停用走单独的接口。主数据不加 `version`（架构 §4.3）。
- **批量**：列表的批量启用、停用、删除，前端对勾选的逐条调单条接口，没成功的列原因、留着勾（原型 `BatchBar`）。不另写批量接口。
- **图片**：物料、物料 SKU、款式的图挂 `biz_attachment`（`category = IMAGE`）。`PUT /api/<资源>/{id}/images` 传排好序的整组，整组替换，第一张是主图：`ImageUpload` 本来就给出整组，比逐张增删排序简单。文件本身只增不删（RFC 001 §10）。接口返回的地址都过签名工具；存之前去掉签名参数，前端传回签过名的地址也能存。

## 3. 主体公司、用户字段、TRADE 开关

### 3.1 主体公司

表照数据库设计 §5.1。

- 编码 2–6 位字母数字，转大写，唯一。
- 至少留一个启用的：停用、删除时先 `SELECT id FROM bas_company WHERE status = 1 FOR UPDATE` 锁住全部启用的行再数。两个人同时停用最后两个，只有一个成功。
- 给第 3 批的单据用（第一张单据开工时加）：`CompanyService.defaultForUser(long userId)`——用户的默认主体启用就用它；否则启用的只有一个就用那个；都不是返回 null，单据上必须选。basic 调 system 的 `UserService` 取默认主体（任何域都能用 system）。

### 3.2 用户加四个字段

`sys_user` 加五列，照数据库设计 §3.3：`default_company_id`（→ `bas_company`）、`dept`、`post`、`designer_no`、`designer_no_locked`。`designer_no` 的唯一索引不带 `deleted` 条件，离职的人的编号不回收。管理后台的用户页加四个输入。

- 默认主体：下拉调 `/api/companies/options`。system 不能调 basic，后端只靠外键保证它存在；停用的主体照样能留在用户上，取默认时 §3.1 的方法会跳过它。
- 部门、岗位：自由填（二期按部门分支审批时再改成部门表）。
- 设计师编号：两位数字 `01`–`99`；锁了以后不能改、不能清空。规则和并发见 RFC 005 §3.3。

### 3.3 TRADE 开关

`config.TradeFeature` 读 `scm.trade.enabled`（部署配置 `SCM_TRADE_ENABLED`，默认 false），别处都问它（架构 §14.4）。各域和 system 都能用 `config`。

关着时第 2 批要拦的，都返回 400：

| 哪里 | 拒收 |
|---|---|
| 款式来源 | `CUSTOMER_SAMPLE` 客户来样；`customer_id`、`customer_style_no` 必须为空（RFC 005 §6） |
| 物料默认来源 | `CUSTOMER_SUPPLIED` 客供 |
| 字典选项 `GET /api/dict-data/by-type/{type}` | 滤掉 `style_source` 的 `CUSTOMER_SAMPLE`、`order_type` 的 `CUSTOMER`（缓存照旧，取出来以后再滤） |
| 物料导入 | 领猫"客供"按"自购"导，列进导入提示（附录 A.2 第 8 列） |

保留值清单只在 `TradeFeature` 里写一处。管理后台的字典页照常列出它们，标"代工"。订单类型、BOM 来源、入库类型、物权由各自的 RFC 加。

前端一期按"关"做，不读开关；`/api/auth/me` 先不带它，补客户界面时再加（架构 §14.4 那一句到时候做）。

## 4. 字典

### 4.1 新列

`sys_dict_type.num_label`；`sys_dict_data.num_value`、`builtin`、`text_value`（数据库设计 §3.1、§3.2）。字典页：类型有 `num_label` 的，数据多一列数值；内置项标"内置"。

### 4.2 规则改动

- **value 建好以后不能改**，所有字典项都是，不只内置项。业务表存的是 value（数据库设计 §1.3），改了旧数据就对不上；system 在最底下，查不了哪些表用过它。要换就新建一项、停用旧的。这条也替掉了架构 §4.5 的"改大类字典项时查一下 `sty_style`"——system 不能依赖 style。
- **内置项**（`builtin = true`）：不能删、不能停用；label、排序、数值能改。
- 普通项的删除照旧（`sys_` 表逻辑删除）。用过的删了，旧数据只能显示 value，所以删除确认写"已经用过的请停用，删了以后旧单据上显示编码"。

### 4.3 预置

迁移里插入数据库设计 §3.2 那张表的全部字典，`ON CONFLICT (type_code, value) WHERE deleted = false DO NOTHING`。几点：

- value 用英文大写（`SPRING`、`FABRIC`）；内置项的 value 照 §3.2 的"内置项"一列；税率的 value 是数字（`13`）；大类的 value 就是 2 位字母（`FS`）。
- 物料类型另加"配件""工艺""鞋底"：PRD Q40 的默认做法是"都加进字典"，数据库设计 §3.2 的预置还没跟上。
- `brand` 品牌预置为空：品牌是甲方的名字，不进公开仓库。款式导入遇到没有的品牌自动建（数据库设计 §3.2"导入时建"，RFC 005 §8）；手建款式之前先在字典里加。
- 后面几批才用的字典（生产节点、异常类型、BOM 部位……）也这次插：甲方能在试用环境里先看、先改。

## 5. 品类、颜色、尺码组、物料分类

### 5.1 品类

三级树（数据库设计 §5.4）。层级由上级算，最多 3 级；上级建好不能改（不挪节点）；同一上级下不重名；有下级的不能删，先删下级。

款式只能选叶子（下面没有启用的子品类），由 style 在新建和换品类时调 `CategoryService` 查。已经被款式用了的品类下面再加子品类，旧款式不受影响。

### 5.2 颜色

编码 2–3 位字母数字，转大写，唯一；名称唯一。名称、色系、色块能改。

### 5.3 尺码组

- 新建时填名称、全部尺码（空格或逗号隔开）、基码，基码默认取中间那个（PRD §6.1.3）。尺码 1–16 位，转大写，组内不重复。
- 之后**只能在末尾追加尺码**，不能删、不能改、不能调顺序，基码不能换（§2）。PRD 写的是"有款式用了以后"才这样，basic 查不到款式，就一律这样。写错了而且没被款式用过的，整组删掉重建；用过的外键拦住。
- 名称能改：别的表存的是 `size_code`，不存组名。

### 5.4 物料分类

两级（数据库设计 §5.8）：一级只有名称（面料、辅料、包材……），二级必须有 2 位字母编码，就是物料编码的前缀。物料只能挂在启用的二级上。编码建好不改；同一上级下不重名。

## 6. 仓库和工厂仓

表照数据库设计 §5.11。

- 页面上只能建物料仓、成品仓，编码手填。工厂仓不能手建；工厂仓的名称、类型、绑定的工厂也不能在仓库页改，地址、负责人、电话、备注、启用停用能改。
- **工厂仓由 supplier 同步**（架构 §3.1、A23）。依赖方向是 supplier → basic，basic 不认识供应商，所以由 supplier 在它自己的事务里调：

```java
public interface WarehouseService {
    /** 有就把名称改成"简称 + 仓"；没有时 create 为 true 才建。调用时机见 RFC 004 §6 */
    void syncFactoryWarehouse(long supplierId, String supplierCode, String supplierShortName, boolean create);

    /** 删供应商之前调：工厂仓没被引用就删；被引用了外键拦住，整个删除回滚，报 1005 */
    void deleteFactoryWarehouse(long supplierId);
}
```

- 编码：`GC` + 供应商编码里的数字（`GYS0004` → `GC0004`）。没有数字、或者这个编码已经被占了，就用 `next("GC", 4)` 一直取到没被占的。
- 停用、拉黑供应商不动工厂仓：仓里可能还有料要退回；不让再往这家发料，是排单、采购单选工厂时拦（架构 §3.1）。分类去掉了成衣厂、加工厂也不删仓。
- 两个请求同时给同一家建仓，`uk_bas_warehouse_factory` 拦住后一个，返回 1000（刷新再试）。

## 7. 物料和 SKU

表照数据库设计 §5.9、§5.10。页面照原型：列表 + 详情页（PRD §6.1.5 写的是抽屉，原型后来改成了详情页，照原型）。

### 7.1 编码

- 新建：`next(分类码, 4)`，如 `ML0012`。取到的号已经有了（导入的老编码），就再取下一个，最多试 100 次。先查后插在同一个事务里：`sys_serial` 这一行的锁持有到提交，同一分类的新建本来就排队；和导入正好撞上，由唯一索引兜底（1000）。不靠"插入失败再重试"：PostgreSQL 里一条语句失败，整个事务就不能再用了。
- 导入：照用领猫的编码；导完把每个分类码的流水推到已用的最大号（`raiseTo`，§10）。
- SKU 码：`物料编码-颜色码[-规格码]`，自动拼，不能改。规格码默认取规格去掉空格和末尾的单位（cm、mm、厘米、毫米、码）再转大写，新建 SKU 时可以改。

### 7.2 规则

- **库存单位建好不能改**：库存、BOM 用量都按它记，改了旧数就错了。**采购单位、换算系数能改**：单据明细存了当时的采购单位和系数（架构 §4.1），价格档案按记录时的采购单位存、取现价时只认现在的采购单位（RFC 006 §4），改了不影响旧账。
- 换算系数 > 0；最小包装量 > 0；默认损耗、备料比 0–100；参考单价 ≥ 0。
- 默认供应商只当默认值：下拉只列合作中的，后端不查状态（架构 A23）。
- **查重只提示不拦**（PRD §6.1.5 规则 1）：`GET /api/materials/dup-check`，同分类同名、同默认供应商同货号的列出来，前端弹"可能和 ML0012 重复，确定新建？"。
- **批量加 SKU**：一次选多个颜色、填多个规格，两两组合；已有的跳过，返回新建了哪些。没有颜色的物料可以只填规格；都不填就是一个不带颜色的 SKU。物料至少留一个 SKU。
- 停用物料以后它的 SKU 不能再选进新单据，下游同时看物料和 SKU 的状态；已有库存照常出库。

### 7.3 给下游的方法

价格档案这一批就用（取采购单位、查状态，RFC 006 §3、§4），资料包、采购、出入库以后接着用：

```java
/** 物料：编码、名称、物料类型、库存单位、采购单位、换算系数、参考单价、默认来源、默认损耗、备料比、状态。不存在的 id 抛 404 */
List<MaterialRef> materialRefs(Collection<Long> materialIds);

/** SKU：上面这些 + SKU 码、颜色、规格、SKU 单价（空则物料参考价）、SKU 状态 */
List<MaterialSkuRef> skuRefs(Collection<Long> skuIds);
```

## 9. 物料的导入导出

列对照照数据库设计附录 A.2，这里只定结构。

- **模板就是领猫导出的样子**（理由见 §15）：工作表"物料信息"一行一个物料，"物料信息SKU"一行一个 SKU，表头用领猫的列名；我们多出来的列（采购单位、换算系数、最小包装量、默认物料来源……）接在"物料信息"后面，选填。"物料信息多单位"可选，有就按附录 A.2 定采购单位和换算系数。另有一张"填写说明"。
- 表头不认识的列报错（拼错的列不会被悄悄丢掉）；附录 A.2 写"丢弃"的列认识、忽略；写 `legacy_attrs` 的有值才存。
- 分类按"物料分类"路径的前两级名称匹配，匹配不上整批报错：二级分类码要人定，不自动建。
- 颜色按编码匹配；没有就用编码 + 名称新建一个，列进提示；编码对上了名称不一样也列进提示。
- 字典类的列按 label 匹配，季节去掉"季"字；匹配不上整批报错，列出值，先去字典里加。
- 受待决问题影响的，按 PRD §12 的默认做法写：默认损耗、采购损耗按百分数导（Q31）；最小库存作安全库存（Q32）；成本价当含税含运、按采购单位（Q33）；配件、工艺、鞋底已经预置（Q40）。甲方答了只改列对照。
- "物料信息多供应商"那张表要进价格档案，basic 写不了 price（架构 §3.2），放在价格档案的导入里（RFC 006 §6）。
- 只新增，编码已存在算错误（§15）。导错了：没用过的在列表里勾上批量删，改好再导。
- 导完把分类码的流水推到已用的最大号（§7.1）。
- 导入结果除了条数还带提示（新建了哪些颜色、客供改成了自购……），不拦导入。
- 图片（11-21 加，领猫 11-21 的物料导出图片嵌在表里）：两张表的"图片"列，图片浮在哪一行就挂到那一行建的物料或 SKU 上（`biz_attachment` 的 `IMAGE`，同一行几张从左到右排，第一张是主图）。文件在解析时就存好（解析不在写事务里），写库只挂引用；没导成的没人引用，24 小时后自动清掉。同一个文件里一样的图只存一份。不是 jpg、png、gif 的，落在空行上的，图本身坏了的（打不开、像素超过 1 亿），不导、进提示，别的照常导；存储忙、空间不足是整批的事，整批报错。导入批量存图同时只占一个位置，留一个给页面上传。压缩包里的图片另算条数（最多 5000 张，别的条目还是 128 个），总大小还是 10MB 以内。

导出：一行一个 SKU，两张表的列和模板一致。不带图片。

## 15. 取舍

- **"建好就不能改"代替"用过以后不能改"**（§2）。另一种做法是给尺码组、物料、字典项加"已使用"标记，由款式、资料包、库存第一次用到时回写（像设计师编号的锁）：每个用到它的地方都要记得回写，漏一处就会改坏数据。代价是没用过的录错了要删掉重建。
- **物料导入照领猫导出的两张表**，不照 PRD §10 的"一行一个 SKU、物料信息重复填"（§9）：甲方要先在 Excel 里合成一张，几百行里物料信息抄错一处就是两个物料；打开另存，长数字还会被改坏（Q35）。照领猫的样子，导出来的文件建好颜色和分类就能直接导。
- **导入只新增，不做"已存在就更新"**：已经被资料包、采购单用了的物料，导入悄悄改它的单位、系数，比报错危险。
- **查重单独一个接口**，不做成"保存时拦一下、带确认标记重发"：两步提交要多一个错误码和一个参数，查重本来就不拦。
- **自动编码撞号时先查后插**，不靠"插入失败再重试"：PostgreSQL 里一条语句失败，整个事务就不能再用了。
- **图片整组替换**（§2）：`ImageUpload` 本来就给出整组，比逐张增删、排序简单。
- **"基础"六种资料共用一组权限码**：PRD §3.1 的角色表就是按"基础资料"一行给的。以后要分开给（比如仓库只给仓管改），再拆码。
- **季节、款号大类不放进业务的"基础"页**：它们是字典，超级管理员在管理后台改（PRD §3）。原型的这两个页签不做。
- **`TradeFeature` 放 `config`**（§3.3）：它是部署开关，不是框架代码，不进 `common`。

### 和数据库设计、上文不一样，或者上文没写到的

- **外键**：写成 `REFERENCES x (id)`，不写动作，所以是 NO ACTION，不是 §11 说的 RESTRICT。
  - 两者只差检查时机：NO ACTION 在语句结束时查，RESTRICT 马上查。"删被引用的报 23503"没有区别。
  - 约束名用 PostgreSQL 默认的 `<表>_<列>_fkey`，比如 `bas_material_sku_color_id_fkey`。1005 的提示取的是引用方的表注释，不看约束名。
  - `SchemaConventionsIT` 两种都认。
- **补了两个索引**。外键列都要是某个索引的第一列，数据库设计漏了两个：`idx_sty_style_pattern_maker (pattern_maker_id)`、`idx_prc_price_supplier (supplier_id)`。数据库设计已改（v0.6）。
- **仓库加检查约束** `ck_bas_warehouse_factory`：`(type = 'FACTORY') = (factory_id IS NOT NULL)`。工厂仓必须绑工厂，别的仓不能绑。数据库设计原来只写了"工厂仓必填"。
- **加工价的单位**：`prc_price.unit` 存 `PIECE`（字典 `unit` 的"件"）。数据库设计原来写的是"件"，已改。
- **审计列**：主数据有四个审计列。下面这些没有：
  - 跟着上级整批改的行：`bas_size_group_item`、`sty_style_color`、`sup_supplier_category`、`sup_supplier_good_at`（照数据库设计）；
  - `prc_price` 只插不改，只有 `create_by`、`create_time`。
- **表注释**：V1–V9 的表本来都有注释，不用补。新表的注释写成能放进"已被××引用"的名词，比如 `bas_material_sku` 是"物料 SKU"。
- **主体公司不预置**：主体名是甲方的名字，不进公开仓库。甲方在 资料 › 基础 › 主体公司里建。
- **字典 value**：数据库设计只写了 label，value 是这次定的，见下面"预置数据"。

### 后面几步要知道的

**`SchemaConventionsIT`**：查的是 `pg_catalog`，以后每批的新表都自动受检查。

- 每张表有注释，测试临时建的 `it_` 开头的表除外。
- 外键的删除、更新动作只能是 RESTRICT 或 NO ACTION。
- 外键列是某个索引的第一列。部分索引只认条件是 `列 IS NOT NULL` 的那种。
- 叫 `xxx_id` 的 BIGINT 列都要有外键。不要外键的列（"类型 + id"、物权 `owner_id` 存 0）写进 `NO_FK`，写明理由。
- `sys_` 以外的表不能有 `deleted`；数量、金额不能是浮点。

### 加一个详情页

2. 写 `views/supplier/supplier/detail.vue`：
   - setup 里取一次 `const id = Number(route.params.id)`、`const path = route.path`。不要 watch 路由：别的详情页签留在 keep-alive 里，也看得到路由在变。

3. 列表页点一行：`` router.push(`/suppliers/${row.id}`) ``。

机制：

- 用户有 `parent` 那个菜单，才挂这条路由，没有就是 404。id 只认数字。侧边栏高亮、分组跟着列表页。
- 一条记录一个页签，各留各的状态。keep-alive 按 key 留页面、按组件名清（`include`），同一个组件分不开，所以 `AppLayout` 给每个详情页签套一层按地址起名的壳（`Detail:/suppliers/12`，见 `tabs.cacheNameOf`），关页签时按名字清掉。
- `AppLayout` 的 keep-alive 下面现在是 `v-if / v-else` 两支，菜单页那一支的 `:key` 不能去掉。去掉以后，v-if 给两支配的固定 key 会让所有菜单页挤在 keep-alive 的同一格里：无头 Chrome 测出来，从基础切到物料，显示的还是基础。
