# RFC 002 交付部署包

状态：**草案**（2026-11-05），等用户审。

对应：架构 §12；PRD §8、Q21；`docs/进度.md` 第 1 次发版的"部署包"。

## 1. 解决什么

甲方 IT 拿到一个压缩包，在一台装了 Docker 的 Linux 服务器上照手册半小时内装好；之后每周升级一次，一条命令、几分钟；每天自动备份，坏了能恢复。

默认我们不登录甲方的服务器：甲方 IT 自己执行，我们开屏幕共享远程协助（PRD Q21）。

不做：

- 域名、证书、防火墙、异地备份：部署方负责。手册写清楚怎么做、为什么必须做。
- 监控告警平台、高可用、多台机器（架构 §12.5）。

要赶在 11-14 第一次发版时交出去，甲方 11-13 前准备好服务器（PRD Q21）。

## 2. 要先问甲方的

这几条影响打包方式，建议并进 PRD 的 Q21 一起问：

| 问题 | 为什么要问 | 没回复就按 |
|---|---|---|
| 服务器 CPU 是 x86_64 还是 ARM，什么系统 | 镜像要按 CPU 架构打。我们在 Mac（ARM）上打包，默认打出来的是 ARM 的，放到 x86 服务器上起不来 | x86_64；Ubuntu 22.04 / 24.04 或 Debian 12 |
| 服务器能不能访问 Docker Hub | 大陆的服务器大多拉不下来 | 拉不下来：安装包自带全部镜像 |
| 系统从公网访问，还是只在公司内网用；有没有已经备案的域名 | 要 HTTPS 就要域名；大陆服务器上的域名要先 ICP 备案，通常一到三周，没备案的域名会被云厂商拦住 | 试用期用 IP + 端口，云安全组只放行公司的出口 IP；上线前换成已备案的域名 + HTTPS。甲方已有备案的域名的话，用它的子域名最快 |

## 3. 包里有什么

每次发版出一个包，`scm-<版本>.tar.gz`：

```
scm-2026.11.14/
├── VERSION
├── compose.yml
├── env.example                 配置模板，安装时生成 .env
├── images/                     镜像（docker save 出来的）
│   ├── scm-app.tar             每个包都有
│   ├── scm-web.tar             每个包都有
│   ├── postgres-16.tar         只在"完整包"里
│   └── redis-7.tar             只在"完整包"里
├── nginx/                      http.conf、https.conf、trusted-proxies.conf、upgrading.json
├── scripts/                    install、upgrade、backup、restore、check-restore、reset-admin-password
└── docs/                       部署手册.md、openapi.json
```

**完整包**（第一次安装用）带四个镜像，大约几百 MB；**升级包**只带应用的两个镜像。PostgreSQL、Redis 的镜像很少变，不用每周传一遍。

版本号用发版日期，如 `2026.11.14`，同一天发第二次加 `-2`。

装好以后的目录（默认 `/opt/scm`，可以换）：

```
/opt/scm/
├── 包里的文件（compose.yml、nginx/、scripts/、docs/）
├── .env                        配置和密钥，chmod 600
├── compose.override.yml        部署方自己要改 compose 时写这里（可选）
├── certs/                      HTTPS 证书（可选）
├── data/postgres/              数据库
├── data/uploads/               上传的文件
├── backups/                    备份
└── logs/                       应用日志
```

**升级时会覆盖的**：包里的文件。**永远不覆盖的**：`.env`、`compose.override.yml`、`nginx/trusted-proxies.conf`、`certs/`、`data/`、`backups/`、`logs/`。部署方的改动都写在后者里，升级不会冲掉。

## 4. 服务

| 服务 | 镜像 | 对外端口 | 内存上限 | 说明 |
|---|---|---|---|---|
| web | `scm-web`（`nginx` 稳定版 + 前端文件） | `SCM_HTTP_PORT`，默认 80；HTTPS 模式再加 443 | 64M | 唯一对外的服务 |
| app | `scm-app`（`eclipse-temurin:21-jre` + jar） | 无 | 1.2G | 堆最多用 75% |
| postgres | `postgres:16` | 无 | 不设 | 按 4G 机器调几个参数（`shared_buffers` 512MB 等）；`shm_size` 256MB |
| redis | `redis:7` | 无 | 128M | 有密码；不落盘：里面只有登录态和缓存，丢了大家重新登录一次（架构 §9） |
| backup | `postgres:16`（复用） | 无 | 256M | 每天定时备份，见 §8 |

- 都用 Debian / Ubuntu 系的官方镜像，不用 alpine（架构 §12.1）。
- 都设 `restart: unless-stopped`，服务器重启后自己起来。
- 容器日志滚动：每个 10MB、留 3 个，不会写满磁盘。
- 应用用普通用户（uid 10001）跑，不用 root。
- 上传的文件由 Nginx 直接发（只读挂载 `data/uploads`），不经过 Java：快，也不占应用的线程。文件名是随机的、内容不会变，可以让浏览器缓存 30 天。

## 5. 配置和密钥

`.env` 里的项：

| 项 | 默认 | 说明 |
|---|---|---|
| `SCM_VERSION` | 包的版本 | 升级脚本改它 |
| `SCM_HTTP_PORT`、`SCM_HTTPS_PORT` | 80、443 | |
| `SCM_WEB_MODE` | `http` | `https`：用 `certs/` 里的证书（§7） |
| `POSTGRES_PASSWORD`、`REDIS_PASSWORD`、`JWT_SECRET` | 安装时随机生成 | |
| `INIT_ADMIN_PASSWORD` | 安装时随机生成 | 第一次启动时用它建 admin |
| `BACKUP_TIME`、`BACKUP_KEEP_DAYS` | `02:30`、`7` | |

- 密钥只在 `.env` 里，`chmod 600`，不进仓库、不写进手册。
- **安装脚本不在屏幕上打印初始密码**，只告诉部署人员去 `.env` 里看。远程协助时屏幕是共享的，打印出来我们这边就看到了，录屏里也会有。部署人员登录后马上改掉（RFC 001 §7 的自己改密码）。

## 6. 镜像怎么打

在我们的 Mac 上执行 `deploy/build-package.sh [--full]`：

1. 检查：工作区干净、本机 Docker 在跑。
2. `mvn verify`：单元测试和集成测试都跑。
3. `pnpm build`。
4. 按服务器的 CPU 架构打镜像：`docker buildx build --platform linux/amd64`。完整包同样按这个架构拉 `postgres:16`、`redis:7`。
5. 起一次应用，导出 `openapi.json`（生产环境关了 Swagger，接口文档随包给）。
6. `docker save` 出镜像，连同 `deploy/package/` 下的文件打成 `dist/scm-<版本>.tar.gz`，附 sha256 校验值。

仓库里的样子：

```
deploy/
├── build-package.sh
├── app.Dockerfile
├── web.Dockerfile
└── package/            原样进包：compose.yml、env.example、nginx/、scripts/、部署手册.md
```

现在 `deploy/` 下面给旧服务器写的 `deploy.sh`、`server-init.sh`、`docker-compose.app.yml` 删掉，`Dockerfile`、`nginx.conf` 按上面重写。本机的 `deploy.local`（gitignore）不再用。

## 7. Nginx 和 HTTPS

三种接法，手册里各写一节：

| 情况 | 怎么做 |
|---|---|
| 前面已经有入口（云负载均衡、公司网关）负责 HTTPS | 默认的 `http` 模式；入口转发到 `SCM_HTTP_PORT`。把入口的 IP 写进 `nginx/trusted-proxies.conf`，Nginx 才会从它传来的头里取用户的真实 IP |
| 没有入口，证书直接放这台机器上 | `SCM_WEB_MODE=https`，证书放 `certs/fullchain.pem`、`certs/privkey.pem`；80 端口自动跳 443 |
| 只在内网用，或试用期 | `http` 模式，用云安全组限制只有公司的 IP 能访问 |

另外几条：

- 上传上限 11MB（Spring 那边 10MB；超了由应用返回"文件太大"，而不是 Nginx 的 413 页面）。
- js、css 文件名带内容哈希，缓存 30 天；`index.html` 不缓存，升级后刷新一下就是新版本。
- **升级时的提示**：应用重启的那几十秒里，`/api` 返回 `{"code": 503, "msg": "系统正在升级或重启，请稍等一分钟再试"}`，而不是"网络错误"。错误码表加一个 503。
- 加两个安全头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`。

## 8. 备份

- **每天一次**：`backup` 服务到 `BACKUP_TIME` 执行 `pg_dump -Fc`，存到 `backups/daily/`，留 `BACKUP_KEEP_DAYS` 天。先写成临时文件，用 `pg_restore --list` 读一遍确认文件完整，再改成正式的名字：备份到一半断了，不会留下一个看起来正常的坏文件。每次的结果追加到 `backups/backup.log`。
- **每次升级前一次**：存到 `backups/pre-upgrade/`，文件名带升级前的版本号，留最近 5 个。备份失败，升级就停下来，不往下走。
- **上传的文件不在本机另做副本**：它们只增不删（RFC 001 §10），本机再复制一份只是多占一倍硬盘。真正要防的是整台机器坏掉，靠异地。
- **异地（部署方必做）**：每天把 `backups/` 和 `data/uploads/` 同步到另一个地方。手册给两种做法：另一台机器用 `rsync` 拉，或者用云厂商的对象存储命令行工具（阿里云 `ossutil`、腾讯云 `coscli`）同步。手册里写清为什么：备份和数据在同一块硬盘上，硬盘坏了一起没。
- **备份停了要有人知道**：应用只读挂载 `backups/`，管理后台加一个接口读最新一份备份的时间和大小。超级管理员的首页顶部显示"最近备份：11-20 02:30"；超过 36 小时没有新备份就标红。没人盯服务器的公司，备份往往是坏了几个月都没人发现。

为什么备份放在容器里，不用服务器的 cron：`docker compose up -d` 起来就有备份，部署方不用另外配；换服务器时整个目录搬走就行。

## 9. 安装、升级、回滚、恢复

### 9.1 安装 `install.sh`

1. 检查：Docker 24 以上、带 compose 插件；CPU 架构和包一致；内存不到 3.5G、空闲硬盘不到 20G 时警告；端口没被占。
2. 把包里的文件复制到安装目录；生成 `.env`（已经有就不动）；建目录，上传和日志目录交给 uid 10001。
3. `docker load` 镜像，`docker compose up -d`。
4. 等 `/api/version` 返回本次的版本号（最多 3 分钟）。迁移在应用启动时执行，版本号对上了说明数据库也好了。
5. 打印访问地址、管理员账号、去哪看初始密码，以及两件必做的事：HTTPS、异地备份。

可以重复执行，已经有的不会覆盖。

### 9.2 升级 `upgrade.sh`

1. 检查新版本号比现在的新。
2. `docker load` 新镜像。
3. 升级前备份（§8），失败就停。
4. 覆盖包里的文件；`.env` 里的 `SCM_VERSION` 改成新版本；`docker compose up -d`（只重建 app 和 web）。
5. 等 `/api/version` 变成新版本。超时就打印最近 100 行日志和回滚办法。
6. 只留最近 3 个版本的镜像。

停机大约一分钟，放在晚上或者甲方不用系统的时候。

### 9.3 回滚

- **应用回滚**：`.env` 里的版本号改回上一个，`docker compose up -d`。前提是迁移只加不改（架构 §12.3）；Flyway 默认忽略库里比代码新的迁移，旧版本能在新的表结构上启动。
- **迁移出了错、数据乱了**：用升级前的备份恢复（下面）。

### 9.4 恢复 `restore.sh <备份文件>`

要输入"恢复"两个字确认。然后：停应用 → 把当前的库再备份一份（以防选错了文件）→ 删库重建 → `pg_restore` → 起应用 → 等版本号。

### 9.5 恢复演练 `check-restore.sh <备份文件>`

把备份恢复到一个临时库，逐张表数行数，和线上的对比（线上只会比备份多，不会少），然后删掉临时库。上线前必须演练一次（`docs/进度.md`"上线前"）：没恢复过的备份不算备份。

### 9.6 忘了管理员密码 `reset-admin-password.sh`

生成一个新的随机密码，用 PostgreSQL 自带的 `pgcrypto` 算出 BCrypt 哈希写进库（和应用用的是同一种哈希），同时启用 admin 账号、清掉登录失败计数；新密码只打印这一次。不需要另起一个应用。

## 10. 日志

- 应用日志：除了容器日志，再写到 `logs/scm.log`，按天滚动，留 30 天，总共不超过 1GB。容器日志只留 30MB，用户隔几天才报问题时已经找不到了。
- 用户发来错误编号（RFC 001 §5.3）：`grep <编号> logs/scm*.log`。
- 加一个 `GET /api/version`，不用登录：返回版本号和打包时间。升级脚本靠它判断新版本起来了没有，页面底部也显示版本号，甲方报问题时说得清是哪个版本。

## 11. 部署手册的目录

1. 准备服务器：配置、系统、装 Docker（用云厂商或清华的镜像源）；云安全组只开 Web 端口。注意 Docker 发布的端口会绕过服务器上的 ufw、firewalld，控制访问要用云安全组。
2. 安装
3. 第一次登录，改掉管理员密码
4. 域名和 HTTPS：三种接法；ICP 备案
5. 异地备份（必做）
6. 每周升级
7. 回滚和恢复
8. 恢复演练
9. 常见问题：端口被占、内存不够、忘了管理员密码、时间不对、上传失败
10. 卸载：`docker compose down`；数据目录要手动删，脚本不替你删

手册写在 `deploy/package/部署手册.md`，进公开仓库，所以里面不出现任何地址和密钥。

## 14. 取舍

| 选了 | 没选 | 为什么 |
|---|---|---|
| 镜像打进安装包 | 推到镜像仓库让甲方拉 | 大陆服务器拉 Docker Hub 大多不通；自建或用云厂商的仓库要开账号、给甲方权限。代价是每周传一两百 MB |
| 备份放容器里 | 服务器 cron | §8 |
| 上传文件不在本机另做副本 | 每天打包 | 只增不删，本机副本防不了硬盘坏，白占空间 |
| 两种 HTTPS 接法都支持 | 只支持一种 | 不知道甲方有没有入口；没有的话证书直接放这台机器上最简单 |
| 数据库不开端口 | 开端口方便连 | 要查数据用 `docker compose exec postgres psql`；开了端口就多一个被扫的口子 |

## 16. 实现记录

**11-05，1c**（8e8699b、fb533f2，合并 3ffc071）：应用这边的 `/api/version`、备份状态接口、生产日志文件、`Clock`（`config/ClockConfig`，全项目只有这一个）；部署包。本机没有 Docker，打镜像、安装、升级、恢复都还没真跑过，下面"2c 要测的"一项项过完才算做完。接口约定没变。和上文不一样、或者上文没写到的：

- Nginx 每次请求时重新解析 app 的地址：`resolver 127.0.0.11 valid=10s`，再写成 `set $app http://app:8080; proxy_pass $app;`。应用重建后 IP 变了，最多 10 秒就能连上。没用 `server app:8080 resolve`，它要 Nginx 1.27.3 以上。
- 升级时的提示：`error_page 502 503 504 =200` 转到一个内部 location，返回 `upgrading.json`。只替换 Nginx 自己产生的错误，应用自己的响应原样转发。error_page 转过去时请求方法会改成 GET，所以 POST 也拿得到这段 JSON。
- `web` 不依赖 `app`：应用重启期间 Nginx 照常在，页面才收得到上面那条提示。
- http / https 两种模式：`extends.file: web-${SCM_WEB_MODE:-http}.yml`，多了 `web-http.yml`、`web-https.yml` 两个文件。改 `.env` 里一个值，端口、配置、证书挂载一起换。
- 备份校验更严：用 `pg_restore --file=/dev/null` 把整个文件读一遍，不用 §8 写的 `--list`。`--list` 只读文件开头的目录，写到一半断掉的文件它也读得通。
- 备份时间按"今天做没做"判断：
  - 关机错过了，开机就补；装好时已经过了备份时间，马上备份一次。
  - 镜像里没有时区数据时改用 `TZ=CST-8`，保证按北京时间。
  - 每天的备份超过保留天数才删，但最新的几份不管多旧都留着。
- 升级和恢复的细节：
  - 升级到同一个版本，等于把文件重新应用一遍（不备份），不报错。
  - 升级时重启 `backup` 容器，让它用上新脚本。
  - 应用镜像留最近 3 个版本，回滚用。
  - 恢复以后重启 Redis，清掉登录态和缓存。
- Redis 的密码从 `REDISCLI_AUTH` 环境变量取，不写进 compose 的启动命令，`docker inspect` 看命令行看不到。启动命令换成了 `sh -c`，镜像的启动脚本不会自动切到 redis 用户，所以加了 `user: redis`。
- 重置管理员密码：
  - 哈希在维护库 `postgres` 里用 pgcrypto 算，不往业务库装扩展。
  - 密码从标准输入传给 psql；这个会话关掉慢查询日志，明文不进日志。
  - 同时启用 admin、补上 admin 角色、删掉登录失败计数。
- 脚本共用的函数放 `lib.sh`：
  - 读 `.env` 只取要的那一项，从不 `source` 它。
  - 用文件锁 `.scm.lock` 防止两个脚本同时跑。
  - 升级前先检查 `.env`（模式、证书、`BACKUP_TIME`），有错就在改动任何东西之前停下。
- 另外多出的：
  - 包里的 `ARCH`：安装和升级时核对服务器的 CPU 架构，对不上直接停。
  - `nginx/site.conf`、`backups/pre-restore/`、`backups/.daily-done`。
- `openapi.json` 去掉了 `servers`：里面只是打包时临时起的本机地址。
- 打包暂时排除 `ScmApplicationTests`：它要用的 `application-local.yaml` 不在 git 里。等 RFC 001 把它改成集成测试（第二阶段 2b）再去掉这个排除。
