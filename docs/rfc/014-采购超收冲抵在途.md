# RFC 014 采购超收冲抵在途

状态：**已定稿**（用户 11-21 照推荐通过），已实现（V53）。11-21 甲方答了 §9 的两条（不同仓库也冲、按下单时间先冲），§2 已照答复改；实现时补了三处规则（§2 末尾"实现时定的三条"）。

对应：PRD §6.6.2 规则 1–3、§6.6.3、§6.6.1 的可用在途、§6.6.7 补货的在途；数据库设计 §12.3；docs/api/03（采购单、待到料）。

## 1. 解决什么

甲方 11-19 提的（用户转述）：

> 采购单 1、采购单 2 各下 1000 条。采购入库一共 1500 条以后：采购单 1 已入库 1050（超入），采购单 2 已入库 450。实际在途只有 500 条，系统显示 550，应该显示 500。

为什么是 550：现在在途一行一行算，未入库 = max(0, 采购数 − 净入库)。采购单 1 多收的 50 只让它自己的未入库变成 0，抵不到采购单 2 上。

要的结果：在途 500。采购单 1 照样显示已入库 1050，采购单 2 照样显示已入库 450。

不做：

- 不同供应商、不同主体、不同品类线之间不冲。
- 先超收、后下的单不冲：新单下的时候，多收的料已经在库存里，算料、补货已经扣过了，再冲就重复算了一遍。
- 钱照各单实际入库的数算。一期不做结算，这里只记一句。

## 2. 规则

**同一组**：同一主体、同一供应商、同一品类线、同一物料 SKU、同一采购单位（换算系数一样）的采购行，交货仓库不管（甲方 11-21：不同仓库的也冲，因为是同一个供应商）。只有同一组的行之间才冲。

不同仓库也冲的后果：多收的料在 A 仓，冲掉的是 B 仓那张单的在途。合计对得上，但按仓库看，B 仓的在途少了、料却在 A 仓，B 仓要用得从 A 仓调拨。采购单详情的冲抵提示里写上是哪个仓库多收的，仓管看得到。

**几个数**（都是采购单位）：

| 名字 | 算法 |
|---|---|
| 净入库 | 已入库 − 已退货（和现在一样） |
| 冲入 | 别的行多收的、冲给这一行的 |
| 冲出 | 这一行多收的、冲给别的行的 |
| 到货 | 净入库 + 冲入 − 冲出 |
| 未入库（在途） | max(0, 采购数 − 到货) |
| 多收 | max(0, 到货 − 采购数) |

**冲**：采购入库单审核过账以后，看这张单入的每一行：还有多收，就冲给同一组里没到齐的行（采购单是已审核或部分到货、未入库 > 0）。先冲下单最早的（采购单的单据日期，甲方 11-21 定），同一天的按采购单号、行号。每行冲到它到齐为止，多收的冲完为止；冲不完的就留着，是普通的超收。

**退回**：反审核入库单、审核退货单以后，如果某一行的到货小于采购数，而它冲出过，就把冲出的从最近一笔往前退回来，退到它重新到齐、或者冲出的退完为止。被退回的那一行未入库又多出来，状态跟着重算（已到齐变回部分到货；已结案的不动）。

**超收上限不变**：每行净入库 ≤ 采购数 × 1.05，冲入不算进去。甲方是按总数看的，两张单合起来最多也只多 5%（2100）。如果冲入也算进上限，供应商按单发货、每单都多几米布的时候，后一张会被拦住。

**状态**（PRD §6.6.2 规则 2 改成按到货算）：每行到货 ≥ 采购数是已到齐；有一行到货 > 0 是部分到货。只靠冲入、自己还没入过库的单也算部分到货，所以不能反审核，要改就先结案、再重下一张。

**实现时定的三条**（11-21，RFC 原文没写到；用户说过"按推荐来"，这里由 Claude 定，都有测试）：

1. **靠冲入到齐的单还能入库**。单 2 冲来 50、自己入了 950 就是已到齐；供应商照单再送 50 来，要能入（上限还是按净入库：1050 − 950 = 100）。已到齐的单只要有一行"有冲入、净入库 < 采购数"，就出"到货入库"按钮，入库也不拦。入了以后，先把冲来的还给多收的那一行（**还回**），单 1 又变回普通的超收。不这样，状态按到货算会把它挡在门外，正是上面"冲入不算进上限"想避免的。
2. **有冲入的行自己又多收了**：先还回冲入，剩下多收的再冲给别的单。按这个顺序，一行不会同时有冲入和冲出，所以退回、还回都只走一步，不会一路连下去，要锁的单就是"这一行冲过的 + 同组没到齐的"，过账前查得出来。锁之前没查到、锁的时候别人刚冲上来的单不在锁里：要退回、还回的冲抵连着这种单就报 1002 让他重试，同组新冒出来没到齐的单不冲给它。
3. **老单多收、当时没单可冲，留着的不冲给以后审核的单**（§1）。这张老单以后再有过账，也只冲这次新到的那部分：退货不冲；反审核退货单回来的那几米是现在才到的，照常冲。还回来的那部分（第 1 条）只冲给多收那一刻（冲抵记录的 `create_time`）以前就审核了的单。

**例子**（同一组两张单，各 1000）：

| 操作 | 单 1 净入库 / 冲出 | 单 2 净入库 / 冲入 | 在途 |
|---|---|---|---|
| 单 1 入 1050 | 1050 / 50 | 0 / 50 | 950 |
| 单 2 入 450 | 1050 / 50 | 450 / 50 | **500** |
| 单 1 退货 30 | 1020 / 20 | 450 / 20 | 530 |
| 单 2 再入 530 | 1020 / 20 | 980 / 20 | 0，两张都到齐 |

## 3. 页面

- **采购单详情**：明细在"已入库、已退货"后面加一列"冲抵"：冲入写 +50、冲出写 −50，鼠标移上去看是和哪张单冲的（"CG… 多收，冲来 50"）。"未入库"按上面的算法。
- **采购单列表**的已入库进度不变，还是净入库。单 1 显示 1050 / 1000，单 2 显示 450 / 1000，和甲方描述的一样。
- **待到料、首页"在途物料"、物料库存的"在途"、补货、算料的可用在途**：都按新的未入库算。
- **操作记录**：两张采购单各记一条："入库单 RK… 多收 50，冲给 CG…"；"CG… 多收，冲来 50"。退回时也记。

## 4. 表结构

实际迁移是 `V53__purchase_over_offset.sql`，比下面多两个检查约束（冲入、冲出不小于 0；不能自己冲给自己）。

```sql
ALTER TABLE pur_order_item
    ADD COLUMN offset_in_qty  NUMERIC(14,3) NOT NULL DEFAULT 0,   -- 冲入，采购单位
    ADD COLUMN offset_out_qty NUMERIC(14,3) NOT NULL DEFAULT 0;   -- 冲出

CREATE TABLE pur_over_offset (            -- 一笔冲抵；退回时改小，退完删掉
    id           BIGSERIAL     PRIMARY KEY,
    from_item_id BIGINT        NOT NULL REFERENCES pur_order_item (id),
    to_item_id   BIGINT        NOT NULL REFERENCES pur_order_item (id),
    qty          NUMERIC(14,3) NOT NULL CHECK (qty > 0),
    create_time  TIMESTAMPTZ   NOT NULL DEFAULT now()
);
CREATE INDEX idx_pur_offset_from ON pur_over_offset (from_item_id);
CREATE INDEX idx_pur_offset_to   ON pur_over_offset (to_item_id);

-- 在途查询、待到料用的部分索引换成按到货算
DROP INDEX idx_pur_item_open;
CREATE INDEX idx_pur_item_open ON pur_order_item (material_sku_id)
    WHERE received_qty - returned_qty + offset_in_qty - offset_out_qty < qty;
```

两列是表里的合计，和表在同一个事务里改。之所以还要存这两列，是因为待到料、在途、列表这些查询都只读一行就能算出未入库，不用每次去汇总冲抵表。集成测试里核对两边对得上。

冲抵只会发生在已审核以后的采购单上，而草稿可以改行、删行，所以外键不会挡住改草稿。

## 5. 代码

实现在：纯函数 `OverOffsetPlan`（退回 → 还回 → 冲），取数、写回、操作记录 `PurchaseOffsetBook`，SQL `PurchaseOffsetMapper`，接进 `PurchaseStockHandler.preparePosting`。下面是当时的计划：

- `PurchaseStockHandler`：
  - 覆盖 `preparePosting`（正反过账都先调它，在库存锁之前）：开头按 id 从小到大一次锁住这张采购单，和同组里会动到的采购单：入库时是没到齐的，反审核、退货时是它冲给过的。
  - `apply` 回写净入库以后，先退回，再冲，再重算这几张单的状态，写操作记录。
  - 冲和退回写成纯函数（输入同组各行的数，输出要改的冲抵），单测直接喂数。
- `PurchaseOrderItem.pending()`、`byArrival`：按到货算。
- `SupplyMapper.selectLines`、`PurchaseOrderMapper.selectPendingRows`：条件和取的列加上冲入、冲出。`SupplyBook.Line` 加两个数：已入的按到货算（多收冲出去的就不算这一行占着的库存了），没到的按新的未入库算。
- 接口：采购单详情的明细加 `offsetInQty`、`offsetOutQty`、`offsets`（`[{ direction: 'IN' | 'OUT', purchaseOrderId, purchaseNo, qty }]`）。待到料、入库单带出的未入库换成新算法，上限不变。先改 docs/api/03 和 `web/src/types/purchase.ts`。

## 6. 并发

冲抵要改别的采购单，所以加锁的顺序很要紧：

- 入库、退货过账时，一次按 id 顺序把要动的采购单都锁上。两张入库单互相冲，也是按同一个顺序排队，不会互相等。过账之前不能先单独锁这一张：由采购单"入库并过账"（`fromSource` 带 `post`）原来建完单先 `check` 锁住这一张，现在马上过账的不先查，过账里锁齐了再查。
- 算料单确认时按 id 顺序共享锁采购单（现有）。两边都按 id 顺序加锁，所以不会成环。
- 万一还是碰上数据库判了死锁，现在会报 500。这次在 `GlobalExceptionHandler` 里改成 1002"有人同时在改，请重试"（按 SQLState 40P01 认，`GlobalExceptionHandlerIT` 真造了一次死锁验证）。

## 7. 取舍

- **入库时拦住，多出来的让仓管入到另一张单上**：改动最小，在途自然就对了。但仓管要把一张送货单拆成两张入库单，数和送货单对不上；甲方的描述里采购单 1 也是照样记 1050。所以没选。
- **不存冲抵，查询时按组现算**：分不出"超收的时候这张单已经下了"还是"超收以后才下的"。这样老单多收的会冲掉新单的在途，而新单下的时候已经扣过这些库存了。所以没选。
- **冲入也算进超收上限**：见 §2。

## 8. 测试点

1. §2 的例子一步步走：在途 950 → 500 → 530 → 0。物料库存页的在途、待到料、算料的可用在途都对得上。
2. 反审核单 1 那张 1050 的入库单：冲抵退回，单 2 未入库回到 550。
3. 单 2 已到齐以后被退回：变回部分到货。单 2 结案了再被退回：还是已结案。
4. 不同供应商、不同主体、不同采购单位的不冲；不同仓库的照冲（多收在 A 仓，冲掉 B 仓单的在途）；超收以后才审核的单不冲。
5. 算料单用了单 2 的 550 在途：冲来的 50 算已到（占着库存），可用在途 500。
6. 集成测试：两张入库单同时过账、互相冲，都成功，数对得上；冲抵表的合计和两列一致。
7. 先冲哪张：同组三张没到齐的单，单据日期 11-10、11-12、11-12，多收的先冲 11-10 那张，再按单号冲 11-12 的两张。
8. §2 实现时定的三条：靠冲入到齐的单还能入库、入了先还回；有冲入的行自己又多收，先还回再冲；老单留着的多收不冲给以后审核的单、还回的只冲给多收以前审核的。

测试在 `OverOffsetPlanTest`（1–4、7、8、最近一笔先退、还回再冲两跳后还按原来的多收时间卡）、`SupplyBookTest`（5）、`PurchaseStockHandlerTest`（已到齐靠冲入的能入）、`PurchaseIT`（1 不同仓库、2、8 第 1 条、6；6 在本机连跑 20 遍都过）。
