## 0. 怎么读

- §1 全局约定：类型、公共列、状态和字典、索引外键、TRADE 留口子、敏感字段、文件、领猫附加属性。后面每张表不再重复。

- §2 表清单，按业务域分组，标分期和现状。

- §3–§19 按业务域逐表写：用途、字段、索引约束、和别的表的关系。字段表里写"公共列：主数据 / 单头 / 明细 / 只插"的一行，代表 §1.2 的一组列，不逐列重复。

- 说明里的来源写法：「PRD §x」是需求；「原型 xxx」是 `docs/原型/src/` 里的字段名；「领猫 xxx」是领猫导出表的列名；「架构 §x」「RFC 001 §x」是技术文档。标「新加」的是 PRD 和架构里没有、这次为了承接领猫数据或甲方 BOM 表加的。

- 附录 A：领猫导出表逐列对照。附录 B：BOM 成本拆分表怎么落到资料包。附录 C：自己拍板的取舍、和 PRD / 架构对不上的地方、要甲方确认的点。

## 1. 全局约定

### 1.1 类型

| 用途 | 类型 | Java | 说明 |
|---|---|---|---|

| 物料数量 | `NUMERIC(14,3)` | BigDecimal | 米、码、公斤，最多 3 位小数（PRD §5.3）。库存、出入库、采购、算料、安全库存都用它 |

### 1.2 公共列

**主数据公共列**（字段表里写"公共列：主数据"）：

| 列名 | 类型 | 非空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT IDENTITY | 是 | | 主键 |
| create_by | BIGINT | | | 创建人 `sys_user.id`，自动填（RFC 001 §4 补上）；不加外键 |
| create_time | TIMESTAMPTZ | 是 | now() | |
| update_by | BIGINT | | | 最后修改人，自动填 |
| update_time | TIMESTAMPTZ | 是 | now() | |
| deleted | BOOLEAN | 是 | false | 逻辑删除。被单据用过的主数据不能删，只能停用（PRD §5.6） |

**单头公共列**（"公共列：单头"）= 主数据公共列，再加：

| 列名 | 类型 | 非空 | 默认 | 说明 |
|---|---|---|---|---|
| no | VARCHAR(32) | 是 | | 单号：前缀 + yyyyMMdd + 4 位流水（PRD §5.2）。全表唯一，不带 deleted 条件，作废、删除的号也不再用（架构 §4.1） |
| company_id | BIGINT | 是 | | 主体公司 → `bas_company`；默认取制单人的默认主体；一期只记不隔离（PRD §5.7、Q13） |
| status | VARCHAR(16) | 是 | 'DRAFT' | 取值见各表 |
| audit_by | BIGINT | | | 审核人；多级审批时是最后一级，各级见 `biz_approval_step` |
| audit_time | TIMESTAMPTZ | | | 审核时间 |
| version | INT | 是 | 0 | 乐观锁：保存草稿和每个状态动作都 +1（架构 §4.3） |
| remark | VARCHAR(500) | | | 备注 |

status、audit_by、audit_time、version，以及各表里"由动作改"的列（累计数、承诺交期、预计交期等，说明里写"动作改"）在实体上标 `@TableField(updateStrategy = FieldStrategy.NEVER)`，普通保存永远写不到它们（架构 §4.3、RFC 001 §4）。

**明细公共列**（"公共列：明细"）：

| 列名 | 类型 | 非空 | 默认 | 说明 |
|---|---|---|---|---|
| id | BIGINT IDENTITY | 是 | | 主键 |
| <单头>_id | BIGINT | 是 | | 单头外键，建索引 |
| seq | INT | 是 | | 行号，从 1 起 |

明细没有审计列和 deleted：草稿保存整单覆盖，审核后不再变（架构 §4.1）。审核后由动作改的列（累计数、预计到货）在单头的操作记录里留痕。

**只插表公共列**（"公共列：只插"）：id、create_by、create_time。只插不改的表用（库存日志、价格档案、报工记录）。

**关联表**（多对多）：两个外键作联合主键，没有审计列，整批删了重插（沿用 V5 `sys_user_role`）。

### 1.3 状态、枚举、字典

- **状态**存英文枚举名，`VARCHAR(16)`，不用 PostgreSQL 的 ENUM、不加 CHECK：以后加状态不用改类型、删约束（架构 §4.2）。合法性由 Java 枚举和转换表 `StatusFlow` 保证。

- **单据通用状态**（架构 §4.2）：`DRAFT` 草稿 → `PENDING` 待审核 → `APPROVED` 已审核 → `RUNNING` 执行中 → `DONE` 已完成；另有 `CLOSED` 已结案、`VOIDED` 已作废。各单据只用其中一部分，页面按单据类型显示中文（采购单的 RUNNING 显示"部分到货"）。资料包、算料单、供应商、异常、合同各有自己的枚举，各表里写。

- **启用停用**：只有两种状态的主数据（颜色、仓库、物料……）用 `status SMALLINT`，1 启用 0 停用，和已有的 sys 表一个写法。

- **枚举还是字典**（拍板）：代码要按它分支的值用 Java 枚举（`VARCHAR(16)` 或 `VARCHAR(32)`），页面上不能增删；只用来分类、显示、筛选的用字典（`sys_dict_*`），甲方能自己增改。
  - 枚举：所有状态；BOM 物料来源；配料方式；用量方式；资料包阶段；仓库类型；采购类型；出入库类型；物权；责任方；价格类型；订单来源；数据范围。
  - 字典：其余的，预置值见 §3.2。
  - 中间情况：字典里有代码要认的值（生产节点的"裁剪"、订单类型的"客户订单"、供应商分类的"成衣厂""加工厂"），这几项在 `sys_dict_data` 上标 `builtin = true`：value 不能改、不能删，label 甲方能改（§3.2）。加工方式按 PRD §6.1.7 做字典，价格档案按它的 value 区分加工价。

- 业务表存字典的 **value**，不存 label：label 改了不影响历史数据。

### 1.4 索引、唯一、外键

- **唯一**：编码类用部分唯一索引 `WHERE deleted = false`；单号全表唯一；业务唯一（同款同阶段只有一个已生效、一家供应商只有一份待批改动）用 `WHERE status = ...`（架构 §6）。可空列参与唯一时用 `COALESCE` 表达式索引，因为唯一索引里 NULL 和 NULL 不算重复。

- **外键**：都加，不级联（默认 RESTRICT），外键列都建索引（架构 §6）。各表"关系"一节列出。例外：
  - `create_by`、`update_by`、`audit_by` 这类审计人不加外键，沿用 V1–V7。
  - 用"类型 + id"指向多种单据的列（`biz_doc_log` 的 doc_type + doc_id、出入库单的源单、合同的源单）没法加外键，靠"只有对应域的 Service 会写"保证（RFC 001 §14）。

- **跨域外键**：表上可以指向别的域的表（物料的默认供应商、仓库的工厂），Java 里照样只调对方的 Service（架构 §3.1）。

- **命名**：`uk_<表>_<列>` 唯一索引，`idx_<表>_<列>` 普通索引。

### 1.5 TRADE 留口子

贸易代工收起来，表结构留口子（PRD §2.6、架构 §14.4）。建这些表时一起建，一期的值固定：

| 位置 | 列 | 一期的值 |
|---|---|---|
| `bas_customer` | 整张表 | 空表 |
| `ord_order` | customer_id、customer_order_no | 空 |
| `sty_style`、`dev_sample` | customer_id、customer_style_no | 空 |
| `pur_order_item`、`inv_doc_item`、`inv_stock`、`inv_stock_log`、`mrp_calc_item` | owner_type、owner_id | `'OWN'`、0 |
| `inv_doc` | customer_id（客供入库） | 空 |
| 保留值 | 订单类型 `CUSTOMER`、款式来源 `CUSTOMER_SAMPLE`、BOM 物料来源 `CUSTOMER_SUPPLIED`、出入库类型 `CUSTOMER_IN`、物权 `CUSTOMER`、责任方 `CUSTOMER` | 开关关着时后端拒收，下拉里滤掉 |

物权用 `owner_type + owner_id` 两列，自有时 owner_id 存 0 不存 NULL：库存的唯一键里有物权，NULL 和 NULL 不算重复会多出行（架构 §5.1）。

### 1.7 文件和图片

上传的文件不进库：`/api/files` 存盘，返回地址（已有）。库里只存引用，三种放法：

- **挂在一条记录上的附件和图片**进 `biz_attachment`（doc_type + doc_id + category + sort）：款式图、物料图、样衣图、报工照片、异常照片、回货照片、评审照片、合同签回件、各单据的附件。同一条记录 category = IMAGE、sort 最小的是主图（PRD §5.8）。PRD §7.2 的 `sty_style_image` 因此不建。

- **文件本身有属性的**，在自己的表里存 `file_url`：供应商证照（类型、有效期）、合同模板版本、生成的合同。

- **整单覆盖保存的明细行上的图**（工序图示）：明细行每次保存会换 id，挂不了 `biz_attachment`，所以单独一张 `tp_process_image`，跟着工序行一起覆盖。

### 1.8 领猫附加属性 `legacy_attrs`

`bas_material`、`sup_supplier`、`sty_style` 各有一列 `legacy_attrs JSONB`：领猫里有、我们没有对应列的**描述性**属性（面料功能、经缩纬缩、产地、领猫自定义列 Att01–10……），导入时按 `{"领猫列名": "值"}` 原样存一份，详情页只读显示，不参与任何规则。

- 为什么用 JSONB：这是导入那一刻领猫数据的快照，符合架构 §6"JSONB 只用于快照"；不为几十个没有规则用到的属性各开一列，也不把它们塞进备注。
- 只放描述性的：有规则要用的（损耗、最小库存、默认供应商）都有正经列；敏感的（银行账号）不放；冗余的（供应商电话在物料表里又出现一次）、系统列（领猫的操作人、操作时间）不放。
- 以后某个属性真要参与规则（比如来料检验要用卷重），再加正经列，把值从 JSONB 搬过去，一个一次性脚本。

## 附录 A：领猫导出表逐列对照

三份文件都在 `docs/原型/`，文件名带领猫租户号，这里分别叫"供应商管理导出表""物料信息导出表""BOM 成本拆分表"。这里只写列名和去向，不抄任何值。

**导入时通用的规则**：

- 编码类、账号类、电话类的单元格**按文本读原值**。领猫导出的账号是数字单元格，位数超过 Excel 的 15 位精度：甲方在 Excel 里打开再另存，后几位会变成 0。导入说明里要写清楚"导出后不要在 Excel 里另存"，导入程序读 xlsx 里存的原始字符串。
- 数字列的 0 当空（领猫没填时导出 0，如 SKU 成本价、起订量、门幅）。
- 字典类的列（结算方式、单位、季节、物料类型……）按 label 匹配字典；匹配不上的整批报错，列出值，先在字典里加或在模板里改。季节去掉"季"字再匹配（"夏季"→"夏"）。
- 去向写"丢弃"的，都说了原因；写"`legacy_attrs`"的进那条记录的领猫附加属性（§1.8），**有值才存**。
- 领猫的系统列（创建人、创建时间、操作人、操作时间、最后操作人、最后操作时间）一律丢弃：我们的审计列记导入人、导入时间；领猫的历史不迁（PRD §10）。

## 附录 B：BOM 成本拆分表怎么落到资料包

甲方给的是一个款的 BOM 成本表（Excel，一张表）。拿它逐行核对资料包的表能不能装下，结论：**都装得下**，要加的是"随尺码配料"、含税含运两个标记、"其他费用"一张表；损耗要从系数换成百分数。

### B.1 表的结构

| 部分 | 内容 | 落到哪 |
|---|---|---|
| 标题行 | 款名 + "BOM 表" | 资料包本身（`tp_tech_pack` → 款式） |
| 面料块 | A 料（面料）、B 料（里料，规格写"定制"）两行，下面一行"小计" | 两行 `tp_bom_item`；小计现算 |
| 辅料块 | 编号 1 起约 27 行，第 2 列都写"辅料"；其中一种拉链合并了三行（三个长度三个价） | 每行一条 `tp_bom_item`；拉链见 B.3 |
| 汇总 | 材料成本（面料 = A + B 小计；辅料&耗材 = 辅料合计）、制造成本（加工费，手填）、快递运费（空）、合计 | 现算 + `tp_cost_item`，见 B.6 |

### B.2 逐列对照

| BOM 表的列 | 落到哪 | 怎么转 |
|---|---|---|
| 项目 | `tp_bom_item.seq` | A 料、B 料、辅料编号只是排序；部位（`part`）表里没有，录入时选，面料默认"大身"、里料默认"里布" |
| 第 2 列（面料 / 里料 / 辅料） | 物料的 `material_type` | 不存在 BOM 行上；成本汇总按物料类型分组（B.6） |
| 物料名称 | `tp_bom_item.material_id` | 按名称找物料档案；没有的先建物料（PRD §10：BOM 不导入，手工建） |
| 规格 | `bas_material_sku.spec` | 真规格（长度、宽度、型号）建成 SKU 的规格；描述性的文字放 BOM 行 `remark` |
| 色号/颜色 | `sku_mode` + `tp_bom_item_sku` | 写成"颜色1/颜色2"的 = 跟着款色走 → `BY_COLOR`，每个款色配一个 SKU；写"/"的 = 不分颜色 → `FIXED`，选无色 SKU；写一个颜色的 → `FIXED`；文字里夹着供应商色号的 → 色号进 `bas_material_sku.supplier_color_no` |
| 价格/含税 | `tp_bom_item.ref_price` 或 `tp_bom_item_sku.ref_price` | 元 / 用量单位，就是我们的"元 / 库存单位"；同一行不同 SKU 不同价的写在配料行上 |
| 单位 | `tp_bom_item.unit` | 必须等于物料的库存单位（PRD §5.3），见 B.5 |
| 单件用量 | `usage_qty` 或 `tp_bom_item_size` | 统一用量直接填；纸箱写的是"1 / 每箱件数"，按 6 位小数存（§1.1）。二期有了 `tp_label.pcs_per_carton` 可以由它算 |
| 损耗 | `tp_bom_item.loss_pct` | 表里是系数（1 + 损耗率），换成百分数：`(系数 − 1) × 100`，见 B.4 |
| 总单耗 | 不存 | = 用量 ×（1 + 损耗%），现算 |
| 预估价 | 不存 | = 单价 × 总单耗，就是我们的"单件成本"，现算 |
| 工厂 | `tp_bom_item.supplier_id` | **这一列写的是物料供应商，不是加工厂**。一格里写了两家的，第一家进 `supplier_id`，另一家写进 `remark`，两家的价都可以录进价格档案；空的取物料的默认供应商 |
| 备注 | `price_tax_included`、`price_freight_included`、`remark` | "含税运" → 两个都 true；"含运不含税" → 含税 false、含运 true；其他文字进 `remark` |

### B.3 一种拉链三个长度三个价

表里有一种拉链合并了三行：三个长度、三个价，只有中间一行算进了预估价——也就是只按基码算单件成本。

落法：这一行 `sku_mode = BY_SIZE`（随尺码），拉链物料建三个 SKU（规格 = 三个长度），`tp_bom_item_sku` 每个尺码一条，指向对应长度的 SKU，`ref_price` 写各自的价。单件成本按尺码组的基码（`bas_size_group.base_size`）取那条配料的价，和表里"只算中间一行"一致；算料时每个尺码按自己的 SKU 出需求，三种长度分开采购。

表里没写哪个尺码配哪个长度，录入时要问清楚（附录 C.3）。

PRD 原来只有"固定"和"随款色"两种配料方式，装不下这一行，所以加了 `BY_SIZE`；拉链颜色又跟款色走时用 `BY_COLOR_SIZE`。

### B.4 损耗、含税、含运的口径

- **损耗**：一律存百分数（`loss_pct`，3 表示 3%），和架构 §6 一致，页面上也这么填。甲方表里是系数（1 + 损耗率）：手工录入时页面提示"填百分数，不填系数"；以后做 BOM 导入，模板表头写"损耗率（%）"，导入程序遇到 1 到 2 之间的值按系数换算并在结果里提示。领猫物料表里的"默认损耗"口径待确认（附录 C.3）。
- **含税、含运**：表头写"价格/含税"，但备注列里有"含运不含税"的行，说明同一张表里价格口径不统一。所以 BOM 行、价格档案、采购单都带 `tax_included` 和 `freight_included` 两个标记（BOM 行上叫 `price_tax_included`、`price_freight_included`），记下"这个价是什么口径"。单件成本一期直接按录入的价加总、不换算口径；口径不一样的行在页面上标出来。按统一口径（如不含税）折算放到核价（M05）做。

### B.5 单位

表里用到的单位有米、厘米、张、个、套、根、颗，还有写"-"的。

- 根、颗、厘米不在 PRD §6.1.7 的单位字典里，字典预置时加上（§3.2）。
- BOM 的用量单位就是物料的库存单位，不在 BOM 行上另选单位（PRD §5.3）。物料按米采购和管库存、表里写厘米的（如松紧带、织带），建物料时库存单位定成米，录入时用量 ÷ 100、单价 × 100；真按厘米管库存的，库存单位就定厘米。
- 写"-"的是没填，录入时按物料的库存单位。

### B.6 成本汇总

| 汇总项 | 怎么算 | 数据在哪 |
|---|---|---|
| 材料成本 · 面料 | 物料类型是 `FABRIC` 面料、`LINING` 里料的行的单件成本之和（= 表里 A + B 小计） | `tp_bom_item` + `bas_material.material_type`（字典内置项，§3.2） |
| 材料成本 · 辅料&耗材 | 其余物料类型（辅料、包材、标签吊牌……）的行之和 | 同上 |
| 制造成本 · 加工费 | `tp_cost_item` 里 `cost_type = PROCESS` 的金额；新建时默认 = 工艺单工价合计，可改 | `tp_cost_item`、`tp_process` |
| 快递运费等 | `tp_cost_item` 的其他行 | `tp_cost_item` |
| 合计 | 材料成本 + 其他费用 | 现算 |

单件成本按基码用量算（PRD §6.4.2）；随款色的行各款色单价可能不同，汇总按页面上选的款色算，默认第一个颜色。"物料来源 = 工厂自备"的行照样算进材料成本（包工包料时含在加工价里，页面上可以勾掉）。

这就是"估一件大概多少钱"，在资料包里看，研发 BOM、生产 BOM 都有。管理费、税点、报价这些核价的东西不在资料包里，留给 M05（§17.2 `cst_costing`）。

### B.7 要不要导入 BOM

PRD §10 说 BOM 不提供导入、"每款十几行"手工建。甲方这张表实际约 30 行物料，加上配色、分码，手工建一款要花一些时间。默认仍按 PRD 不做导入（一期时间紧，BOM 格式各款不统一，规格、颜色列是自由文字，自动识别不可靠）；上面的对照已经证明表结构装得下，甲方要导入时按 B.2 做模板。是否需要，问甲方（附录 C.3）。
