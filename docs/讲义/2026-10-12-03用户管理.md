## 2. 为什么这么设计

### 2.1 接口

| 接口 | 干什么 |
|---|---|
| `GET /api/users?page=1&size=20&username=zhang&status=1` | 分页查询。用户名模糊搜，状态精确筛 |
| `GET /api/users/{id}` | 详情 |
| `POST /api/users` | 新增，返回新 id |
| `PUT /api/users/{id}` | 修改昵称、手机号、状态 |
| `DELETE /api/users/{id}` | 删除（逻辑删除） |
| `POST /api/users/{id}/reset-password` | 重置密码 |

和字典类型的五个接口是同一个套路，多了一个**动作接口** `reset-password`。

**为什么重置密码单独一个接口，不放进 PUT**：

- **频率和风险不一样**：改昵称是日常操作，改密码是敏感操作。分开以后，05 做权限时可以只让一部分人能重置密码
- **PUT 不用每次都带密码**：如果密码也在 PUT 里，前端改个昵称也得把密码传过来，可前端根本拿不到旧密码（我们从不返回它）
- 按 [架构设计 §7](../docs/架构设计.md) 的约定，"动作"用 `POST /资源/{id}/动作名`，和以后的 `POST /api/purchase-orders/{id}/audit`（审核采购单）一个写法

**为什么用户名不能改**：用户名是登录用的身份。改了以后，这个人用旧用户名登录不上；操作日志里记的也是旧名字，对不上了。要改就删掉重建。

### 2.2 入参：为什么拆成三个类，不像字典那样只用一个 SaveReq

| 类 | 用在 | 字段 |
|---|---|---|
| `UserCreateReq` | 新增 | username、password、nickname、phone |
| `UserUpdateReq` | 修改 | nickname、phone、status |
| `UserPasswordReq` | 重置密码 | password |

字典的新增和修改，字段和校验规则完全一样，所以共用一个 SaveReq。用户不一样：

- 新增要 username 和 password，修改**不能有**（用户名不能改，密码走单独的接口）
- 如果共用一个类，就只能把 password 写成"可以为空"，新增时再在 Service 里手动检查"新增必须有密码"。校验就从注解里跑到了代码里，前端看 Swagger 也看不出来新增时密码是必填的

**判断标准**：新增和修改的字段、校验规则一样，就共用；不一样，就拆开。

### 2.3 出参：用 `UserVO` 挑字段，不在实体上隐藏 password

要让 password 不出现在返回的 JSON 里，有两种做法：

| 做法 | 写法 | 新加一个敏感字段时 |
|---|---|---|
| **白名单**：专门的 VO，只挑要给前端的字段 | `record UserVO(id, username, nickname, phone, status, createTime)` | 不在 VO 里写，就**自动不会**出去 |
| **黑名单**：直接返回实体，在 password 上贴 `@JsonIgnore` | `@JsonIgnore private String password;` | **要记得**再贴一个 `@JsonIgnore`，忘了就泄露 |

我们选白名单。以后 sys_user 表要是加了身份证号、最后登录 IP，什么都不用做，它们也不会出现在接口里。默认安全，比靠人记住要可靠。

02 下 的 `UserInfoVO` 也是这个思路。两个 VO 字段不同：`/me` 是给页面右上角用的，只要三个字段；用户管理的列表要显示手机号、状态、创建时间。

### 2.4 新增时为什么不用 `BeanUtils.copyProperties`

字典的新增是 `BeanUtils.copyProperties(req, entity)`，一行就把同名字段都复制过去了。用户的新增，我们一个字段一个字段地 set：

```java
user.setUsername(req.getUsername());
user.setPassword(passwordEncoder.encode(req.getPassword()));
user.setNickname(req.getNickname());
user.setPhone(req.getPhone());
```

**因为 req 里的 password 是明文**。copyProperties 会把明文原样复制到实体上，之后只要哪一次忘了用加密后的值覆盖，**明文就存进了库**。

我在副本里故意把这四行换成 copyProperties，跑测试，`create_ok_savesEncodedPassword` 当场变红：

```
expected: "encoded-123456"
 but was: "123456"
```

这就是那个测试存在的意义：钉住"存进库的必须是加密后的"这条规矩。

### 2.5 "不能删除自己"：当前用户 id 从 Controller 传进 Service

Service 要知道"现在操作的人是谁"，有两种拿法：

| 做法 | 写法 |
|---|---|
| **A. Controller 传进来** | `userService.delete(id, loginUser.userId())`，Service 的签名是 `delete(Long id, Long currentUserId)` |
| B. Service 自己去读 | Service 里写 `SecurityContextHolder.getContext().getAuthentication()...` |

我们选 A：

- **Service 不依赖 Spring Security**：B 让业务层知道了"登录是用 Spring Security 做的"，以后定时任务这类没有登录用户的地方调它，就会出问题
- **好测**：A 的测试就是 `userService.delete(1L, 1L)`，一行。B 的测试要先往 SecurityContextHolder 里塞一个假的身份，测完还要记得清掉（就像 JwtAuthFilterTest 的 `@AfterEach`）
- **一眼看得出依赖**：看签名就知道这个方法要用当前用户；B 把这件事藏在方法里面

### 2.6 为什么新建 UserService，不往 AuthService 里加

| | AuthService | UserService |
|---|---|---|
| 谁在用 | 每个用户（登录、看自己、退出） | 管理员（管别人） |
| 什么时候会改 | 登录方式变了（加验证码、单点登录） | 用户管理的规则变了 |

两者操作的是同一张表，但**改动的原因不同**，就放在不同的类里。一个类只因为一种原因改动，改起来不容易误伤别的功能。

### 2.7 已知问题（今天不解决）

**一、停用或重置密码以后，他已经拿到的 token 还能用。** 我在副本里试过：

```
李四登录，拿到 token
管理员停用李四                        → code 0
李四重新登录                          → {"code":1000,"msg":"账号已停用"}
李四用停用前拿到的 token 查 /me        → {"code":0,"data":{"id":4,"username":"lisi","nickname":"李四"}}   ← 还能用
李四用停用前拿到的 token 查用户列表     → code 0                                                       ← 还能用
```

原因：过滤器只查"Redis 里有没有这个 jti"，不查用户的状态。这张 token 要等 2 小时过期才失效。要做到"停用立即踢下线"，需要能按用户找到他所有的 jti。我把它记成一个需求，后面作为作业来做。

**二、任何登录了的人都能管理用户**，包括刚刚新增的张三。这要等 05 角色权限。

## 4. 逐个文件

### 4.1 `module/system/dto/UserQuery.java`

```java
package com.lingmao.scm.module.system.dto;

import com.lingmao.scm.common.page.PageQuery;
import lombok.Data;
import lombok.EqualsAndHashCode;

/** 用户列表的查询条件：用户名模糊搜，状态精确筛。空字段表示不筛 */
@Data
@EqualsAndHashCode(callSuper = true)
public class UserQuery extends PageQuery {

    private String username;

    /** 1 启用 0 停用 */
    private Integer status;
}
```

和 `DictTypeQuery` 一个样子：继承 PageQuery 拿到 page、size，再加自己的两个筛选字段。

**status 为什么是 `Integer` 不是 `int`**：前端不传 status 时，`Integer` 是 null，表示"不按状态筛"；`int` 不能是 null，不传就是 0，结果变成"只查停用的"。

### 4.2 `module/system/dto/UserCreateReq.java`

```java
package com.lingmao.scm.module.system.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;
import lombok.Data;

/** 新增用户的入参：比修改多了登录名和初始密码 */
@Data
public class UserCreateReq {

    @NotBlank(message = "用户名不能为空")
    @Pattern(regexp = "^[a-z0-9_]{3,32}$", message = "用户名只能是 3-32 位小写字母、数字、下划线")
    private String username;

    @NotBlank(message = "密码不能为空")
    @Size(min = 6, max = 32, message = "密码长度 6-32")
    private String password;

    @NotBlank(message = "昵称不能为空")
    @Size(max = 64, message = "昵称最长 64")
    private String nickname;

    @Size(max = 20, message = "手机号最长 20")
    private String phone;
}
```

- **`^[a-z0-9_]{3,32}$`**：`^` 和 `$` 表示从头到尾都要符合；`[a-z0-9_]` 是小写字母、数字、下划线中的一个；`{3,32}` 是 3 到 32 个。只允许小写，是为了避免 `Admin` 和 `admin` 被当成两个用户
- **密码最长 32**：BCrypt 最多只能处理 72 个字节。我在副本里试过，80 个字符的密码交给我们这个版本的 BCrypt，直接抛 `IllegalArgumentException: password cannot be more than 72 bytes`，到了全局异常处理器就是 500。在入口限制到 32，这种请求在校验这一步就返回 400 了
- **没有 status**：新用户默认启用。实体上 status 是 null，MyBatis-Plus 插入时会跳过 null 的字段，于是用了表里的默认值 `DEFAULT 1`。第 5 节的 INSERT 语句里确实没有 status 这一列

### 4.3 `module/system/dto/UserUpdateReq.java`

```java
package com.lingmao.scm.module.system.dto;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import lombok.Data;

/** 修改用户的入参：登录名不能改，密码走单独的重置接口 */
@Data
public class UserUpdateReq {

    @NotBlank(message = "昵称不能为空")
    @Size(max = 64, message = "昵称最长 64")
    private String nickname;

    @Size(max = 20, message = "手机号最长 20")
    private String phone;

    @NotNull(message = "状态不能为空")
    @Min(value = 0, message = "状态只能是 0 或 1")
    @Max(value = 1, message = "状态只能是 0 或 1")
    private Integer status;
}
```

- **`@NotNull` 不是 `@NotBlank`**：`@NotBlank` 只能用在字符串上，数字用 `@NotNull`
- **为什么 status 在修改里必填**：修改是"整体替换"，前端把表单里的三个值都传过来。不传 status 就当作不改，会让"前端漏传"和"故意不改"分不清

### 4.5 `module/system/dto/UserVO.java`

```java
package com.lingmao.scm.module.system.dto;

import com.fasterxml.jackson.annotation.JsonFormat;
import com.lingmao.scm.module.system.entity.SysUser;

import java.time.OffsetDateTime;

/** 用户管理列表、详情返回给前端的样子：没有 password 字段 */
public record UserVO(Long id,
                     String username,
                     String nickname,
                     String phone,
                     Integer status,
                     @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "Asia/Shanghai")
                     OffsetDateTime createTime) {

    /** 实体 → VO：一个字段一个字段挑，挑剩下的（密码、删除标记）就不会出去 */
    public static UserVO from(SysUser user) {
        return new UserVO(user.getId(), user.getUsername(), user.getNickname(),
                user.getPhone(), user.getStatus(), user.getCreateTime());
    }
}
```

- **record 的字段上也能贴注解**：`@JsonFormat` 贴在 createTime 上，和 BaseEntity 里的写法一样，返回的是 `"createTime":"2026-10-12 15:24:45"`。我在副本里去掉它试过，返回的是 `"createTime":"2026-10-12T15:24:45.745715+08:00"`，和字典接口返回的时间格式就不一样了
- **`static UserVO from(SysUser user)`**：静态的"转换方法"，名字叫 from，意思是"从实体造一个 VO"。放在 VO 自己身上，以后哪里要转都调它，挑哪些字段只写在这一个地方
- **为什么不叫 `UserInfoVO` 复用 02 下 那个**：见 2.3 最后一段，两个 VO 的用途不同

### 4.6 `module/system/service/UserService.java`

```java
package com.lingmao.scm.module.system.service;

import com.lingmao.scm.common.page.PageResult;
import com.lingmao.scm.module.system.dto.UserCreateReq;
import com.lingmao.scm.module.system.dto.UserQuery;
import com.lingmao.scm.module.system.dto.UserUpdateReq;
import com.lingmao.scm.module.system.dto.UserVO;

/** 用户管理：给管理员用的增删改查。和 AuthService（登录、当前用户）分开 */
public interface UserService {

    PageResult<UserVO> page(UserQuery query);

    UserVO getById(Long id);

    /** 新增用户，返回新 id。用户名已存在抛 BizException */
    Long create(UserCreateReq req);

    void update(Long id, UserUpdateReq req);

    /** 删除用户。currentUserId 是当前登录的人：不能删自己 */
    void delete(Long id, Long currentUserId);

    /** 管理员把某个用户的密码重置成新密码 */
    void resetPassword(Long id, String password);
}
```

**和字典 Service 的不同**：返回的是 `UserVO`，不是实体。字典的实体里没有敏感字段，直接返回没关系；用户的实体有 password，**Service 往外给的东西里就不能有它**。这样不只是 Controller，以后别的模块调 UserService，也拿不到密码。

**`resetPassword(Long id, String password)` 收的是 String，不是 `UserPasswordReq`**：Service 只要一个密码字符串，用不着整个请求对象。将来要是"用户自己改密码"也要调它，传个字符串就行。

### 4.7 `module/system/service/impl/UserServiceImpl.java`

```java
package com.lingmao.scm.module.system.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lingmao.scm.common.exception.BizException;
import com.lingmao.scm.common.page.PageResult;
import com.lingmao.scm.module.system.dto.UserCreateReq;
import com.lingmao.scm.module.system.dto.UserQuery;
import com.lingmao.scm.module.system.dto.UserUpdateReq;
import com.lingmao.scm.module.system.dto.UserVO;
import com.lingmao.scm.module.system.entity.SysUser;
import com.lingmao.scm.module.system.mapper.SysUserMapper;
import com.lingmao.scm.module.system.service.UserService;
import lombok.RequiredArgsConstructor;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.util.Objects;

@Service
@RequiredArgsConstructor
public class UserServiceImpl implements UserService {

    private final SysUserMapper sysUserMapper;
    private final PasswordEncoder passwordEncoder;

    @Override
    public PageResult<UserVO> page(UserQuery query) {
        LambdaQueryWrapper<SysUser> wrapper = new LambdaQueryWrapper<SysUser>()
                .like(StringUtils.hasText(query.getUsername()), SysUser::getUsername, query.getUsername())
                .eq(query.getStatus() != null, SysUser::getStatus, query.getStatus())
                .orderByDesc(SysUser::getId);
        return PageResult.of(sysUserMapper.selectPage(query.toPage(), wrapper).convert(UserVO::from));
    }

    @Override
    public UserVO getById(Long id) {
        return UserVO.from(getEntity(id));
    }

    @Override
    @Transactional
    public Long create(UserCreateReq req) {
        boolean exists = sysUserMapper.exists(new LambdaQueryWrapper<SysUser>()
                .eq(SysUser::getUsername, req.getUsername()));
        if (exists) {
            throw new BizException("用户名已存在: " + req.getUsername());
        }
        SysUser user = new SysUser();
        user.setUsername(req.getUsername());
        user.setPassword(passwordEncoder.encode(req.getPassword()));
        user.setNickname(req.getNickname());
        user.setPhone(req.getPhone());
        sysUserMapper.insert(user);
        return user.getId();
    }

    @Override
    @Transactional
    public void update(Long id, UserUpdateReq req) {
        SysUser user = getEntity(id);
        user.setNickname(req.getNickname());
        user.setPhone(req.getPhone());
        user.setStatus(req.getStatus());
        sysUserMapper.updateById(user);
    }

    @Override
    @Transactional
    public void delete(Long id, Long currentUserId) {
        if (Objects.equals(id, currentUserId)) {
            throw new BizException("不能删除自己");
        }
        getEntity(id);
        sysUserMapper.deleteById(id);
    }

    @Override
    @Transactional
    public void resetPassword(Long id, String password) {
        SysUser user = getEntity(id);
        user.setPassword(passwordEncoder.encode(password));
        sysUserMapper.updateById(user);
    }

    /** 查实体，不存在抛 404。只在本类里用，所以是 private，返回实体不返回 VO */
    private SysUser getEntity(Long id) {
        SysUser user = sysUserMapper.selectById(id);
        if (user == null) {
            throw new BizException(404, "用户不存在: " + id);
        }
        return user;
    }
}
```

**page**

- `.eq(query.getStatus() != null, ...)`：status 是数字，不能用 `StringUtils.hasText`（那是给字符串的），所以直接判断是不是 null
- **`.convert(UserVO::from)`**：今天的新方法。`selectPage` 返回的分页对象里装的是 `SysUser`，`convert` 把里面每一个 SysUser 都用 `UserVO::from` 变成 UserVO，总数不变。这样 `PageResult.of` 拿到的就是装着 UserVO 的分页了
- `UserVO::from` 是方法引用，等于 `user -> UserVO.from(user)`

**create**

- **先查重再插入**：和字典一样。表上还有部分唯一索引 `uk_sys_user_username` 兜底，就算两个请求同时新增 zhangsan，也只有一个能插进去
- **为什么用 `exists` 不用 `selectCount`**：只关心"有没有"，不关心"有几个"，`exists` 读起来更直接。两个发的 SQL 一样，都是 `SELECT COUNT(*)`
- **一个字段一个字段地 set**：见 2.4
- `return user.getId()`：insert 以后，数据库生成的 id 会被回填到 user 上

**update**

- 先 `getEntity(id)`：不存在直接 404，也顺便拿到了旧数据
- 只 set 三个允许修改的字段，username 和 password 一个字都碰不到。因为入参类里根本没有这两个字段（2.2）

**delete**

- **先检查规则，再查库**：`Objects.equals(id, currentUserId)` 不用查库就能判断。第 5 节里"删除自己"的请求，日志里一条 SQL 都没有
- **为什么用 `Objects.equals` 不用 `==`**：两个都是 `Long` 对象。`==` 比的是"是不是同一个对象"。Java 只缓存了 -128 到 127 的 Long，超过这个范围，每次都是新对象。我跑过：

```
Long.valueOf(200) == Long.valueOf(200)   → false
Long.valueOf(100) == Long.valueOf(100)   → true
Objects.equals(200L, 200L)               → true
```

  用 `==` 的话，id 小的时候一切正常，用户多到 128 个以后，"不能删除自己"就悄悄失效了。`Objects.equals` 比的是值
- 然后 `getEntity(id)`：删一个不存在的用户，返回 404，而不是假装成功

**resetPassword**

- 和 create 一样，存的是 `passwordEncoder.encode(password)`

**getEntity**

- 字典里这个方法叫 `getById`，是公开的，因为字典直接返回实体。用户的公开 `getById` 要返回 VO，所以把"查实体 + 404"挪到一个 **private** 方法里，update、delete、resetPassword 都用它

**规则和测试的对照**：

| 规则 | 测试 |
|---|---|
| 用户名重复不能新增 | `create_usernameExists_throwsAndNotInsert` |
| 新增时存的是密文 | `create_ok_savesEncodedPassword` |
| 不能删除自己 | `delete_self_throwsAndNotDelete` |
| 重置密码存的是密文 | `resetPassword_savesEncodedPassword` |

**为什么这么写**

- **`passwordEncoder` 是假的**：`encode("123456")` 返回什么由我们规定，这里叫 `"encoded-123456"`。测试只关心"Service 有没有调用 encode，并把**它的返回值**存进去"，不关心 BCrypt 算出来具体是什么（02 上 已经看过真 BCrypt 了）
- **`ArgumentCaptor<SysUser>`**：02 下 抓过 String，这次抓的是整个 SysUser 对象：insert 收到的那个用户，抓下来看它的 username 和 password。2.4 那个"换成 copyProperties 就变红"，就是这个测试抓到的
- **`any(SysUser.class)`、`any(Long.class)`**：`insert` 和 `deleteById` 在 MyBatis-Plus 里都有好几个同名的版本（insert 一个 / insert 一批，按 id 删 / 按实体删），只写 `any()` 编译器不知道你指的是哪个。写上类型就确定了。字典的测试里也是这么写的
- **`delete_self` 没有任何 `when`**：规则是在查库之前判断的，所以根本不需要规定 Mapper 返回什么。要是有人把检查挪到了 `getEntity(id)` 后面，`selectById` 没被规定，会返回 null，于是抛的是 404 而不是"不能删除自己"，这个测试就会变红
- **`resetPassword` 直接检查 user 对象**：`selectById` 返回的就是我们 new 的这个 user，Service 改的也是它，所以测完直接看 `user.getPassword()`。再用 `verify(...).updateById(user)` 确认这个改过的对象确实被存了

## 6. 🎤 今天的面试题

**问：你们系统里的密码是怎么处理的？**

**答**：三个环节。**存**：新增用户和重置密码时，用 Spring Security 的 BCryptPasswordEncoder 加密后再存，库里是 `$2a$10$` 开头的 60 位哈希，每次加密结果都不一样，因为带了随机盐。新增时我们特意不用 BeanUtils.copyProperties，而是逐个字段赋值，避免把请求里的明文直接复制到实体上；还有一个单元测试用 ArgumentCaptor 抓住 insert 收到的对象，断言存的是 encode 的返回值。**比**：登录时用 `matches(明文, 哈希)`，不解密，也没法解密。**出**：所有返回给前端的用户数据都用专门的 VO，只挑需要的字段，实体里的 password 根本进不了 VO；接口测试里用 `jsonPath(...).doesNotExist()` 钉住这一点。管理员也看不到任何人的密码，忘了只能重置。

**问：为什么重写 equals 就必须重写 hashCode？**（Java 基础必考，[知识图谱](../docs/知识图谱.md) I7）

**答**：HashMap、HashSet 找东西分两步：先用 hashCode 算出在哪个桶里，再在桶里用 equals 比较。约定是"equals 相等的两个对象，hashCode 必须相等"。只重写 equals 的话，两个内容相同的对象 hashCode 不同，会被分到不同的桶里，equals 根本没机会比较。我写了个小例子跑过：

```
只重写 equals：a.equals(b) = true，hashCode 一样吗 = false
  HashSet 里放了 a，contains(b) = false；再 add(b) 后 size = 2
record：c.equals(d) = true，HashSet contains(d) = true；再 add(d) 后 size = 1
```

明明 equals 相等，Set 里却放进了两个。本项目里，实体用 Lombok 的 `@Data` 同时生成 equals 和 hashCode，继承了 BaseEntity 的还要加 `@EqualsAndHashCode(callSuper = true)` 把父类的 id 也算进去；`UserVO`、`LoginUser` 是 record，两个都自动生成。测试里 `assertThat(info).isEqualTo(new UserInfoVO(1L, "admin", null))` 能通过，靠的就是 record 自动生成的 equals。
