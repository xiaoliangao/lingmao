## 2. 为什么这么设计

### 2.1 RBAC：用户 → 角色 → 权限

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
  张三            张三-仓管          仓管          仓管-用户管理       用户管理（system:user:list）
                                                  仓管-系统管理       系统管理（目录）
```

RBAC（Role-Based Access Control，基于角色的权限控制）：**权限不直接给人，给角色；人拿到角色**。公司里有 10 个仓管，加一个新权限，只改"仓管"这一个角色，不用改 10 个人。

两张**关联表**（`sys_user_role`、`sys_role_menu`）只有两列，没有 id、审计字段和逻辑删除。重新分配时"先整批删掉，再整批插入"，最简单，也不会留下垃圾。启动日志里 MyBatis-Plus 会警告：

```
class com.lingmao.scm.module.system.entity.SysUserRole Not found @TableId annotation, Cannot use Mybatis-Plus 'xxById' Method.
```

意思是：这个实体没有主键字段，`selectById`、`deleteById` 这些按 id 的方法用不了。我们本来就只按 user_id、role_id 条件操作，这个警告可以忽略。

### 2.2 菜单和按钮权限放在同一张表

`sys_menu` 的 type：1 目录、2 菜单（一个页面）、3 按钮（页面上的一个操作）。

- **目录、菜单**决定**侧边栏显示什么**：`/me` 返回的 `menus` 就是这个用户能看到的目录和菜单组成的树
- **菜单、按钮**的 `perms`（权限标识，如 `system:user:add`）决定**能调哪些接口**

放一张表的好处：给角色分配权限时，前端显示的就是一棵树，勾"用户管理"下面的"新增"，就是给了 `system:user:add`。一个页面和它上面的按钮天然是父子关系。

### 2.3 后端怎么拦：`@PreAuthorize`

```java
@PostMapping
@PreAuthorize("hasAuthority('system:user:add')")
public R<Long> create(@Valid @RequestBody UserCreateReq req) {
```

- **`hasAuthority('system:user:add')`**：当前请求的身份标签上，有没有这个权限。没有就抛 `AccessDeniedException`，`GlobalExceptionHandler` 新加的一个方法把它变成 `{"code":403,"msg":"没有权限"}`
- **身份标签上的权限从哪来**：`JwtAuthFilter` 认出人以后，调 `PermissionService.loadPermissions(userId)` 查出来，放进 `UsernamePasswordAuthenticationToken` 的第三个参数（02 下 那里一直传的是空列表 `List.of()`，现在填上了）
- **`SecurityConfig` 上加了 `@EnableMethodSecurity`**：不加它，`@PreAuthorize` 就只是一张没人读的标签（[注解速查](../docs/注解速查.md) 第 0 节）
- **前端也会按 perms 隐藏按钮**，但那只是体验；真正挡人的是后端。别人可以绕过页面直接调接口

### 2.4 每个请求都查一次库，不缓存

`JwtAuthFilter` 现在每个请求做三件事：验签、查 Redis 会话、**查库拿权限**。查库这一步是两条 SQL（真实打印）：

```
SELECT id,username,password,... FROM sys_user WHERE id=? AND deleted=false          ← 用户还在不在、停没停用
SELECT DISTINCT m.perms FROM sys_menu m WHERE m.deleted = false AND m.status = 1 AND m.perms IS NOT NULL AND m.perms <> ''
  AND (EXISTS (... r.code = 'admin' ...) OR m.id IN (... sys_role_menu ... sys_user_role ...))
```

| 做法 | 改了权限、停了账号 | 代价 |
|---|---|---|
| **每次查库（我们选的）** | **下一个请求立即生效** | 每个请求多两条 SQL |
| 登录时查一次，存进 Redis 会话 | 要等他重新登录才生效 | 几乎没有 |
| 缓存在 Redis，改权限时删缓存 | 立即生效 | 要在"改用户、改角色、改菜单"每个地方记得删对缓存，漏一处就是权限 bug |

用户只有几十个，两条走索引的小查询在同一台服务器上是 1 毫秒级的，不值得为它背上"删缓存"的复杂度。哪天真慢了，再换第三种（换的时候只改 `PermissionServiceImpl` 一个类）。

### 2.5 超级管理员：角色编码 admin

admin 角色**不在 sys_role_menu 里存任何关联**，SQL 里一个 `EXISTS (... r.code = 'admin' ...)` 就让它拥有所有菜单的权限。以后新加菜单，admin 自动就有，不用记得去分配。

所以 admin 角色不能修改（改了编码就不是超管了）、不能删除、不能分配菜单（`RoleServiceImpl.ensureNotAdmin`）。

**admin 用户怎么拿到 admin 角色**：V5 只建了角色。生产库是空库，执行 V5 的时候还没有 admin 用户。所以由启动时的 `AdminInitializer` 负责：没有 admin 用户就建，admin 还没有超管角色就补上。两步都"先查再做"，重启多少次都不会重复插入。

### 2.6 菜单是一棵树：两条规矩

- **有下级的不能删**（`MenuServiceImpl.delete`）。不然下级就成了"孤儿"，挂在一个不存在的上级下面
- **上级不能是自己或自己的下级**（`ensureNotOwnDescendant`）。不然树会变成环：1 的上级是 3，3 的上级是 2，2 的上级是 1，前端展开时会无限递归。检查办法是从新上级开始一路往上找，找到自己就说明成环了

平铺的菜单怎么变成树，在 `MenuVO.tree`：先按 parentId 分组，再从顶层（parentId = 0）开始，递归地给每个节点挂上下级。

## 7. 🎤 今天的面试题

**问：你们的权限是怎么设计的？**

**答**：RBAC，五张表：用户、角色、菜单，加上用户-角色、角色-菜单两张关联表。菜单表里 type 区分目录、菜单、按钮，菜单和按钮带权限标识，比如 `system:user:add`。登录后前端调 `/me` 拿到角色、权限标识和侧边栏菜单树，用来渲染菜单、隐藏没权限的按钮。后端在每个 Controller 方法上用 `@PreAuthorize("hasAuthority('system:user:add')")` 做最终校验。JWT 过滤器认出人以后，每个请求都从库里查一次他的权限，放进 Spring Security 的 Authentication 里。这样停用账号、改角色权限，下一个请求就生效，不用等 token 过期。代价是每个请求多两条小查询，我们用户量小，不值得引入缓存失效的复杂度。超级管理员用角色编码 admin 识别，SQL 里直接给它所有菜单的权限，新加的菜单不用再分配。

**问：`@PreAuthorize` 是怎么生效的？为什么同一个类里的方法互相调用时，它不生效？**（[知识图谱](../docs/知识图谱.md) I3 Spring 原理）

**答**：`@EnableMethodSecurity` 打开以后，Spring 不会把原始的 Controller 对象直接放进容器，而是放一个**代理对象**。外面的调用先到代理，代理先做权限检查，过了才调用真正的方法。这是 AOP（面向切面编程）的典型用法：权限检查这种"每个方法都要做的事"，不写进业务代码，由代理统一做。正因为检查在代理里，同一个类里 `this.methodB()` 这样的调用不经过代理，methodB 上的 `@PreAuthorize` 就不会执行。`@Transactional` 也是同一个原理、同一个坑：同类内部调用，事务注解不生效。所以我们把权限注解放在 Controller 上，外部请求一定先经过代理。
