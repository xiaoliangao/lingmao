## 1. 今天做什么

做完以后：

```
POST /api/auth/login   {"username":"admin","password":"你的密码"}
→ {"code":0,"data":"eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwian...","msg":"ok"}
```

在整个系统里，登录是所有功能的大门：W2 的菜单、角色、权限，都建立在"知道当前是谁"的基础上。

## 2. 为什么这么设计

### 2.1 认证和授权是两件事

| | 回答的问题 | 本项目在哪做 |
|---|---|---|
| **认证**（Authentication） | 你**是谁**？ | 02 登录（今天、明天） |
| **授权**（Authorization） | 你**能做什么**？ | 05 角色和权限（W2） |

先认证，才能授权。今天只管"你是谁"。

### 2.2 登录以后，后端怎么"记住"你

HTTP 是**无状态**的：每个请求都是独立的，后端不会自动记得"刚才那个人登录过"。所以登录成功后，必须给前端一样东西，让它以后每次请求都带上。常见有两种做法：

| | Session（会话） | JWT（JSON Web Token） |
|---|---|---|
| 登录后给前端什么 | 一个随机编号（session id） | 一个**自带信息**的字符串（里面写着"我是 1 号用户，几点过期"） |
| 后端存什么 | 编号 → 用户信息，存在服务器上 | 什么都不用存，靠签名验真假 |
| 怎么踢人下线 | 删掉服务器上那条记录 | **做不到**：token 没过期之前一直有效 |

本项目的选法（见 [架构设计 §6](../docs/架构设计.md)）是 **JWT + Redis**：

- 用 JWT 当通行证，前端处理起来简单
- 明天再在 Redis 里记一笔"这张 token 还有效"，退出登录时删掉这一笔，补上 JWT"踢不掉人"的短板

今天只做 JWT 这一半。

### 2.3 JWT 长什么样

这是我在副本里真实登录拿到的 token，它用 `.` 分成三段：

```
eyJhbGciOiJIUzI1NiJ9                                         ← 第 1 段：头
.eyJzdWIiOiIyIiwianRpIjoiOWNlMWMy...                          ← 第 2 段：内容
.Mzy8ZumsShF2I0jrX4ojczytG3uGvgfmT9hpJ9kQScE                  ← 第 3 段：签名
```

前两段只是 **Base64 编码**，不是加密，谁都能还原出来。我把它们解码了一下：

```
{"alg":"HS256"}
{"sub":"2","jti":"9ce1c24a-a8f4-4c7f-b3f2-112779a11a22","iat":1791386636,"exp":1791393836}
```

| 字段 | 意思 | 这里的值 |
|---|---|---|
| `alg` | 签名算法 | HS256 |
| `sub` | subject，这张 token 是**谁**的 | 用户 id 2 |
| `jti` | JWT ID，这张 token 自己的**编号** | 一个随机 UUID，明天存 Redis 时用 |
| `iat` | issued at，签发时间 | 2026-10-07 23:23:56 |
| `exp` | expiration，过期时间 | 2026-10-08 01:23:56，两小时后 |

**第 3 段签名**是用一把只有后端知道的**密钥**，对前两段算出来的。有人把内容里的 `"sub":"2"` 改成 `"sub":"1"`，想冒充 1 号用户，签名就对不上了，后端一验就知道是假的。验签明天做。

由此得出两条规矩：

- **token 里不能放秘密**：谁都能解码，绝不能放密码
- **密钥必须保密**：拿到密钥的人能给任何用户签发 token

### 2.4 密码怎么存：BCrypt

数据库里**不能存明文密码**。库一旦泄露，所有用户的密码就全暴露了，很多人还在别的网站用同一个密码。

要存的是密码的**哈希**。哈希是单向的：从密码能算出哈希，从哈希算不回密码。登录时，把用户输入的密码再算一次，看结果对不对得上。

我们用的哈希算法是 **BCrypt**。我在副本里跑了一段演示：

```
第一次 encode("123456") = $2a$10$c57pj4hFBakncnU5vH33jeSCPz.gZgE.9iioJNsY6iByql9RYN89S
第二次 encode("123456") = $2a$10$GrzkWAeDZBo1L708p0a5DeX9ctwKt3KBUzOfG7DTiiEajzO.iiN0G
两次一样吗？ false
matches("123456", 第一次) = true
matches("123456", 第二次) = true
matches("1234567", 第一次) = false
BCrypt 校验一次平均 53 毫秒
SHA-256 算一次平均 0.0004 毫秒
```

从这段输出能看出 BCrypt 的两个特点：

- **同一个密码，每次算出的哈希都不一样**。因为 BCrypt 每次都会随机加一段"盐"（salt），盐就写在哈希里（`$2a$10$` 后面那 22 个字符）。好处是：两个用户密码相同，存在库里的哈希也不同；攻击者也没法提前算好一张"常见密码 → 哈希"的对照表来查
- **故意算得很慢**。53 毫秒对登录的用户来说没感觉，但比 SHA-256 慢了十几万倍。攻击者拿到哈希想暴力猜密码，每猜一次都要付出这个代价。`$2a$10$` 里的 `10` 就是控制慢的程度的参数

所以**比较密码不能自己写 `equals`**，必须用 `passwordEncoder.matches(明文, 哈希)`，让 BCrypt 从哈希里取出盐，再算一遍比对。

BCrypt 的原理 03 用户管理时还会细讲，今天会用就行。

### 2.5 四个取舍

**取舍一：用户名不存在、密码错，返回同一句话"用户名或密码错误"。**

如果分别提示"用户不存在"和"密码错误"，攻击者就能拿一份名单挨个试，哪些用户名在你的系统里存在，一试就知道。之后再集中猜这些账号的密码。统一成一句话，就不泄露这个信息。

**取舍二：初始管理员不写在迁移脚本里，而是应用启动时按配置创建。**

迁移脚本会进 git，W4 还要原样在生产库上执行。如果在里面 `INSERT` 一个 admin，它的密码（就算是哈希）就进了 git，而且开发库、生产库的 admin 密码一模一样。

所以改成：启动时检查"库里有没有 admin"，没有的话，就用配置里的 `INIT_ADMIN_PASSWORD` 创建一个。这个配置放在 `application-local.yaml` 里（不进 git），生产环境放在服务器的 `.env` 里。

**取舍三：今天只引入 Spring Security 里的加密工具 `spring-security-crypto`，不引入整个 Spring Security。**

整个 Spring Security 一引入，它默认会把**所有接口都锁上**：字典接口、Swagger 全部变成 401，连登录接口本身也进不去。哪些接口放行、怎么认 token，这些规则明天一起配。今天先用它的 BCrypt 工具。

**取舍四：JWT 密钥放在配置里，不写死在代码里。**

代码会进 git。密钥写在代码里，等于把"签发任何人 token 的能力"交给了所有能看到仓库的人。

## 4. 逐个文件

### 4.1 `pom.xml`

在 `<properties>` 里加一行版本号：

```xml
<properties>
    <java.version>21</java.version>
    <jjwt.version>0.13.0</jjwt.version>
</properties>
```

在 `<dependencies>` 里、lombok 那个依赖的**上面**，加四个依赖：

```xml
<!-- 密码加密：只引入 Spring Security 里的加密工具（BCrypt），不引入整个安全框架 -->
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-crypto</artifactId>
</dependency>
<!-- JWT：api 是写代码时用的接口；impl（实现）和 jackson（读写 JSON）只在运行时需要 -->
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>${jjwt.version}</version>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-impl</artifactId>
    <version>${jjwt.version}</version>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-jackson</artifactId>
    <version>${jjwt.version}</version>
    <scope>runtime</scope>
</dependency>
```

**为什么这么写**

- **spring-security-crypto 没写版本号**：Spring Boot 替我们管着 Spring 家族所有依赖的版本，彼此保证兼容。jjwt 不是 Spring 家族的，所以要自己写版本。0.13.0 是写讲义时的最新版
- **版本号提到 `<properties>` 里**：三个 jjwt 依赖必须同一个版本，写在一处，升级时只改一个地方
- **`<scope>runtime</scope>`**：编译时只需要 jjwt-api（接口），impl 和 jackson 是运行时才加载的实现。这样写可以防止你在代码里不小心直接用了实现类，以后升级时就不容易出兼容问题
- **jjwt-jackson**：jjwt 需要一个 JSON 库来读写 token 内容。Spring Boot 4 自己用的是 Jackson 3，jjwt 用的是 Jackson 2，两个版本包名不同，可以共存

**改完 pom 要让 IDEA 重新加载**：右上角会冒出一个带 M 和刷新箭头的小按钮（Load Maven Changes），点它，或者按 **⇧⌘I**。不加载的话，下面的代码会到处标红"找不到类"。

### 4.2 `src/main/resources/db/migration/V3__sys_user.sql`

```sql
-- V3：系统用户表。登录要用，用户管理（03）也在这张表上做。

CREATE TABLE sys_user (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username    VARCHAR(64)  NOT NULL,                   -- 登录名，如 admin
    password    VARCHAR(100) NOT NULL,                   -- BCrypt 哈希，不是明文；哈希固定 60 个字符，留点余量
    nickname    VARCHAR(64)  NOT NULL,                   -- 显示名，如 管理员
    phone       VARCHAR(20),
    status      SMALLINT     NOT NULL DEFAULT 1,         -- 1 启用 0 停用
    create_by   BIGINT,
    create_time TIMESTAMPTZ  NOT NULL DEFAULT now(),
    update_by   BIGINT,
    update_time TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted     BOOLEAN      NOT NULL DEFAULT FALSE
);
-- 登录名在未删除的用户里唯一（部分索引，和字典数据同一个道理）
CREATE UNIQUE INDEX uk_sys_user_username ON sys_user (username) WHERE deleted = false;
COMMENT ON TABLE sys_user IS '系统用户';
```

**为什么这么写**

- **password 是 VARCHAR(100)**：BCrypt 的哈希固定 60 个字符，比如上面的 `$2a$10$c57pj4...`。留到 100，以后换算法不用改列
- **username 用部分唯一索引**：和字典数据 value 的道理一样。用户被删除（逻辑删除）以后，同名的用户还能重新建
- **status 默认 1**：新建的用户默认启用
- **为什么不在这里插入 admin**：见 2.5 取舍二
- 字段和 [架构设计 §5](../docs/架构设计.md) 的 sys_user 一致。`dept`（部门）先不建，需求定稿后如果用得上再加 V 几

**提醒**：这个文件只要启动过一次，就**一个字都不能再改**（第一份讲义第 0 节讲过校验和）。敲完先对照检查一遍，再启动。

### 4.3 配置

**`application.yaml`**，在文件最后加：

```yaml
lingmao:
  jwt:
    secret: ${JWT_SECRET}          # 签名密钥，真实值在 application-local.yaml（服务器上在 .env），不进 git
    ttl: 2h                        # token 有效期
  init-admin-password: ${INIT_ADMIN_PASSWORD:}   # 初始管理员密码；库里已有 admin 时不用
```

**`application-local.yaml`**（不进 git 的那个），加两行，**值你自己定**：

```yaml
JWT_SECRET: <在终端执行 openssl rand -base64 32，把输出贴在这里>
INIT_ADMIN_PASSWORD: <你自己定一个管理员密码>
```

在 IDEA 的 Terminal 里执行：

```bash
openssl rand -base64 32
```

它会输出一串 44 个字符的随机字符串，贴到 `JWT_SECRET:` 后面。

**为什么这么写**

- **`${JWT_SECRET}`**：和数据库密码 `${DB_PASSWORD}` 同一个套路。提交到 git 的 application.yaml 里只放占位符，真实值放在不进 git 的地方
- **`${INIT_ADMIN_PASSWORD:}` 末尾的冒号**：意思是"没配置就用空字符串"。admin 已经存在时根本用不到它，不配也不该报错。`JWT_SECRET` 后面没有冒号，因为它必须配，不配就该报错
- **密钥为什么要用 openssl 随机生成**：HS256 要求密钥至少 256 位（32 个字节）。`openssl rand -base64 32` 正好生成 32 个随机字节，再用 Base64 写成文字
- **两个值都只写在 application-local.yaml 里**：别写进讲义、提交信息、聊天记录，任何会被别人看到的地方都不行

**忘了配会怎样**：启动时直接失败，我在副本里试过：

```
Could not resolve placeholder 'JWT_SECRET' in value "${JWT_SECRET}"
Error creating bean with name 'jwtUtil'
```

**密钥太短会怎样**：比如随手写了个 `short-secret`：

```
io.jsonwebtoken.security.WeakKeyException: The specified key byte array is 96 bits which is not secure enough for any JWT HMAC-SHA algorithm.
```

12 个字符只有 96 位，不够 256 位，jjwt 直接拒绝。

### 4.6 `config/PasswordConfig.java`

```java
package com.lingmao.scm.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class PasswordConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

**为什么这么写**

- **`@Configuration` + `@Bean`**：意思是"Spring，启动时请调用这个方法，把返回的对象收进你的容器"。之后哪个类需要 `PasswordEncoder`，在构造器参数里写上它，Spring 就会把这个对象传进去。和 Mapper 被注入到 Service 里是同一个机制，只是 Mapper 由 MyBatis 生成，这个由我们自己 new
- **为什么不在用到的地方直接 `new BCryptPasswordEncoder()`**：今天有两处要用（登录、创建 admin），03 还要用。集中在一处，以后换算法只改这里。测试时也能把它换成假的
- **返回类型写接口 `PasswordEncoder`，不写 `BCryptPasswordEncoder`**：用的人只需要知道"能加密、能比对"，不需要知道背后是哪种算法。和 Controller 只认 Service 接口是同一个道理

**补充讲解（10-08 应你的要求）：一张图看 Bean 从哪来、到哪去**

启动时，Spring 先把下面三样东西放进容器：

```
PasswordConfig.passwordEncoder()   → 调用这个方法，返回的 BCryptPasswordEncoder 对象放进容器
JwtUtil（贴了 @Component）          → new JwtUtil(配置里的密钥, 配置里的 2h)，放进容器
SysUserMapper（贴了 @Mapper）       → MyBatis 生成一个实现对象，放进容器
```

然后，谁的构造器要什么，就从容器里拿什么传进去：

```
new AuthServiceImpl(SysUserMapper, PasswordEncoder, JwtUtil)
new AdminInitializer(SysUserMapper, PasswordEncoder, 配置里的初始密码)
```

几个容易想不通的点：

- **`passwordEncoder()` 这个方法，我们自己从来没调用过**。是 Spring 启动时调用的，而且只调用一次。整个应用里只有**一个** BCryptPasswordEncoder 对象，AuthServiceImpl 和 AdminInitializer 拿到的是同一个
- **Spring 按"类型"找**：AuthServiceImpl 的构造器参数写的是 `PasswordEncoder` 类型，容器里正好有一个这个类型的对象，就传它。跟参数叫什么名字无关
- **为什么不在 BCryptPasswordEncoder 上贴 `@Component`**：它是 Spring Security 的人写的，源码我们改不了。别人写的类想放进容器，就用 `@Configuration` + `@Bean` 这种方式自己 new 一个交给 Spring

**把 `@Bean` 删掉会怎样**，我在副本里试过，启动直接失败：

```
APPLICATION FAILED TO START

Description:

Parameter 1 of constructor in com.lingmao.scm.module.system.AdminInitializer required a bean of type 'org.springframework.security.crypto.password.PasswordEncoder' that could not be found.
```

读法："AdminInitializer 的构造器，第 1 号参数（从 0 开始数，就是第二个参数 `passwordEncoder`），需要一个 PasswordEncoder 类型的 Bean，容器里找不到。"以后看到 `required a bean of type ... that could not be found`，就去查那个类型有没有被放进容器：类上有没有贴 `@Service`、`@Component`，或者有没有对应的 `@Bean`。

### 4.7 `security/JwtUtil.java`

```java
package com.lingmao.scm.security;

import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.io.Decoders;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import javax.crypto.SecretKey;
import java.time.Duration;
import java.time.Instant;
import java.util.Date;
import java.util.UUID;

@Component
public class JwtUtil {

    private final SecretKey key;
    private final Duration ttl;

    public JwtUtil(@Value("${lingmao.jwt.secret}") String secret,
                   @Value("${lingmao.jwt.ttl}") Duration ttl) {
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
        this.ttl = ttl;
    }

    /** 给某个用户签发 token */
    public String createToken(Long userId) {
        Instant now = Instant.now();
        return Jwts.builder()
                .subject(String.valueOf(userId))
                .id(UUID.randomUUID().toString())
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(ttl)))
                .signWith(key)
                .compact();
    }
}
```

**类的开头**

- **`@Component`**：和 `@Service` 一样，告诉 Spring"这是一个要交给你管理的对象"。它不是业务 Service，只是一个工具，所以用更通用的 `@Component`
- **为什么这次自己写构造器，不用 `@RequiredArgsConstructor`**：两个参数要用 `@Value` 从配置里取值，`@Value` 得写在构造器参数上。Lombok 默认不会把 `@Value` 带到它生成的构造器参数上（要另外配置 lombok.config），所以手写最直接。效果和 Lombok 一样，都是构造器注入，字段也是 `final`
- **`@Value("${lingmao.jwt.ttl}") Duration ttl`**：配置里写的是 `2h`，Spring 会自动把它转成 `Duration`（时长）类型。写 `30m`、`7d` 也行

**构造器里那一行**

```java
this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
```

从里往外读：配置里的密钥是 Base64 文字 → `Decoders.BASE64.decode` 还原成 32 个字节 → `Keys.hmacShaKeyFor` 把字节做成 HMAC 签名用的密钥对象（不够 256 位就抛 WeakKeyException，见 4.3）。

为什么放在构造器里做：密钥只需要做一次，应用启动时就做好，之后每次签发直接用。而且配置有问题时，启动就会失败，不会等到有人登录才发现。

**`createToken`**

`Jwts.builder()` 是**建造者**写法：一项一项往上加，最后 `.compact()` 拼成字符串。每一项对应 2.3 那张表的一个字段：

| 代码 | 写进 token 的字段 |
|---|---|
| `.subject(String.valueOf(userId))` | `sub`：这张 token 是谁的。规范要求它是字符串，所以把 Long 转成 String |
| `.id(UUID.randomUUID().toString())` | `jti`：这张 token 的编号。每次登录都不一样，明天用它当 Redis 的 key |
| `.issuedAt(Date.from(now))` | `iat`：签发时间 |
| `.expiration(Date.from(now.plus(ttl)))` | `exp`：过期时间，现在加 2 小时 |
| `.signWith(key)` | 第 3 段签名。jjwt 看密钥的长度和类型，自动选 HS256 |

**今天只有签发，没有验签。** 验签（拿到 token → 验证签名 → 取出用户 id）明天和过滤器一起写。

**补充讲解（10-08 应你的要求）：JwtUtil 一生中的两个时刻**

**时刻一：应用启动时，只发生一次**

```
Spring 读配置：lingmao.jwt.secret = "（你生成的那串）"，lingmao.jwt.ttl = "2h" → 转成 Duration
   ↓
调用构造器 new JwtUtil(secret, ttl)
   ↓
构造器里：Base64 解码 → 做成 SecretKey → 存进 key 字段；ttl 存进 ttl 字段
   ↓
JwtUtil 对象放进容器，等着别人来用
```

配置有问题（没配、太短），**就在这一刻失败**，应用起不来。4.3 那两个报错都是在这一步出的。

**时刻二：每次有人登录时**

```
AuthServiceImpl.login → 用户名密码都对 → jwtUtil.createToken(1L)
   ↓
用启动时就做好的 key 签名，用 ttl 算过期时间 → 返回 token 字符串
```

`key` 和 `ttl` 之所以是字段，就是为了"启动时算一次，之后每次都直接用"。字段写成 `final`，保证启动以后谁也改不了。

**构造器就是一个普通方法，Spring 只是替你调用了它。** 我在副本里写了几行普通的 Java 代码，不启动 Spring，自己 new：

```java
JwtUtil jwtUtil = new JwtUtil(secret, Duration.ofHours(2));   // 自己调用构造器
System.out.println(jwtUtil.createToken(1L));
```

输出：

```
自己 new 出来的 JwtUtil 签发的 token：
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwianRpIjoiMGUxMmZjNzAtZWUwNy00YjVhL...
```

和 Spring 创建出来的效果完全一样。Spring 多做的只有一件事：替你从配置文件里取出 secret 和 ttl，再调用这个构造器。构造器的完整讲解见第 8 节答疑。

### 4.10 `module/system/service/impl/AuthServiceImpl.java`（今天的重点）

```java
package com.lingmao.scm.module.system.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lingmao.scm.common.exception.BizException;
import com.lingmao.scm.module.system.dto.LoginReq;
import com.lingmao.scm.module.system.entity.SysUser;
import com.lingmao.scm.module.system.mapper.SysUserMapper;
import com.lingmao.scm.module.system.service.AuthService;
import com.lingmao.scm.security.JwtUtil;
import lombok.RequiredArgsConstructor;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class AuthServiceImpl implements AuthService {

    private final SysUserMapper sysUserMapper;
    private final PasswordEncoder passwordEncoder;
    private final JwtUtil jwtUtil;

    @Override
    public String login(LoginReq req) {
        SysUser user = sysUserMapper.selectOne(new LambdaQueryWrapper<SysUser>()
                .eq(SysUser::getUsername, req.getUsername()));
        if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPassword())) {
            throw new BizException("用户名或密码错误");
        }
        return jwtUtil.createToken(user.getId());
    }
}
```

**三个依赖**：用户表的 Mapper、密码比对工具、签发 token 的工具。都是 `private final`，由 `@RequiredArgsConstructor` 生成构造器注入。

**第一步：按用户名查用户**

```java
SysUser user = sysUserMapper.selectOne(new LambdaQueryWrapper<SysUser>()
        .eq(SysUser::getUsername, req.getUsername()));
```

`selectOne` 是"查一条"：查到就返回那一条，查不到返回 null。真实 SQL：

```
SELECT id,username,password,nickname,phone,status,create_by,create_time,update_by,update_time,deleted FROM sys_user WHERE deleted=false AND (username = ?)
Parameters: admin(String)
```

已删除的用户被 `deleted=false` 自动排除了，删掉的账号登不上。部分唯一索引保证了未删除的同名用户最多一个，所以 `selectOne` 不会查出两条。

**第二步：用户不存在，或者密码不对，都抛同一句话**

```java
if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPassword())) {
```

这一行有三个要点：

- **`||` 是"或"**，而且是**短路**的：左边 `user == null` 为 true 时，右边**根本不会执行**。这很重要，因为 user 是 null 的话，右边的 `user.getPassword()` 会空指针。所以 `user == null` 必须写在左边
- **`matches(明文, 哈希)`，参数顺序不能反**：第一个参数是用户这次输入的明文，第二个参数是库里存的哈希。写反了，永远都会返回 false
- **一句话覆盖两种情况**：就是 2.5 的取舍一

**第三步：签发 token**

```java
return jwtUtil.createToken(user.getId());
```

能走到这里，说明用户名、密码都对了。

**这里故意少了一条规则：停用的账号也能登录。** 这是今天的作业。

**为什么这么写**

### 4.12 `module/system/AdminInitializer.java`

放在 `module/system` 包的根下，和 `controller`、`service` 这些文件夹平级。

```java
package com.lingmao.scm.module.system;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lingmao.scm.module.system.entity.SysUser;
import com.lingmao.scm.module.system.mapper.SysUserMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

@Slf4j
@Component
public class AdminInitializer implements ApplicationRunner {

    private final SysUserMapper sysUserMapper;
    private final PasswordEncoder passwordEncoder;
    private final String initPassword;

    public AdminInitializer(SysUserMapper sysUserMapper,
                            PasswordEncoder passwordEncoder,
                            @Value("${lingmao.init-admin-password}") String initPassword) {
        this.sysUserMapper = sysUserMapper;
        this.passwordEncoder = passwordEncoder;
        this.initPassword = initPassword;
    }

    @Override
    public void run(ApplicationArguments args) {
        boolean exists = sysUserMapper.exists(new LambdaQueryWrapper<SysUser>()
                .eq(SysUser::getUsername, "admin"));
        if (exists) {
            return;
        }
        if (!StringUtils.hasText(initPassword)) {
            log.warn("库里还没有 admin，也没配置 INIT_ADMIN_PASSWORD，跳过创建");
            return;
        }
        SysUser admin = new SysUser();
        admin.setUsername("admin");
        admin.setPassword(passwordEncoder.encode(initPassword));
        admin.setNickname("管理员");
        sysUserMapper.insert(admin);
        log.info("已创建初始管理员 admin，id = {}", admin.getId());
    }
}
```

**为什么这么写**

- **`implements ApplicationRunner`**：Spring Boot 启动完成后（数据库连好、Flyway 跑完、所有 Bean 都建好），会自动调用每个 ApplicationRunner 的 `run` 方法。适合做"启动时检查一下、补点数据"这种事
- **`@Slf4j`**：Lombok 生成一个日志对象 `log`。`log.info` / `log.warn` 打到控制台，比 `System.out.println` 多了时间、级别、类名，上线后还能写进日志文件
- **先查 exists，有了就直接 return**：每次启动都会执行 `run`，但只有第一次真正创建。这种"执行多少次结果都一样"的性质叫**幂等**
- **没配密码只警告，不报错**：admin 不存在、又没配密码时，应用照样能启动，只是没人能登录。日志里那句 warn 会告诉你原因
- **`passwordEncoder.encode(initPassword)`**：存进库的是 BCrypt 哈希，不是你配置的明文
- **构造器手写**：理由和 JwtUtil 一样，有一个参数要用 `@Value`
- **为什么放在 `module/system` 而不是 `config`**：它在操作系统域的用户表，属于系统域自己的事

**补充讲解（10-08 应你的要求）：AdminInitializer 什么时候执行**

点了运行以后，应用启动是按这个顺序走的：

```
① 创建所有 Bean，并按构造器互相传进去
     其中 Flyway 会执行还没跑过的迁移           ← V3 在这时建好 sys_user 表
     AdminInitializer 的构造器也在这时被调用   ← 只是存好三个字段，什么都不查
② Tomcat 启动，打印 Started ScmApplication
③ 挨个调用 ApplicationRunner 的 run()         ← AdminInitializer.run 在这一步执行
```

副本里第一次启动的真实日志顺序（只摘了关键行）：

```
Migrating schema "scratch" to version "3 - sys user"
Successfully applied 3 migrations to schema "scratch", now at version v3
Tomcat started on port 18080 (http) with context path '/'
Started ScmApplication in 7.225 seconds
==>  Preparing: SELECT COUNT( * ) AS total FROM sys_user WHERE deleted=false AND (username = ?)
==>  Preparing: INSERT INTO sys_user ( username, password, nickname, ... ) VALUES ( ... )
已创建初始管理员 admin，id = 1
```

注意"已创建初始管理员"是打在 `Started ScmApplication` **后面**的，`run` 确实是最后才执行。

**为什么查库、建 admin 写在 `run` 里，不写在构造器里？** 构造器执行的时候（第 ① 步），别的 Bean 可能还没全部准备好。构造器只做"把传进来的东西存好"这一件事。`run` 是 Spring Boot 专门留给"启动完成后要做的事"的位置，到第 ③ 步，表建好了，所有 Bean 都能用了。

**`run` 里逐行读：**

| 代码 | 意思 |
|---|---|
| `sysUserMapper.exists(... username = "admin")` | 库里有没有 admin？发 `SELECT COUNT(*) ... WHERE username = ?` |
| `if (exists) { return; }` | 有了就什么都不做，直接结束。所以第二次启动只看到一条 SELECT |
| `if (!StringUtils.hasText(initPassword))` | `hasText` 判断"有没有内容"，前面的 `!` 取反：**没配**密码 |
| `log.warn(...); return;` | 没配密码就打一条警告，然后结束，不建 admin，也不报错 |
| `admin.setPassword(passwordEncoder.encode(initPassword))` | 把配置里的明文用 BCrypt 算成哈希再存 |
| `sysUserMapper.insert(admin)` | 插入，数据库生成的 id 回填到 `admin` 对象上 |
| `log.info("... id = {}", admin.getId())` | `{}` 是占位符，会被后面的 `admin.getId()` 替换，打出来就是 `id = 1` |

**`@Slf4j` 生成了什么**：Lombok 在类里加了一行 `private static final org.slf4j.Logger log = org.slf4j.LoggerFactory.getLogger(AdminInitializer.class);`，所以下面才能直接用 `log`。

**第一次启动**的真实日志：

```
Migrating schema "public" to version "3 - sys user"
==>  Preparing: SELECT COUNT( * ) AS total FROM sys_user WHERE deleted=false AND (username = ?)
==> Parameters: admin(String)
==>  Preparing: INSERT INTO sys_user ( username, password, nickname, create_by, create_time, update_by, update_time ) VALUES ( ?, ?, ?, ?, ?, ?, ? )
INFO ... c.l.scm.module.system.AdminInitializer   : 已创建初始管理员 admin，id = 1
```

（我的副本里 schema 名不是 public，其余一样。）注意 INSERT 里没有 `status` 列：我们没给 status 赋值，它是 null，被 MyBatis-Plus 跳过了，于是用上了表里的默认值 1（启用）。01 讲 `Integer` 和 `int` 的区别时说过这个机制。

**第二次启动**只剩一条查询，查到 admin 已经存在，什么都不做：


**为什么这么写**

- **三个 `@Mock`**：ServiceImpl 的构造器要三个依赖，就准备三个假的。少一个的话，`@InjectMocks` 会传 null 进去（昨天作业里见过）
- **`.hasMessage(...)` 整句比对**：今天换成了整句比对，原因就是第 0 节那个 🟡。这里的提示文字是取舍一的核心，两种失败必须**逐字相同**，差一个字测试就会红
- **PasswordEncoder 也是假的**：`"hashed"` 不是真的 BCrypt 哈希，只是一个占位字符串。我们用 `when(passwordEncoder.matches("wrong", "hashed")).thenReturn(false)` 直接规定"这个密码不对"。BCrypt 自己算得对不对，是 Spring 的事，不归我们测。而且真跑 BCrypt 每次要 50 多毫秒，测试会变慢
- **JwtUtil 是一个类，不是接口，也能 mock**：Mockito 可以给普通类造假对象。`when(jwtUtil.createToken(1L)).thenReturn("token-for-1")` 规定了"给 1 号用户签发的 token 是这个字符串"。最后断言拿到的正是它，就证明 Service 是拿**这个用户的 id** 去签发的
- **`verify(jwtUtil, never()).createToken(any())`**：失败的情况下，确认没有签发 token。道理和昨天的 `verify(never()).deleteById` 一样
- **`admin()` 小工具方法**：三个测试里有两个要用"库里有一个 admin"，抽成一个方法，作业里也会用到它

## 6. 🎤 今天的面试题

**问：JWT 和 Session 有什么区别？JWT 有什么缺点？**

**答**：Session 是服务器存状态：登录后给前端一个随机编号，用户信息存在服务器上，每次请求按编号去查。JWT 是 token 自带信息：比如我们项目登录后签发的 token，内容是 `{"sub":"1","jti":"...","exp":...}`，用服务器的密钥签名。服务器不用存任何东西，验一下签名就知道是谁，所以天然适合多台服务器。缺点有两个：一是内容只是 Base64，谁都能解码，所以不能放敏感信息；二是签发以后，在过期之前没法作废，退出登录或者封号都做不到立即生效。我们项目的做法是 JWT 加 Redis：签发时在 Redis 里记一笔"这个 jti 有效"，每次请求同时检查 Redis，退出时删掉这一笔，这样就能立即失效。代价是又变回了"服务器要存状态"，但只存一个很小的 key。

**问：为什么推荐构造器注入，而不是在字段上写 `@Autowired`？**

**答**：用我们的代码举例。`AuthServiceImpl` 的三个依赖都是 `private final`，通过构造器传进来，有三个好处。第一，`final` 保证注入以后不会被改掉，对象一创建出来就是完整的，不存在"依赖还是 null"的中间状态。第二，测试方便：`@InjectMocks` 通过构造器把假的 Mapper 传进去，就算不用 Spring，自己 `new AuthServiceImpl(假Mapper, 假Encoder, 假JwtUtil)` 也能测。字段注入的话，字段是 private 的，不靠反射就塞不进去。第三，循环依赖暴露得早：两个 Service 互相通过构造器要对方，谁都没法先创建出来，启动直接报错（01 讲义取舍一讲过）。字段注入在早年的 Spring 里能被悄悄绕过去，把设计问题藏了起来（Spring Boot 2.6 起默认也禁止了）。`JwtUtil` 和 `AdminInitializer` 因为要用 `@Value`，构造器是手写的，原理完全一样。

## 8. 答疑

**问：测试里的 `"hashed"` 是什么意思？**

**答**：它是一个**占位字符串**，代替“数据库里存的那个 BCrypt 哈希”。

真实运行时，库里 admin 的 password 列存的是 `$2a$10$...` 这样一个 60 个字符的哈希。测试里用 `admin()` 造的用户不来自数据库，password 字段总得填点什么，于是填了 `"hashed"`，意思就是“这里本来应该是个哈希”。换成 `"abc"`、`"xxx"` 都行，它不需要是真的哈希。

为什么它能用：`passwordEncoder` 是假对象，它根本不会去算 BCrypt。我们直接规定它的回答：

```java
when(passwordEncoder.matches("right", "hashed")).thenReturn(true);
```

意思是：“有人拿明文 `right` 和哈希 `hashed` 来比对，你就回答‘对上了’。”login 里调用的是 `passwordEncoder.matches(req.getPassword(), user.getPassword())`，两个参数分别是请求里的 `"right"` 和 `admin()` 里的 `"hashed"`，正好对上这条规定。

所以 `admin()` 里的 `setPassword("hashed")` 和 `when(...matches(..., "hashed"))` **必须是同一个字符串**。我在副本里把 `admin()` 改成了 `setPassword("abc")`，`when` 里还写 `"hashed"`，测试报：

```
PotentialStubbingProblem: Strict stubbing argument mismatch. Please check:
 - this invocation of 'matches' method:
    passwordEncoder.matches("right", "abc");
 - has following stubbing(s) with different arguments:
    1. passwordEncoder.matches("right", "hashed"); stubbed with: [Returns: true]
```

翻译一下：代码实际调用的是 `matches("right", "abc")`，你规定的却是 `matches("right", "hashed")`，参数对不上。

为什么不用真哈希：我们测的是“比对结果出来以后，login 做得对不对”，不是“BCrypt 算得对不对”，那是 Spring 的事。而且真算一次 BCrypt 要 50 多毫秒。

**问：构造器到底是怎么回事？谁调用的？参数从哪来？**

**答**：分四层讲。

**① 先不管 Spring：构造器就是 `new` 的时候自动执行的那个方法**

名字和类名一样、没有返回值的方法，就是构造器。它的任务是把对象**装配好**，让它一出生就能用。JwtUtil 不知道密钥就没法签发 token，所以把密钥写成构造器参数，没有密钥就造不出 JwtUtil。

不启动 Spring，自己 new 一个，完全可以用（副本里实际跑过）：

```java
JwtUtil jwtUtil = new JwtUtil(secret, Duration.ofHours(2));
System.out.println(jwtUtil.createToken(1L));   // 打印出 eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIi...
```

**② Spring 做的事：替你 new，替你准备参数**

在 Spring 项目里，你不用自己写 `new AuthServiceImpl(...)`。启动时 Spring 扫描到贴了 `@Service`、`@Component` 的类，就去看它的构造器要几个参数、各是什么类型，把参数一个个准备好，然后调用这个构造器。参数只有两个来源：

| 参数 | 从哪来 | 例子 |
|---|---|---|
| 别的 Bean | 按**类型**去容器里找 | `SysUserMapper`（MyBatis 生成）、`PasswordEncoder`（`PasswordConfig` 的 `@Bean`）、`JwtUtil`（`@Component`） |
| 配置里的值 | 参数上贴 `@Value("${配置名}")`，从 application.yaml 里取 | JwtUtil 的 `secret`、`ttl`，AdminInitializer 的 `initPassword` |

找不到的话，启动直接失败，而且报错会准确告诉你是**哪个类的构造器、第几个参数、要什么类型**（4.6 的补充讲解里有真实报错）。

**③ 项目里的三种构造器写法**

| 类 | 写法 | 为什么 |
|---|---|---|
| 实体、DTO（`SysUser`、`LoginReq`） | 无参构造器（`@Data` 生成） | 框架先 `new SysUser()`，再一个个 `setXxx(...)`，不需要参数 |
| `AuthServiceImpl`、各 Controller | `@RequiredArgsConstructor`，字段 `private final` | 参数全是别的 Bean，交给 Lombok 生成 |
| `JwtUtil`、`AdminInitializer` | 手写 | 有参数要贴 `@Value`，Lombok 默认不会把它带到生成的构造器参数上 |

第二种写法，Lombok 生成的构造器长这样（delombok 还原出来的真实结果）：

```java
public AuthServiceImpl(final SysUserMapper sysUserMapper, final PasswordEncoder passwordEncoder, final JwtUtil jwtUtil) {
    this.sysUserMapper = sysUserMapper;
    this.passwordEncoder = passwordEncoder;
    this.jwtUtil = jwtUtil;
}
```

和 JwtUtil 里你手写的那个是同一个样子：参数进来，存进 `final` 字段。区别只在于这次是 Lombok 替你写的。

**④ 测试里也是同一个构造器**

`@InjectMocks` 就是“Mockito 版的 Spring”：它找到 `AuthServiceImpl` 的构造器，把三个 `@Mock` 假对象当参数传进去。所以测试里少写一个 `@Mock`，那个参数就会变成 null。

**一句话**：构造器写清楚“我要什么才能工作”；在 Spring 里由 Spring 负责调用它、把东西送进来，在测试里由 Mockito 负责。项目里所有 `private final` 字段，都是这样被赋值的。
