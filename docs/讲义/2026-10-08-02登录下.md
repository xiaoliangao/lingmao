## 2. 为什么这么设计

### 2.1 一个请求进来，要过几道关

加入 Spring Security 以后，每个请求到达 Controller 之前，都要先经过一串**过滤器**（filter），这一串叫**过滤器链**。我们关心其中两道：

```
请求
  │
  ▼
① JwtAuthFilter（我们写的）：认人
     有 Authorization: Bearer xxx 吗？
     → 验签通过、Redis 里也有这一笔 → 在这个请求上记下“这是 1 号用户”
     → 否则什么都不记（不拦，直接放行到下一道）
  │
  ▼
② 授权规则（SecurityConfig 里配的）：看门
     这个接口要登录吗？
     → /api/auth/login、Swagger：不用，放行
     → 其他所有接口：要登录。① 没认出人 → 直接返回 401，根本到不了 Controller
  │
  ▼
Controller
```

**两道关各管一件事**：① 只负责"认出是谁"，认不出也不拦；② 只负责"这个接口要不要登录"。这样分开，以后加"某个接口不用登录"，只改 ② 的规则就行，① 一行都不用动。

### 2.2 JWT 和 Redis 各管什么

| | 管什么 | 怎么查 |
|---|---|---|
| JWT 签名 | 这张 token **是不是我们发的、有没有被改过、过期没有** | 用密钥验签，不用查任何地方 |
| Redis 里的一笔 | 这张 token **现在还算不算数**（退出了就不算） | 按 token 里的 `jti` 去 Redis 查 |

两个都过了才算登录。登录时，我们在 Redis 里记一笔；退出时，把这一笔删掉。下面是副本里登录后 Redis 的真实内容：

```
> KEYS login:token:*                 → ['login:token:4ee41aa9-489f-4b2e-889b-877dcd480d5c']
> GET login:token:4ee41aa9-...       → 1          （值是用户 id）
> TTL login:token:4ee41aa9-...       → 7200       （还剩 7200 秒，和 token 同时过期）
```

退出以后：

```
> EXISTS login:token:4ee41aa9-...    → 0          （这一笔没了）
```

这时 token 的签名还是好的，也没过期，可 Redis 里查不到这一笔，① 就认不出人，于是 401。

### 2.3 SecurityContext：请求上的"身份标签"

① 认出人以后，要把"这是 1 号用户"记在**当前这个请求**上，后面的 Controller 才能知道。Spring Security 提供的地方叫 **SecurityContext**。你可以把它理解成：每个请求进来时，手上都有一张空白的身份标签，① 认出人就把名字填上，请求处理完，这张标签就扔掉。

Controller 里用 `@AuthenticationPrincipal LoginUser loginUser` 把标签上的人取出来。

### 2.4 取舍

**取舍一：未登录也返回 HTTP 200，错误码 401 放在返回体的 code 里。**

和项目里其他错误保持一致（400、404、1000 都是这样）。前端的请求拦截器只看一个地方：`code` 是 401 就跳去登录页。另一种做法是 HTTP 状态码也返回 401，更符合 HTTP 规范，前端看两个地方。两种都有人用，我们选了一致。

**取舍二：JwtAuthFilter 不贴 `@Component`，在 SecurityConfig 里 new 出来。**

我在副本里试过给它贴 `@Component`：接口测试（`@WebMvcTest`）会把所有过滤器都扫进来，它的构造器要 JwtUtil，可接口测试的小容器里没有 JwtUtil，于是启动失败：

```
Parameter 0 of constructor in com.lingmao.scm.security.JwtAuthFilter required a bean of type 'com.lingmao.scm.security.JwtUtil'
```

而且它是安全过滤器链的一部分，放在 SecurityConfig 里一起配，看一个文件就知道请求要过哪几道关。

**取舍三：Redis 里存的 key 是 `jti`，不是整个 token。**

token 有 180 多个字符，jti 是一个 36 个字符的 UUID，而且本来就是"这张 token 的编号"，用它当 key 正合适。

**取舍四：`/me` 返回一个专门的 `UserInfoVO`，不返回 `SysUser` 实体。**

上一份 4.4 说过，实体里有 password 字段（哈希），绝不能原样返回给前端。VO（View Object）就是"专门给前端看的对象"，只挑前端要的字段。

**取舍五：关掉 CSRF、表单登录、HTTP Basic、Session。**

这四样是 Spring Security 默认开着、为"传统网页 + Cookie 登录"准备的：

| 关掉的 | 它原本干什么 | 为什么我们不要 |
|---|---|---|
| CSRF 防护 | 防止别的网站借用你浏览器里的 Cookie 偷偷发请求 | 我们不用 Cookie，token 放在请求头里，别的网站拿不到 |
| 表单登录 | 自带一个登录页 `/login` | 我们自己写了 `/api/auth/login` |
| HTTP Basic | 浏览器弹框输用户名密码 | 同上 |
| Session | 服务器记住登录状态 | 我们用 JWT + Redis，`STATELESS` 表示 Spring Security 自己不要再存 |

## 4. 逐个文件

### 4.1 `pom.xml`

把上一份加的 `spring-security-crypto` 那个依赖（连同上面那行注释）**整个换成**下面两个：

```xml
<!-- 安全框架：过滤器链、认证、放行规则；BCrypt 也在里面 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
<!-- Redis：存登录会话 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

在 `spring-boot-starter-webmvc-test` 那个测试依赖**下面**，加一个：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security-test</artifactId>
    <scope>test</scope>
</dependency>
```

**为什么这么写**

- **crypto 换成 starter**：starter 是"全家桶"，里面已经包含了 crypto（BCrypt），所以 crypto 不用单独写了。上一份只要加密工具；今天要用过滤器链，需要整个框架
- **`spring-boot-starter-data-redis`**：Spring Boot 管版本，帮我们连 Redis，提供 `StringRedisTemplate`
- **`spring-boot-starter-security-test`**：Spring Boot 4 把测试支持拆成了单独的包。不加它，接口测试会少一部分 Security 的测试配置
- 改完记得 **⇧⌘I**（Load Maven Changes）

**一引入 Security，6 个接口测试会马上变红**（我在副本里试过）：

```
[ERROR] Tests run: 2, Failures: 2 -- in ...DictDataControllerTest
java.lang.AssertionError: No value at JSON path "$.code"
```

DictType、DictData、Auth 三个 ControllerTest 全红。原因是：Security 一进来，默认**所有接口都要登录**，请求在过滤器那一关就被挡回去了，根本没到 Controller，返回体是空的，所以找不到 `$.code`。4.12 修它。

### 4.2 `src/main/resources/application.yaml`

两处改动。第一处，在 `spring:` 下面、`application:` 那一段后面加：

```yaml
spring:
  application:
    name: scm
  autoconfigure:
    # 不要 Spring Security 自动建的那个“默认用户”：我们自己管用户（sys_user 表），它只会在日志里打一个没用的随机密码
    exclude: org.springframework.boot.security.autoconfigure.UserDetailsServiceAutoConfiguration
```

第二处，在 `flyway:` 那一段后面、`jackson:` 前面加：

```yaml
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT}
      password: ${REDIS_PASSWORD}
      database: ${REDIS_DB:0}      # 开发用 0 号库；生产用另一个库号
```

**为什么这么写**

- **Redis 的连接信息**：`REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD` 三个值，你的 application-local.yaml 里**已经有了**（建项目时就配好的），不用再加
- **`database: ${REDIS_DB:0}`**：一个 Redis 里有 16 个编号的库（0～15），彼此隔离。开发用 0 号；W4 上线时，生产用另一个号，同一个 Redis 里两边的数据不会混
- **`autoconfigure.exclude`**：Spring Security 发现项目里没有"用户从哪查"的配置，就会自动建一个内存里的默认用户，并在日志里打印 `Using generated security password: <一串随机字符>`。我们的用户在 sys_user 表里，用不着它。不排除也不影响功能，只是日志里那句话容易让人以为"有个密码要用"

### 4.3 `security/LoginUser.java`

```java
package com.lingmao.scm.security;

/** 当前登录的是谁：用户 id，以及这次登录的 token 编号（退出时要用） */
public record LoginUser(Long userId, String jti) {
}
```

**`record` 是什么**：Java 16 起有的一种写法，专门用来定义"**只装数据、创建以后不改**"的类。这一行等于自动生成了：两个 `private final` 字段、一个两参数的构造器、两个读取方法 `userId()` 和 `jti()`（注意没有 `get` 前缀），还有 `equals`、`toString`。

为什么这里用 record 不用 `@Data` 类：LoginUser 在过滤器里创建，之后只读、不改，正好是 record 的用途。实体和 DTO 不用 record，因为框架要先 new 一个空的再一个个 set。

**为什么要带 jti**：退出时要删 Redis 里的那一笔，key 里就是 jti。

### 4.4 `security/LoginSessionStore.java`

```java
package com.lingmao.scm.security;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;

@Component
public class LoginSessionStore {

    private static final String KEY_PREFIX = "login:token:";

    private final StringRedisTemplate redis;
    private final Duration ttl;

    public LoginSessionStore(StringRedisTemplate redis,
                             @Value("${lingmao.jwt.ttl}") Duration ttl) {
        this.redis = redis;
        this.ttl = ttl;
    }

    /** 登录成功：记一笔“这张 token 有效”，和 token 同时过期 */
    public void save(String jti, Long userId) {
        redis.opsForValue().set(KEY_PREFIX + jti, String.valueOf(userId), ttl);
    }

    /** 这张 token 还有效吗？有效返回用户 id，已退出或已过期返回 null */
    public Long getUserId(String jti) {
        String value = redis.opsForValue().get(KEY_PREFIX + jti);
        return value == null ? null : Long.valueOf(value);
    }

    /** 退出登录：删掉这一笔，token 立即失效 */
    public void remove(String jti) {
        redis.delete(KEY_PREFIX + jti);
    }
}
```

**为什么这么写**

- **`StringRedisTemplate`**：Spring Boot 根据 application.yaml 里的 Redis 配置自动建好、放进容器的工具，key 和 value 都按字符串存。构造器参数写上它，就注入进来了
- **`opsForValue()`**：Redis 有好几种数据结构，最简单的是"一个 key 对一个字符串值"，`opsForValue` 就是操作这种的
- **`set(key, value, ttl)`**：存进去，并且 ttl（2 小时）后**自动删除**。token 两小时后过期，Redis 里这一笔也同时消失，不会越积越多。2.2 里看到的 `TTL → 7200` 就是它
- **key 写成 `login:token:` 加 jti**：冒号是 Redis 里约定俗成的分隔符，一看就知道是"登录 → token → 哪一张"。和 [架构设计 §6](../docs/架构设计.md) 定的 key 一致
- **为什么单独一个类，不在 AuthServiceImpl 里直接用 StringRedisTemplate**：存、查、删三个地方（登录、过滤器、退出）都要用同一个 key 格式。写在一处，key 格式只有一份；测试时也能把整个类换成假的
- **ttl 和 JwtUtil 读的是同一个配置**：两边永远一样长

### 4.5 `security/JwtUtil.java`（改两处）

**第一处：`createToken` 多一个参数 `jti`**，由外面传进来，不再自己生成：

```java
/** 给某个用户签发 token，jti 是这张 token 的编号 */
public String createToken(Long userId, String jti) {
    Instant now = Instant.now();
    return Jwts.builder()
            .subject(String.valueOf(userId))
            .id(jti)
            .issuedAt(Date.from(now))
            .expiration(Date.from(now.plus(ttl)))
            .signWith(key)
            .compact();
}
```

`import java.util.UUID;` 这一行删掉，这个文件里不再用它了。

**为什么要改**：登录时要做两件事：在 Redis 记一笔、签发 token。**两边必须是同一个 jti**，不然过滤器拿着 token 里的 jti 去 Redis 一查，永远查不到。所以 jti 由 AuthServiceImpl 生成一次，同时交给这两边。

**第二处：在文件最后加验签方法 `parse`**（顶部要加 `import io.jsonwebtoken.Claims;`）：

```java
/** 验签并取出内容。签名不对、已过期、格式不对，都会抛 JwtException */
public Claims parse(String token) {
    return Jwts.parser()
            .verifyWith(key)
            .build()
            .parseSignedClaims(token)
            .getPayload();
}
```

| 代码 | 意思 |
|---|---|
| `Jwts.parser()` | 准备一个解析器（又是建造者写法） |
| `.verifyWith(key)` | 用我们的密钥验签。不是这把密钥签的 → 抛异常 |
| `.build()` | 解析器准备好了 |
| `.parseSignedClaims(token)` | 拆开 token，验签，**同时检查有没有过期**。过期 → 抛 `ExpiredJwtException` |
| `.getPayload()` | 取出第二段的内容（`Claims`），里面就是 sub、jti、exp 这些 |

**`Claims` 是什么**：可以理解成一个装着 token 内容的 Map。`claims.getId()` 取 jti，`claims.getSubject()` 取 sub。

过期、签名不对、格式不对，抛的异常（`ExpiredJwtException`、`SignatureException`、`MalformedJwtException`……）都是 `JwtException` 的子类，所以过滤器里接一个 `JwtException` 就够了。

### 4.6 `security/JwtAuthFilter.java`

```java
package com.lingmao.scm.security;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.List;

/** 每个请求先经过这里：带了有效的 token，就告诉 Spring Security“这个请求是谁发的” */
public class JwtAuthFilter extends OncePerRequestFilter {

    private static final String PREFIX = "Bearer ";

    private final JwtUtil jwtUtil;
    private final LoginSessionStore loginSessionStore;

    public JwtAuthFilter(JwtUtil jwtUtil, LoginSessionStore loginSessionStore) {
        this.jwtUtil = jwtUtil;
        this.loginSessionStore = loginSessionStore;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String header = request.getHeader("Authorization");
        if (header != null && header.startsWith(PREFIX)) {
            authenticate(header.substring(PREFIX.length()));
        }
        chain.doFilter(request, response);
    }

    private void authenticate(String token) {
        Claims claims;
        try {
            claims = jwtUtil.parse(token);
        } catch (JwtException | IllegalArgumentException e) {
            return;
        }
        Long userId = loginSessionStore.getUserId(claims.getId());
        if (userId == null) {
            return;
        }
        LoginUser loginUser = new LoginUser(userId, claims.getId());
        SecurityContextHolder.getContext().setAuthentication(
                new UsernamePasswordAuthenticationToken(loginUser, null, List.of()));
    }
}
```

**类的开头**

- **`extends OncePerRequestFilter`**：Spring 提供的过滤器父类，保证每个请求只经过这个过滤器**一次**。我们只要实现 `doFilterInternal` 这一个方法
- **没有 `@Component`**：见 2.4 取舍二。它由 SecurityConfig 来 new
- **构造器手写**：没贴 `@Component`，就不是 Spring 来调用它的构造器，而是 SecurityConfig 里我们自己 `new JwtAuthFilter(jwtUtil, loginSessionStore)`。这就是答疑里说的"构造器就是个普通方法"

**`doFilterInternal`：每个请求都会走一遍**

```java
String header = request.getHeader("Authorization");
```

前端会把 token 放在请求头 `Authorization` 里，格式是 `Bearer eyJhbGci...`。`Bearer` 意思是"持有者"：谁拿着这张票，谁就能进。这是 HTTP 里约定俗成的写法。

```java
if (header != null && header.startsWith(PREFIX)) {
    authenticate(header.substring(PREFIX.length()));
}
```

有这个请求头、而且以 `"Bearer "` 开头，才去认人。`substring(PREFIX.length())` 是把前面 7 个字符 `"Bearer "` 切掉，剩下的就是 token 本身。`&&` 和上一份讲的 `||` 一样是短路的：header 是 null 时，右边不会执行，不会空指针。

```java
chain.doFilter(request, response);
```

**不管认没认出人，都要调用这一句**，意思是"交给下一道关"。忘了写这一句，请求就卡在这里，永远到不了 Controller，前端一直转圈。

**`authenticate`：认人的三步**

| 步 | 代码 | 不通过会怎样 |
|---|---|---|
| 1 验签 | `jwtUtil.parse(token)` | 伪造的、过期的、乱写的：抛异常 → `catch` 住，`return`，当作没带 token |
| 2 查 Redis | `loginSessionStore.getUserId(claims.getId())` | 查不到（退出了，或者已经过期被 Redis 删了）→ `return` |
| 3 记到身份标签上 | `SecurityContextHolder.getContext().setAuthentication(...)` | — |

- **`catch (JwtException | IllegalArgumentException e)`**：竖线表示"这两种异常都接"。`IllegalArgumentException` 是因为 `Authorization: Bearer ` 后面什么都没写时，parse 收到的是空字符串，jjwt 抛的是这个
- **认不出人时只是 `return`，不返回 401**：这就是 2.1 说的"① 只认人，不拦人"。该不该拦，由第 ② 道关决定。比如登录接口，没带 token 也应该能访问
- **`new UsernamePasswordAuthenticationToken(loginUser, null, List.of())`**：Spring Security 规定的"身份"格式，三个参数分别是：**是谁**（我们的 LoginUser）、凭证（密码已经验过了，这里不需要，传 null）、**有哪些权限**（W2 做角色权限时再填，现在是空列表）。名字里有 UsernamePassword，是历史原因，它是最通用的一种，不是说一定要用户名密码

### 4.7 `config/SecurityConfig.java`

```java
package com.lingmao.scm.config;

import com.lingmao.scm.common.result.R;
import com.lingmao.scm.security.JwtAuthFilter;
import com.lingmao.scm.security.JwtUtil;
import com.lingmao.scm.security.LoginSessionStore;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.AuthenticationException;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;
import tools.jackson.databind.json.JsonMapper;

import java.io.IOException;

@Configuration
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtUtil jwtUtil;
    private final LoginSessionStore loginSessionStore;
    private final JsonMapper jsonMapper;

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
                .csrf(csrf -> csrf.disable())
                .formLogin(form -> form.disable())
                .httpBasic(basic -> basic.disable())
                .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/api/auth/login").permitAll()
                        .requestMatchers("/swagger-ui.html", "/swagger-ui/**", "/v3/api-docs/**").permitAll()
                        .anyRequest().authenticated())
                .exceptionHandling(e -> e.authenticationEntryPoint(this::writeUnauthorized))
                .addFilterBefore(new JwtAuthFilter(jwtUtil, loginSessionStore),
                        UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    /** 没登录就访问需要登录的接口：和其他错误一样，返回 R，code 是 401 */
    private void writeUnauthorized(HttpServletRequest request, HttpServletResponse response,
                                   AuthenticationException e) throws IOException {
        response.setContentType("application/json;charset=UTF-8");
        jsonMapper.writeValue(response.getWriter(), R.fail(401, "未登录或登录已过期"));
    }
}
```

**整体**：和 PasswordConfig 一样是 `@Configuration` + `@Bean`。这次放进容器的是一条 `SecurityFilterChain`（安全过滤器链）。Spring Security 看到容器里有我们自己的链，就不再用它默认的"全部要登录 + 弹框登录"那一套了。

**`http` 后面那一长串，逐行读：**

| 代码 | 意思 |
|---|---|
| `.csrf(csrf -> csrf.disable())` 等前四行 | 关掉为 Cookie 登录准备的那四样（2.4 取舍五） |
| `.requestMatchers("/api/auth/login").permitAll()` | 登录接口：谁都能访问 |
| `.requestMatchers("/swagger-ui.html", "/swagger-ui/**", "/v3/api-docs/**").permitAll()` | Swagger 页面和接口文档：谁都能访问。`/**` 表示"这个路径下面的所有东西"。Apifox 导入也要读 `/v3/api-docs` |
| `.anyRequest().authenticated()` | **其他所有接口：必须是已认出的人** |
| `.exceptionHandling(e -> e.authenticationEntryPoint(this::writeUnauthorized))` | 没认出人却访问了要登录的接口时，调用下面的 `writeUnauthorized` 来回应 |
| `.addFilterBefore(new JwtAuthFilter(...), UsernamePasswordAuthenticationFilter.class)` | 把我们的过滤器插进链里，放在 Spring 自带的"用户名密码登录过滤器"**前面** |

- **`csrf -> csrf.disable()` 这种写法**是 lambda：意思是"把 csrf 的配置对象交给你，你调用它的 disable"。每一行都是"拿到某一项的配置，对它做点什么"
- **规则从上往下匹配，先匹配上的生效**：所以具体的放行规则写在前面，`anyRequest()` 兜底写在最后
- **为什么插在 UsernamePasswordAuthenticationFilter 前面**：认人必须发生在"检查要不要登录"之前。这是 Spring Security 链条里一个固定的位置标记，插在它前面就足够早了

**`writeUnauthorized`：401 怎么返回**

- 这个时候请求还没到 Controller，`GlobalExceptionHandler` 管不到这里，所以要自己写返回内容
- **`JsonMapper`**：Spring Boot 4 自带的 JSON 工具（Jackson 3），也在容器里，构造器注入进来。用它把 `R.fail(401, ...)` 转成 JSON 写出去，格式和其他所有接口的返回**完全一样**
- **`this::writeUnauthorized`**：方法引用。意思是"出现这种情况时，调用我这个类的 writeUnauthorized 方法"。和 `DictData::getTypeCode` 是同一种写法

```java
@Service
@RequiredArgsConstructor
public class AuthServiceImpl implements AuthService {

    private final SysUserMapper sysUserMapper;
    private final PasswordEncoder passwordEncoder;
    private final JwtUtil jwtUtil;
    private final LoginSessionStore loginSessionStore;

    @Override
    public String login(LoginReq req) {
        SysUser user = sysUserMapper.selectOne(new LambdaQueryWrapper<SysUser>()
                .eq(SysUser::getUsername, req.getUsername()));
        if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPassword())) {
            throw new BizException("用户名或密码错误");
        }
        if (user.getStatus() != 1) {
            throw new BizException("账号已停用");
        }
        String jti = UUID.randomUUID().toString();
        loginSessionStore.save(jti, user.getId());
        return jwtUtil.createToken(user.getId(), jti);
    }

    @Override
    public UserInfoVO me(Long userId) {
        SysUser user = sysUserMapper.selectById(userId);
        if (user == null) {
            throw new BizException(404, "用户不存在: " + userId);
        }
        return new UserInfoVO(user.getId(), user.getUsername(), user.getNickname());
    }

    @Override
    public void logout(String jti) {
        loginSessionStore.remove(jti);
    }
}
```

### 4.11 `module/system/controller/AuthController.java`（加两个接口）

- **为什么不让前端传用户 id**：比如 `GET /api/auth/me?userId=1`，前端就能随便填别人的 id，看到别人的信息（这叫"越权"）。"我是谁"只能从 token 里来，不能从参数里来
- **这两个接口没在 SecurityConfig 里放行**，属于"其他所有接口"，所以必须带有效 token。能走进这两个方法，loginUser 就一定不是 null
- **退出用 POST**：退出会改变服务器上的状态（删 Redis），不是"只读"，所以不用 GET

```java
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

    private JwtUtil jwtUtil;

        SecurityContextHolder.clearContext();

    @Test

        when(jwtUtil.parse("bad-token")).thenThrow(new JwtException("签名不对"));
        MockFilterChain chain = new MockFilterChain();

        filter.doFilter(requestWithToken("bad-token"), new MockHttpServletResponse(), chain);

        assertThat(SecurityContextHolder.getContext().getAuthentication()).isNull();
        verify(loginSessionStore, never()).getUserId(any());
        assertThat(chain.getRequest()).isNotNull();
    }

    private MockHttpServletRequest requestWithToken(String token) {
        MockHttpServletRequest request = new MockHttpServletRequest();
        request.addHeader("Authorization", "Bearer " + token);
        return request;
    }

```

**规则和测试的对照**：

| 规则 | 测试 |
|---|---|
| 有效 token + Redis 有记录 → 认出是谁 | `validTokenWithSession_authenticated` |
| 有效 token + Redis 没记录（退出过）→ 认不出 | `loggedOutToken_notAuthenticated` |
| 假 token → 认不出、不查 Redis、请求照样往下走 | `invalidToken_notAuthenticatedButPassedOn` |

**为什么这么写**

- **不启动 Spring，直接测过滤器**：过滤器就是一个普通对象，`@InjectMocks` 调用它的构造器，传进两个假的依赖
- **`MockHttpServletRequest`、`MockHttpServletResponse`、`MockFilterChain`**：spring-test 提供的假请求、假响应、假的"下一道关"。`requestWithToken` 造一个带 `Authorization: Bearer xxx` 请求头的假请求
- **`Jwts.claims().id("jti-1").subject("1").build()`**：造一个假的 token 内容。jwtUtil 是假的，我们直接规定"解析 good-token 得到的内容是这个"
- **`thenThrow(new JwtException(...))`**：和 thenReturn 相对，规定"调用时抛这个异常"，模拟验签失败
- **`chain.getRequest()` 不是 null**：说明过滤器调用了 `chain.doFilter`，请求被交给了下一道关。这钉住了 4.6 里"认不出也要放行"那条规矩。忘了写 `chain.doFilter`，这一行就会失败
- **`@AfterEach` 清掉身份标签**：SecurityContextHolder 是全局的，上一个测试放进去的身份不清掉，会影响下一个测试的结果。`@AfterEach` 的方法在每个测试跑完后自动执行

7. **还是这个 token**，再查 `/me` → `401`

第 7 步是今天最重要的一步：签名没变，也没过期，可 Redis 里那一笔被删了，所以不认了。

## 6. 🎤 今天的面试题

**问：Spring Security 的过滤器链是怎么工作的？你们项目怎么做 JWT 认证？**

**答**：每个请求到 Controller 之前，都要依次经过一串过滤器。我们在链里插了自己的 JwtAuthFilter，放在 UsernamePasswordAuthenticationFilter 前面。它从请求头 `Authorization: Bearer xxx` 里取出 token，用 jjwt 验签和检查过期，再拿 token 里的 jti 去 Redis 查这次登录还在不在。都通过，就把 `LoginUser(userId, jti)` 放进 SecurityContext。认不出也不拦，直接交给下一个过滤器。拦不拦由授权规则决定：我们在 SecurityConfig 里放行了登录接口和 Swagger，其他接口一律要求已认证。没认证的请求由 AuthenticationEntryPoint 统一返回 `{"code":401}`。Controller 里用 `@AuthenticationPrincipal` 取当前用户，用户 id 从不让前端传，防止越权。因为是 token 认证、不用 Cookie，所以关了 CSRF，Session 设成 STATELESS。

**问：JWT 怎么做到退出登录立即失效？**

**答**：JWT 本身做不到，签发以后在过期之前一直有效。我们的做法是登录时生成一个 jti（UUID），同时写进 token 和 Redis：`login:token:{jti}` → 用户 id，过期时间和 token 一样，都是 2 小时。过滤器除了验签，还要求 Redis 里能查到这个 jti。退出时删掉这个 key，同一个 token 立刻就是 401。代价是每个请求多查一次 Redis，Redis 在内存里，一次查询在一毫秒以内。这其实是"有状态"的做法，只是存的状态很小。想做"踢人下线"或者"改密码后全部失效"，也是在 Redis 里删 key。

## 8. 答疑

**问：4.5 的 `createToken` 和 `parse` 这两个方法，到底在干什么？**

**答**：一个是**做票**，一个是**验票**。两个方法用的是同一把钥匙 `key`，它在构造器里只做一次。

```
登录时（只一次）     AuthServiceImpl → createToken(1, jti) → 一串 token → 返回给前端，前端存起来
之后的每个请求       前端带上 token → JwtAuthFilter → parse(token) → Claims → getId() 拿到 jti → 去 Redis 查
```

下面的输出都是我在副本里用一把**演示用的密钥**真实跑出来的（不是项目的真实密钥）。

**一、`createToken(1L, "jti-demo")` 做出来的票**

```
token = eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwianRpIjoianRpLWRlbW8iLCJpYXQiOjE3OTE1MTA5NzMsImV4cCI6MTc5MTUxODE3M30.jG5fHpTB-dyBnroAcdr88WvaQlRsuvonjvV_cBH4v1s
第1段 header  = {"alg":"HS256"}
第2段 payload = {"sub":"1","jti":"jti-demo","iat":1791510973,"exp":1791518173}
第3段 签名     = jG5fHpTB-dyBnroAcdr88WvaQlRsuvonjvV_cBH4v1s
```

方法里每一行，对应 payload 里的哪一项：

| 代码 | 做了什么 | 结果 |
|---|---|---|
| `Instant now = Instant.now();` | 取**一次**当前时间，下面两行都用它 | 签发时间和过期时间正好差 ttl |
| `Jwts.builder()` | 拿一张空白的票 | — |
| `.subject(String.valueOf(userId))` | 写上"这是谁的票"。JWT 规定 sub 是字符串，所以 Long 转成 String | `"sub":"1"` |
| `.id(jti)` | 写上票的编号 | `"jti":"jti-demo"` |
| `.issuedAt(Date.from(now))` | 写上签发时间。jjwt 的这个方法只收老式的 `Date`，`Date.from` 把 `Instant` 转过去 | `"iat":1791510973`（从 1970 年起的秒数） |
| `.expiration(Date.from(now.plus(ttl)))` | 写上过期时间：现在 + 2 小时 | `"exp":1791518173`，比 iat 正好多 7200 |
| `.signWith(key)` | 用密钥给前两段算一个签名。header 里的 `HS256` 是 jjwt 根据密钥自动选的算法 | 第 3 段 |
| `.compact()` | 三段各自编码，用点连起来，变成一个字符串 | 整个 token |

**建造者写法**：`builder()` 后面每个方法都返回**同一个**建造者，所以可以一直用点接下去；最后的 `compact()` 才真正生成结果。和 `LambdaQueryWrapper` 的 `.eq(...).eq(...)` 是一个思路。

**注意**：第 2 段只是编码，不是加密，谁都能解开看（上面就是我直接解开的）。所以 payload 里只放用户 id 和 jti，**绝不放密码、手机号**。

**二、`parse(token)` 验票**

| 代码 | 做了什么 |
|---|---|
| `Jwts.parser()` | 准备一个验票员（还是建造者写法） |
| `.verifyWith(key)` | 交给他**做票时用的同一把钥匙** |
| `.build()` | 验票员准备好了 |
| `.parseSignedClaims(token)` | 拆开三段 → 用钥匙对前两段**重新算一遍签名**，和第 3 段比 → 比上了再看 exp 过没过期 → 任何一步不对就抛异常 |
| `.getPayload()` | 都通过了，取出第 2 段的内容 |

验票通过时拿到的 `Claims`：

```
parse => {sub=1, jti=jti-demo, iat=1791510973, exp=1791518173}
getSubject() = 1   getId() = jti-demo
getIssuedAt() = Fri Oct 09 09:56:13 SGT 2026   getExpiration() = Fri Oct 09 11:56:13 SGT 2026
```

`Claims` 可以当成一个 Map，打印出来就是 payload 的内容。`getId()` 取 jti，`getSubject()` 取 sub。

**三、五种坏票，`parse` 的真实反应**

| 坏票 | 抛出的异常 | 是 JwtException 吗 | 真实 message |
|---|---|---|---|
| A 把 payload 里的 sub 从 1 改成 2，签名不动 | `SignatureException` | 是 | `JWT signature does not match locally computed signature. ...` |
| B 别的密钥签的 | `SignatureException` | 是 | 同上 |
| C 已经过期（过期了 5 分钟） | `ExpiredJwtException` | 是 | `JWT expired 300809 milliseconds ago at 2026-10-09T01:51:13.000Z. ...` |
| D 乱写的 `abc` | `MalformedJwtException` | 是 | `Invalid compact JWT string: Compact JWSs must contain exactly 2 period characters, ... Found: 0` |
| E 空字符串 | `IllegalArgumentException` | **不是** | `CharSequence cannot be null or empty.` |

几点说明：

- **A 为什么能被发现**：签名是对"前两段的内容"算出来的。内容改了一个字，重新算出来的签名就完全不同，和第 3 段对不上。想改了内容又让签名对上，就得有密钥，攻击者没有
- **B 也是同样的道理**：钥匙不同，算出来的签名不同
- **C**：签名是好的，但 exp 已经过了。message 末尾的 `Allowed clock skew: 0 milliseconds` 是"允许几台服务器的时钟有多少误差"，我们只有一台，不用设
- **E 是过滤器里要多接一个 `IllegalArgumentException` 的原因**：请求头写成 `Authorization: Bearer `（后面什么都没有）时，切掉前缀，剩下的就是空字符串
- A 到 D 都是 `JwtException` 的子类，所以 4.6 的 `catch (JwtException | IllegalArgumentException e)` 一次全接住

**四、为什么今天要把 jti 改成从外面传进来**

上一份里，jti 是在 `createToken` 里面用 `UUID.randomUUID()` 生成的，外面拿不到。今天 Redis 也要用这个 jti，所以改成由 AuthServiceImpl 生成一次，同时交给 `loginSessionStore.save` 和 `createToken`。之后过滤器 `parse` 出来的 `getId()`，就和 Redis 里的 key 对得上。
