## 1. 服务器上现在跑着什么

```
浏览器 ──<端口>──▶ lingmao-web（Nginx）── 直接返回前端页面（web/dist）
                        │ /api/、/files/ 转给后端
                        ▼
                  lingmao-app（Spring Boot，prod 配置）──▶ lingmao-postgres（生产库 lingmao_prod）
                                                      └─▶ lingmao-redis（1 号库）
```

四个容器在同一个 docker compose 项目里，互相用服务名访问（`postgres:5432`、`redis:6379`、`app:8080`）。对外只开 Nginx 一个端口。后端、数据库不经过 Nginx 是访问不到的（开发用的数据库、Redis 端口是给你本机开发用的，单独开的）。

**开发和生产的区别**

| | 开发（你本机 IDEA） | 生产（服务器） |
|---|---|---|
| 配置 | `application.yaml` + `application-local.yaml` | `application.yaml` + `application-prod.yaml` + 环境变量 |
| 数据库 | `lingmao` 库，用户 `lingmao` | `lingmao_prod` 库，用户 `lingmao_prod`，同一个 PostgreSQL 容器 |
| Redis | 0 号库 | 1 号库，同一个 Redis 容器 |
| 密钥 | `application-local.yaml`（不进 git） | 服务器 `/opt/lingmao/.env`（只在服务器上） |
| SQL 打印到控制台 | 开 | 关 |
| 接口文档 Swagger | 开 | 关 |
| 上传的文件 | `SCM/uploads/` | 服务器 `/opt/lingmao/uploads/` |

**内存**（真实值，服务器一共 2GB）：

```
lingmao-app 246.7MiB / 512MiB
lingmao-web 2.938MiB / 64MiB
lingmao-postgres 69.8MiB / 512MiB
lingmao-redis 5.43MiB / 192MiB
```

`669f1e0` 是这次发布的提交号，同时写进了网站的 `/version.txt`。以后 +1 说"我这边不对"，先看 `/version.txt`，就知道他用的是哪一版。

**它按顺序做了六件事**

| 步骤 | 做什么 | 失败了会怎样 |
|---|---|---|
| 1 | 把当前提交（HEAD）导出到一个临时目录 | — |
| 2 | 在临时目录里 `mvn package`：编译、跑 57 个单元测试、打成 jar | 测试不过就停，服务器上什么都没动 |
| 3 | `pnpm build`：类型检查、打包前端 | 类型错误就停 |
| 4 | 在服务器上执行 `server-init.sh`：生成密钥、建目录、建生产库（已有的跳过） | — |
| 5 | rsync 把 jar、前端文件、配置传上去 | — |
| 6 | 服务器上重建 app 镜像、重启 app 和 web，每 2 秒问一次后端，起来了就报"已上线" | 90 秒没起来就提示你看日志 |

## 3. 为什么这么设计

### 3.1 打包的是"提交"，不是你的工作区

```bash
BUILD=$(mktemp -d)
trap 'rm -rf "$BUILD"' EXIT
git archive HEAD | tar -x -C "$BUILD"
```

- **`git archive HEAD`**：把当前提交里的文件打成一个包。没提交的改动、`.gitignore` 里的文件都不在里面
- **`trap '...' EXIT`**：脚本不管怎么结束（成功、失败、Ctrl+C），最后都删掉临时目录

**为什么不直接在 SCM 目录里打包**：两个原因。

一是你的工作区里可能有敲到一半的代码。发出去的必须是提交过的、说得清是哪一版的东西。

二是 `src/main/resources/application-local.yaml`（开发库的密码）也在 resources 下面。直接在工作区打包，它会被打进 jar。我检查过这次 jar 里的配置文件，只有这三个：

```
BOOT-INF/classes/application-prod.yaml
BOOT-INF/classes/application-local.yaml.example
BOOT-INF/classes/application.yaml
```

### 3.2 本机打 jar，服务器只做运行镜像

服务器只有 2GB 内存，还跑着你的旧项目，不适合在上面装 Maven、下几百 MB 的依赖、编译。jar 和平台无关，你的 Mac 打出来的 jar 在服务器的 Linux 上照样跑。

服务器上的镜像只有两层：Java 运行时 + jar。

```dockerfile
FROM eclipse-temurin:21-jre-alpine
LABEL project=lingmao
RUN addgroup -S -g 10001 app && adduser -S -u 10001 -G app app
WORKDIR /app
COPY app.jar app.jar
ENV TZ=Asia/Shanghai
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

- **`jre` 不是 `jdk`**：运行只需要 JRE，镜像小一半
- **`USER app`**：不用 root 跑。应用万一被攻破，攻击者拿到的只是一个普通用户。上传目录 `chown` 给了 uid 10001，所以上传照样能写。我在生产上传了一张图，文件属主是 `10001:10001`，能下载回来
- **`-XX:MaxRAMPercentage=75`**：compose 里给这个容器限了 512MB 内存，堆最多用它的 75%，剩下的留给 JVM 自己。不设的话 JVM 按整台机器的内存算，可能超过 512MB 被系统直接杀掉
- **`LABEL project=lingmao`**：发版后清理旧镜像时只清带这个标签的，不会误删你旧项目的镜像

### 3.3 Nginx 挡在前面

`deploy/nginx.conf` 做四件事：

- **返回前端页面**：`/system/user` 这种地址，服务器上没有这个文件，一律返回 `index.html`，由前端路由去显示对应页面（`try_files $uri $uri/ /index.html`）
- **把 `/api/`、`/files/` 转给后端**：和开发时 Vite 的代理是一个道理，浏览器只认一个地址，没有跨域
- **压缩**：Element Plus 的 js 原本 1066KB，实际传输 391KB（真实测的）
- **覆盖 `X-Forwarded-For`**：06 操作日志按这个请求头记 IP。客户端可以自己伪造这个头，所以 Nginx 不在后面追加，而是直接覆盖成真实连接的 IP。我伪造了一个 `X-Forwarded-For: 6.6.6.6` 去登录，日志里记的不是 6.6.6.6

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

还有一个细节：上传上限 Spring 是 10MB，Nginx 放到 11MB。超过 10MB 的文件能到 Spring，由它返回"文件太大，最大 10MB"；如果 Nginx 也设 10MB，它会先挡住，返回一个英文的 413 错误页。

### 3.4 密钥只在服务器上生成、只在服务器上存

`server-init.sh` 第一次执行时，在服务器上生成三个随机值，写进 `/opt/lingmao/.env`（权限 600，只有 root 能读）：

```bash
add_secret LINGMAO_PROD_DB_PASSWORD "$(openssl rand -hex 16)"
add_secret LINGMAO_PROD_JWT_SECRET "$(openssl rand -base64 32)"
add_secret LINGMAO_PROD_ADMIN_PASSWORD "$(openssl rand -hex 8)"
```

它们从没离开过服务器：没有打印、没有传回本机、没有进 git。compose 文件里写的是 `${LINGMAO_PROD_DB_PASSWORD:?在 .env 里配置}`，启动时从 `.env` 读。`:?` 的意思是：没配就直接报错停下，不会带着空密码启动。

- JWT 密钥是 `-base64 32`：32 字节 = 256 位，HS256 至少要这么长。`JwtUtil` 用 `Decoders.BASE64.decode` 读它，所以生成成 Base64
- 生产的 admin 是第一次启动时由 `AdminInitializer` 建的，密码就是 `LINGMAO_PROD_ADMIN_PASSWORD`

**生产 admin 的密码怎么看**：在终端里执行（只在你自己屏幕上显示）：

```
ssh root@<服务器IP> "grep LINGMAO_PROD_ADMIN_PASSWORD /opt/lingmao/.env"
```

登录后在用户管理里给 admin 重置一个你自己记得住的强密码。

### 3.5 生产库和开发库隔开

同一个 PostgreSQL 里建了两套库和用户。PostgreSQL 默认允许任何用户连任何库，所以建完生产库马上收回：

```sql
CREATE DATABASE lingmao_prod OWNER lingmao_prod;
REVOKE CONNECT ON DATABASE lingmao_prod FROM PUBLIC;
```

用开发账号去连生产库，真实结果：

```
DETAIL:  User does not have CONNECT privilege.
```

这样你本机开发时连错库、跑错 SQL，也碰不到生产数据。

### 3.6 两个 compose 文件

- **`/opt/lingmao/docker-compose.yml`**：10-01 建的 PostgreSQL、Redis，只在服务器上
- **`SCM/deploy/docker-compose.app.yml`**：app 和 web，在仓库里，每次发版传上去

服务器的 `.env` 里有一行 `COMPOSE_FILE=docker-compose.yml:docker-compose.app.yml`，在 `/opt/lingmao` 下执行 `docker compose` 时自动读两个文件，当成一个项目。好处是应用怎么部署（环境变量、端口、内存）跟着代码一起提交，改了能在 git 里看到是谁、什么时候、为什么改的。

发版时用 `docker compose up -d --no-deps app`：`--no-deps` 是"只动 app，不管它依赖的 postgres、redis"，所以发版不会重启数据库。

## 4. 这次踩到的坑

**Nginx 起不来，一直重启**

日志：

```
nginx: [crit] pwrite() "/run/nginx.pid" failed (1: Operation not permitted)
```

服务器是 CentOS 7，内核 3.10，十年前的版本。新的 alpine 版 Nginx 镜像在这么老的内核上调用不了某些系统调用。换成 Debian 版的 `nginx:1.30` 就好了（镜像从 62MB 变成 163MB，无所谓）。我先起了一个临时容器试过 Debian 版能跑，才改的配置。

**外面访问不了 `<端口>`**

服务器上 `curl localhost:<端口>` 正常，从你电脑访问没反应。排查：在服务器上用 `tcpdump` 抓包，同时从本机发请求。开发库的端口能抓到包，`<端口>` 一个包都没有。说明请求在到达服务器之前就被挡了，是**腾讯云的安全组**没放行这个端口。这个要你在控制台开，见第 7 节第 1 步。

顺便：你本机开着 Clash 的 TUN 模式，它会先替你"连上"，所以 `curl -v` 里总会显示 `Connected`，然后是 `Empty reply from server`。看到 Connected 不代表真的连通了。

## 5. 常用命令（在服务器上，先 `cd /opt/lingmao`）

| 想干什么 | 命令 |
|---|---|
| 看四个容器的状态 | `docker compose ps` |
| 看后端日志（最近 100 行，并持续跟着看） | `docker compose logs -f --tail 100 app` |
| 只看报错 | `docker compose logs app \| grep -A 20 ERROR` |
| 重启后端 | `docker compose restart app` |
| 看内存 | `docker stats --no-stream` |
| 进生产库 | `docker exec -it lingmao-postgres psql -U lingmao_prod -d lingmao_prod` |
| 看线上是哪一版 | `curl localhost:<端口>/version.txt` |

**回滚**：本机 `git checkout <上一个好的提交号>`，执行 `./deploy/deploy.sh`，再 `git checkout main` 回来。代码能回滚，**数据库迁移回滚不了**：Flyway 只会往前执行。这就是方案里"首发后迁移只增不删、不改类型"的原因，新版的迁移加了一列，退回旧版代码时，旧代码不认识这一列也不会出错。

新的命令（`git archive`、`rsync`、`docker compose`、`openssl rand`）已补进 `docs/方法速查.md` 第 7 节。

## 7. 练习：你自己发一次版（20 分钟）

**1. 在腾讯云放行端口**：控制台 → 云服务器 → 找到这台机器 → 安全组 → 入站规则 → 添加：协议 TCP，端口 `<端口>`（值在服务器 `/opt/lingmao/.env` 的 `LINGMAO_WEB_PORT`），来源 `0.0.0.0/0`。浏览器打开 `http://<服务器IP>:<端口>`，能看到登录页就对了。

**2. 改一行字**：`web/src/views/dashboard/index.vue` 里"业务模块（物料、采购、库存）等需求确定后上线。"改成你想写的任何一句话。

**3. 提交，发版**：

```
git commit -m "首页文案" -- web/src/views/dashboard/index.vue
./deploy/deploy.sh
```

`-- 文件路径` 表示只提交这一个文件：你手上要是有修到一半的 bug，不会被带进去（deploy.sh 本来也只发提交过的东西）。

**4. 验证**：

- 输出最后一行"已上线：xxxxxxx"，和 `git log --oneline -1` 的提交号一样
- 浏览器打开 `http://<服务器IP>:<端口>/version.txt`，是同一个提交号
- 用生产 admin 登录（密码见 3.4），首页是你改的那句话
- 在服务器上进生产库（命令见第 5 节），查 `sys_oper_log` 最新一条：是你刚才的登录，IP 不是 172 开头（是你的公网 IP；开着 Clash 的话可能是代理的出口 IP）

**完成标准**：上面四条都对上，在对话里说"部署练习好了"，附上 `version.txt` 的内容。

## 8. 🎤 今天的面试题

**问：Docker 的镜像和容器有什么区别？**

**答**：镜像是只读的模板，容器是用镜像跑起来的一个实例，像类和对象的关系。我们项目里，`deploy/Dockerfile` 描述怎么做镜像：在 JRE 21 的基础镜像上放进 jar，指定用普通用户、用 `java -jar` 启动。`docker compose build app` 按它做出 `lingmao-app` 这个镜像；`docker compose up -d app` 用这个镜像起一个容器，同时给它环境变量（数据库地址、密钥）、挂载上传目录、限制 512MB 内存。容器里写的东西随容器删掉就没了，所以上传的文件通过挂载放在容器外面的 `/opt/lingmao/uploads`，每次发版重建容器，文件还在。

**问：为什么后端前面要放一个 Nginx？**

**答**：Nginx 在我们这里是反向代理加静态文件服务器。一是前端打包出来就是一堆 html、js、css，Nginx 直接返回，比让 Spring Boot 去返回快，还能开 gzip 压缩（Element Plus 的 js 从 1MB 压到 391KB）。二是对外只暴露一个端口，`/api/` 开头的请求转给后端容器，后端本身不对外开端口，浏览器看来前端和接口是同一个地址，没有跨域问题。三是统一处理一些和业务无关的事：上传大小限制、缓存头、把真实客户端 IP 写进 `X-Forwarded-For` 交给后端记日志。以后上 HTTPS，证书也只配在 Nginx 上，后端不用改。
