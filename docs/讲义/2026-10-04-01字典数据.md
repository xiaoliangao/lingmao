## 0. 开工前：先把 V1 改回去

你在 `V1__init.sql` 里加了一行注释 `--唯一索引`。现在这样启动应用会失败，我在副本里试过，报错是：

```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
Either revert the changes to the migration, or run repair to update the schema history.
```

**为什么加一行注释也不行**

Flyway 每执行完一个迁移文件，都会在库里的 `flyway_schema_history` 表记一行，其中有这个文件内容算出来的**校验和**（checksum）。这是我们开发库里现在的记录：

```
 installed_rank | version | description |    script    |  checksum  | success
----------------+---------+-------------+--------------+------------+---------
              1 | 1       | init        | V1__init.sql | -130243950 | t
```

每次启动，Flyway 都会把 `V1__init.sql` 现在的内容重新算一遍校验和，和表里记的 `-130243950` 对比。你加了注释，文件内容变了，校验和也就变了。Flyway 没法判断"文件变了，数据库要不要跟着变"，干脆拒绝启动。

这么严格是故意的：迁移文件就是数据库结构的历史记录。要是允许改旧文件，你的库、同事的库、生产库就会各自是不同的样子，而且没人知道。

**规矩**：执行过的迁移文件一个字都不能改，注释也不行。要改表结构，就加一个新文件 `V2`、`V3`……今天就会写第一个。

**怎么改回去**：IDEA 里右键 `V1__init.sql` → Git → Rollback。或者在 SCM 目录下执行：

```bash
git checkout -- src/main/resources/db/migration/V1__init.sql
```

改回去以后，`git status` 里应该看不到 V1 了。

## 1. 今天做什么

做"字典数据"的 6 个接口。做完之后：

- 在 Swagger 里能给"季节"这个字典类型加上春、夏、秋、冬四个选项，能改、能删、能分页查。（Swagger 是一个自动生成的接口文档网页）
- 前端的下拉框调 `GET /api/dict-data/by-type/season`，拿到按顺序排好、只包含启用项的选项列表。

**它在整个系统里的位置**：系统里所有的下拉选项都从这里取，比如 W3 物料的"季节""单位"、W5 采购单的"订单类型"。加一个选项不用改代码、不用重新发布，在页面上加一条数据就行。

**字典类型和字典数据的关系**：

```
sys_dict_type（字典类型，已经写好的样板）    sys_dict_data（字典数据，今天写）
id | code    | name                          id | type_code | label | value | sort | status
 1 | season  | 季节        1 ──────── N       1 | season    | 春季  | 1     | 1    | 1
                                              2 | season    | 夏季  | 2     | 2    | 1
                                              3 | season    | 冬季  | 4     | 0    | 0（停用）
```

- `label` 是给人看的（"春季"），`value` 是存进业务表的（"1"）。W3 的物料表存的是 `1`，不是"春季"。这样"春季"以后改名叫"春"，所有物料自动跟着变。
- `type_code` 存的是类型的 code（`season`），不是 id。因为前端代码里写死的就是 `season` 这个名字；要是存 id，前端得先查"season 的 id 是几"，而且开发库和生产库的 id 还可能不一样。

## 2. 为什么这么设计

### 2.1 接口

| 方法 | 路径 | 作用 | 出错时 |
|---|---|---|---|
| GET | `/api/dict-data?typeCode=&label=&page=&size=` | 管理页的分页列表，停用的也显示 | 400 参数不合法 |
| GET | `/api/dict-data/by-type/{typeCode}` | 下拉框用：只要启用的、按 sort 排好、不分页 | — |
| GET | `/api/dict-data/{id}` | 详情 | 404 |
| POST | `/api/dict-data` | 新增，返回新 id | 400；1000 类型不存在；1000 存储值已存在 |
| PUT | `/api/dict-data/{id}` | 修改 | 同上，外加 404 |
| DELETE | `/api/dict-data/{id}` | 删除（逻辑删除） | 404 |

路径规则和字典类型一样：资源名用复数名词，"查、增、改、删"分别对应 GET、POST、PUT、DELETE。错误码见 `R.java` 的注释：400 参数错、404 不存在、1xxx 业务上不允许。

### 2.2 三个取舍

**取舍一：新增时检查"类型存在"，直接注入 `DictTypeMapper`，不调 `DictTypeService`。**

字典类型和字典数据都属于系统域（`module/system`）。今天的作业要让 `DictTypeServiceImpl` 反过来查字典数据。要是两边都注入对方的 Service，就成了 A 依赖 B、B 又依赖 A。我们用的是构造器注入，Spring 启动时会直接报错：`The dependencies of some of the beans in the application context form a cycle`。

所以项目里定一条规矩：**同一个域内，可以直接用兄弟表的 Mapper 做只读检查；跨域必须调对方的 Service。** 跨域为什么不行，见 [H2 第 4 节](../docs/原理卡/H2-模块划分.md)。

**取舍二："同一类型下 value 不能重复"，代码查重和数据库唯一索引两样都要。**

- **代码查重**：负责给用户一句看得懂的提示，`存储值已存在: 1`。
- **唯一索引**：负责兜底。两个人同时提交同一个 value 时，两边的查重都可能查到"没有"，然后都插进去。只有唯一索引能在数据库这一层挡住第二条。时间线图见 [C2 第 5 节](../docs/原理卡/C2-索引.md)。
- **索引只管没删除的行**（部分索引 `WHERE deleted = false`）。我们的删除只是把 `deleted` 改成 true，行还留在表里。普通唯一索引会让删过的 value 永远建不回来，部分索引不会。见 [C2 第 6 节](../docs/原理卡/C2-索引.md)。
- **列顺序是 `(type_code, value)`，type_code 在前**。by-type 接口单独按 type_code 查。按最左前缀规则，type_code 放在前面，这个索引也能服务那条查询；反过来放就用不上了。见 [C2 第 4 节](../docs/原理卡/C2-索引.md)。

**取舍三：by-type 只返回启用的，分页查询返回全部。**

停用一个选项，意思是"新单据不要再选它"，所以下拉框里不该再出现。但旧单据里还存着它的 value，管理页也还要能看到它、把它重新启用。所以"只要启用的"这个过滤只加在 by-type 一个接口上。

## 3. 要建的文件

从下往上建：表 → 实体 → 数据访问 → 入参 → 业务 → 接口 → 测试。每一层都要用到下一层，所以下层先有。

| 顺序 | 文件（都在 `src/main/...` 或 `src/test/...` 下） | 作用 |
|---|---|---|
| 1 | `resources/db/migration/V2__dict_data_unique_value.sql` | 加部分唯一索引 |
| 2 | `java/.../system/entity/DictData.java` | 表的镜像 |
| 3 | `java/.../system/mapper/DictDataMapper.java` | 拿到现成的增删改查 |
| 4 | `java/.../system/dto/DictDataQuery.java` | 分页查询的入参 |
| 5 | `java/.../system/dto/DictDataSaveReq.java` | 新增、修改的入参和校验 |
| 6 | `java/.../system/service/DictDataService.java` | 这个模块能做的事 |
| 7 | `java/.../system/service/impl/DictDataServiceImpl.java` | 业务规则 |
| 8 | `java/.../system/controller/DictDataController.java` | HTTP 接口 |
| 9 | `test/.../system/service/impl/DictDataServiceImplTest.java` | 钉住业务规则 |
| 10 | `test/.../system/controller/DictDataControllerTest.java` | 钉住接口层 |

`...` 代表 `com/lingmao/scm/module`。建 Java 类的方法：IDEA 里右键对应的包 → New → Java Class，输入类名；接口要在弹窗里选 Interface。

一个请求穿过这些文件的路径，以新增为例：

```
POST /api/dict-data  {"typeCode":"season","label":"春季","value":"1"}
  → DictDataController.create        JSON 转成 DictDataSaveReq，@Valid 校验
  → DictDataService.create           Controller 只认识接口
  → DictDataServiceImpl.create       查类型存在 → 查 value 不重复 → 拷成 DictData → insert
  → DictDataMapper.insert            生成 INSERT，数据库回填 id
  → 返回 id → R.ok(id) → {"code":0,"msg":"ok","data":1}
```

各层为什么这么分，见 [A4](../docs/原理卡/A4-分层架构与依赖方向.md)。

## 4. 逐个文件

### 4.1 `src/main/resources/db/migration/V2__dict_data_unique_value.sql`

右键 `db/migration` 目录 → New → File，文件名照抄，**V2 后面是两个下划线**。

```sql
-- V2：同一个字典类型下，存储值 value 不能重复。
-- 只约束未删除的行（部分索引），这样删掉的 value 以后还能重新建。
CREATE UNIQUE INDEX uk_sys_dict_data_type_value ON sys_dict_data (type_code, value) WHERE deleted = false;
```

**为什么这么写**

- **文件名 `V2__xxx.sql`**：Flyway 靠文件名认版本，`V` + 版本号 + 两个下划线 + 描述。启动时它发现库里只执行到 V1，就会自动执行 V2。
- **为什么要新建文件，不往 V1 里加**：第 0 节讲过，V1 已经执行过，一个字都不能动。
- **索引名 `uk_表名_列名`**：`uk` 代表唯一（unique key），普通索引用 `idx`。报唯一冲突时，错误信息里会带着索引名，一眼就知道是哪条规则被违反了。
- **`WHERE deleted = false`**：这就是"部分索引"，只把没删除的行放进索引，见 2.2 的取舍二。

**⚠️ 注意**：这个文件一旦被执行过（你启动一次应用，或者跑一次全部测试），就和 V1 一样不能再改了。**启动之前对着上面再核对一遍。** 真要是执行后才发现写错了，先来问我，别直接改文件。

### 4.2 `entity/DictData.java`

```java
package com.lingmao.scm.module.system.entity;

import com.baomidou.mybatisplus.annotation.TableName;
import com.lingmao.scm.common.entity.BaseEntity;
import lombok.Data;
import lombok.EqualsAndHashCode;

@Data
@EqualsAndHashCode(callSuper = true)
@TableName("sys_dict_data")
public class DictData extends BaseEntity {
    private String typeCode;
    private String label;
    private String value;
    private Integer sort;
    private Integer status;
    private String remark;
}
```

**为什么这么写**

- **`extends BaseEntity`**：id、创建时间、修改时间、deleted 这 6 个字段每张表都有，写在父类里只写一次。继承之后，插入时自动填时间、删除时变成逻辑删除，这些功能自动就有了。
- **`@TableName("sys_dict_data")`**：类名 `DictData` 和表名 `sys_dict_data` 对不上，要告诉 MyBatis-Plus 这个类对应哪张表。
- **字段写 `typeCode`，列名是 `type_code`**：`application.yaml` 里开了 `map-underscore-to-camel-case`（下划线转驼峰），框架会自动对应。
- **用 `Integer` 不用 `int`**：`int` 不能为空，没赋值就是 0；`Integer` 可以是 null。插入时 MyBatis-Plus 会**跳过值为 null 的字段**，这样表里定义的默认值（`sort DEFAULT 0`、`status DEFAULT 1`）才会生效。要是用 `int`，就会把 0 硬写进去，`status` 默认就成了 0（停用）。
- **`@Data`**：Lombok 在编译时帮你生成 getter、setter、toString。
- **`@EqualsAndHashCode(callSuper = true)`**：`@Data` 生成的 equals 默认只比较本类的字段，不比较父类里的 id。这样两条 id 不同、内容一样的数据会被判成"相等"，放进 Set 就会被去重。加上这个注解，比较时会把父类字段也算进去。
- **实体里没有校验注解，也没有业务方法**：实体只描述"表长什么样"。"参数合不合法"归 DTO 管，"业务上允不允许"归 Service 管。

### 4.3 `mapper/DictDataMapper.java`（接口）

```java
package com.lingmao.scm.module.system.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.lingmao.scm.module.system.entity.DictData;
import org.apache.ibatis.annotations.Mapper;

@Mapper
public interface DictDataMapper extends BaseMapper<DictData> {
}
```

**为什么一个空接口就能用**

- **你不用写实现类**：应用启动时，MyBatis 会自动生成一个实现这个接口的对象（叫"代理"），放进 Spring 容器。Service 里注入的就是它。
- **`BaseMapper<DictData>`**：尖括号里的 `DictData` 告诉框架"我管这张表"，于是 `insert`、`selectById`、`selectPage`、`deleteById`、`exists` 这些方法都是现成的。
- **`@Mapper`**：给扫描器做个标记，告诉它"这个接口要生成实现"。
- **什么时候才往里面加方法**：联表、统计这类 BaseMapper 做不到的 SQL。W5 才会遇到。

### 4.4 `dto/DictDataQuery.java`

```java
package com.lingmao.scm.module.system.dto;

import com.lingmao.scm.common.page.PageQuery;
import lombok.Data;
import lombok.EqualsAndHashCode;

@Data
@EqualsAndHashCode(callSuper = true)
public class DictDataQuery extends PageQuery {
    private String typeCode;
    private String label;
}
```

**为什么这么写**

- **`extends PageQuery`**：分页参数 `page`、`size` 和它们的校验（size 最多 500，防止一次拉几十万行）写在父类里，每个列表接口都继承它，前端传参的方式全系统统一。
- **两个筛选字段可以为空**：为空表示"不按这个条件筛"。Service 里会根据它们是不是空，决定要不要拼进 WHERE。
- **为什么是 GET 参数而不是 JSON**：查询不改数据，用 GET。GET 的参数在 URL 上（`?typeCode=season&page=1`），Spring 会按字段名自动填进这个对象。

### 4.5 `dto/DictDataSaveReq.java`

```java
package com.lingmao.scm.module.system.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import lombok.Data;

@Data
public class DictDataSaveReq {

    @NotBlank(message = "字典类型不能为空")
    @Size(max = 64, message = "字典类型最长 64")
    private String typeCode;

    @NotBlank(message = "显示文本不能为空")
    @Size(max = 64, message = "显示文本最长 64")
    private String label;

    @NotBlank(message = "存储值不能为空")
    @Size(max = 64, message = "存储值最长 64")
    private String value;

    /** 越小越靠前 */
    private Integer sort = 0;

    /** 1 启用 0 停用 */
    private Integer status = 1;

    @Size(max = 255, message = "备注最长 255")
    private String remark;
}
```

**为什么这么写**

- **校验写在这里，不写在实体上**：校验是"接口入参"的规矩，不是"表"的规矩。Controller 上的 `@Valid` 会在进入 Service **之前**检查这些注解，不合格直接返回 400，业务代码根本不会执行。这叫"在边界拦截"。
- **`@NotBlank` 和 `@NotNull` 的区别**：`@NotNull` 只拦 null；`@NotBlank` 连 `""` 和 `"   "` 也拦。字符串一般用 `@NotBlank`。
- **`@Size(max = 64)` 和表里的 `VARCHAR(64)` 对应**：不在这里拦的话，超长的字符串会一路传到数据库才报错，用户看到的是 500。
- **`sort = 0`、`status = 1` 是默认值**：前端没传时用它们，和表里的 DEFAULT 一致。
- **没有 id 字段**：新增时 id 由数据库生成；修改时 id 从 URL 路径上拿（`PUT /api/dict-data/5`）。要是 id 写在请求体里，前端就有机会传一个和路径不一样的 id，不知道该信哪个。
- **新增和修改用同一个 DTO**：两者要填的字段完全一样。等哪天不一样了（比如某个字段创建后不许改），再拆成两个。

### 4.6 `service/DictDataService.java`（接口）

```java
package com.lingmao.scm.module.system.service;

import com.lingmao.scm.common.page.PageResult;
import com.lingmao.scm.module.system.dto.DictDataQuery;
import com.lingmao.scm.module.system.dto.DictDataSaveReq;
import com.lingmao.scm.module.system.entity.DictData;

import java.util.List;

public interface DictDataService {

    PageResult<DictData> page(DictDataQuery query);

    DictData getById(Long id);

    /** 某个类型下启用的选项，按 sort 排好，给下拉框用 */
    List<DictData> listByType(String typeCode);

    Long create(DictDataSaveReq req);

    void update(Long id, DictDataSaveReq req);

    void delete(Long id);
}
```

**为什么这么写**

- **为什么要单独一个接口**：Controller 只依赖这个接口，不知道实现类的存在。好处一：写 Controller 测试时，可以用一个假的实现换掉它（见 4.10）；好处二：读这 6 行就知道这个模块能做什么，不用翻 100 行的实现。
- **`listByType` 返回 `List`，`page` 返回 `PageResult`**：下拉框要的是全部选项，不分页；管理页的表格才要分页，`PageResult` 就是 `{list, total}`。
- **`create` 返回 `Long`**：返回新数据的 id，前端新增完要跳转详情或刷新列表时用得到。

### 4.7 `service/impl/DictDataServiceImpl.java`（今天的重点）

先看完整代码，再分段讲：

```java
package com.lingmao.scm.module.system.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.lingmao.scm.common.exception.BizException;
import com.lingmao.scm.common.page.PageResult;
import com.lingmao.scm.module.system.dto.DictDataQuery;
import com.lingmao.scm.module.system.dto.DictDataSaveReq;
import com.lingmao.scm.module.system.entity.DictData;
import com.lingmao.scm.module.system.entity.DictType;
import com.lingmao.scm.module.system.mapper.DictDataMapper;
import com.lingmao.scm.module.system.mapper.DictTypeMapper;
import com.lingmao.scm.module.system.service.DictDataService;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.BeanUtils;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.util.List;

@Service
@RequiredArgsConstructor
public class DictDataServiceImpl implements DictDataService {

    private final DictDataMapper dictDataMapper;
    private final DictTypeMapper dictTypeMapper;

    @Override
    public PageResult<DictData> page(DictDataQuery query) {
        LambdaQueryWrapper<DictData> wrapper = new LambdaQueryWrapper<DictData>()
                .eq(StringUtils.hasText(query.getTypeCode()), DictData::getTypeCode, query.getTypeCode())
                .like(StringUtils.hasText(query.getLabel()), DictData::getLabel, query.getLabel())
                .orderByAsc(DictData::getSort)
                .orderByAsc(DictData::getId);
        return PageResult.of(dictDataMapper.selectPage(query.toPage(), wrapper));
    }

    @Override
    public DictData getById(Long id) {
        DictData entity = dictDataMapper.selectById(id);
        if (entity == null) {
            throw new BizException(404, "字典数据不存在: " + id);
        }
        return entity;
    }

    @Override
    public List<DictData> listByType(String typeCode) {
        return dictDataMapper.selectList(new LambdaQueryWrapper<DictData>()
                .eq(DictData::getTypeCode, typeCode)
                .eq(DictData::getStatus, 1)
                .orderByAsc(DictData::getSort)
                .orderByAsc(DictData::getId));
    }

    @Override
    @Transactional
    public Long create(DictDataSaveReq req) {
        ensureTypeExists(req.getTypeCode());
        ensureValueUnique(req.getTypeCode(), req.getValue(), null);
        DictData entity = new DictData();
        BeanUtils.copyProperties(req, entity);
        dictDataMapper.insert(entity);
        return entity.getId();
    }

    @Override
    @Transactional
    public void update(Long id, DictDataSaveReq req) {
        DictData entity = getById(id);
        ensureTypeExists(req.getTypeCode());
        ensureValueUnique(req.getTypeCode(), req.getValue(), id);
        BeanUtils.copyProperties(req, entity);
        dictDataMapper.updateById(entity);
    }

    @Override
    @Transactional
    public void delete(Long id) {
        getById(id);
        dictDataMapper.deleteById(id);
    }

    private void ensureTypeExists(String typeCode) {
        boolean exists = dictTypeMapper.exists(new LambdaQueryWrapper<DictType>()
                .eq(DictType::getCode, typeCode));
        if (!exists) {
            throw new BizException("字典类型不存在: " + typeCode);
        }
    }

    private void ensureValueUnique(String typeCode, String value, Long excludeId) {
        boolean exists = dictDataMapper.exists(new LambdaQueryWrapper<DictData>()
                .eq(DictData::getTypeCode, typeCode)
                .eq(DictData::getValue, value)
                .ne(excludeId != null, DictData::getId, excludeId));
        if (exists) {
            throw new BizException("存储值已存在: " + value);
        }
    }
}
```

#### 类的开头

- **`@Service`**：告诉 Spring "这是一个要交给你管理的对象"。启动时 Spring 会创建它的唯一一个实例，谁需要 `DictDataService`，就把这个实例给谁。
- **`private final` + `@RequiredArgsConstructor`**：Lombok 会给所有 `final` 字段生成一个构造器，Spring 通过这个构造器把两个 Mapper 传进来，这叫"构造器注入"。为什么用 `final`：注入后就不能再被改掉；而且 `@RequiredArgsConstructor` 只把 final 字段放进构造器，忘了写 `final`，这个 Mapper 就没人赋值，编译和启动都正常，第一次调用才空指针（答疑里有实验）。
- **两个 Mapper**：一个是自己表的，一个是兄弟表的（只读检查用），对应 2.2 的取舍一。

#### `page`：分页查询

- **`LambdaQueryWrapper`** 是用 Java 代码拼 WHERE 条件的工具。
- **`DictData::getTypeCode`** 代替字符串 `"type_code"` 写列名：列名拼错的话，编译时就能发现。
- **`.eq(条件, 列, 值)`**：第一个参数是 false 时，这一句**不拼**。前端没传 typeCode 时，`StringUtils.hasText` 返回 false，就不按类型筛选。
- **`.eq` 和 `.like`**：typeCode 是精确匹配（等于），label 是模糊匹配（包含），因为管理员搜"春"应该能搜出"春季"。
- **排序**：先按 sort，sort 一样再按 id。只按 sort 的话，sort 相同的几行每次查出来的顺序可能不一样，翻页时会出现重复或漏行。

传 `typeCode=season&label=春` 时，真实发出的 SQL：

```
SELECT COUNT(*) AS total FROM sys_dict_data WHERE deleted = false AND (type_code = ? AND label LIKE ?)
Parameters: season(String), %春%(String)
SELECT id,type_code,label,... FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND label LIKE ?) ORDER BY sort ASC,id ASC LIMIT ?
Parameters: season(String), %春%(String), 20(Long)
```

- `deleted=false` 是逻辑删除自动加的。
- `%春%` 两边的 % 是 `.like` 加的。
- 第一条算总数，第二条取当页数据。`LIMIT` 由分页插件拼上。

更多写法和 SQL 的对照见 [C5 第 2、3 节](../docs/原理卡/C5-ORM与MyBatis-Plus.md)。

#### `getById`：查不到就抛 404

- **为什么抛异常，而不是返回 null**：返回 null 的话，每个调用方都得写一遍 `if (x == null)`，总会有地方漏掉，然后空指针。抛 `BizException(404, ...)` 之后，它会一路传到 `GlobalExceptionHandler`，自动变成 `{"code":404,"msg":"字典数据不存在: 5"}`。Controller 里一个 try/catch 都不用写。
- **后面的 update、delete 都先调它**：等于顺手做了"存在性检查"，这个规则只写这一次。

#### `listByType`：下拉框用

- **`selectList`**：不分页，返回全部，因为一个类型下的选项最多几十个。
- **`.eq(DictData::getStatus, 1)`**：只要启用的，对应 2.2 的取舍三。

真实 SQL：

```
SELECT id,type_code,label,... FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND status = ?) ORDER BY sort ASC,id ASC
Parameters: season(String), 1(Integer)
```

#### `create`：新增

执行顺序是：**先检查，再写库**。两项检查有一项不过就抛异常，后面的 insert 根本不会执行。

- **为什么先查类型、再查重复**：类型都不存在的话，"值重复"的提示就没意义了。先报最根本的问题。
- **`BeanUtils.copyProperties(req, entity)`**：把 DTO 里同名的字段拷到实体上。DTO 里没有 id、deleted，所以前端改不到这些列。
- **`insert` 之后 `entity.getId()` 就有值了**：数据库生成 id 后，MyBatis-Plus 会把它回填到这个对象上。
- **为什么只有一条 insert 也加 `@Transactional`**：一是习惯，所有写操作统一加，不用每次判断"这次要不要"；二是检查和插入在同一个事务里；三是以后这个方法多写一张表（比如记操作日志）时，不会忘了加。

新增"春季"时真实发出的三条 SQL：

```
SELECT COUNT( * ) AS total FROM sys_dict_type WHERE deleted=false AND (code = ?)                       ← ensureTypeExists
SELECT COUNT( * ) AS total FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND value = ?)    ← ensureValueUnique
INSERT INTO sys_dict_data ( type_code, label, value, sort, status, create_by, create_time, update_by, update_time ) VALUES ( ?, ?, ?, ?, ?, ?, ?, ?, ? )
```

注意 `remark` 没出现在 INSERT 里：它是 null，被跳过了（4.2 讲过）。

#### `update`：修改

- **第一行 `getById(id)`**：不存在直接 404。顺便拿到旧数据，下面在它的基础上改。
- **查重时传 `id`，排除自己**：把"春季"的 label 改成"春"、value 还是 `1`，这时库里 value=1 的那条正是它自己。不排除自己的话，就会报"已存在"，改不了。
- **`.ne(excludeId != null, DictData::getId, excludeId)`**：`ne` 是"不等于"。新增时 `excludeId` 是 null，这句不拼；修改时拼成 `id <> ?`。

修改时真实的查重 SQL，多了 `id <> ?`：

```
SELECT COUNT( * ) AS total FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND value = ? AND id <> ?)
Parameters: season(String), 1(String), 1(Long)
```

#### `delete`：删除

- **先 `getById`**：删除不存在的记录要报 404，不能"静默成功"。
- **`deleteById` 实际发的是 UPDATE**，因为 BaseEntity 的 deleted 上有 `@TableLogic`：

```
UPDATE sys_dict_data SET update_by=?,update_time=?, deleted=true WHERE id=? AND deleted=false
```

#### 两个私有方法

- **为什么把检查抽成私有方法**：`create` 和 `update` 都要做这两项检查，写一次，用两次。方法名就是规则名，`create` 读起来像一句话："确认类型存在，确认值不重复，然后插入"。
- **`exists` 和 `selectCount`**：字典类型的样板用的是 `selectCount(...) > 0`，这里用的是 `exists(...)`。两者发出去的 SQL 一样（上面的 `COUNT( * )` 就是 `exists` 发的），但 `exists` 返回 boolean，读起来更直白。写测试时要注意：实现里调的是 `exists`，测试里就得 stub `exists`，见 4.9。

### 4.8 `controller/DictDataController.java`

```java
package com.lingmao.scm.module.system.controller;

import com.lingmao.scm.common.page.PageResult;
import com.lingmao.scm.common.result.R;
import com.lingmao.scm.module.system.dto.DictDataQuery;
import com.lingmao.scm.module.system.dto.DictDataSaveReq;
import com.lingmao.scm.module.system.entity.DictData;
import com.lingmao.scm.module.system.service.DictDataService;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;

@Tag(name = "字典数据")
@RestController
@RequestMapping("/api/dict-data")
@RequiredArgsConstructor
public class DictDataController {

    private final DictDataService dictDataService;

    @Operation(summary = "分页查询")
    @GetMapping
    public R<PageResult<DictData>> page(@Valid DictDataQuery query) {
        return R.ok(dictDataService.page(query));
    }

    @Operation(summary = "按类型取启用的选项（下拉框用，不分页）")
    @GetMapping("/by-type/{typeCode}")
    public R<List<DictData>> listByType(@PathVariable("typeCode") String typeCode) {
        return R.ok(dictDataService.listByType(typeCode));
    }

    @Operation(summary = "详情")
    @GetMapping("/{id}")
    public R<DictData> get(@PathVariable("id") Long id) {
        return R.ok(dictDataService.getById(id));
    }

    @Operation(summary = "新增，返回新 id")
    @PostMapping
    public R<Long> create(@Valid @RequestBody DictDataSaveReq req) {
        return R.ok(dictDataService.create(req));
    }

    @Operation(summary = "修改")
    @PutMapping("/{id}")
    public R<Void> update(@PathVariable("id") Long id, @Valid @RequestBody DictDataSaveReq req) {
        dictDataService.update(id, req);
        return R.ok();
    }

    @Operation(summary = "删除（逻辑删除）")
    @DeleteMapping("/{id}")
    public R<Void> delete(@PathVariable("id") Long id) {
        dictDataService.delete(id);
        return R.ok();
    }
}
```

**为什么这么写**

- **每个方法只做三件事**：收参数、调 Service、包成 `R`。没有 if，没有 try/catch。规则全在 Service 里，出错由全局异常处理器统一处理。
- **`@RestController`**：方法的返回值会自动转成 JSON。
- **`@RequestMapping("/api/dict-data")`**：类上写公共前缀，方法上只写后半段。
- **`@Valid`**：触发 DTO 上的校验注解。查询参数（`DictDataQuery`）和请求体（`DictDataSaveReq`）都要加，漏了的话校验注解就成了摆设。
- **`@RequestBody`**：POST、PUT 的参数在 JSON 请求体里，要加它；GET 的查询参数在 URL 上，不加。
- **`@PathVariable("id")` 把名字写明**：不写名字的话，Spring 要靠编译参数 `-parameters` 才能知道参数名叫 id。IDEA 自己编译时不一定带这个参数，那样就会报错。写明名字最稳。
- **`/by-type/{typeCode}` 和 `/{id}` 不冲突**：前者是两段路径（`/by-type/season`），后者是一段（`/5`），Spring 能分清。
- **`@Tag`、`@Operation`**：只用来给 Swagger 页面分组和写说明，不影响功能。


**规则和测试的对照**：

| 规则 | 测试 |
|---|---|
| 类型不存在不能新增，也不写库 | `create_typeNotExists_throwsAndNotInsert` |
| 同类型下 value 重复不能新增，也不写库 | `create_valueExists_throwsAndNotInsert` |
| 检查都通过才插入，返回新 id | `create_ok_returnsGeneratedId` |
| 修改不存在的记录报 404，不发 update | `update_notFound_throws404AndNotUpdate` |

**为什么这么写**

- **两个 `@Mock`**：ServiceImpl 的构造器要两个 Mapper，`@InjectMocks` 会把这两个假的传进去。**少写一个的话，Mockito 会传 null 进去**，用到那个 Mapper 时就会空指针。今天的作业会碰到这个问题。
- **`when(dictTypeMapper.exists(any())).thenReturn(false)`**：一行代码就决定了"库里没有这个类型"。不用连数据库，也不用准备数据。
- **stub 的是 `exists`，不是 `selectCount`**：实现里调的是 `exists`。`exists` 是接口里的默认方法，在假对象上它不会去调 `selectCount`，所以 stub `selectCount` 根本不起作用。**实现里调什么，测试就 stub 什么。**见 [G2 第 6 节](../docs/原理卡/G2-Mock的意义.md)。
- **第一个测试为什么不 stub `dictDataMapper.exists`**：类型不存在时，代码在第一项检查就抛异常了，根本不会走到第二项。`MockitoExtension` 是严格模式：stub 了却没被调用，测试会报 `UnnecessaryStubbingException`。
- **`verify(..., never()).insert(...)`**：只断言"抛了异常"还不够，还要确认**没写库**。万一有人把检查挪到 insert 后面，异常照样会抛，但数据已经写进去了。
- **`doAnswer` 回填 id**：`insert` 的返回值是"影响了几行"（1），不是 id。id 是数据库回填到 entity 对象上的，所以只能用 `doAnswer` 拿到传进来的 entity，手动 set 一个 id。
- **mock 测不到什么**：`exists(any())` 不管你的 Wrapper 写了什么条件都返回 true。比如把 `.eq(DictData::getValue, value)` 写成了 `.eq(DictData::getLabel, value)`，测试照样是绿的。SQL 对不对，要靠第 5 节启动后实际调接口、看控制台打印的 SQL。

**问：Flyway 已经执行过的迁移脚本，为什么不能改？**

**答**：Flyway 在 `flyway_schema_history` 表里记录了每个已执行脚本的校验和，每次启动都会重新计算并比对，对不上就拒绝启动。我改 `V1__init.sql`、只加了一行注释，应用就报 `Migration checksum mismatch for migration version 1` 起不来。这个机制保证了所有环境的库结构都由同一串脚本按同样的顺序生成。要改结构就加新脚本，比如我用 `V2__dict_data_unique_value.sql` 加了一个唯一索引。

**问：代码里已经查重了，为什么还要建唯一索引？逻辑删除下唯一索引怎么建？**

**答**：查重和插入之间有时间空隙，两个请求可以同时通过查重，只有唯一索引能在数据库层挡住第二条。我们是逻辑删除，删掉的行还在表里，普通唯一索引会让删过的值再也建不回来，所以在 PostgreSQL 里用部分索引：`CREATE UNIQUE INDEX ... ON sys_dict_data (type_code, value) WHERE deleted = false`。type_code 放在前面，这样按类型查下拉选项的查询也能用上这个索引。

## 8. 答疑

（你在对话里问的问题，如果别人也会问，补在这里）

**问：“索引只管没删除的行”是什么意思？**

**答**：我们的“删除”只是把 `deleted` 改成 true，这一行还留在表里。普通唯一索引会把表里每一行都算进去，已删除的行也算。部分索引后面带 `WHERE deleted = false`，只把没删除的行放进索引，已删除的行不参与比较。

下面是在 PostgreSQL 临时表里真实跑出来的结果。先看普通唯一索引：建一条 `(season, 1)`，删掉，再建同样的一条：

```
UPDATE t_plain SET deleted = true WHERE id = 1;
UPDATE 1
INSERT INTO t_plain VALUES (2, 'season', '1', '春季', false);
ERROR:  duplicate key value violates unique constraint "uk_plain"
DETAIL:  Key (type_code, value)=(season, 1) already exists.
```

用户在页面上已经看不到春季了，想重新建一条，结果数据库说“已存在”。原因是那条已删除的行还占着这个键。

换成部分索引，同样的操作：

```
INSERT INTO t_partial VALUES (2, 'season', '1', '春季', false);
INSERT 0 1
 id | type_code | value | label | deleted
----+-----------+-------+-------+---------
  1 | season    | 1     | 春季  | t
  2 | season    | 1     | 春季  | f
```

这次插得进去。两条没删除的行撞在一起时照样报 `duplicate key`，所以“同一类型下 value 不能重复”这条规矩一点没松。不管删几次、重建几次，表里可以有任意多条已删除的 `(season, 1)`，但没删除的最多一条。

**问：新建文件时，什么时候选 Class，什么时候选 Interface？**

**答**：问自己一句：**这个文件里的方法体由谁来写？** 你自己写，或者文件主要用来装数据，就选 Class。别人来写（框架自动生成，或者另一个类去实现），这里只声明“能做什么”，就选 Interface。

| 层 | 选 | 原因 |
|---|---|---|
| entity、dto | Class | 装数据，框架要 `new` 出对象往字段里填值 |
| mapper | Interface | 实现由 MyBatis 启动时自动生成，你只声明 |
| service | Interface | 写下这个模块能做哪些事，Controller 只依赖它 |
| service/impl | Class | 业务规则的方法体在这里写，`implements` 上面那个接口 |
| controller、config、异常处理 | Class | 方法体你自己写，也没有别的类依赖它 |

选错了怎么办：不用删掉文件重建，把文件里的 `class` 改成 `interface` 就行，IDEA 弹窗只是帮你写好第一行。Mapper 选成 Class 时，编译器报的是：

```
error: no interface expected here
class DictDataMapper extends BaseMapper<DictData> {}
```

意思是 `extends` 后面只能跟类，`BaseMapper` 却是接口。要是改写成 `implements`，又会报 `DictDataMapper is not abstract and does not override abstract method selectById(Long) in BaseMapper`：这时候 BaseMapper 那二十来个方法都得你自己实现，可它们本来应该交给 MyBatis 生成。

**问：`@EqualsAndHashCode(callSuper = true)` 到底在干什么？**

**答**：`equals` 用来判断两个对象算不算相等。`@Data` 会替你生成一个 equals，做法是把字段挨个比一遍，但只比**本类自己声明的字段**。`DictData` 自己声明的是 typeCode、label、value 这些；id 和 deleted 声明在父类 `BaseEntity` 里，不在比较范围内。

用 `delombok` 把 Lombok 生成的代码还原出来（节选）：

```java
// 只有 @Data
public boolean equals(Object o) {
    ...
    if (!other.canEqual(this)) return false;
    // 比 typeCode、label、value，没有 id
}

// 加了 callSuper = true
public boolean equals(Object o) {
    ...
    if (!other.canEqual(this)) return false;
    if (!super.equals(o)) return false;      // 多出这一行：先让父类比 id、deleted
    // 再比 typeCode、label、value
}
```

拿上面部分索引例子里的三行来试：都是 `(season, 1, 春季)`，id 分别是 1、2、3，前两行已删除。下面是真实运行结果：

```
== 不加 callSuper ==
a1.equals(a3) = true
放进 HashSet 后剩几个: 1  [DictDataNoSuper(typeCode=season, label=春季, value=1)]
== 加 callSuper = true ==
b1.equals(b3) = false
放进 HashSet 后剩几个: 3
```

HashSet 每放一个元素都要问一句“里面有没有和它 equals 的”，有就不放。所以不加 callSuper 时，三条不同的数据只剩下一条。hashCode 是 HashSet 用来快速找位置的编号，必须和 equals 保持一致，所以注解名字里两个都有，Lombok 一起生成。

不加这个注解，编译时 Lombok 自己就会警告：`Generating equals/hashCode implementation but without a call to superclass, even though this class does not extend java.lang.Object.`

规矩：**实体继承 BaseEntity，又用了 @Data，就一定要加 `@EqualsAndHashCode(callSuper = true)`**。

**问：“筛选字段为空就不筛”“GET 参数自动填进对象”，能举个例子吗？**

**答**：字典类型的列表接口已经是同一个写法（code、name 两个可空的筛选字段），下面是用它真实跑出来的结果。表里有三行：season/季节、unit/单位、season_old/旧季节。

| URL | 拼出来的 WHERE | 查到 |
|---|---|---|
| `/api/dict-types` | `deleted=false` | 3 条 |
| `?code=season` | `deleted=false AND (code LIKE ?)`，参数 `%season%` | season、season_old |
| `?name=季` | `deleted=false AND (name LIKE ?)`，参数 `%季%` | 季节、旧季节 |
| `?code=season&name=旧` | `deleted=false AND (code LIKE ? AND name LIKE ?)` | 旧季节 |
| `?code=&name=` | `deleted=false` | 3 条 |

决定拼不拼的是 `.like(StringUtils.hasText(query.getCode()), ...)` 的第一个参数：true 就拼，false 就跳过。一个接口就能覆盖“全部”和各种组合，不用每种组合写一个方法。`hasText` 会把 null、空串 `""`、全是空格都当成“没填”。前端表单的输入框留空时，传过来的是 `code=`，值是空串而不是 null。要是写成 `query.getTypeCode() != null`，DictData 的 `.eq` 就会拼出 `type_code = ''`，一条都查不到。

GET 参数是这样填进对象的：Spring 先 `new DictTypeQuery()`，再按 URL 里的参数名找同名字段的 setter（`code=season` → `setCode("season")`，`page=2` → `setPage(2)`，字符串顺手转成 long）。URL 里没给的字段保持默认值，所以不传分页参数时 SQL 里是 `LIMIT 20`。值转不过去或校验不过，返回 400：

```
?page=abc   → {"code":400,"msg":"page Failed to convert property value of type 'java.lang.String' to required type 'long' ..."}
?size=1000  → {"code":400,"msg":"size size 最多 500"}
```

参数前面没有 `@RequestBody`，Spring 只看 URL。用 GET 带上 JSON 请求体 `{"code":"unit"}` 去请求，请求体直接被忽略，SQL 里没有 code 条件，返回全部 3 条。查询用 GET 还有一个好处：筛选条件都在 URL 里，可以刷新、复制、收藏。

**问：DictDataSaveReq 和 Mapper 有什么区别？**

**答**：两个根本不是一类东西。SaveReq 是**数据**：前端交上来的一张表单。Mapper 是**工具**：负责对 `sys_dict_data` 表做增删改查。

| | DictDataSaveReq | DictDataMapper |
|---|---|---|
| 是什么 | 前端交上来的表单 | 操作 sys_dict_data 表的工具 |
| Class 还是 Interface | Class，用来装数据 | Interface，实现由 MyBatis 生成 |
| 里面有什么 | 字段和校验注解 | 没有字段，方法都继承自 BaseMapper（insert、selectById……） |
| 什么时候创建 | 每来一个请求，Spring 就 new 一个新的 | 应用启动时创建一个，之后所有请求共用 |
| 认识谁 | 只认识前端传来的 JSON，不认识数据库 | 只认识实体 DictData 和表，不认识 SaveReq |

两者在 `create` 里碰头，中间隔着实体 DictData：

```java
DictData entity = new DictData();
BeanUtils.copyProperties(req, entity);   // 表单上的内容抄到“表的一行”上
dictDataMapper.insert(entity);           // 工具把这一行存进表
```

Mapper 的方法只收实体，从来不收 SaveReq。SaveReq 管“前端能传什么、传得对不对”，实体管“表长什么样”，两者分开以后，接口入参和表结构就可以各改各的。

**问：DictDataSaveReq 和 DictData 有什么区别？为什么要两个文件？是 controller → service（dto）→ mapper 这样走吗？**

**答**：理解得对：DTO 接 HTTP 请求的数据，实体描述表的一行。流向要补一个细节：**DTO 只走到 Service，Service 把它转成实体，Mapper 只收实体。**

```
请求：Controller(DictDataSaveReq) → Service(DictDataSaveReq → 转成 DictData) → Mapper(DictData) → INSERT
返回：数据库 → Mapper 返回 DictData → Service → Controller 包成 R → JSON
```

为什么要两个文件，做个反面实验：在副本里加一个直接拿实体当请求体的接口 `create(@RequestBody DictType entity)`，然后发 `{"code":"hack","name":"伪造","createBy":999,"deleted":true}`。真实 SQL：

```
INSERT INTO sys_dict_type ( code, name, create_by, create_time, update_by, update_time, deleted ) VALUES ( ?, ?, ?, ?, ?, ?, ? )
Parameters: hack(String), 伪造(String), 999(Long), ..., true(Boolean)
```

前端伪造了创建人，还插进了一条一出生就是“已删除”的行。接口返回成功、给了 id，列表里却看不到它。接着正常新建 code=hack，得到的是 500：`duplicate key value violates unique constraint "uk_sys_dict_type_code"`，这条看不见的行占住了编码。

同一段 JSON 发给正常的接口（`@RequestBody DictTypeSaveReq`），SaveReq 上没有 createBy、deleted，这两个键被直接忽略。INSERT 里没有 deleted 列，create_by 是空的，数据正常。

所以 SaveReq 决定了前端最多能碰到哪些字段。另外，一张表可以对应好几个 DTO：DictDataQuery 里的 page、size 根本不是表里的列。

**问：@Data 不是也生成构造器吗？和 @RequiredArgsConstructor 有什么区别？**

**答**：对，`@Data` 里本来就包含 `@RequiredArgsConstructor`，此外还有 @Getter、@Setter、@ToString、@EqualsAndHashCode。`@RequiredArgsConstructor` 只做一件事：把所有 `final` 字段都放进构造器的参数里。

用 delombok 还原出来的真实结果：

```java
// @Data，字段不是 final（实体、DTO）→ 构造器没有参数，外加 getter/setter/equals/toString
public DictData() {
}

// @RequiredArgsConstructor，字段是 final（ServiceImpl）→ 只有这一个构造器
public DictDataServiceImpl(final DictDataMapper dictDataMapper) {
    this.dictDataMapper = dictDataMapper;
}
```

实体和 DTO 的字段要让框架 new 出来以后一个个 set 进去，所以不能是 final，构造器也就没有参数。ServiceImpl 的 Mapper 是 Spring 在 new 的时候通过构造器传进来的，所以要 final。ServiceImpl 不用 `@Data`：它不需要 getter 把 Mapper 暴露出去，比较两个 Service 是否相等也没有意义。

坑：在 ServiceImpl 里忘了写 `final`，Lombok 生成的是无参构造器 `public ForgotFinalServiceImpl() {}`，编译能通过，Spring 也能正常启动，但 Mapper 一直是 null。等到第一次调用接口才报错：

```
java.lang.NullPointerException: Cannot invoke "DictDataMapper.insert(DictData)" because "this.dictDataMapper" is null
```

**问：`ensureCodeUnique(req.getCode(), id)` 有什么用？**

**答**：查重时把正在修改的这一行排除掉。第二个参数 `excludeId` 的意思是“查重时不算这个 id”。新增时传 null，因为还没有自己；修改时传 id。字典数据的 `ensureValueUnique(..., id)` 是同一个道理（4.7 已讲）。

表里有 season（id=13）和 unit。真实 SQL：

| 操作 | 查重 SQL 和参数 | 结果 |
|---|---|---|
| 新增 color | `deleted=false AND (code = ?)`，`color` | 成功 |
| 修改 season，只把名字改成“季节类型” | `deleted=false AND (code = ? AND id <> ?)`，`season, 13` | 成功 |
| 修改 season，编码改成 unit | 同上，`unit, 13` | `1000 编码已存在: unit` |

把修改里的 `id` 换成 `null` 再试“只改名字”：SQL 变成 `deleted=false AND (code = ?)`，查到的正是 season 自己，返回 `1000 编码已存在: season`。用户只是改个名字，却永远保存不了。

所以修改时查重要做两件事：编码改成别人已经在用的值，要拦住；编码没变，不能把自己算成重复。

**问：查询参数（DictDataQuery）和请求体（DictDataSaveReq）有什么区别？**

**答**：区别在于数据放在 HTTP 请求的哪个位置。下面是用 nc 抓到的、curl 实际发出去的原始请求：

```
GET /api/dict-data?typeCode=season&label=%e6%98%a5&page=1&size=20 HTTP/1.1     ← 查询参数在第一行的 URL 里
Host: localhost:18080
Accept: */*
                                                                               ← 空行之后什么都没有
```

```
POST /api/dict-data HTTP/1.1
Host: localhost:18080
Content-Type: application/json                                                 ← 告诉服务器下面是 JSON
Content-Length: 59
                                                                               ← 空行
{"typeCode":"season","label":"春季","value":"1","sort":1}                      ← 请求体
```

| | 查询参数 | 请求体 |
|---|---|---|
| 位置 | 第一行 URL 的 `?` 后面 | 空行之后 |
| 格式 | `键=值&键=值`，全是字符串，中文要编码 | JSON：有数字、布尔、嵌套对象、数组 |
| 放多少 | 少量，URL 太长服务器会拒收 | 可以很大 |
| 谁能看到 | 浏览器地址栏、历史记录、服务器访问日志 | 默认不出现在这些地方 |
| 我们用在 | GET 查询：筛选条件、分页 | POST/PUT：要写进数据库的数据 |
| Controller 写法 | `@Valid DictDataQuery query`，不加注解 | `@Valid @RequestBody DictDataSaveReq req` |
| 谁来转换 | Spring 按名字调 setter，字符串转 long | Jackson 解析 JSON |
| 转换失败 | `?page=abc` → 400 | JSON 格式错 → 现在是 500（bug 003） |

`PUT /api/dict-data/5` 里的 `5` 是第三个位置：路径变量 `@PathVariable`，用来指明“哪一条”。修改接口三样都用到了：路径上是 id，请求体里是新内容。

请求体能表达嵌套结构，查询参数不能。以后做出库单时，一张单子下面挂着多行明细，就只能用 JSON 请求体传：`{"warehouseId":1,"items":[{...},{...}]}`。

**问：`when(dictTypeMapper.exists(any())).thenReturn(false);` 是什么意思？**

**答**：照字面读：**当**假的 dictTypeMapper 的 `exists` 被调用时，**不管传什么参数**（`any()`），都**返回 false**。

单元测试不连数据库，`@Mock` 造出来的 Mapper 是个假对象，它的每个方法该返回什么，都要由测试来规定。这一行规定的场景是“库里没有这个字典类型”。真实运行时，`ensureTypeExists` 里的 `exists` 会发一条 `SELECT COUNT(*) ... WHERE deleted=false AND (code = ?)`；在测试里不发 SQL，直接拿到 false，于是抛出“字典类型不存在”。

用 `any()`，是因为 `exists` 的参数是 Service 内部 new 出来的 Wrapper，测试拿不到同一个对象，只能说“什么参数都行”。代价是测试检查不了 Wrapper 里的条件写得对不对（见 4.9 最后一条）。

在副本里改这一行做了两个实验：

- 改成 `thenReturn(true)`：测试失败，`Expecting code to raise a throwable.`。类型“存在”了，value 查重用的 `dictDataMapper.exists` 没有 stub，返回 false，于是一路走到 insert，没抛异常。
- 整行删掉：测试**照样通过**。没有 stub 的方法会返回默认值：boolean 是 false，对象是 null，数字是 0，集合是空的。之所以还要写这一行，是为了把“库里没有这个类型”这个前提明明白白写在测试里，不靠读者去记默认值。

**问：`assertThatThrownBy(...).isInstanceOf(...).hasMessageContaining(...)` 和 `verify(..., never()).insert(...)` 是什么意思？**

**答**：前三行检查“抛了对的异常”，最后一行检查“没写库”。

- `() -> dictDataService.create(...)`：lambda，把“调用 create”这件事打包交给 `assertThatThrownBy`，由它来执行并接住异常。不用 lambda、直接调用的话，异常会把测试打断，报的是 `Errors: 1  BizException: 字典类型不存在: season`，后面的检查一行都不执行。
- `.isInstanceOf(BizException.class)`：异常必须是业务异常，不能是空指针之类。
- `.hasMessageContaining("字典类型不存在")`：确认是**这条**规则拦下来的。value 重复抛的也是 BizException，只看类型分不出来。写错文字时的报错：`Expecting throwable message: "字典类型不存在: season" to contain: "存储值已存在" but did not.`
- `verify(dictDataMapper, never()).insert(any(DictData.class))`：假对象会记下自己被调用过的每个方法，`verify` 去翻这个记录，`never()` 要求 insert 一次都没被调用过。

在副本里把 create 改成先 insert 再检查：异常照样抛，前三行全过，只有 verify 报错：

```
org.mockito.exceptions.verification.NeverWantedButInvoked:
```

**问：`create_valueExists_throwsAndNotInsert` 是怎么判断 value 不能重复的？**

**答**：这个测试**不判断**重复。真正判断重复的是 `ensureValueUnique` 发出的 SQL：`SELECT COUNT(*) FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND value = ?)`，查到大于 0 就抛“存储值已存在”。测试里的 `when(dictDataMapper.exists(any())).thenReturn(true)` 是**直接假设**这条 SQL 查到了，然后只检查 Service 的反应：抛出对的异常，并且不写库。

第一行 `when(dictTypeMapper.exists(any())).thenReturn(true)` 是为了让代码通过第一道检查，走到 value 查重。删掉它，exists 返回默认的 false，代码在第一道检查就停了：`Expecting throwable message: "字典类型不存在: season" to contain: "存储值已存在"`。

在副本里做的另外两个实验，说明了这个测试能抓到什么、抓不到什么：

| 改坏的地方 | 测试结果 |
|---|---|
| 业务代码里删掉 `ensureValueUnique(...)` 这一行 | 失败：`Expecting code to raise a throwable.` |
| 查重条件写错：`.eq(DictData::getValue, value)` 写成 `.eq(DictData::getLabel, value)` | **照样通过** |

所以一条规则要靠三层一起保证：单元测试保证“查到重复就拦、不写库”；第 5 节启动后实际调接口（E 行）、看 SQL，保证“查重条件写对了”；数据库的部分唯一索引兜底，保证并发时也不会重复。

**问：第 5 节第 ③ 步在 Swagger 里具体怎么操作？**

**答**：每个接口都是同样四步：点开那一行 → `Try it out` → 填参数 → `Execute`，然后往下翻到 **Server response** 看 Response body。下面是在 Swagger 里实际点过发现的三个坑：

- **默认值是示例，不是空的**。新增的请求体默认是 `{"typeCode":"string", ..., "sort":0, "status":0, "remark":"string"}`。只改其中几个字段的话，`status` 会是 0（停用），G 行就查不到它。要**全选删掉**，再粘贴第 5 节表里的请求体。
- **分页查询的参数是一个 JSON 框（名字叫 query）**，默认值是 `{"page":1,"size":1,"typeCode":"string","label":"string"}`，直接 Execute 会发出 `?page=1&size=1&typeCode=string&label=string`，查到 0 条。H 行要把框里改成 `{"typeCode": "season"}`，Swagger 会把它拆成 `?typeCode=season` 发出去。
- **业务出错时，HTTP 状态码也是 200**。我们的错误码写在返回体的 `code` 里（0 成功，400、404、1000 是各种错误）。Server response 那一栏 Code 显示 200，不代表成功，要看 Response body 里的 `code`。

Responses 区域里那个 `{"code":0,"msg":"string","data":0}` 是接口文档的示例，不是真实返回，别看错。

**用 Apifox 代替 Swagger 也可以**。可以从 `http://localhost:8080/v3/api-docs` 导入，也可以自己新建请求。按数据放的位置选标签：路径上的 id、typeCode 直接写进 URL；H 的筛选条件写在 Params（Query 参数）里；新增、修改的 JSON 写在 Body 里，类型选 JSON。Swagger 里的三个坑在 Apifox 里同样存在。

**问：数据库不是有外键吗？为什么“类型下有数据不让删”要自己写代码？**

**答**：外键（`type_code TEXT REFERENCES t_type(code)`）在临时表里实测：新增数据时类型不存在、物理 DELETE 有数据的类型、修改有数据的类型的 code，三种都会被数据库拒绝（`violates foreign key constraint ... is still referenced from table "t_data"`）。没有逻辑删除的系统里，这三条规则外键全包了。

但我们的“删除”是 `UPDATE ... SET deleted = true`，外键只认行在不在，不认 deleted：逻辑删除照样成功，之后还能往这个“已删除”的类型下面继续加数据。另外，修好 bug 001 以后，code 只靠部分唯一索引保证唯一，外键连建都建不了：`there is no unique constraint matching given keys for referenced table`。所以这几条规则只能写在 Service 里。详见 [C1 第 4 节](../docs/原理卡/C1-关系模型与建表.md)。

**问：作业里“类型下有没有数据”为什么查的是字典数据表？为什么要抛 BizException？**

**答**：**谁记着关系，就查谁。** 类型和数据之间的关系记在 `sys_dict_data.type_code` 这一列上，`sys_dict_type` 里没有任何一列记着“我下面有哪些数据”。所以要问“season 下面有没有数据”，只能去字典数据表里找 `type_code = 'season'` 的行。就像问“这个班还有没有学生”，要去学生表里查班级 id，而不是去查班级表。

**抛异常就是“拒绝”的写法。** delete 返回 void，没法用返回值说“不行”。抛出异常后，后面的 `deleteById` 不会执行，`@Transactional` 也会回滚。选 `BizException` 是因为全局异常处理器专门接它：转成 `{"code":1000,"msg":"该类型下还有字典数据，不能删除"}`，提示原样给前端。换成别的异常，就会落进兜底分支，变成 `500 服务器内部错误，请查看日志`。测试里 `.isInstanceOf(BizException.class)` 检查的正是这一点：确认是业务规则拒绝的，而不是程序出了错。

**问：作业里 `update_onlyNameChanged_ok` 这个测试在测什么？**

**答**：测的是“code 没变时，update 能顺利走完，而且真的保存了”。测试里没有 `assertThatThrownBy`，因为成功的情况本来就不该抛异常；要是意外抛了，JUnit 会直接判它失败（Errors）。`verify(dictTypeMapper).updateById(...)` 不写 `never()`，默认检查“正好调用了一次”。没写 `when(dictDataMapper.exists...)`，是因为 code 没变时代码根本不会去查数据，写了反而会报 `UnnecessaryStubbingException`。

最初给的版本有个漏洞：把实现里的 `if` 去掉（不管 code 变没变都去查数据），这个测试照样是绿的。原因是没 stub 的 `exists` 默认返回 false，代码以为下面没有数据，就放行了。补上一行 `verify(dictDataMapper, never()).exists(any());` 以后，同样的错误实现会报 `NeverWantedButInvoked: dictDataMapper.exists(<any>) ... But invoked here: DictTypeServiceImpl.ensureNoData`，正确实现仍然是绿的。
