## 1. 字典缓存

### 1.1 做了什么

`GET /api/dict-data/by-type/{typeCode}`（下拉框用的那个接口）加了 Redis 缓存。真实过程：

```
第一次查 by-type/season → {"data":[{"label":"春季","value":"1"}]}
   SQL：SELECT ... FROM sys_dict_data WHERE deleted=false AND (type_code = ? AND status = ?) ORDER BY sort ASC,id ASC
   Redis：GET dict:season → [{"label":"春季","value":"1"}]     TTL dict:season → 86400
第二次查 → 一样的结果，sys_dict_data 的 SQL 条数：0
新增"夏季" → Redis：EXISTS dict:season → 0（缓存被删了）
再查 → [{"label":"春季","value":"1"},{"label":"夏季","value":"2"}]（查库重建）
```

**返回值变了**：以前返回整个 `DictData`（id、备注、创建时间……一大堆），现在只返回 `[{label, value}]`。下拉框只要这两样。

### 1.2 为什么改成只返回 label 和 value

一开始我想直接缓存 `DictData`。在副本里试了一下：写进 Redis 没问题，**读回来时报错**：

```
tools.jackson.databind.exc.InvalidFormatException:
Cannot deserialize value of type `java.time.OffsetDateTime` from String "2026-10-12 15:24:45": ...
Unable to obtain OffsetDateTime from TemporalAccessor: ...
```

`createTime` 上的 `@JsonFormat` 把时间写成了 `2026-10-12 15:24:45`，没有时区偏移。`OffsetDateTime` 必须有偏移，读不回来。

与其想办法绕过去，不如换个思路：**下拉框本来就只要 label 和 value**。新建一个 `record DictOption(String label, String value)`，接口返回它，缓存也存它。返回的数据少了，也不再把 id、备注这些内部字段暴露给每个页面。

### 1.3 读：Cache-Aside（旁路缓存）

`DictDataServiceImpl.listByType`：

```java
List<DictOption> cached = dictCache.get(typeCode);
if (cached != null) {
    return cached;                       // 缓存里有：直接返回
}
List<DictOption> options = ...查库...;   // 没有：查库
dictCache.put(typeCode, options);        // 放进缓存，下次就有了
return options;
```

注意 `cached != null`：缓存里是空列表 `[]` 也算"有"。不存在的类型编码查一次也会缓存 `[]`，不会每次都打到库上。

### 1.4 写：先改库，再删缓存，而且等事务提交以后再删

改了字典数据（新增、修改、删除）以后，调 `dictCache.evictAfterCommit(类型编码)`：

| 问题 | 我们的做法 | 不这么做会怎样 |
|---|---|---|
| 改了数据，缓存怎么办 | **删掉**缓存，下次读时重建 | 直接"更新"缓存：两个请求同时改，可能后改库的先更新缓存，缓存里留下旧值 |
| 什么时候删 | **事务提交以后**（`TransactionSynchronization.afterCommit`） | 提交前删：删完、提交前，另一个请求来读，查到的还是旧数据，又把旧数据放回了缓存 |
| 万一哪里漏删了 | 缓存 24 小时过期，最多一天后自己好 | 旧数据永远留在缓存里 |
| 修改时把类型从 season 改成 color | **两个类型都删**：`evictAfterCommit(oldTypeCode, newTypeCode)` | 只删新的：season 的下拉框里还留着这一项 |

这几条是缓存一致性的经典问题，第 6 节面试题会再讲。

### 1.5 关键代码

| 文件 | 看什么 |
|---|---|

| `module/system/dto/DictOption.java` | 下拉选项 |

## 2. 单号生成器

### 2.1 做了什么

`common/seq/SerialNoGenerator`：`generator.next("PO")` 返回 `PO202610120001`，前缀 + 日期 + 4 位当天流水号。采购单、入库单、出库单生成单号都用它。现在没有接口，等采购单来用。

我在副本里用 50 个线程同时要了 200 个号（真实输出）：

```
200 个请求，拿到不同单号 200 个；最小 DEMO202610120001，最大 DEMO202610120200
```

### 2.2 为什么用 Redis INCR

```java
String key = "seq:" + prefix + ":" + day;          // seq:PO:20261012
Long n = redis.opsForValue().increment(key);        // Redis 的 INCR：加 1 并返回新值
if (n == 1L) {
    redis.expire(key, Duration.ofDays(2));          // 当天第一个号：两天后自动删掉计数器
}
return prefix + day + String.format("%04d", n);     // 12 → 0012
```

- **INCR 是原子的**：Redis 一次只执行一条命令，200 个请求同时来，也是一个一个加，每个人拿到的数都不一样
- **为什么不用数据库**：查"今天最大的单号"再加 1，两个请求同时查到 0011，都生成 0012，就重复了。要不重复就得加锁，又慢又复杂
- **每天一个 key**：日期变了，key 就变了，流水号自然从 1 重新开始
- `%04d` 超过 9999 会变成 5 位（`PO2026101210000`），照样不重复。小公司一天开不了一万张单

**风险**：Redis 的数据丢了（比如没开持久化又重启了），当天的流水号会从 1 重新开始。所以以后的业务表在单号列上**一定要加唯一索引**兜底，宁可报错也不能重号。

## 3. 文件上传

### 3.1 做了什么

`POST /api/files`（multipart，字段名 `file`，登录即可），存到服务器本地目录，返回访问地址。真实结果：

| 请求 | 返回 |
|---|---|
| 上传 demo.png | `{"url":"/files/2026/10/12/52464d53-06fd-48e3-b540-47271e34cd30.png","name":"demo.png","size":12}` |
| **不带 token** 访问这个 url | HTTP 200，12 字节 |
| 上传 x.html | `{"code":1000,"msg":"不支持的文件类型: x.html"}` |
| 上传 11MB 的文件 | `{"code":400,"msg":"文件太大，最大 10MB"}` |
| 不登录上传 | 401 |
| 请求里没有 file 这个字段 | `500`（记成 bug 007，和 bug 003、006 是一家，留给你） |

### 3.2 几个决定

- **存在哪**：`application.yaml` 的 `lingmao.upload.dir`，开发时是项目下的 `uploads/`（加进了 `.gitignore`），生产环境挂到容器外的目录，重新部署不会丢
- **文件名自己生成（UUID）**：不用用户给的名字。防止两个人都传 `1.png` 互相覆盖，也防止 `../../etc/passwd` 这种路径穿越
- **按日期分目录**：`2026/10/12/`，一个目录里不会堆几十万个文件
- **扩展名白名单**：只收图片、pdf、Office 文件。不收 html、js、exe：别人上传一个 html，再把地址发给你，浏览器打开就会执行里面的脚本
- **`/files/**` 不要求登录**：页面里的 `<img src="/files/...">` 是浏览器自己发的请求，不会带 token。文件名是随机的 UUID，猜不到。真正敏感的文件（合同、发票）以后要改成"带权限的下载接口"
- **大小限制**：`spring.servlet.multipart.max-file-size: 10MB`。超了 Spring 抛 `MaxUploadSizeExceededException`，`GlobalExceptionHandler` 新加的一个方法把它变成 400

| `config/WebConfig` | `/files/**` 映射到上传目录 |

## 6. 🎤 今天的面试题

**问：缓存和数据库怎么保证一致？**

**答**：我们用 Cache-Aside：读的时候先查缓存，没有再查库并放进缓存；写的时候先改数据库，再删缓存。删而不是更新，是因为两个并发的更新可能"后改库的先写缓存"，缓存里留下旧值；删掉的话下次读一定从库里重建。删缓存放在事务提交以后（Spring 的 `TransactionSynchronization.afterCommit`）：提交前删的话，删完到提交之间有人来读，读到的还是旧数据，又被放回缓存。再加一个兜底的过期时间（我们是 24 小时），万一哪里漏删了也会自己恢复。这样仍然有极小的窗口：读请求查到旧数据后、放进缓存前，写请求刚好提交并删了缓存，旧数据就会被放回去。对字典这种很少改的数据，过期时间兜底就够了；要求更严的场景可以做"延迟双删"，或者用订阅数据库变更日志（binlog / WAL）的方式删缓存。

**问：分布式系统里怎么生成不重复的单号？**（[知识图谱](../docs/知识图谱.md) I6）

**答**：常见三种。Redis INCR：我们项目在用，key 是"前缀 + 日期"，每天从 1 开始，INCR 是原子操作，50 个线程同时要 200 个号，实测拿到 200 个不同的号；单号短、有业务含义（`PO202610120001`），缺点是依赖 Redis，数据丢了会从 1 重来，所以业务表的单号列要加唯一索引兜底。雪花算法：64 位整数，由时间戳、机器号、序列号拼成，本地生成、不依赖任何服务，适合做主键，但又长又看不出含义，而且怕服务器时钟回拨。号段模式：每台服务器一次从数据库领一段号（比如 1001-2000），用完再领，数据库压力小，美团的 Leaf 就是这个思路。我们是单体应用、单号要给人看，所以选 Redis INCR。
